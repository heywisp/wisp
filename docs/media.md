# `wisp-media`

A pure crate for images that users attach: sniffing, sizing and normalisation. It does no I/O, reads no clock or environment, and installs no panic hook. Both the kernel and the TUI use it, so the chip's estimate and refusals always match what the kernel sends (plan M3.1 §10.2, architecture P20). It depends on `image-webp` (the version `image` itself uses), `image` (with only the `bmp`, `gif`, `jpeg`, `png` and `webp` features, no default features), `base64` and `thiserror`, and on no workspace crate.

## API

| Item | What it does |
|---|---|
| `sniff(bytes) -> Option<SourceFormat>` | Detects PNG, JPEG, GIF, WebP or BMP from magic bytes only. File names and extensions are never consulted. |
| `Tier { max_edge, max_tokens }` | One model's image limits. `Tier::STANDARD` is 1,568 px and 1,568 tokens; `Tier::HIGH` (Claude 4.7 and later) is 2,576 px and 4,784 tokens [V1]. Each model's row in `crates/wisp-core/data/models.toml` names its tier (`images`, `"standard"` or `"high"`, read through `Tier::NAMED` into `ImageCaps.tier`). |
| `tokens(w, h)` | Visual tokens: ⌈w/28⌉ × ⌈h/28⌉. |
| `api_size(w, h, tier) -> ImageSize` | The size the API resizes an image to, ported from the docs' reference implementation [VC1]. |
| `target(w, h, tier) -> ImageSize` | Wisp's size: `api_size`, then capped at a 2000 px long edge (`MAX_LONG_EDGE`, call 8). The API never resizes a target again. |
| `normalise(bytes, tier) -> Result<Normalised, MediaError>` | Decodes, orients, downscales and re-encodes. |
| `Normalised { bytes, media_type, width, height }` | The bytes to send and store. `media_type` is `MediaType::Png` or `MediaType::Jpeg`, with `as_str()` (`image/png`) and `extension()` (`png`, `jpg`). |
| `encode_base64`, `decode_base64`, `base64_len` | Standard alphabet, padded, as the wire's `ImageData.data` uses. Decoding refuses input longer than the 40 MB source cap encodes to. |
| `panic_is_contained()` | True on the current thread while `normalise` is decoding or encoding. |
| `contain_for_testing(work)` | Only with the `testing` feature, which `wisp-tui` enables for its tests: runs `work` inside the same containment, so the TUI can test that its hook honours the flag. |
| `MediaError` | Every refusal, each with a one-sentence message for the UI and for `Rejected { reason }`. Messages never include decoder text. |

Constants: `MAX_IMAGES_PER_MESSAGE` (10), `MAX_SESSION_MEDIA_BASE64` (20,000,000 bytes), `MAX_IMAGE_BASE64` (10,000,000 bytes), `MAX_ATTACHMENT_BYTES` (7,500,000 bytes, the largest file whose base64 fits in `MAX_IMAGE_BASE64`), `MAX_SOURCE_BYTES` (40,000,000 bytes), `MAX_DECODE_SIDE` (16,384 px), `MAX_DECODE_ALLOC` (256,000,000 bytes), `MAX_ANIMATED_CANVAS` (85,333,333 bytes), `MIN_FALLBACK_EDGE` (256 px), `JPEG_QUALITY` (90). Every byte cap uses decimal megabytes, the conservative reading of the API's "10 MB" [V1], so the error sentences' "40 MB", "256 MB" and "10 MB" are exact.

## The resize rule

`api_size` finds the largest aspect-preserving size where each side, padded up to a multiple of 28, fits the tier's edge, and the token count fits its token cap. It binary-searches the long edge and rounds the short edge half to even, as the reference implementation does and as the live API resolves ties [VC1].

The vision page's table lists 2000 × 1500 on the standard tier as 1269 × 952. The reference implementation, which the docs say to use instead of hand calculation, gives 1270 × 952 (also 1,564 tokens). Wisp follows the reference implementation, and its test asserts 1270 × 952.

## Normalising

1. **Refuse early.** Empty input, input over 40 MB, and anything `sniff` doesn't recognise are refused before decoding. WebP is guarded twice, because `image-webp` 0.2.4 allocates a metadata chunk (`EXIF`, `XMP `, `ICCP`) at its declared size, and `image` never sets a limit on that: a 96-byte file declaring a 4 GB `EXIF` chunk, or a 76-byte animated file whose first frame nests one, would abort the process when the orientation is read. First, `normalise` drives `image_webp::WebPDecoder` itself with `set_memory_limit` at the 40 MB source cap, which bounds every metadata read (no chunk can be larger than an input Wisp accepts), and checks the dimensions and output size before allocating pixels. An animated WebP is held three times at once while its first frame decodes (the output buffer, the composition canvas and a frame buffer), so its canvas (width × height × 4) must also fit in a third of `MAX_DECODE_ALLOC` (`MAX_ANIMATED_CANVAS`, 85,333,333 bytes, about 4618 × 4618), or it is refused as too big. That keeps the peak near the 256 MB cap instead of 2.7 times it; a test decodes two full-size frames on a canvas just under the bound inside a 384 MiB address space (measured peak about 232 MB). Second, before decoding, the RIFF size, every top-level chunk's declared size, and every subchunk of each `ANMF` frame (from 16 bytes into its payload) must fit inside their container, or the file is refused as malformed. Tests show each layer refuses the nested bombs on its own.
2. **Decode under limits.** `image::Limits` caps each side at 16,384 px and allocations at 256 MB. The `image` crate doesn't check its own output buffer against `max_alloc`, so `normalise` also refuses any image whose decoded buffer would exceed 256 MB, before it is allocated. A decompression bomb is refused from its header. The other formats were checked for the WebP problem: PNG chunk data is buffered as it arrives, within the `png` crate's limit, which `image` sets from `max_alloc`; JPEG segments are at most 64 KB; GIF extensions are 255-byte sub-blocks and frames sit under the `gif` crate's 50 MB memory limit; BMP allocations follow the checked dimensions.
3. **Orient.** The EXIF orientation (JPEG APP1, PNG `eXIf`, WebP `EXIF`) is read first. The target is computed on the upright size, the image is scaled in its stored orientation, and the orientation is applied to the small result, so rotating never copies a full-size image.
4. **Take GIF's first frame.** Animations aren't sent, as the API uses only the first frame [V1].
5. **Downscale.** Images more than twice the target in a dimension are first reduced with an integer area filter to at most twice the target, then resized exactly with Lanczos3. The pre-shrink bounds Lanczos's floating-point intermediate buffer. Images are never enlarged.
6. **Re-encode.** PNG (default compression, adaptive filter) for PNG, GIF, WebP and BMP sources; JPEG at quality 90 for JPEG sources. Colour types are reduced to 8 bits per channel: grey stays grey, alpha is kept for PNG. Re-encoding drops every chunk and segment of metadata, EXIF and GPS included.
7. **Fit the 10 MB cap.** A result over 10 MB in base64 isn't refused straight away:
   - a PNG with no real alpha (no alpha channel, or every pixel opaque) is re-encoded as JPEG at quality 90, which keeps noisy photos at full size;
   - if that is still too big, or the image has real alpha, it is downscaled in fixed steps of three quarters of the long edge (2000, 1500, 1125, 843, …) and re-encoded in the same format until it fits;
   - below a 256 px long edge it is refused with `EncodedTooLarge`.

   The steps are fixed, so the result stays deterministic. The image then has a smaller size than `target`, so the chip's estimate must come from the `Normalised` size, not from `target`. This is a deviation from plan §10.2, recorded in §14.

The output is deterministic: no threads (`image`'s `rayon` feature is off), fixed encoder settings, and tests that compare repeated runs and runs on other threads.

## Peak memory

Decoding is the peak: once the image is decoded, the pre-shrink keeps at most about 64 MB, the full-size image is dropped, and Lanczos's working buffer is at most about 128 MB. WebP's worst cases, from `image-webp` 0.2.4's decode paths, all limited by the 256 MB output cap (`MAX_DECODE_ALLOC`) and the 85,333,333-byte animated canvas bound:

| Path | What is held at once | Worst case |
|---|---|---|
| Still lossless, opaque | a temporary w×h×4 RGBA buffer, then the w×h×3 output it is copied into: 7 bytes a pixel, at most 85.3 million pixels | about 600 MB (measured 586 MB at 16383×5208) |
| Still lossless, alpha | the w×h×4 output only: at most 64 million pixels | about 260 MB |
| Still lossy, opaque | the YUV frame (1.5 bytes a pixel) and the w×h×3 output: 4.5 bytes a pixel | about 385 MB (measured 379 MB) |
| Still lossy, alpha | the YUV frame, the alpha plane (1 byte a pixel) and the w×h×4 output: 6.5 bytes a pixel, at most 64 million pixels | about 420 MB |
| Animated | the output, the canvas and one frame buffer, each at most the 85.3 MB canvas bound, plus a lossy frame's YUV and alpha planes | about 310 MB (measured 232 MB for two full-size lossless frames) |

These are bounded because every one is a fixed multiple of a size checked before any pixel is allocated: the dimensions (16,384 px a side), the output buffer (256 MB) and, for animations, the canvas. Still images over 256 MB are not refused further: the 7-bytes-a-pixel lossless case is a property of `image-webp`, and refusing it would reject real panoramas. Other formats decode into a buffer checked against the same 256 MB cap, plus their decoder's working memory.

## Contained panics

`normalise` runs its decode and encode inside `catch_unwind` and sets a thread-local flag for the duration. A panic in a decoder comes back as `MediaError::Panicked`, never past `normalise`. The TUI's panic hook (`wisp-tui`'s `term::contain::contained`) checks `wisp_media::panic_is_contained()` beside `wisp_contain::is_contained()`, which plugin calls and `wisp-render`'s Markdown parse set, so a decoder panic is only recorded: it never restores the terminal or counts toward `MAX_RESTORES`.

The flag is per thread, which is where a panic hook runs, so a panic on another thread at the same time is never mistaken for a contained one. Aborts can't be caught: a failed allocation aborts the process before any hook runs, and so does a stack overflow. So `normalise` checks every declared length and size it can before a decoder sees the bytes (step 1 and 2). A test runs hostile inputs for every format in a child process limited to a 1 GiB address space, where an unchecked 4 GB allocation would abort it.

## Tests

- `size` unit tests: the vision table on both tiers, the reference implementation's examples, both caps over a grid of sizes, stability (`api_size` of a result is the result), the 2000 px cap, and degenerate sizes up to `u32::MAX`.
- `tests/corpus.rs`, all generated in the test: PNG, JPEG with EXIF orientation and fake GPS coordinates, all eight EXIF orientations in PNG, JPEG and WebP, an animated GIF and an animated WebP, lossless WebP, BMP; metadata stripping checked on the output bytes for WebP EXIF and XMP, GIF comments, PNG iCCP, tEXt, iTXt and tIME, and JPEG COM, APP2 ICC and XMP; every truncation of each format, random byte corruption, header-declared bombs in every format, the WebP chunk-length regression, spoofed magic bytes and non-image formats, JPEG quality 90, the JPEG fallback and the stepped downscale, and determinism across runs and threads.
- `tests/purity.rs`: no `std::fs`, `env`, `process`, `io` (except an in-memory `Cursor`), `net` or `thread`, no clock, no printing, no panic hook, and none of `image`'s own file I/O (`save`, `save_buffer`, `save_with_format`, `ImageReader::open`).
- `tests/dependencies.rs`: the crate's only dependencies are `base64`, `image`, `image-webp` and `thiserror`; `image` has exactly the five format features; `wisp-tui` reaches `wisp-media`. `wisp-render`'s workspace-wide check keeps `wisp-core` out of `wisp-tui` and `wisp-media`.

## Attaching images in the TUI

The full-screen TUI attaches images in two ways (plan M3.1 §10.1). Both run on a worker thread (`term::clipboard::reader`), so the UI never waits on a child process or a file.

**Alt-V, and Ctrl-V where the terminal passes it through.** Wisp asks the operating system for the clipboard's image:

| Platform | What runs |
|---|---|
| SSH (`SSH_CONNECTION` or `SSH_TTY`, checked first) | Nothing. The status row says `Paste the image's path: no clipboard over SSH.` |
| WSL | `powershell.exe -NoProfile -NonInteractive -Sta -EncodedCommand <script>`, found on `PATH` or at `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`. The fixed script (`WSL_READ_SCRIPT`) prints `image:` and the PNG in base64, `file:` and a path per line for a copied file list, or `none`. Listed files go through `wslpath -u`. Then the Wayland and X11 readers, when their displays are set |
| Wayland | `wl-paste --list-types`, then `wl-paste --type <type>` for the first of `image/png`, `image/jpeg`, `image/webp`, `image/gif` and `image/bmp` on offer |
| X11 | `xclip -selection clipboard -t TARGETS -o`, then `-t <type> -o` |
| macOS (best effort) | `osascript -e 'the clipboard as «class PNGf»'`, whose hex output is decoded, then `pngpaste -`. An `osascript` that times out or passes the cap stops the read with its own sentence; one that only finds no PNG falls through to `pngpaste` |

Every command is a fixed argv. Children start in their own session (through `setsid` when it is on `PATH`, otherwise in their own process group), with stdin and stderr on `/dev/null` and stdout on a pipe, so none of them touches the terminal. Each read has a 5 s timeout, after which the child and its whole process group are killed, and a 40 MB output cap (the PowerShell and `osascript` caps allow for their base64 and hex), past which the read stops at once. A read still running after 300 ms shows `Reading the clipboard…`; a second Alt-V meanwhile says `Still reading the clipboard.`

Each platform on the list is tried in turn. The first image wins; otherwise the first platform's answer is the sentence (`No image on the clipboard.`, or the tool's failure), and when no tool was found at all the sentence names what to install (`install wl-clipboard`, `install xclip`, `install pngpaste`, or `powershell.exe wasn't found`).

**An empty paste.** Terminals that keep Ctrl-V for their own paste, such as VS Code's, send an empty bracketed paste (`ESC[200~ESC[201~`) when the clipboard holds only an image. Wisp reads that as Ctrl-V: it takes the same path as Alt-V, including while a turn runs, but quietly: an empty clipboard doesn't say `No image on the clipboard.` and a second empty paste during a read doesn't say `Still reading the clipboard.` A slow read still shows `Reading the clipboard…` after 300 ms. Every other sentence (SSH, no tool, an unreadable or too-large clipboard, a model without images, the image limit) still shows. A whitespace-only paste stays text. An empty paste is ignored in a picker, a question card while it has the keys, the transcript, `/ps`, `/agents`, a step-in card, the sidebar overlay, the retry choice's endpoint picker, a process you're typing into, a selection handed to the terminal, and while quitting.

**Right-click with nothing selected** (Windows Terminal; `docs/commands.md`, "Right-click"). Wisp asks for the clipboard's text first, on the same worker with the same 5 s timeout, 300 ms `Reading the clipboard…` and `Still reading the clipboard.`:

| Platform | What runs |
|---|---|
| SSH | Nothing (right-click doesn't paste over SSH) |
| WSL | `powershell.exe -NoProfile -NonInteractive -Sta -EncodedCommand <script>`; the fixed script (`WSL_TEXT_SCRIPT`) runs `Get-Clipboard -Raw` and prints `text:` and the text, or `none` |
| Wayland | `wl-paste --no-newline --type text` |
| X11 | `xclip -selection clipboard -t UTF8_STRING -o` |
| macOS | `pbpaste` |

The first platform whose tool is found answers. Its text, when it isn't empty, goes into the composer as a bracketed paste of that text would, so the paste chip rules, the sanitisation and pasted image paths all apply. Text over 40 MB is refused with `The clipboard text is larger than 40 MB.`; a timeout or a tool that can't start is named as for images. When there is no text (an empty answer, a non-zero exit, `none`, or no tool), the image read above runs as for Alt-V, quietly as for an empty paste. A result that arrives in a picker, a card or another place where a right-click paste is ignored is dropped.

**Pasting paths.** A bracketed paste whose words are all image paths attaches the files instead of inserting the text. A word is a path when it is absolute, starts with `~/`, is a `file://` URL (percent-decoded, `localhost` allowed), or, on WSL only, is a Windows path such as `C:\Users\me\shot.png` (converted with `wslpath -u`). Words may be single- or double-quoted or backslash-escaped, as terminals and file managers write dropped files. The extension must be `png`, `jpg`, `jpeg`, `gif`, `webp` or `bmp`, in any case. Relative paths and words with control characters, checked again after a `file://` URL is percent-decoded, are never taken as paths. On the worker, each file is opened read-only and non-blocking, checked with `fstat` to be a regular file of at most 40 MB, and read. If any file is missing or isn't a regular file, the paste goes into the composer as ordinary text. If a file exists but can't be attached (it can't be read, is larger than 40 MB or isn't a supported image), or the images would take the message past 10 by the time they are ready, the pasted text goes into the composer as well and the status row says why.

**Chips.** An attached image is normalised once on the worker with the next turn's model tier (`ModelFacts.image_tier`, which `wisp-cli` copies from the capability row), only to size the chip and refuse a bad image early. The chip reads `[Image #1 · 1456×819 · ≈1.6k tokens]`, from the `Normalised` size, and moves, deletes, undoes and yanks like a text chip. Image numbers count separately from pasted-text numbers and restart after a send. A model with no tier refuses with the kernel's sentence; more than 10 images in a message are refused with the kernel's sentence too.

**Sending.** The image file's original bytes go to the kernel as `ImageData` in base64, in the order the chips appear in the composer (a chip yanked twice is sent once), and the chips are left out of the text. A message of images and no text is sent. The kernel normalises the same bytes with the same tier, so the chip's size and estimate equal what is sent; `wisp-cli`'s agreement test checks this for every capability row through a real kernel turn. The transcript shows each chip's label in muted text. The images travel in `ClientCommand::Send`'s `images`. `ImageData.data` is an `Arc<str>`, so the base64 is shared with the composer rather than copied on the UI thread; it serialises as the same JSON string as before. If the kernel refuses them, it answers with `Rejected { id, kind: image }`; the transcript says `This message wasn't sent: <reason>.` and the message goes back into the composer ahead of the draft with its chips, as every refused or returned message does (`docs/plans/steering.md` §6.3). Returned image chips are renumbered after the draft's own, rewriting the number in their labels. A waiting row shows a message's images first, as their chip labels, in the order they are sent, then its first line of text; an image in a message from another client is labelled the same way from the kernel's image record.

The re-cache hint and the `cache rebuilt: image added` label of plan §10.3 are not shown: MR 10 measured that adding an image keeps the cached prefix (`docs/pricing.md`).

## A refused attachment

The API, or a gateway, can refuse a request because of an image in it: a 400 `invalid_request_error` ("Could not process image"), a 413 `request_too_large`, or a context overflow the new image caused. Without a way back, every later request would carry the same image and be refused too. The kernel withdraws it instead, once, and sends the step again (plan `docs/plans/attach-tool.md` §7).

**Provisional blocks.** A block is committed once a request carrying it has been accepted, that is, once the request got its first event, the moment the rendering forms also call acceptance (`docs/tools.md`, "A refused rendering"). Until then the newest user message is provisional: the turn's message with its pasted images, steered messages delivered into the step, or a tool-result message that no accepted request has carried yet (resume, below). The agent keeps the accepted position, the end of the last accepted request; every media block after it is provisional. Only provisional blocks are ever replaced, so nothing the provider has accepted, and so nothing it may have cached, ever changes.

**Recognising the refusal.** The adapter marks an error `refused: Attachment` when the request carries provisional media (`Rendering.provisional`, set by the agent), it failed before any event, no feature rejection took it, it isn't a thinking-binding error, and it is one of: a 400 `invalid_request_error` (or a 400 with no error type, where an error `code` that is only the status's digits, such as a gateway's `"code": 400`, counts as no type), a 404 whose error message contains `image input`, ignoring case (OpenRouter's `No endpoints found that support image input`, also passed through by LiteLLM), a 413 or `request_too_large`, or a context overflow (`context_length_exceeded`; the API's own "prompt is too long" is a 400 `invalid_request_error`). The status counts, and so does an error before the first event: on Anthropic, a JSON body on a 200 or a first-event error chunk, as an `event: error` or as a gateway's OpenAI-style `data: {"error": ...}` chunk; on OpenAI, an `error`, `response.failed` or `response.incomplete` event, or a gateway's `data: {"error": ...}` chunk with no event type. `refused: Attachment` takes precedence over `refused: Rendering`; the API's message rarely names the block, so all of the message's provisional media blocks are withdrawn together. Both adapters mark both routes, an HTTP refusal and an error event before the response starts (on OpenAI, before `response.created`; a subscription's usage lead event doesn't count). A stream error's status reads as 200, so on that route only an `invalid_request_error`, `request_too_large` or an overflow counts, and a gateway's typeless `invalid_image` code stays unmarked.

**The withdrawal.** Each provisional block is replaced in memory by a text block, `[image #2 couldn't be processed: Could not process image]`: the kind, a label (`#n`, the image's number among the images of its input, as its chip shows it: each sent or steered input counts from 1, with or without text; inside a `tool_result`, its number among that result's images) and the error's message on one line (on OpenAI, the adapter's summary, such as `OpenAI request refused (HTTP 400): invalid_request_error`), control characters removed and cut to 200 characters. Inside a `tool_result` the note takes the attachment's place after the tool's text; `is_error` is unchanged. The step is sent again at once, as the same step and not as a retry: it uses no retry budget and waits for nothing.

**A file a tool attached** (kind `file`, a `media` block inside its `tool_result`) is labelled by its call's display target, the same text its tool row shows (`docs/spec.pdf`), and its note names its media type. The API's message loses one trailing full stop before it is placed. Withdrawn alone, the note points at bash: `[docs/spec.pdf (application/pdf) couldn't be processed: The PDF is password protected. Convert or cut it with bash into something you can read, then view or read that.]`. Withdrawn with other attachments, it may not be the one the API refused, so the note says so: `[a.pdf (application/pdf) was withdrawn with 2 other attachments when the API refused this step: Could not process image. It may be fine: view it again on its own, and convert it with bash only if that is refused too.]`, where the count is every other block withdrawn with it, pasted images included (`1 other attachment` for one). In a session without the bash tool, neither note names bash: `… couldn't be processed: … It can't be read in this session.]` alone, and `… It may be fine: view it again on its own.]` with others. A pasted image's note keeps the form above.

- **Accepted** (its first event): the withdrawal is kept. `AgentEvent::AttachmentsWithdrawn { step, items }` goes to clients, each item `{ call_id, ordinal, kind, label, reason, note }` (`call_id` only for a tool result), and the log records `attachments_withdrawn` before the step's messages (`docs/session-log.md`).
- **Failed:** the message goes back to its provisional form, images and all, and the re-send's error takes the existing path: a refusal tries the rendering forms, then, on a model with no capability row, the notes trial (below, "Attachments a model can't take"), and then ends the turn with that error; a retryable error (a 529, a dropped connection) goes to resilience, whose retry carries the images again, so a later refusal can withdraw them once more. The re-send itself is never withdrawn from, and an overflow that outlives the withdrawal ends the turn as any overflow does.
- **Stopped** before its first event: the message goes back to its provisional form.

A refused request returns no message and no usage, so nothing is priced for it, and the re-send reads the same cached prefix: everything before the provisional message was accepted earlier and is unchanged. The prefix-stability test checks that the steps after a withdrawal share one prefix, with the refused request left out of the chain.

**Resume.** `step_ended.accepted` records whether the step's request got its first event; the rebuild marks the last message provisional when it is a user message of tool results that no accepted step followed (`Rebuilt.provisional`), so an attachment refused after a resume is withdrawn like any other. A failed turn's own message is never kept in history, so it is never provisional after a resume. Logs before version 15 resume with nothing provisional.

**What you see.** In the TUI, the newest message you sent gains a line under its band in plain `text`, led by a faint bullet so it doesn't read as part of what you typed (with steered messages in the same step, under the last of them), `image #2 couldn't be processed: Could not process image`, and the turn's details in transcript mode (ctrl-o, twice once anything can be opened) read `re-send of step 1 without the attachments`. The re-send shows no retry count. A withdrawn tool-result attachment turns its call's row into `⨯ Read {target}  couldn't attach`, with the API's reason as a muted row below, or `withdrawn with N other attachments` when other attachments went with it (`docs/tools.md`, "Tool rows in the TUI"); when no row holds the call, it shows as a notice, `image #1 from call toolu_1 couldn't be processed: …`.

## Attachments a model can't take

After a switch to a model that can't take images or files, the chat goes on: the model gets a note in place of each image and file in the request, `[image/png file not sent: this model can't take it]`, and nothing else changes. A pair is an endpoint name and a model; a pair sends notes when:

1. **Known ahead.** The model's capability row says it takes no images (`ModelCapabilities.images` is `None`), as an account's model list can (Claude's `image_input`, ChatGPT's `input_modalities`). No refused request is sent.
2. **Learned.** The model has no row, and an earlier request on the pair sent notes and was accepted. A row decides whenever one exists, also one that appears after the pair was learned.
3. **On trial.** The model has no row, and the server refused a request that carried attachments as bytes, with an attachment refusal (above, "Recognising the refusal", without the 413 and the overflow, which are size problems). The adapter marks such an error `content_refused` when the request sent media (`Rendering.sends_media`, set by the agent while notes are off). The step loop tries this last, after the withdrawal, the rendering forms, the search probe and the refused-thinking recovery: it ends any search probe, withdraws the step's provisional media again with the refusal's message, and, when none are left, sends the step again with notes, as the same step and not as a retry. The trial stays on through the step's later re-sends and ends with the step. Accepted, the pair is learned; refused again, the turn ends with that refusal, as a refused withdrawal re-send does. A model whose row takes images never gets there: a refusal of an accepted attachment ends the turn, as before.

**Rendering.** Notes exist only in the request (`Rendering.attachments_as_notes`): history, the log and the stored files are untouched, so a switch back sends the original bytes. Every `image` and `media` block in a user message, also inside a `tool_result`, goes as the note: as a `text` block on Anthropic, an `input_text` part on OpenAI. Every attachment becomes a note, files too, since a refusal never names the block it refused. Steps, keep-warm, compaction and the whole-context count on the pair share that rendering, so they share one prefix. An Anthropic `Opaque` block holding a document, such as a fetched PDF in a server tool result, still goes as it is.

**New attachments on such a pair.** Nothing is committed on it without a request having carried its bytes. A pasted image is refused before sending, as for any model without image limits (`… can't take images: its limits are unknown.`). Tools see an empty media list, so a file a tool reads is refused before it joins the chat: `spec.pdf is application/pdf, which this server can't carry (it takes no files). Convert it with bash to text, or inspect it another way (file, xxd, strings).` Attachments still provisional, such as a tool's file whose step was stopped before a switch, are withdrawn before every send on the pair with the reason `this model can't take it`, shown as any withdrawal.

**Kept, resumed and rewound.** At the first event of a request that sent a note for at least one attachment, on a pair not yet recorded, the log records `attachments_as_notes` with the endpoint and model (`docs/session-log.md`), the rebuild mark moves to the first attachment with reason `attachments_as_notes`, and clients get `HistoryAdapted { change: AttachmentsAsNotes { model, images, files } }`. Right after a switch the mark changes nothing, since the switch marked first; on the same pair it makes the rebuild an expected miss. A resumed session restores the learned pairs and sends notes from its first request. A rewind keeps them: they are facts about the pair. A spawned child starts with none.

**What you see.** One muted line under your message, the first time a given account and model gets notes: `text-model can't take attachments, so it gets a note in place of 1 image.`, or `… so it gets notes in place of 2 images and 1 file.` The model is named as the switch names it; the endpoint isn't, since the switch note above it does. A trial's refused request shows nothing of its own and no retry count; a step that still fails shows its error.

**Costs.** A refused request is unbilled. From a refusal, the re-send writes the new pair's prompt once, as any switch does; known ahead, there is no refused request. Each image costs up to about 1.6k tokens on Claude, its note about 15. Later steps on the pair read that prefix, and the original pair renders as before, so the switch back costs what it costs today. `/context` and the `Context:` estimate still count the images.

**Rare cases.**
- A note's re-send can be the same bytes as the refused request: a tool result's media in a flattened rendering form (already `[image]`), or a type the adapter can't carry (already the server's note). A server that refuses it again ends the turn.
- The rendering forms run first. When a gateway with no row answers a typed `invalid_request_error`, the request carries a rendered block and every attachment sits in a rendered tool turn's results, a flattened form may be accepted: its images show as `[image]` from then on, on every pair, and the pair isn't learned.
- For a model with no row, a 400 that dropping the bytes happens to cure learns the pair for the session: a gateway's own context-length wording, which isn't read as an overflow, or one image the backend refuses for its size.
- When several attachments left from before a switch are withdrawn at once, their file note says the API refused this step, though no request was.
- If you switch a chat holding a committed audio, video or Office file to a model that cannot read that kind (such as `gemini-3.1-flash-image`), later turns can fail because Wisp cannot withdraw a committed file; switch to a chat model that accepts that kind.

## Files that tools attach

A tool can return files with its result (`ToolRun.attachments`): raw bytes and a media type each, nothing else. The kernel has no per-type logic for them; `media.media-types` tells the tool which types the session's provider carries (`Provider::media_types`, a sorted list of types and subtype prefixes from the adapter), and the API decides the rest.

- **What the endpoint carries.** After the call returns and before its `ToolCallFinished`, a file whose type doesn't match `Provider::media_types` is refused, so no request is built that the adapter can't serialize: `song.mp3 is audio/mpeg, which this server can't carry (it takes application/pdf, image/gif, image/jpeg, image/png, image/webp). Convert it with bash to one of those or to text, or inspect it another way (file, xxd, strings).` The name is the call's display target.
- **One file's size.** A file over `MAX_ATTACHMENT_BYTES` (7.5 MB) is refused next, before anything is saved, so the store never holds a file a rebuild can't read back (`MAX_BLOB_BYTES`): `big.pdf is 7.6 MB; files over 7.5 MB can't be attached. Make a smaller copy with bash, or extract the part you need, and use that instead.` Sizes are decimal megabytes rounded up to a tenth. A tool can refuse sooner with its own sentence. In a session without the bash tool, both refusals end `…, so it can't be read in this session.` instead of naming bash.
- **The budget.** Then the loop checks the conversation's media budget, `MAX_SESSION_MEDIA_BASE64` (20 MB of base64), against every media block the next request would send (after a compaction, only what follows the compacted head), the waiting messages, the turn's pending pasted images and the earlier results of the same step. A call whose files would pass it attaches none, and its result becomes the error `This file would take this conversation past 20 MB of attachments.` (`These files` for more than one). The pasted-image count check counts `image/*` files too, so a paste can't push a request past the model's image limit; it also counts only what the view sends, so a compaction frees both.
- **A refusal** attaches none of the call's files, whichever check refused them: the result is the error sentence alone (`is_error`, the tool's exit code kept), and of the tool's facts only `exit` and `process` stay, since the others described the output the sentence replaced.
- **Saving.** Each file is saved in the attachments store (`docs/session-log.md`, "Attachments") before the call's `ToolCallFinished`, which lists them in `attachments` (`media_type`, `sha256`, `bytes`, and `saved`, the saved file's path). A store failure turns logging off and the file is still sent. The log keeps a reference to the file, never its base64.
- **The result.** The `tool_result` holds the tool's text, then each file as a `media` block in the order the tool returned them. Like any new attachment it is provisional until a request carrying it is accepted (above). The Anthropic adapter sends `image/gif`, `image/jpeg`, `image/png` and `image/webp` as an `image` block and `application/pdf` as a `document` block. The OpenAI adapter sends `image/jpeg` and `image/png` as an `input_image` item and `application/pdf` and the docx, xlsx, pptx and odt types as an `input_file` item named `file.<extension>` (on the subscription, PDF and docx only; `docs/openai.md`). Gemini sends the tool result as `functionResponse`, then each file as a sibling `inlineData` part with its type and data. On any adapter, a type it doesn't carry, which only a history from another connection can hold, goes as the request-side note `[<type> file not sent: this server can't carry it]`, so the session goes on after an account switch and the model still sees that a file was there. On all three adapters, an `image` block and a `media` block of the same type and data are sent as the same bytes. The flattened rendering form shows a file as `[file]`.
- **After an upgrade.** A Gemini chat holding an OOXML or OpenDocument file from an OpenAI connection now sends the file instead of a note. The first request after the upgrade rebuilds the cache from that file onward; later requests keep the new prefix.
- **Not run to the end.** A call the kernel asked to stop (a cancel, or its time limit) attaches nothing, whatever its tool reported: its files and the facts about them are dropped, its result becomes `Stopped before the file was attached.` (`the files were` for more than one), and its outcome is `cancelled`, or `timed_out` when the time limit stopped it.
- **A compaction.** The files leave the view with everything before the compacted head. The head's tool-call ledger names each call's files by media type (`attached application/pdf`, `(withdrawn)` after a withdrawal) beside its target and turn, and says once that they are no longer in the conversation, so the model can repeat a call to see one again; it never inlines them (`docs/context.md`, "Compaction").
- **`/context`** lists each file under Attachments, named by its call's target and marked `not estimated` (`docs/context.md`).

## Compacted-away media

After a compaction, the base64 of every image and attached file before the view's start (the head's cut, `view_from`) leaves memory and is read back from the attachments store when it is needed again (plan `docs/plans/memory.md`, K3d). Nothing is written: the log, the store and every request stay byte for byte as they were.

- **What is evicted.** An `image` or `media` block, at the top level or inside a `tool_result`, in a message before the cut, when the session's log is on, its base64 decodes (strict standard base64, so a restore encodes it back to the same text) and the store returns its file (`SessionStore::get_blob`, which checks the hash). The block keeps its place with an empty `data`; the agent keeps the file's reference (`BlobRef`) and token estimate beside it, keyed by the message and the block's place among its media. With logging off or failed, or a block logged inline (undecodable base64), the block stays in memory. It runs after each head install and after a resume.
- **Restoring.** A rewind first reads back every evicted block from the point's view start (or its opening message, if earlier) onwards, so the returned input carries its images and the next request resends the same bytes. Before each step's request the agent restores anything at or after the view's start, which is normally nothing. `Agent::history()` returns the restored form. Token estimates for rewind points use the kept estimates.
- **A missing file.** If a file was deleted or can't be read when a rewind needs it, the rewind is refused (`not_rewindable`): `Can't rewind: the image file <sha256>.png is missing from the attachments folder.` (`attachment file` for other types). Nothing is truncated. If the step's own check can't restore a block, the turn ends with an `invalid_request` error rather than sending an empty block: `Wisp can't send this conversation: the image file <sha256>.png is missing from the attachments folder.`
- **Cleanup.** Nothing deletes files from the attachments folder; the old-output sweep removes only `wisp-<session>` folders in the temporary folder (`docs/tools.md`).
