# Gemini and Antigravity connections

Wisp runs Google Gemini models through its own kernel and native Gemini adapter (`ProviderKind::Gemini`). Named accounts select either an Antigravity subscription (`AuthKind::AntigravitySubscription`) or a Google Gemini API key (`AuthKind::ApiKey`, plus `AuthKind::Bearer` for compatible gateways). Signing in never falls back to API billing, and Wisp does not launch another agent's CLI or read its credentials.

## Antigravity subscription

```sh
wisp login antigravity
wisp status antigravity
wisp account models antigravity
wisp --account antigravity --model gemini-4-carbon-high
wisp logout antigravity
```

Login uses Google OAuth 2.0 with S256 PKCE (`https://accounts.google.com/o/oauth2/v2/auth` and `https://oauth2.googleapis.com/token`) with Google's installed-application desktop OAuth client parameters. The desktop client secret (`ANTIGRAVITY_SECRET`) is the app's fixed sign-in identifier, the same for every user, not a user's secret. When a local browser can be opened, Wisp binds an ephemeral loopback listener on `127.0.0.1:0` (`http://127.0.0.1:<port>/oauth-callback`), opens the authorization link and finishes automatically once Google redirects back. On headless or SSH machines where no local browser can open, Wisp switches to manual callback mode (`http://127.0.0.1:51121/oauth-callback`) and prompts for the redirect URL from the browser's address bar (`Callback URL`), validating its host, `/oauth-callback` path, PKCE state and percent-decoded authorization code before exchanging tokens.

Both initial code exchange and hourly refreshes send form-encoded requests (`application/x-www-form-urlencoded`) under the credential-directory lock. Local and keychain storage follow the same owner-only permissions, atomic writes and rotation recovery as other subscription profiles (`docs/openai.md`). Beside the profile, `oauth-<id>.account` stores only a SHA-256 hash of `("wisp-account-1", "antigravity", sub, "google")` extracted from the `id_token` JWT to prevent duplicate aliases for the same account; raw `sub`, email and `id_token` values are never persisted or logged.

Antigravity requests target the Cloud Code PA host configured in `[providers.gemini.antigravity]` of `crates/wisp-core/data/models.toml` (`base_url`, the Antigravity CLI's Cloud Code PA endpoint) with `Authorization: Bearer <access_token>` and the row's `user_agent` (a product identity template rendered with the client version, whose shipped fallback is in `[providers.gemini.client]`; see `docs/endpoints.md`, "Client versions", containing no OS, architecture, machine or personal data). An Antigravity endpoint in `config.toml` may set `url` to another `https://*.googleapis.com` host (such as `https://cloudcode-pa.googleapis.com`) or a loopback address if the service moves; third-party URLs and `url_env` are refused so `cloud-platform` OAuth tokens are never sent off Google's origin. When Cloud Code PA returns HTTP 429 (`RESOURCE_EXHAUSTED`), Wisp classifies it as `ErrorKind::RateLimit`. The retry header takes precedence over `google.rpc.RetryInfo`, which takes precedence over `quotaResetTimeStamp`. A wait over a minute becomes a used-up limit on the request's model; a shorter wait stays a retry. `QUOTA_EXHAUSTED` without a usable reset or retry delay stops the turn. See `docs/endpoints.md`, "Busy endpoints", for the turn's wait bounds and held limits. When the host is unreachable or returns `UNAVAILABLE`, Wisp classifies it as `ErrorKind::Network` or `ErrorKind::Overloaded` with transient retry.

Lazily before the first turn, model list or quota read (`wisp doctor --check` instead sends only `POST /v1internal:fetchAvailableModels` with `{}`), Wisp resolves the user's `cloudaicompanionProject` through `POST /v1internal:loadCodeAssist` (accepting either string or `{"id": ...}` shapes). When the account has not yet been enrolled in a Cloud Code Assist tier, Wisp automatically calls `POST /v1internal:onboardUser` to enroll the default `allowedTiers` entry (`isDefault: true`, falling back to `"free-tier"`) and polls up to ten times until provisioning completes. Ineligible tiers surface a sanitized permission error without raw identity fields. Resolved project IDs are cached in `Tokens.project_id`, preserved across hourly token refreshes and registered in `Redactions` so project IDs never leak into session logs.

Streaming inference posts to `POST /v1internal:streamGenerateContent?alt=sse` using the Cloud Code PA envelope (`project`, `model`, `userAgent` from the row's `envelope_user_agent`, `requestType: "agent"`, `requestId`, `request`) while the HTTP `User-Agent` header keeps the rendered `user_agent`, and unwraps `{"response": ...}` SSE frames. On a route whose row carries `session_id = "cascade_fnv1a64"`, the inner `request` also carries `sessionId`, the signed decimal FNV-1a 64-bit hash of `labels.cascade_id` (stable for a conversation, new when the conversation id changes), and `labels`: `cascade_id` and `trajectory_id` (one id per conversation: a hash of the request's model, system instruction, tools and first message, which adds nothing the same request doesn't already carry and holds no Wisp session id, account, project, path or machine fact), `request_id` (`<id>-<n>`) and `last_step_index` (`<n>`), where `n` counts the conversation's model calls. Both `cascade_id` and `sessionId` change when the start of the prompt does: a compaction, or a switch of model or effort variant. The prompt's own fields and Wisp's cache digest don't change. Live model discovery and subscription quota reads share `POST /v1internal:fetchAvailableModels`, filtered deterministically by `is_gemini_model` (`gemini-` / `ModelTable` Gemini rows with Google Gemini `apiProvider`) so third-party partner entries never appear in `/model`, `wisp account models`, `/usage` or `wisp status`.

Subscription turns record `antigravity_plan` billing provenance and API-equivalent `~` estimates without charging API spend. `/usage` shows one `All models` row when every Gemini model reports the same limit and reset, else one row per model named from its id, each with its whole used percentage (rounded down) and reset time; `wisp status` summarizes the highest-used window under `Model used` / `model used`.

## Gemini API key and gateways

Store a Gemini API key through the hidden prompt or import `GEMINI_API_KEY`:

```sh
wisp account add gemini-api --provider gemini --auth api_key --default
wisp account models gemini-api
wisp --account gemini-api --model gemini-4-carbon --effort high
```

`AuthKind::ApiKey` sends the key exclusively in the `x-goog-api-key` HTTP header against `https://generativelanguage.googleapis.com` (never in a `?key=` URL query parameter). `AIza` keys are masked in diagnostics and HTTP/stream error bodies and caught by Wisp's variable-name key guard even when they contain underscores. Named accounts may instead read `GEMINI_API_KEY` and optional `GEMINI_BASE_URL` on machines without a keychain, and `wisp account import` imports `GEMINI_API_KEY` under the default alias `gemini-api`. Compatible gateways may configure a custom HTTP(S) `url` with `auth = "api_key"` or `auth = "bearer"`.

API turns stream from `POST /v1beta/models/{model}:streamGenerateContent?alt=sse`, account probes call `GET /v1beta/models?pageSize=1` and `wisp account models` paginates `GET /v1beta/models` (filtering `supportedGenerationMethods` containing `generateContent` and `is_gemini_model`).

## Models, thinking signatures, tools and caching

When no model is explicitly configured, a Gemini API account defaults to `gemini-4-carbon` (`[providers.gemini].default_model`), while an Antigravity subscription account prefers `defaultAgentModelId` from the account's saved `fetchAvailableModels` model list and defaults to `gemini-4-carbon-medium` (`[providers.gemini.antigravity].default_model`) until then.

Interactive Wisp refreshes Gemini and Antigravity lists hourly after success, or at the first background check at least about 15 minutes after failure, and sorts both fetched and cached lists as described in `docs/endpoints.md`, "Each account's model list".

Capabilities, thinking budgets and prices come strictly from `crates/wisp-core/data/models.toml`, never from version-number prefixes:
- Rows with `adaptive_thinking = true`, non-empty `efforts` and no `effort_variant` (`gemini-4-neon`, `gemini-4-carbon`, `gemini-4-argon`, `gemini-4-hydrogen`, `gemini-3.8-flash`, `gemini-3.6-flash`, `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`, `gemini-3.1-pro-preview`, `gemini-3-flash-preview`) send `thinkingConfig: { includeThoughts: true, thinkingLevel: "LOW" | "MEDIUM" | "HIGH" | "XHIGH" }` (`"XHIGH"` for rows that list `xhigh`; `Effort::Xhigh` on other rows and `Effort::Max` map to `"HIGH"`).
- Rows with `thinking_budgets = { low = ..., medium = ..., high = ..., max = ... }` (`gemini-2.5-pro`, `gemini-2.5-flash`, `gemini-2.5-flash-lite`) send `thinkingConfig: { includeThoughts: true, thinkingBudget: <tokens> }`.
- Antigravity's seventeen `effort_variant = { family = "…", effort = "…" }` rows have their thinking level in the model ID. The model picker folds each family (`gemini-4-neon`, `gemini-4-carbon`, `gemini-4-argon`, `gemini-4-hydrogen`, `gemini-3.8-flash`) into one row; `/effort low|medium|high` (and `xhigh` on `gemini-4-neon` and `gemini-4-hydrogen`) and a spawn's named effort switch to that level's real ID, refusing an unsupported level or an ID the account does not serve. At start and on resume the ID wins over a saved or flagged effort. Wisp sends `thinkingConfig: { includeThoughts: true, thinkingLevel: "LOW" | "MEDIUM" | "HIGH" | "XHIGH" }` matching the row's own `effort_variant.effort`, ignoring the session effort. `gemini-3.8-flash-tiered` stays a separate row with `efforts = []` and sends only `thinkingConfig: { includeThoughts: true }`. Non-thinking rows such as `gemini-3.1-flash-image` (`adaptive_thinking = false`, `efforts = []`) omit `thinkingConfig`.
- Live-discovered Gemini models that are not yet in `models.toml` (`LISTED_ONLY`) omit `thinkingConfig`, disable image attachments and mark cost unknown: `/model` shows `cost unknown` (on metered accounts) and `"No data for this model yet: thinking, effort and images are off."`, while startup and model-switch notices repeat that thinking, effort and images are off and name `[models."<id>"]` in `config.toml` when no table entry sets window or price.

A shipped model row may carry `reply_cap`, a first-try output token cap (`32768` on `gemini-4-neon`, inherited by its four effort-variant IDs):
- The first try of each step sends `min(full limit, reply_cap)` as `generationConfig.maxOutputTokens` while `session.max_tokens` keeps the full limit; the resend carries the full limit, and the next step starts capped again.
- A reply cut at `MAX_TOKENS` is never committed, on any model (`docs/architecture.md`, "Reply cut at the limit"). On a capped model the first cut becomes a transient `invalid_response` (`max_tokens`, HTTP 200, mid-stream, usage complete) and resends the same request once with the full limit, while a second cut, a cut when the request's limit was already at or below the cap, and any cut on a model without `reply_cap` end the turn with `invalid_response` (`RetryClass::Never`), keeping only earlier committed steps.
- Compaction, titles, side questions, keep-warm and web-search side calls build their own requests and stay uncapped.
- The resend equals the first try except for `generationConfig.maxOutputTokens`, which sits outside Wisp's prefix prints; the Gemini prefix-stability test checks the accepted chain with that limit removed from each copy while keeping `assert_gemini_prefix_stable` strict for every other test.

A shipped model row may carry `turn_form`, four strings that set how a new turn reads (only `gemini-4-neon`, inherited by its four effort-variant IDs; models without it send today's bytes):
- `mail_before` and `mail_after` frame each message from another agent except a `task`, around its `<wisp:message>` block; the text is written once, when the message arrives, by the model it will be sent on (the running turn's, or while no turn has applied its settings, the model of a pending `/account` or `/model` switch), and logged as the input's text.
- `data_open` and `data_close` wrap the `time/sent` and `context/fill` lines into one last part of the turn, after the user's text and images or the mail; the kernel tells the two plugins through the `data-block` capability, and they write `The current local time is: 2026-11-24T07:53:41+08:00.` and `Context window: 211k of 1M tokens (20%); Wisp compacts at 256k.` in place of the `Sent:` and `Context:` lines. Steers that come in later go after that part.
- The form applies to new turns only: turns already in a chat keep their bytes, the `Sent:` and `Context:` sentences stay in the system prompt, and a turn retried after a model switch takes the data part of the model it is retried on. Mail keeps the form it was written in: one held or queued across a later switch reaches the new model framed for the old one.
- Each string is non-blank (more than white space), at most 400 characters and never holds `<wisp:message`.
- Measured on one 213k-token replay of a chat where Neon acted on a report that had not come in: 0 of 60 replies acted on it in this form, against 30 of 124 with the frame alone and 70 of 75 with neither. Not drawn: folded mail in this form, a `task`, a Neon child, a turn with `time` or the context note off, and the context note's two other wordings (`…; automatic compaction is off.` and `Context window: 211k tokens; window unknown.`).

Every streamed Gemini part round-trips losslessly within the same Gemini account (`identity`, `docs/session-log.md`, "What is never logged"):
- Thought parts (`thought: true`) stream into an unsigned `ContentBlock::Thinking` projection preceded by an identity-bound `wisp_native_item` reasoning envelope (`provider: "gemini"`, `projection_blocks: 1`).
- Text parts carrying a `thoughtSignature` attach an identity-bound `"type": "text_signature"` envelope (`projection_blocks: 1` for non-empty text, `projection_blocks: 0` for trailing empty signature parts, never merged onto an active `thought: true` part) so same-account turns replay `{"text": ..., "thoughtSignature": ...}` without opening a spurious thinking block while cross-account turns keep plain text and strip the signature. Separate signed `thought: true` chunks stay separate blocks rather than concatenating signatures. Signed quiet ends keep their Gemini native thinking and signature items (downgrading signed blank text to `projection_blocks: 0`) before `[no text]`; same-account requests replay those signed native parts without synthetic `[no text]`, while unsigned-only quiet ends, legacy `[no text]` logs, cut thinking without a `text_signature`, compaction and cross-account/cross-provider turns replay `[no text]`. A `STOP` reply with nothing in it (no non-blank text or thought, no signature, call, other part or search query) is not a quiet end: it fails as a retryable `invalid_response` ("Gemini returned an empty reply") and keeps nothing.
- Unrecognized or server-tool model parts (`executableCode`, `codeExecutionResult`, `toolCall`, `toolResponse` and any non-text part) are recorded verbatim as `"type": "part"` opaque envelopes (`projection_blocks: 0`) and replayed in original part order on the same account.
- Function calls receive per-response UUID-backed synthetic IDs (`gemini_call_<uid>_<seq>`) when Gemini omits `functionCall.id`, and `functionResponse.name` resolves from the immediately preceding assistant message's matching `ToolUse` before falling back to session-wide lookup so resumed turns never collide. Function-call `thoughtSignature` tokens round-trip through a trailing `"type": "call_signatures"` block, falling back to `"skip_thought_signature_validator"` on the first `functionCall` part when replaying unsigned or cross-account tool calls.
- Every reply that makes a function call ends with that `call_signatures` block, its `signatures` empty when no call was signed, carrying `"fold_text": true`. In the user turn answering such a reply, each text block after a `functionResponse` (mail, a steer and its note, `Sent:` and `Context:` lines, the opening of the next turn after a stopped or failed one, the retry note appended after a `MALFORMED_FUNCTION_CALL`, the `<environment>` and `<compacted_context>` lines a kept view places after tool results, and the compaction summary instruction) is appended to the last `functionResponse.response.output` so far, after `"\n\n"` unless the output is empty, `is_error` results included; images and files stay separate `inlineData` parts, and the notes for attachments not sent stay separate `text` parts. The field is never sent to Google, Anthropic or OpenAI, and the Antigravity connection shares the rule. Turns answering a reply without the field (older chats, other providers' replies) keep their text as sibling `text` parts, so their requests stay byte-identical.
- Old chats replay hosted search calls as identity-bound `"type": "search_call"` items preserving the original function-call part and signature, paired with `"type": "search_result"` items holding the output and sources (`projection_blocks: 0` for both). The result replays as a user-turn `functionResponse`. New searches use ordinary tool calls, results and call-signature markers.

Call-signature markers and native replay envelopes are recorded and replayed to Google but never drawn in the transcript. Unknown drawable blocks still show the unsupported-block notice.

Client tool schemas are passed in `functionDeclarations[].parametersJsonSchema` with deterministic `BTreeMap` key ordering and only `$schema` stripped recursively, preserving full JSON Schema keywords (`anyOf`, `oneOf`, `$defs`, `$ref`, `const`, `additionalProperties`, `pattern` and nullable type arrays).

Web search is on by default for every shipped Gemini model except `gemini-3.1-flash-image`. The account's list supplies its window and max output; shipped rows supply effort, image input and search facts, including when a saved list holds older copies. The chat declares `web_search(query)` among its ordinary functions; the bundled `web-search` plugin answers it through `model.ask`, with a separate request carrying only Google Search, on the first ID from the account's `webSearchModelIds` that is served and has a model row with native search, then `[providers.gemini].web_search_model`, then the chat's one-shot model (a level-in-ID chat's low ID when served, else the chat model). On gateways it uses the chat model instead; when the chosen search model refuses the search, it retries once on the chat's one-shot model. It returns the findings and a numbered source list as a function result. Search calls run one after another through the kernel like other client calls; their rows show Google's first query. Empty queries get `query must not be empty`, other search failures get `web search failed: <kind>`, and cancellation keeps a `web search cancelled` result. The answer has one Sources list underneath, without marks beside its sentences. Calls, their signatures and results round-trip unchanged, including old native items and after Web search is switched off.

Every Gemini request sends four stop sequences: a newline, a `user` line, then Wisp's `Sent: ` stamp prefix, `Context: ` note prefix or `<wisp:message` opener, plus `\n<wisp:message from="` to stop before an invented user or inline mail turn. A model with `turn_form` gets a fifth, a newline and `data_open` without its last line break (`\n<ADDITIONAL_METADATA>`), which stops an invented data part; the words an invented turn writes before it, and an invented frame sentence before a mail header, stay in the reply. Google excludes the matched sequence and reports `STOP`, which Wisp treats as normal end-of-turn completion. Because the fourth sequence matches any line starting with `<wisp:message from="` after a newline, a legitimate reply that puts that header at the start of a new line truncates there, as one that starts a line with `<ADDITIONAL_METADATA>` does on a model with the fifth, and a fabricated mail header at byte 0 of a reply (with no leading newline) is not stopped.

On an invalid finish (`MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, or an empty `STOP`), the Gemini stream decoder attaches `detail.stream` counts (`stop_reason_seen: true`, `partial_event: false`) to the error detail. For `MALFORMED_FUNCTION_CALL`, it also classifies the candidate's `finishMessage` into `detail.malformed_call` labels (`docs/session-log.md`) using the declared tool names and stop sequences read from the sent request body, without logging Google's message text.

System instructions (`system` plus `instructions`) stay fixed in top-level `systemInstruction`, mid-session `Role::System` deltas append in `contents`, `PrefixBytes` and `cache_prefix` hash `(model, thinkingConfig, tools, systemInstruction)` without serializing `contents`, and `wire_print` hashes each wire `contents` entry so in-life misses distinguish `remote_loss` from `message_changed` (indexed by `contents` entry). Implicit prefix caching reports hits via `usageMetadata.cachedContentTokenCount` (`cache_read_input_tokens`) with no explicit cache-TTL storage resource required.

### Implicit cache

Google caches a request's prefix by itself and documents no lifetime for the Cloud Code PA route. What Wisp measured there is data, in `[providers.gemini.antigravity]` of the model file: `cache_idle_s` is the time since an entry's last use, counted from that request's start, after which it is expected gone, and a miss after that long is `ttl_expired` (`docs/context.md`, "Cache misses"). A Gemini API key has no such row and is judged against the tail TTL. Every hit re-processes about 2,050 tokens of the prompt. Measured on 2026-11-22 with unpinged probes of about 8k and 16k tokens, Neon missed 1 of 33 up to 12.5 minutes (2 of 3 hit at 15) and Carbon hit 3 of 3 at 5 minutes and 1 of 3 at 10; Neon was unchanged at 5 and 10 minutes with `thinkingLevel` sent. So `cache_idle_s` is 600, the longest pause with broad support.

Gemini usage subtracts `cachedContentTokenCount` from `promptTokenCount` for uncached input. A shipped model row with `bill_tool_use_prompt = true` also adds `toolUsePromptTokenCount` to that uncached input, without changing the cache-read count or the separate per-query grounding fee. The flag defaults to false and is enabled where Google's pricing bills grounding's tool-use prompt as input.
