# The learning app

`learn` serves a lesson to a browser on this computer, or over HTTPS to the devices on the home network once the home certificate is made: Wisp's orb, large, with its status under it, which a learner taps to talk. The program, in `apps/learn`, reads the flow's settings and starts its session through `wisp-start`; its page and host are the library `learn-web`, in `apps/learn/web`, a protocol client like the TUI that never depends on `wisp-core`.

## Starting on this computer

```
$ learn
Open http://127.0.0.1:8443 on this computer · ctrl-c stops
```

- A start continues the last lesson: the newest one with a turn, whichever folder `learn` starts in, with its last page on the board. `learn --new` starts a fresh lesson on an empty board. A last lesson still open in another `learn` stops the start: `learn: the last lesson is open in another learn; close that one, or start fresh with learn --new`.
- The host listens on `127.0.0.1` at `--port` (8443 when not given). Open the printed address in a browser on the same computer. `--account NAME` starts the brain on that account for this run, as `wisp --account` does.
- The lesson runs on the user's own Wisp config (`~/.config/wisp/config.toml`, with its accounts and keys) with the flow's settings over it: `flows/interactive_education/settings.toml`, read in place, gives the brain its preset and its one tool, no project instructions and the voice's instructions; its effort, low, is the preset's, so an effort saved in the config or picked in Settings wins over it. A flag wins over the flow's values, and a Settings pick wins over both. The flow's file names no account: one there, `default` and `voice.endpoint` included, stops the start with `learn: the flow's settings can't hold accounts`.
- Lessons are kept in their own folder, `~/.local/share/learn/sessions/`, apart from Wisp's chats.
- Start warnings go to stderr. Each failed turn of the main agent adds one line to stderr, `The brain couldn't answer: ` and the turn's error, sanitized, with key-shaped model ids hidden as the TUI hides them.
- ctrl-c stops the host and ends the lesson.
- The main agent's tools are exactly the `tools` list; with none, it has no tools at all, never the default set.

## What the host checks

- **Every connection:** its peer address, IPv4 tablets on the dual-stack listener counted as IPv4, is loopback, 10/8, 172.16/12, 192.168/16, 169.254/16, fc00::/7 or fe80::/10; any other is closed before TLS. At most 128 connections are open at once, sockets included; a further one is closed at once. A TLS handshake gets 10 seconds, and each request head 10 seconds.
- **Every request:** over plain HTTP, its one `Host` is `127.0.0.1`, `localhost` or `[::1]` with the port, so a DNS-rebinding page can't reach it, and an `Origin`, when sent, is `http://` and that `Host`. Over HTTPS the certificate takes the loopback check's place, since a page that points its own name at the home address fails it, and an `Origin`, when sent, is `https://` and the request's `Host`. `Origin: null` is refused. Only `GET` is served.
- **The socket** (`/socket`, one per screen) also needs an `Origin`, which a browser always sets itself, so a page from another site, or the board's sandboxed frame, is refused. Messages and frames are capped at 64 KiB, and request heads at 16 KiB.
- **In:** a text frame is a `ClientCommand`, passed on only when its `type` is in `learn_web::IN`, the one list of what the page may send: `change_settings` and `describe_settings`, checked further under Settings below, `screen_report` and `voice`. A `start` passes only while no call is held, and `stop` only from the screen that started the call ("Talking to the orb", below); a `screen_report` passes only from that screen while a call is held, from any screen otherwise ("The board", below). Everything else is dropped.
- **Out:** an event reaches the screens, as one JSON line, only when its `type` is in `learn_web::OUT`, the events the page reads: the main agent's `turn_started` and `turn_ended`, for Thinking, `voice`, for a call's start and end, Settings' `settings_changed`, `spend_changed` and `rejected`, and `tool_call_requested`, `tool_call_started` and `tool_call_finished`, for the board. It carries its `type` and only the fields `OUT` lists beside it: none for the turns, for `voice` its event's `type`, `call` and `outcome`, never its `seconds` or `cost`, for a requested call its `call_id`, `tool` and `input`, for a started one only its `call_id`, never its `cwd`, and for a finished one its `call_id` and its outcome's `status` and `is_error`. So every screen sees each tool call's input; with the flow's `tools = ["show_page"]`, that is only lesson HTML. The learner's words, the brain's text, account events and usage limits stay on the computer, and a child's events arrive wrapped as `agent` and stay too; of the accounts and the spend, Settings sends only its rows and the spend line (below). A test ties `OUT` to the handlers in `app.js`, both ways.
- **Audio:** binary frames carry the call's samples only, little-endian 16-bit at 48 kHz, with no header, and only between the host and the screen that started the call, from its `started` to its `ended`; samples from any other screen, or outside that span, are dropped. The host cuts the page's samples into the lane's 20 ms frames and numbers them.
- **Liveness:** the host pings each socket every 5 seconds and closes one that has sent nothing since its last ping, not even the browser's automatic reply, so a device that drops off the Wi-Fi without closing frees its slot and ends its call within 10 seconds. A send that takes longer than 5 seconds closes the socket too.
- Every page response (not the socket's `101` upgrade, nor `/frame`, below) carries the app's `Content-Security-Policy` (`default-src 'self'`, no inline script or style, `frame-ancestors 'none'`), a `Permissions-Policy` that leaves only the microphone and the wake lock to the page itself, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.

## Settings

The gear opens Settings on every device: two rows, `Brain` and `Voice`, each with the model in use and its account (`name · subscription`, `name · API` or `name · sign-in expired`), the Brain row also with `effort <level>` when the model takes an effort. A tap opens the row's list, with `Back`: the brain's opens with `Effort`, one line per effort the model takes, then each signed-in account with the models it offers, in `/model`'s usual order; the voice's has each signed-in account that offers voice with its voice model. `✓` marks the one in use, and an expired account's models are greyed and can't be picked; its row reads `Run wisp login <account> to sign in again.`. A pick is sent at once as `change_settings` and goes back to Settings, where the row reads `saving…` (`effort saving…` for an effort) until the answer, and a refusal shows Wisp's reason under the row. A brain pick that needs a smaller window is answered at once; the lesson is compacted first when the next turn starts, and a compaction that fails puts the old model back. When no voice account is chosen, the only signed-in account that offers voice is used; with none, the Voice row reads `none` and a call fails with `No signed-in account offers voice.`, and with two or more it reads `none` until one is picked. The voice's voice isn't on the sheet; it stays as the config sets it.

- **The rows:** from each settings snapshot the host makes one message, `{"rows": {"brain": …, "voice": …}}`, each row with its `model`, `account` (`name`, `kind`, `tone`, the theme token for `kind`, `expired` and `sign_in`), the brain's `effort`, and its list's `groups`, each a `heading` and its `items` (`shown`, `on` and the `changes` a pick sends). The brain's model and account are the ones its next turn runs on (the snapshot's `context`); the models come from `offered` over the snapshot's `models` and each account's own list, as `/model` lists its usual rows; the voice's account is the snapshot's `voice_account`, the same rule the call uses. `app.js` holds no setting name or model id: a pick sends back the item's `changes`. It is the first message on every socket and the answer to each `describe_settings`; the snapshot itself never leaves the host.
- **Where a pick is kept:** the host sets each command's `save` itself. A voice pick (`voice.endpoint`, which applies from the next call) is saved to the user's Wisp config, where the voice reads it at each call. The brain's account, model and effort are the lesson's, in its log, so a restart keeps them, and `learn` also keeps them in `~/.config/learn/settings.toml` for new lessons (`account`, `model` and `effort`, only those picked here, mode 0600); deleting the file forgets them. A new lesson starts on the picked account while it is still one of the config's accounts or the keys-file one, else it prints `learn: <account>, picked in Settings, is no longer an account here; starting on <account>`; on the picked model only when it starts on that account and the account serves it; and on the picked effort when the model takes it. A file that doesn't read prints one line and is skipped. `learn --account` or `WISP_ACCOUNT` starts a new lesson on another account for that run.
- **What the host refuses itself:** anything but the brain's account with its model in one command, the brain's effort, or the voice's account: a lone account or model, a change by path, a change with no value, no changes at all, and a command that mixes them. A name Wisp doesn't know is dropped as malformed. The asking screen alone gets a `rejected` with `Settings here can't make that change.`; Wisp's own refusals, such as a model the account doesn't serve, keep Wisp's reason.
- **Request ids:** the host gives each settings request its own id and maps the answer back. The asking screen gets its own id, in `answers` on `settings_changed` or `request` on `rejected`; other screens get `settings_changed` with none, and never another screen's `rejected`. A `rejected` the host didn't ask for goes to no screen.
- **Out:** `settings_changed` carries only `answers`; every sheet asks for the rows again on it, so a change made elsewhere still reaches every sheet. `spend_changed` carries only `total`, as the sheet's words: `about $0.60, included` when a subscription covers it, `$0.42` when an API account was charged, both joined by `·` when the session used both. Its latest line is also sent after the rows on every socket.

## The look and its one source

The page is `apps/learn/web/page/` (`index.html`, `app.js`, `app.css`, `audio.js`, the AudioWorklet that records and plays the call, and `frame.html`, the board's shell), built into the binary. It holds no colour and no motion of its own:

- `/theme.css` is `wisp_render::theme::css` of the dark true-colour theme: one custom property per token, `text.muted` as `--text-muted`. A test fails on any colour value in `page/`, outside the bundled libraries in `page/lib/`.
- `/orb.json` holds, for full and reduced motion, each state's film from `wisp_render::motion::film` (Ready's idle comet, Listening, Muted, Thinking, Answering, and two that play once: the chunk that relights Answering's core, and Stopped) as frames of `[x, y, colour, part]` dots from `OrbFrame::dots` on the braille cells' 6 × 4 grid, colours resolved by `Theme::ink_rgb`, and each dot's part, `ring` or `core` (`motion::Part`), from its cell, so the page knows which dots swell (below) and keeps no copy of the orb's shape. The page draws the dots as SVG circles and plays the frames, so the orb moves exactly as the TUI's; it cuts between states where the TUI blends. Motion pauses while the page is hidden, and reduced motion holds each still pose.
- Before a lesson the orb is alone and centred; the status sits on its own pill, `surface` with no border, as wide as its widest status so it never jumps: `Ready · tap to talk`, `Listening · tap to stop`, `Muted · tap to stop`, `Thinking · tap to stop`, `Speaking · tap to stop`, `On another screen`, and `Offline. Reconnecting` with the orb at rest while the socket reconnects by itself.
- The gear is Phosphor's `gear-six`, and the mic button's icons its `microphone` and `microphone-slash` (MIT, its notice in `page/phosphor-LICENSE`).
- **The bundled libraries** are in `page/lib/`, each byte for byte as its npm package ships it, banners and comments included, with its licence beside it as `<package>-LICENSE`; they are third-party files, not Wisp source, so the no-comments rule doesn't apply to them. `learn_web::LIBRARIES` lists the ones a lesson imports, each with its import name, file and SHA-256, and `learn_web::ENCODER` the one the frame draws its picture with; a test checks every hash. All are MIT:
  - `three` (`three.module.min.js`) and `three/addons/controls/OrbitControls.js` (`OrbitControls.js`): three.js r170, https://registry.npmjs.org/three/-/three-0.170.0.tgz, `build/` and `examples/jsm/controls/`. r170 is the last whose module build is one file; later ones import a relative `three.core.js` that a `blob:` module can't resolve.
  - `animejs` (`anime.esm.min.js`): anime.js 4.5.0, https://registry.npmjs.org/animejs/-/animejs-4.5.0.tgz, `dist/bundles/`.
  - `html-to-image.js`: html-to-image 1.11.13's UMD build, https://registry.npmjs.org/html-to-image/-/html-to-image-1.11.13.tgz, `dist/`.

## Talking to the orb

A tap on the orb, or on the pill under it, starts a call: the page asks for the microphone (with the browser's echo cancelling, noise suppression and gain control), sends `voice` `start`, and the host carries the call's audio over the socket. Wisp's voice layer holds the call itself (`docs/voice.md`).

- The orb follows the call: Listening (`Listening · tap to stop`) from `started` to `ended`, its ring closed while the microphone is open; Thinking while the brain's turn runs; Speaking while the voice's sound is above a threshold, its core lighting again at each loud stretch; Stopped once, then Ready, when the call ends. Speaking outranks Thinking, which outranks Listening.
- **Muting:** from `started` to `ended` the calling screen shows a mic button under the pill (at a phone's width beside a board, at the right end of the pill's row, the pill's words wrapping where the row is too narrow for both), `surface` with no border, its spoken name `Mute`. A tap turns the microphone track off (`MediaStreamTrack.enabled`), so the call carries silence and the browser may put out its microphone light, while the call stays up: the pill reads `Muted · tap to stop`, the icon is `microphone-slash` in `text`, its name `Unmute`, and the orb holds the Muted pose, Ready's open ring in Listening's colour with a dim core, still. Thinking and Speaking show as usual. Another tap turns the track back on, with no new permission prompt. Nothing new reaches the host: staying muted counts as quiet, so two minutes with no speech and no tap still end the call, and every call starts unmuted. Other screens show no button.
- **The orb moves with the voices.** While Listening the ring swells with the learner's voice, up to 1.2 times its size, and while Speaking the core swells with the voice's, up to twice its size, both about the orb's centre; the films still set every colour and every frame. `audio.js` measures both levels in the browser, the microphone's on the samples it records and the voice's on the sound it plays, and posts each at most every 50 ms; `app.js` eases each, rising within 50 ms and falling over 300 ms, and redraws the swell once a screen frame. The orb draws past its box for the largest swell, so nothing is cut and it keeps its size. There is no swelling with reduced motion, while muted, or on another screen, which hears no sound.
- A tap during the call hangs up; one while it is still connecting does nothing. So does the call's own end (two minutes of quiet, the provider closing, a failure), and the calling screen leaving: hiding the page or locking the screen sends `stop`, and a closed page or a lost socket makes the host send it for that screen. One command channel serves every screen, so a lost screen's call ends as `hangup`, never `client_gone`, which means the whole host left.
- A call that fails shows its sentence once in the pill's place: `The voice didn't start:` before `started`, or `The voice stopped:` after it, then the voice layer's sentence, `The board still works.` and `tap to try again`. A microphone the browser refuses shows `The microphone is blocked.` with `Allow it for this page in the browser, then tap to try again`; any other failure setting up the sound shows `The voice didn't start:` with no sentence after it.
- **Other screens** see the call's start and end and the brain's turns, never its audio: their orb shows Listening or Thinking, never Speaking, their pill says `On another screen`, and a tap starts nothing. A screen that connects during a call gets its `started` first. A `start` the host refuses because another screen holds a call is answered, to that screen only, with an `ended` for its own call, `completed` as `hangup`, with no seconds and no cost.
- **The screen stays on during a call.** The calling screen holds a screen wake lock from `started` to `ended`, and stops the microphone at `ended`, so the browser's microphone light matches the orb's ring. If the browser drops the lock itself, the page asks again while the call is live, the page visible and a person touched it in the last 10 minutes. After 10 minutes with no touch anywhere on the page it lets go, so a call left beside a TV ends when the device sleeps. Where the browser has no wake lock (iPhone and iPad before iOS 16.4, for example), the call ends when the device sleeps: lengthen its auto-lock in its settings.

## The board

The brain draws lessons with the `show_page` tool (`docs/plugins.md`): a whole page replaces the board, and a `part` fills the block with that id, or adds it at the end. The board appears beside the orb with the first page, and the orb moves to its left. The brain says a short lead, calls `show_page` and then explains with the board up, since the voice also says the first text after each successful call (`docs/voice.md`).

- **How a page arrives:** the page keeps each `show_page` call's input from `tool_call_requested` and shows it on the call's `tool_call_started` (the input has passed its checks by then), or, for a call it never saw start, such as one a new screen catches up on, on a `tool_call_finished` that is `completed` without an error. A whole page gets a fresh frame, so the old page's timers and loops end with it; a part goes to the frame that is there. Every page fits the board's width: nothing is wider than the frame, long words and `pre` wrap, a canvas, SVG, image or video also fits its height and keeps its shape, and a page still wider or taller after that is zoomed down to fit, measured after each page or part and whenever the page's size changes, a script's own changes and a resize included; an SVG with a plain width and height but no `viewBox` gets one, so its whole drawing scales. For height the zoom stops at 0.6: a page taller than that scrolls. Each new part slides in once, and the board scrolls it into view unless the learner touched or scrolled the board in the last 5 seconds. A whole page starts at its top.
- **The board's answer:** 1 s after a page or part is built, the frame posts its size in CSS pixels, its zoom and the page's script errors since the last report (from `error` and `unhandledrejection`, and as `couldn't load <url>` from a script, image or other element that fails to load and from a content-policy violation that names a URL, at most 5 of 200 characters each, with a repeat within one report dropped and errors caught while the picture is drawn left out), and the screen sends them as `screen_report` for the call whose content the frame built, one it showed on `tool_call_started`, when it holds the live call or no screen does. For every whole page, and for any report that is scaled or has errors, the frame adds a picture of itself, drawn with html-to-image as a JPEG at most 768 px on its long edge and at most 48 KiB of base64, its quality stepped down to fit, else none, with an image it can't fetch drawn blank; `show_page` attaches it to its answer under the kernel's media rules (`docs/media.md`). The screen leaves out the picture, then the errors, when the message would pass the socket's cap. The host takes a report only from the calling screen while a call is held, from any screen otherwise. `show_page` waits up to 4 s for it and answers the brain with it (`docs/tools.md`, "`show_page`"), so the explanation after the call starts about 1 to 2 s after the board is up.
- **The frame** is `<iframe sandbox="allow-scripts" src="/frame">`, with no `allow` attribute. `/frame` is a fixed shell that receives each page or part from the app page by `postMessage`, builds it with `DOMParser` and runs its scripts. With the first content the app page posts `/theme.css`, so a lesson uses `var(--accent)` and the other tokens on the board's `surface`, and the bundled libraries, fetched once at load from `/lib/map.json` and `/lib/<file>`, served as plain text, which the frame turns into `blob:` modules under one import map, so a lesson writes `import * as THREE from "three"`. The app page never runs them. The encoder is inlined into the `/frame` shell.
- **What the sandbox holds:** without `allow-same-origin` the frame's origin is opaque, so it can't read the app page, its storage or its cookies, and its socket would arrive with `Origin: null`, which the host refuses. `/frame` carries its own headers:

  ```
  Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline' blob:; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; form-action 'none'; base-uri 'none'; frame-ancestors 'self'
  Permissions-Policy: autoplay=(), camera=(), microphone=(), screen-wake-lock=(), geolocation=(), display-capture=(), fullscreen=(), payment=(), usb=(), serial=(), hid=(), bluetooth=()
  ```

  with `nosniff`, `no-referrer` and `no-store` as on every page. So a lesson loads nothing from the network: no `fetch`, sockets, outside images, scripts, fonts or styles, only what is inline, with `data:` and `blob:` images and fonts and the bundled libraries as `blob:` modules; `blob:` scripts add no power, since inline script already runs any code. It submits no form, opens no pop-up and gets no microphone, camera or other permission. Audio and video elements don't load, and nothing autoplays; the only sound with no tap is a lesson's `sound()`, which plays on the calling screen during a call, within its limits ("Sounds", below). The app page's `frame-src 'self'` keeps the frame from navigating to another site. Its own policy keeps no inline script or style, since the content arrives by message rather than `srcdoc`.
- **What it can't stop:** a lesson that loops forever freezes the tab on most tablets and phones. Before it hands content to the frame, the page marks it in `sessionStorage`, and clears the mark when the frame answers; a reload after a freeze skips that one call. Traffic the content policy doesn't cover, such as a WebRTC connection from the frame, could send only what the brain wrote, since nothing secret is inside. After a tap, a lesson's script can make a sound with its own Web Audio, which no header turns off; only `BRAIN.md`'s rule keeps lessons to `sound()`. A lesson's script can also post `touched` itself (below).
- **Catch-up:** the host keeps the last 1 MiB of successful tool calls, each requested call with its finish, and sends them, with any call still running, to each screen when it connects, before live events. So a reload or a second screen builds the last whole page and the parts after it, and every screen follows along. A continued lesson fills the catch-up from its log before it serves, so its first screen shows the last page; `learn --new` begins with an empty board. A continued lesson started with no `--account` goes on with the brain's account, model and effort from its log, and the voice account picked in Settings.
- **Sounds:** a lesson's `sound(seconds, build)` renders a cue in the frame with an `OfflineAudioContext` (mono, 48 kHz, at most 5 s; `build`, which may be async, connects its nodes to `context.destination`) and posts the samples to the app page. That page plays it through the calling screen's own call `AudioContext`, the one the voice plays through, so the browser's echo cancellation keeps it out of the mic as it does the voice; the mic isn't held. It refuses a sound over 5 s or with a sample that isn't a finite number, scales its peak down to 0.5, and starts it only while the voice is quiet; a sound that waits more than 10 s is dropped. When the voice starts, a playing sound fades out within 100 ms. A new sound stops the one before at once and replaces it; a new page or the call's end drops it, and with no live call on this screen nothing plays.
- **Taps:** a lesson's `tell(text)` posts the text to the app page, which sends it as `voice` `note` from any screen, naming this screen's call or the other screen's, else none, only while the page has a person's action (`navigator.userActivation.isActive`: a click, tap or key in the board counts), so a lesson's script that calls `tell` at load, from a timer or as a reload replays it sends nothing. The voice layer cuts and paces taps, and each reaches the brain as a `Tapped:` line, during a call or not, within half a second unless the brain is still answering (`docs/voice.md`). The app page takes messages only from the board's frame.
- **Touches keep the screen on:** a person's touch on the board (a trusted `pointerdown`, which a script can't make) is reported to the app page at most once a minute and counts as a touch on the page for the calling screen's wake lock. It stays in the page and never reaches the socket. A lesson's script could still post `touched` on purpose; nothing the brain reads names it.

## What leaves the computer

- The learner's voice and its transcripts go to OpenAI's voice route, under the voice account (`voice.endpoint`): the subscription's, or OpenAI's API when the voice account is an API one, where the brain's answers also go to be read aloud.
- Each hand-off's lines (what was heard, said, tapped and asked since the last one) go to the brain's account, under its own data controls, and the brain's answers go back to the voice route to be said.
- Each board report (the board's size, its zoom, the page's own script errors and the picture of the board, which may show or quote what the page holds, typed text included) goes from the screen to `learn` and into the brain's tool answer, under the brain account's data controls.
- As with every request, the home's public address goes too. No name, account ID or local address does (`docs/voice.md`, "The media leg").
- Lessons' logs stay on the computer, in `~/.local/share/learn/sessions/` (`docs/session-log.md`): every hand-off is a message there, each `show_page` answer is kept with its picture, and each call's record keeps the lines no hand-off of that call carried. Wisp never deletes them; delete a session's `.jsonl` file there to remove it.

## Opening it on the home network

```
$ learn
Open https://192.0.2.10:8443 on each device · ctrl-c stops
```

- With `cert.pem` and `key.pem` in `~/.config/learn/web/`, the host serves HTTPS on every interface at `--port`; with neither, plain HTTP on this computer only. Only one of the two, or one that can't be used, stops the start and is named.
- The address printed is this computer's on its network. When it finds none, the line is `Serving https on port 8443 · ctrl-c stops`.
- A `key.pem` that other users can read gets a start warning: `learn: ~/.config/learn/web/key.pem is readable by other users (chmod 600)`.

### Who can open the app

There is no sign-in and no PIN. Any device that reaches the port from a private address opens the app and can do whatever the page offers; what reaches it is `OUT` and what it may send is `IN` (above).

- Private addresses include a café's or a school's Wi-Fi, so on a laptop anyone on that network gets in too, as does a guest's phone on the home Wi-Fi.
- A call draws on the subscription's voice allowance, and each answer on its usage limits. A call on an API voice account (Settings' voice account, such as `openai-api`) is billed per use to that key, about $0.86 for a lesson hour with 20 minutes of each side talking, and any device on the home network can start one.
- A web page on another site can't drive it: the browser sets its `Origin`, and the check refuses it. A program on the home network can send any `Origin`, so it can do what a guest's browser does.
- The cheap guards:
  - **The spend under Settings.** Every screen's Settings shows what the lesson has spent, an API account's charges in dollars, so a cost no one meant shows at once.
  - **The Private profile, on Windows.** Windows 11 makes every network Public when it first joins it, and both firewall rules below are on the Private profile only, so a café's or school's network left Public reaches nothing. Make only the home network Private.
  - That guard is Windows' alone: on a Linux or macOS computer only the peer check stands, which lets every private network in.
  - **Guests on the guest Wi-Fi.** Put guests on the router's guest network where it has one; a guest on the home network itself gets in.

### The home certificate

Browsers give the microphone only to HTTPS pages or to `localhost`, so devices need HTTPS. Done once:

1. Give the computer a fixed address with a reservation in the router.
2. Make the certificate in `~/.config/learn/web/` with [mkcert](https://github.com/FiloSottile/mkcert), naming that address, `localhost` and `127.0.0.1`:

   ```
   mkdir -p ~/.config/learn/web
   mkcert -cert-file ~/.config/learn/web/cert.pem -key-file ~/.config/learn/web/key.pem 192.0.2.10 localhost 127.0.0.1
   ```

3. Install only mkcert's `rootCA.pem` (in the folder `mkcert -CAROOT` prints) on each device:
   - iPhone and iPad: open it to download the profile, install it in Settings, then turn on full trust for it in Settings › General › About › Certificate Trust Settings.
   - Android: install it as a CA certificate, under Security in Settings (the place varies by maker).
   - Laptops: add it to the system's trusted root store.
4. `rootCA-key.pem`, beside it, can sign a certificate for any site those devices visit. Never copy it; keep it on the computer, or delete it once the certificate is made, and a new certificate then needs a new root. Removing the profile or the certificate from a device undoes the trust.

If the terminal ever prints another address, the router reservation is missing, and devices will refuse the certificate.

### On WSL2

1. Turn on mirrored networking, so WSL shares Windows' home address (Windows 11 22H2 and later): in `.wslconfig` in your Windows user folder, `networkingMode=mirrored` under `[wsl2]`, then `wsl --shutdown`.
2. In an administrator PowerShell, allow the port through the Hyper-V firewall and the Windows firewall, both on the Private profile only (a Hyper-V rule left at its default applies on every profile):

   ```
   New-NetFirewallHyperVRule -Name WispWeb -DisplayName "Wisp web" -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol TCP -LocalPorts 8443 -Profiles Private
   New-NetFirewallRule -DisplayName "Wisp web" -Direction Inbound -Protocol TCP -LocalPort 8443 -Action Allow -Profile Private
   ```

3. Keep the terminal open and the computer awake: WSL stops a while after its last terminal closes, which ends the app, and a sleeping computer shows `Offline. Reconnecting` on every device.
