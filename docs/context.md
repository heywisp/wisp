# Context

How Wisp measures how full the model's context window is, and how it shows it. The design is in `docs/plans/context.md`; this page describes what is built.

## The window

Each model's window before any growth comes from the first of:

1. the endpoint's model table in `config.toml`, `[endpoints.NAME.models."ID"]` (source `account`);
2. your model table, `[models."ID"]` (source `config`);
3. the account's model list, if it supplies the window (source `subscription` or `API`); on a ChatGPT subscription, a usable listed default is the starting window for [token-point growth](#the-point-and-the-reserve). Without one, the list's maximum or an older saved window can only bound the fallback (source `subscription` if that bound sets the window, otherwise `shipped`; `docs/endpoints.md`, "Each account's model list");
4. the shipped model file, `crates/wisp-core/data/models.toml` (source `shipped`), which holds a row for every model whose window the provider documents, with its price where the provider lists one, each naming the page its values come from. A row with `listed = true` is one the `/model` picker lists under every account of its provider, except one with its own model list, which lists that list's entries instead; typing a name finds the rest.

A row also answers to the dated IDs in its `aliases`, so a configured table keyed by a dated ID applies to the same model. An `aliases` save made while Wisp runs reaches the window and the point at the next change of either, and everything else next session.

A `context_window` you set is your limit. Below the documented window it becomes the window, and `/context` shows the documented one beside it (`window 400k (config; documented 1M)`). Above it, it is accepted with a warning in the start warnings and in `wisp doctor`, naming the documented window and its page. A model with no shipped row takes any limit without a warning.

A limit whose default point (`window − reserve`) is under 40,000 tokens is refused, naming the reserve and the floor: `context_window 100000 for my-model puts the compaction point at 36,000 (window − reserve 64,000); it must be at least 40,000. Set at least 104000.` At the default reply limit of 64,000 the smallest window is 104,000.

A `max_output` you set for a model lowers its reply limit, and with it the reserve in the session and in `wisp doctor`; the `context_window` floor check keeps the default reply limit.

With no window from any of these, the window is unknown: the meter shows tokens only and the start warnings say `Window unknown for my-model: set context_window under [models."my-model"] in config.toml to enable automatic compaction.`

```toml
compact_at = 400000

[models."my-new-model"]
context_window = 400000

[endpoints.manifest.models."claude-opus-5-5"]
compact_at = "60%"
```

An invalid model table, a refused limit included, stops Wisp at start with the line it is on; `wisp doctor` shows it as an error row.

## The point and the reserve

- **Reserve:** the largest of 15% of the window (rounded up), 40,000 tokens and the reply limit.
- **Point:** `compact_at` from, highest first: a change made this session (for one model, or for every model, which replaces the ones made for one model), `--compact-at TOKENS|PERCENT` (this run only, for every model), the endpoint's model table, your model table, then `compact_at` at the top level of `config.toml`, which every model without a value of its own follows, new models included; as tokens (`400000`, `400k`) or a share of each model's own window (`"85%"`, rounded down), never past that model's `window − reserve`; otherwise `window − reserve`.
- **A point past the reserve** is capped: `/context` shows `Compacts at 208k (config 400k, capped at window − reserve)`, followed by the window and its source. `wisp doctor` uses the model's reply limit on that account; the `wisp config set` notes use the default reply limit.
- **A token point on a ChatGPT subscription** grows a usable listed default to the smallest window that fits the point, no higher than the listed maximum or a proved overflow: Astra with `compact_at = 400000` shows `window 471k (subscription; documented 272k)`. A share never grows the window, and there is no growth when you set `context_window` or use any other kind of account.
- **A point below 40,000** is kept, with a warning for `--compact-at` and for `config.toml` at start and in `wisp doctor`. `wisp config set` warns when the saved point wins for that model and account. The warning uses that model's prices for a typical 15,000-token head (`TYPICAL_HEAD_TOKENS`), the head written at the session's `cache_ttl`: `compact_at 10000 is below 40,000: once the head after a compaction is above it, every turn starts with a compaction, ~$0.123 a turn to compact and ~$0.12 to write the head again, at claude-opus-5-5's prices.`

## Automatic compaction

On by default; `--no-auto-compact`, `--set context.auto_compact=off` or `auto_compact = false` under `[context]` turn it off, and then the point is only the point Wisp *would* compact at. `/compact` and overflow handling work either way.

- **When.** Before every request: before a turn's first request, and at each step boundary after the tool results and any waiting steers. It fires when the estimate for the next request reaches the point. With an unknown window it never fires.
- **Before a turn.** The estimate is the turn's message (without its `Context:` line) on the next model's window and point. Its head is provisional, since the `before-turn` hooks haven't run yet: the prompt sections' texts from their last turn render (the `<environment>` block among them; refreshed at the start of each turn, at each step boundary and right after a resume, so an edit made while idle counts at the pre-turn decision, and never rendered from the sync estimate itself), then each on hook's manifest `reserve` in the hooks' resolved order: the `time` plugin's `time/sent` reserves a stamp of the epoch, as long as a real one, while stamps are on, and the `context` plugin's `context/fill` reserves nothing; it never counts the `<processes>` notice or the `core/tools` note. The plugin switches (`plugins.<id>.enabled`, `plugins.<id>.installed` and `plugins.<id>.hooks.<hook>`) apply just before this estimate, so a hook switched off since the last turn drops its reserve from this decision; a manifest `switch` and the other settings it reads are those applied at the last turn's start, so a change to them queued for this turn doesn't move this turn's decision (`docs/plugins.md`, "Hooks" and "Turning plugins on and off"). The estimate keeps that model's reply limit in the reserve, so a pending `/model`, `/endpoint` or window change counts. The compaction runs on the current model before the switch is applied: its `compaction_started`, `compacted` and `context_changed` come before `turn_started`, its `context_compacted` carries the turn's number and is logged before that turn's `turn_started`, and the turn's `Context:` line and effort marker are computed from the compacted view.
- **Between steps.** Held while a server call is open or paused. Waiting steers count toward the estimate but are never summarised: the next request is the head, then `Wisp compacted the conversation in the middle of this turn; continue the task from where you left off.` (logged as its own `message_committed`), then the effort marker if one is due, then the steers. A system message that also restates tools goes to a Claude model after the steers, while the history and the log keep it before them (`docs/tools.md`, "Switching tools in a running session"). No `Context:` line is added. When no step of the turn was kept yet (the first reply was empty or held only thinking), there is no note: the head is followed by the turn's own message, then the marker and the steers. A steer sent while the compaction runs waits for the next boundary.
- **Cost and retries.** The compaction's cost counts in the turn's cost and in `compaction_cost_usd`; foreground Wisp compaction follows the normal request policy, unbounded by default and still subject to its retry budget. Native compaction uses the finite fallback policy (five retries per step and ten total, shared with the enclosing turn for in-turn compaction); explicit finite overrides are preserved. Its `retrying` records carry the turn's number and no step.
- **The thrash guard.** At most one automatic compaction per request. Once one fails, or leaves the estimate at or over the point, there are no more in that turn and the request goes ahead; the next turn tries again. That compaction's `Compacted` or `CompactionFailed` event then carries `paused: true` (absent otherwise), and the transcript adds a note after it: `Automatic compaction paused for the rest of this turn: the conversation is still over the point after compacting.`, or for a failure `Automatic compaction failed (overloaded, after retries); paused for the rest of this turn.`, naming the failure and adding `after retries` only when the compaction was retried. If the estimate is then over `window − 8,000`, the turn ends without sending: with the failure's own kind and message (`overloaded` after retries, `invalid_response` for an empty summary, and so on), or, when the compaction succeeded, with `context_overflow` and `This message alone is too large for the model's window.` A turn that ends before its first request logs `compaction_failed` (or `context_compacted`), `turn_started`, then `turn_ended`. A compaction a `context-threshold` hook asked for (`requested_by`) isn't the core's own and pauses nothing here; but once the core's own fails or leaves the estimate over the point, hook requests are refused for the rest of that turn too ("Plugins and compaction", below).
- **The hold.** A compaction that can't get the conversation under the point turns automatic compaction off until something changes. After an automatic compaction (before a turn or between steps) or an automatic background swap, the first accepted request is measured: its measured fill (its `prompt_tokens`, or the last iteration's when the reply had iterations, such as server-side searches) minus the reserve the compaction couldn't touch: the turn's message and its context block before a turn, and the waiting steers between steps (a step's tool results are already in the history, so they are summarised). A swap counts the same reserve, and the messages it keeps count toward the measure. The reserve is always the current turn's: a measure left by a turn that ended before a request was accepted takes the next turn's message and context block. So a paste never arms the hold. At or over the point, automatic compaction is held: no automatic compaction runs, before a turn or between steps, the quote names none, and no background compaction starts. An `auto_compaction_held` event (`tokens`, the measured size; `point`) is emitted once, and the transcript shows `Automatic compaction is off: after compacting, the conversation is still 15.2k, over the 14.5k point. It turns back on when the point, the model, the system prompt or the tools change; /compact and a plugin's compaction requests still work.` The hold lasts until the point, the model or the fixed prompt (system prompt, tools and instructions) changes, or the first request after a `/compact`, an overflow compaction or a swap for an overflow measures under the point the same way (these never arm it) (after `/compact`, the reserve is the next turn's message and context block). `/compact`, overflow recovery and a plugin's compaction requests run as usual while held: the hold holds only the core's own trigger. The hold is never logged and isn't rebuilt on resume, so a resumed held session pays one compaction before it holds again. The per-turn pause above still applies to a failed compaction. A compaction a `before-compact` hook vetoed did nothing, so it neither arms nor releases the hold, and a measure already waiting stays in place for the next accepted request ("Plugins and compaction", below).
- **Cancel.** `Cancel` during an automatic compaction ends the turn `cancelled`, after `compaction_failed` with `kind: cancelled`; before the first request nothing else is sent, and between steps every committed step is kept.
- **`/compact` while one runs.** Refused `turn_running`, as during any turn.

## Background compaction

Where native compaction is used (the model's `native_compaction` is set and the pair is documented or proven, never in trial and never on Wisp's engine), Wisp prepares the summary in the background before the point and swaps it in on the next request, so a compaction usually costs no wait. It is on by default; `background_compaction = false` turns it off under `[context]`, for one endpoint (`[endpoints.NAME]`), for one model (`[models."ID"]`) or for one model on one endpoint (`[endpoints.NAME.models."ID"]`), the most specific winning, and `background_tokens` (default 40,000) sets how far below the point it starts. It is also off with automatic compaction off and while the window is unknown. The shipped model table never sets either key.

- **When it starts.** At the end of a completed turn whose fill is within `background_tokens` of the point and at least `background_tokens` above the head a compaction would leave. It covers exactly the messages of the turn's last request (the anchor), so it reads them from the cache, and it starts only when that request was the last one sent and its messages don't end in an effort marker; not while a switch is pending, and not when the anchor's system prompt or tools differ from the next request's (a Retry's first request sent with the failed request's tools, which the next step drops). A failed precompute is never restarted on its anchor: the next start is at a later completed turn's end, whose last request is always a newer one. A turn whose tool loop crosses the whole band gets an ordinary automatic compaction instead.
- **While it runs.** `compaction_started` (`trigger: background`, no `turn`) comes when it starts. When it finishes, `compaction_prepared` carries its usage and cost (in the turn it overlaps, or between turns in the session's cost alone), and the `compaction_prepared` record holds the block, so its cost is on disk even if it is never used. If the point is reached while it runs, Wisp waits for it instead of starting another, then swaps it in.
- **The swap.** On the first request after it arrives: before a turn, in the turn's pre-turn work, logged before `turn_started` with that turn's number, so the turn's `Context:` line and effort marker are computed from the swapped view; inside a turn, at the next step boundary. `compacted` (`trigger: background`) carries no usage or cost of its own.
- **With an overflow.** A ready summary comes first. Before a turn whose previous reply was cut off by the window, it is swapped in only if the swapped view (with the head's `<environment>` and `<compacted_context>`), the turn's message (with its `Sent:` and `Context:` lines) and the reply's `max_tokens` fit the window; otherwise it is discarded as `superseded` and the turn's overflow compaction runs. When a request is rejected as too long inside a turn, it is swapped in only if the swapped view, the pending content and `max_tokens` fit under the overflow's limit (below); otherwise it is discarded as `bound` when the kept messages exceed the bound, `unsaved` when the request carried the turn's own message, or `superseded`, and the overflow compaction runs. A swap there is the turn's one overflow compaction: the step is sent again once, with no continue note (the kept turns carry the context), and a second rejection ends the turn. Either way, at most one compaction runs for the overflow. A summary still being prepared when an overflow compaction starts, before a turn or inside one, is aborted as `superseded` first, as `/compact` does.
- **The view with kept turns.** The block stays even with threads on: it sits alone in an assistant message first in the request, and every message added since the anchor follows it unchanged, so the turns written while the summary was prepared keep their thinking. `<environment>` and `<compacted_context>` (without a summary) go first in the next turn's message; when the history ends in tool results (a failed turn's), they follow those results, ahead of the next turn's own blocks; after a swap inside a turn they follow the last kept message's tool results. When the swap drops the effort marker in force, the marker is logged again after that message; when the swap comes after a reply without tool calls, that marker is logged right after the reply, and the additions open the next user message after it (a steer's). When no message to hold them exists yet, they are sent as a user message of their own at the end; only a `compact` between turns sends that shape, and its result replaces the view. No continue note is added. A kept reply's open server tool calls are closed (`tail_closed`, `search_ended` as unfinished) before `context_compacted`, and rendered as closed calls from then on; while the last reply is a paused one, the swap waits for the step after its continuation. The request layout check allows exactly this leading message.
- **Discards.** A prepared summary that can't be used ends in `compaction_failed` with `kind: {"discarded":{"reason"}}`, and the transcript shows the note: `view_changed` (the covered messages are no longer an exact prefix of the view, the first kept message isn't an assistant reply, answers a server tool call in the covered messages or continues a covered paused reply, or the system prompt, tools or pair changed), `bound` (the kept messages exceed twice `background_tokens`), `superseded` (a model or endpoint switch was queued, `/compact` or an overflow compaction ran, background compaction was turned off, or, at the next turn or Retry, automatic compaction was turned off or the window became unknown), `cancelled` (the turn was cancelled while it ran), `resent` (the same step's request was sent again: a step retry, a feature fall-back, or a Retry's first request), `unsaved` (the next request carries the turn's own message, not yet saved), `refused` (its request was refused for search; unbilled) and `session_ended`. A summary discarded after `compaction_prepared` adds no cost, and its note names what it cost (`(it cost $0.28)`); one that finished but wasn't read yet is read first, so its real usage is counted; one stopped while its request ran adds a lower bound, its read estimated from the covered messages, and one stopped while waiting to retry adds only the failed attempts' cost.
- **Failures.** A transient error is retried in the background with the finite fallback policy (five step retries by default, the common backoff and no `retrying` events); it never takes the busy-wait path, each failed attempt's cost counted. An error after the retries, or a reply without a summary, ends in `compaction_failed` with `kind` `error` or `no_summary` and its cost, with no fallback to Wisp's engine and no Convert; the ordinary automatic compaction runs at the point. A request whose feature was rejected (the beta rejected by shape or named as unexpected) records `fallen_back` for the precompute's own endpoint and model, so no later turn starts another. A request refused for search ends as `discarded` with `refused`, its own attempt unbilled (earlier failed attempts keep their cost), with nothing recorded for search: the turn's next step meets the refusal and handles it once. A request refused because the endpoint can't read earlier search results is not converted here either: it ends in `compaction_failed` with `kind: error`, and the next foreground request converts them (`docs/endpoints.md`, "Unreadable search results"); after a conversion, the precompute's own requests send the converted text.
- **The warning.** Where background compaction would run (on, with automatic compaction on and native compaction used), a point below `15,000 + background_tokens + 5,000` (60,000 with the defaults; the band is the one that applies to that model and endpoint) gets the line `background compaction rarely runs below about 60,000, and claude-opus-5-5 compacts at 46,000; compaction will usually wait at the point.`, naming the model and its point. It is checked for every `compact_at` and `context_window` limit in `config.toml` at start (a start warning and a `wisp doctor` row), by `wisp config set` after it saves `context_window`, `background_compaction`, `background_tokens` or a `compact_at` that wins for the model and account (the default model on the default account when the key is global), and when one of them is changed in a session, where the line is part of the change's note (`warnings` on the applied change), for the model and endpoint the change applies to, with that place's settings.
- **A model switch with kept turns.** Kept turns keep their thinking only on the model that wrote them, so once a swap has kept turns, a `/model` switch compacts on the old model and endpoint before the switch applies, even below the new point: its verdict carries `compacts_before_switch` with `cause: kept_turns`, the compaction's estimate and `head_tokens`, and `compaction_started` (`trigger: switch`) the same. The new model's first request holds the fresh summary and no kept turns. Esc during that compaction cancels the turn and withdraws the switch; if it fails, the head is converted to Wisp's form (no kept turns) and the switch goes ahead. An endpoint switch that keeps the model, and a switching Retry, keep the turns and compact nothing.
- **Known limit.** An idle Esc doesn't stop a running precompute: only a turn cancel, a discard or the session's end does.

## Overflow recovery

Recovery runs whether or not automatic compaction is on, with an unknown window too, and in a turn whose automatic compaction is paused. Each turn gets one overflow compaction (trigger `overflow`).

- **A rejected request (`context_overflow`).** Wisp compacts the messages of the most recent earlier request that fits (below), then sends the same step again once, outside the retry counts, with the same pending content after the new head: the turn's message, its marker and the steers when the turn's message wasn't kept yet (no note, and the head's turn range ends at the turn before), otherwise the continue note, then the marker and the steers. A `Context:` line already sent is sent again unchanged. A second rejection in the turn ends it with `context_overflow`; an overflow compaction that fails for another reason ends the turn with that failure's kind, as for an automatic one.
- **A stated limit.** When the error says `prompt is too long: N tokens > M maximum` and M is below the window or below the most it may grow to (or the window is unknown), the session keeps M as a ceiling for that model on that endpoint. A window lowered to M or grown up to it shows source `overflow` in `/context`. A `window_lowered` event (`endpoint`, `model`, `tokens`) is followed by `context_changed`, and the transcript says: `The server says claude-opus-5-5's window on manifest is 200k; Wisp won't use more than that for the rest of this session. Your saved settings are unchanged.` A larger stated limit changes nothing. The kept ceiling is logged as a `window_lowered` record (`docs/session-log.md`) even if the window in use did not change, and a resumed session applies the last one logged for each endpoint and model again, whatever session `context_window` is set, so its point and `Context:` line match the session that never quit, also once that setting is cleared.
- **A reply cut off by the window (`model_context_window_exceeded`).** The reply is kept and each of its tool calls gets a `not_run` result (`reply_stopped`). Its unanswered server calls are closed as `unfinished` (`compacted`, not billed) right after it is committed. With tool calls the turn goes on: Wisp compacts at once and the next step is the head, the continue note, the marker and any steers. Without tool calls the turn ends `completed` with that stop reason, and the next turn compacts first, before its `turn_started`, when anything follows the head; that compaction is the turn's one overflow compaction, and if it is cancelled the next turn tries it again. A steer waiting at that boundary keeps the turn going instead: the compaction runs first, then the next request is the head and the continue note before the steers, or, when nothing of the turn was kept (the cut-off reply held only thinking on the first step), the head, the turn's message and the steers. A second cut-off reply in the same turn ends it. With nothing after the head (a first turn's reply that held only thinking), nothing is compacted. When the compaction after a cut-off fails or is cancelled, the reply's end is dropped, so no later head quotes it. The fallback's tail marker sits where the earlier request's anchor was, on both engines, even when Wisp's engine joins its instruction to that request's last message.
- **The earlier-request fallback.** Every `context_overflow` compacts through it, and any compaction whose own request is rejected as too long, or whose native reply stops with `model_context_window_exceeded`, falls back to it, manual and automatic ones included. Wisp picks the most recent committed request since the last compaction whose logged `prompt_tokens` is below the limit by at least the summary's `max_tokens` plus the instruction's estimate; a request sent on another model counts 35% more. The limit is the smallest of the window, a limit the error stated and the rejected request's size; after a native window stop it is the compaction iteration's prompt (input, cache reads and writes), or, with no usage, the compaction request's own estimated size capped by the window. The compaction covers exactly that request's messages, with its tail marker only when the request came after the list's rebuild mark and its cache is still warm. On the native engine the turns after that request are kept after the block, which stays even with threads on, as in a background swap's view, when they fit: the block, the head's additions (`<environment>` and `<compacted_context>`), the kept messages, the pending content and the reply's `max_tokens` under the limit. The pending content is counted on every path: inside a turn, the unsaved message and steers; before a turn, the turn's message with its `Sent:` and `Context:` lines. A view with kept turns sends no continue note, and a live server call in the kept tail is closed as `compacted` first, carrying the turn's billed calls, as a swap inside a turn does. A cross-account recovery inside the compaction (search results the endpoint can't read) closes it earlier, as `refused`, carrying the failed turn's billed calls when a turn failed with the tail live. The head's turn range and `covers` name only the summarised turns, up to the chosen request's turn; the kept turns are not counted as summarised. Each request remembers the log position of its reply, restored on resume, so a fallback after a restart covers the same records and turns as one in a session that ran straight through. Turns are not kept on Wisp's engine, in a `switch` compaction, or when the chosen request or any after it was sent on another model; nor when they won't fit. Then the record and the `compacted` event are `partial`: the turns after it are carried by the verbatim user messages and the tool-call ledger, and, after a cut-off reply, the head adds the reply's last 2,000 tokens of text in `<cut_off_reply>`. When turns would be kept but the chosen request's reply can't start a kept view (it answers a server call in the covered messages, or continues a covered paused reply), Wisp steps back to the latest earlier request that fits and whose reply can, provided every request from there on was sent on the same model and the larger kept tail would fit with a summary at its full `max_tokens`; otherwise, or with no such request, it compacts the first pick and keeps no turns. A request logged with no `prompt_tokens` is judged by its estimated size. If that compaction is rejected or stops the same way, it falls through once to the next earlier request that fits, always one sent before the first pick; a second time ends the turn with `context_overflow` (a manual `/compact` fails with that kind), with no third request.
- **Kept tools.** When a Retry's first step was sent with the failed request's server tools (kept after a search refusal) and overflows, the kept tools end there: the overflow compaction's request and the re-send use the pair's search mode, the re-send logs its tools-change `thinking_cut`, and no later request carries the kept tools.
- **When nothing fits.** The turn ends `context_overflow` with no Retry offer. The message is `This message alone is too large for the model's window.` when no request was committed since the last compaction, even if the error stated a limit; `the conversation doesn't fit claude-opus-5-5's 200k window on manifest, even after compacting · /model or /account to switch back, or start a new session` when the window shrank since those requests (a stated limit, or an earlier request on a pair with a larger window); otherwise `the conversation doesn't fit the model's window, even after compacting · start a new session`.

## Compaction before a Retry

A Retry is accepted before this work runs, so none of it ends the Retry offer. It all runs before the Retry's `turn_started`, carries the Retry's turn number, and moves with the Retry's run in `--replay`.

- **The re-run.** When the failed turn ended on its own compaction's failure (a pre-turn or mid-turn automatic compaction whose failure left the request over `window − 8,000`, or an overflow compaction), its Retry runs that compaction again with the same trigger, instead of skipping automatic compaction, then sends the turn's message on the compacted view (a new `Context:` line computed from it), or, when the failed turn had kept steps, the head, the continue note, the marker and the steers. If it fails again, the Retry ends with the failure's kind: `compaction_failed`, `turn_started`, `turn_ended`, and the next Retry re-runs it once more.
- **A smaller window.** A Retry on another endpoint whose known window (for the session's model) is below the failed request's estimated size runs the earlier-request fallback there before its first request (`trigger: overflow`): it is the Retry turn's one overflow compaction, so a later `context_overflow` in that turn ends it. The head is followed by the re-sent message (with a `Context:` line from the compacted view), or, after kept steps, the continue note, the marker and the steers. With no earlier request that fits, the Retry ends `context_overflow` with the smaller-window message and no request; a fallback that fails otherwise ends it with the failure's kind and offers Retry, which re-runs it on the same endpoint. A Retry on another endpoint judges the fallback afresh for that endpoint's window: it runs there with that window as the limit, or not at all when the failed request fits it. Like every fallback, it counts the re-sent message (with its `Sent:` and `Context:` lines) and steers against the kept turns, so turns are kept only when the request after them fits. While the offer stands, `describe_settings` gives that endpoint's quote `retry_compaction`: `{"estimate_micros", "head_write_micros"}`, the fallback priced cold on that endpoint from the chosen request's `prompt_tokens` (the system and tools as a 1h write, the conversation as plain input, plus the summary) and the new head's write at the session's cache lifetime. An endpoint listed only for it has no `consequence`.
- **A block the target can't take.** The head is converted instead, with no request; when the converted view (the converted head, the system prompt, tools and instructions, and the re-sent message and steers) is over the target's `window − 8,000`, nothing is converted and the Retry ends `context_overflow` with the smaller-window message and no request.
- **Record order.** A switching Retry logs `settings_changed` when it is accepted, then the re-sent `input_accepted` records; the switch is applied before its Convert or fallback, so `rebuild_marked` comes next, then the compaction's records and `context_compacted`, then `turn_started`. A compaction on the failing endpoint (above, **Before a switch**) runs before the switch is applied, so its `context_compacted` comes before `rebuild_marked`.
- **Instruction files.** A head built before a Retry's first request will target the failed turn's settled set of instruction files once heads carry an `<instructions-update>` (the instructions plan's MR 3); today no head carries one, so there is nothing to choose.
- **Open on resume.** Neither a pending pre-turn overflow compaction (after a reply cut off by the window) nor a window stated by an overflow error is logged, so a resumed session doesn't compact first and starts from the configured window. The re-run and the failed request's size behind the smaller-window fallback aren't restored either, so a Retry offered after a resume skips them. A switching Retry to a smaller window then sends the failed request as is; when it overflows and no restored request fits, the Retry ends `context_overflow` with the smaller-window message. These join with the resume work (resume 4.5 or 4.4b).
- **The resumed prefix.** A full-screen root session resumes on its logged system prompt and tools (`docs/tools.md`, "Resuming a session"), so the summary fork, a compaction's head and a keep-warm refresh send those bytes, not this build's. A difference since the log goes at the first opening as tool blocks or the `core/tools` note, and the new base instructions as one text block; a compaction or rewind that drops them restates them at the next opening, as for a switch, and a Retry of that turn sends them again.

## Measured and estimated

- **Measured:** after every step, the fill is that request's prompt tokens (input, cache reads and cache writes), or the last conversation iteration's when the response reports iterations. Search-only asks have their own records and do not change the fill. It is the only exact figure.
- **Estimated (`~`):** the categories and the next request's size. Text counts at 3 bytes per token, images by `wisp_media`'s rule, and replies by their measured output tokens, thinking included.
- **Next request:** the last fill, plus the last reply's output tokens, plus everything added since. Before the first request it is the sum of the categories.

## Telling the model

- **The `Context:` line.** Each turn's user message carries one line after its `Sent:` stamp, or, with stamps off, after the `<environment>` block when the message has one (the first turn with tools) and first otherwise, before its images and text: `Context: 62k of 1M tokens (6%). Wisp compacts at 850k.` With your limit set it reads the limit (`62k of 400k tokens (15%)`); with an unknown window it reads `Context: 62k tokens; window unknown.` The bundled `context` plugin writes it from its `context/fill` hook at `before-turn`, after `time/sent` and before `core/processes`, reading `context.current-fill`: the estimate is the next-request estimate for the message being sent (the lead so far, mail included), the window, and the point only while automatic compaction is on. Its figures are written as `format_tokens` writes them, and the share is rounded down to a whole percent, so it reads 100% only once the window is full. With automatic compaction off, the second sentence reads `Automatic compaction is off.` On a model whose shipped row has `turn_form` (`docs/gemini.md`), the line reads `Context window: 62k of 1M tokens (6%); Wisp compacts at 850k.` and sits in the turn's last data part, after its images and text.
- **Only on user messages.** No line follows tool results, so a long tool loop learns its fill at the start of each turn. The line and its wording are the same for every model, except one with `turn_form` (above).
- **Per-turn data, never the system prompt.** The line rides on content appended for the first time, so no cached byte changes. Its text is logged as the `context/fill` entry of `turn_started.lead` (`context_note` up to log version 28; inside the `core/data` tail entry on a model with `turn_form`) and a resume rebuilds it byte for byte.
- **The system sentences.** The system prompt always ends with two fixed sentences, the `[system]` texts of the `time` and `context` plugins (in that order, since `context` comes `after = ["time"]`), whether the lines are sent or not: "A user message may begin with a 'Sent:' line that Wisp adds, giving the time it was sent; use it for anything involving dates or time, and don't mention it otherwise." and "A 'Context:' line, when present, gives how much of your context window the conversation fills; at the stated point Wisp replaces older turns with a summary." Turning either line on or off never edits the system prompt; a sentence is there while its plugin is installed (`docs/plugins.md`, "The system prompt").
- **The setting.** `context.context_note`, on by default: `--context-note on|off` for one run, `--set context.context_note=off`, or `context_note` under `[context]` in `config.toml`. The flag beats the file, which beats the default. The resolved value is logged in `session_started.context_note_enabled`.

## The sidebar section

The bundled `context` plugin also declares a sidebar section, `context/window`, titled `Context` (`docs/plugins.md`, "Sidebar sections"). It is off by default, since the status row already shows the same figures: turn it on in `/config`, or with `--set plugins.context.slots.window=on` for one run; its old name, `context/usage`, still reads as it. It runs no hook, and its content adds nothing to any request or to the log (switching it, like any setting change, logs `settings_changed`); the plugin's `[system]` sentence and `context/fill` hook are unchanged by it.

- **What it draws.** Its `render_slot` passes `context.current-fill` through as a fill span in the title note and a fill block, the same for the panel and the page; Wisp draws both, so the figure, its levels, the dots and the part words, glyphs and colours are the renderer's, as on the status row and `/context`:
  - the title's figure is the status row's: used against `meter_limit`, `159k/400k`, or `159k` with an unknown window, `~` marking an estimate, in the same levels ("The status row", below);
  - two rows of 25 dots of the fill against `meter_limit`, each dot 2% of it at any width, filled column by column (a column's top dot, then its bottom dot): `⣿` in each part's colour, system, tools, chat and skills in that order, then `⣀` free (ASCII `#` and `.`; the AmbiguousWide set draws the Unicode cells, as `/context` does). The dots are counted as `/context`'s cells are ("The grid", below), so the used dots are half the %, rounded down, unless a part is below one dot. There are no dots while the window is unknown, or when the dots and the % don't fit side by side (under 31 columns inside for a % below 1000%);
  - the share of `meter_limit` (rounded down) in the figure's level, at the end of the first row of dots, or heading the parts without them;
  - the parts: one row per part that has tokens, `system`, `tools`, `chat` and `skills` (skills once Wisp loads skills), then, when the window is known, `free`: `meter_limit` less the figure, `0` past it. With automatic compaction off `meter_limit` is `window − reserve`, so `free` can differ from `/context`'s Free, which counts to the point;
  - `cached`: the share of the last request's prompt read from the cache, rounded down, or `—` before the first request and after a compaction until a request is measured. A rewind keeps it, also after a resume. An endpoint that never reports cache reads shows `cached 0%`. The status row's `cache N%` is the session's rate, a different measure.
- **The box.** In the panel the section is a box like every sidebar section (`docs/design/tui-brand.md`, §7.8): the title, the two rows of dots, the parts and `cached` each sit in their own cell, ruled off from the next.
- **The picture.** Where the terminal shows pictures (`display.pictures`, `docs/settings.md`), the two rows are drawn as 100 small rounded squares instead, four to a column, each 1% of `meter_limit` and filled column by column: each part's colour, then dim free squares. The parts' marks become squares in their colours, and `free` keeps its `⣀`. The box keeps its rows; with no dots (the window unknown, or too narrow) the marks stay text, and a page is always text.
- **The parts.** System is the system prompt and the instructions, tools the tool definitions, and chat everything in the messages (`Category::part`). System and tools are the estimates `/context` shows before it counts; chat is the rest of the figure, so the parts always add up to it. With `context.count_tokens` on, `/context` shows the endpoint's counts for the fixed rows on Anthropic, so its rows can differ from the panel's by the estimate's error; the panel never counts. Every number ends in one column, one space inside the box's right side. On a page the same groups are split by blank rows, the dots keep their 25 columns and the rows stop at 47 columns.
- **When it is redrawn.** Its `marks` are `after-response`, `after-compact`, `rewound`, `model-switched` and `settings-changed`, so it follows each reply, compaction, rewind, model switch and setting change while shown, with no `refresh_s`.

## The status row

The meter reads the fill against `meter_limit`, `159k/400k`, or against the window when there is no limit, or `62k` with an unknown window, `~` marking an estimate. It is muted below 75% of `meter_limit` and in bold plain `text` from there, past it too while automatic compaction is on, since Wisp compacts before the next request; past it with automatic compaction off it is in bold error colour, since the next reply may not fit. `/agents` colours each agent's figure the same way, from its `ContextFill`.

While a reply's text streams, the working line shows its speed after the token counter: `16s · ↓ ≈180 tokens · ≈42 tok/s · esc to stop` (`~42 tok/s` in Ascii). Both count reply text only, at about 4 characters a token, so they always agree. Thinking isn't counted, since what streams for it is a short summary written for display. The speed is the reply text that arrived in the 3 seconds before the clock's last tick, divided by 3, or by the time since the reply's text began, if that is shorter, but never by less than 1 second. It changes only when the clock ticks, appears on the first tick after the text begins, reads `≈0 tok/s` when the text stalls, and goes when the reply ends at a tool call, a thinking block or the end of the turn. Thinking, writing a tool call, running a tool, waiting for the next request, a retry, compaction and replay show the clock with no speed. When the working line is crowded, `· esc to stop` moves to the right first, then the counter goes, then the clock, then the speed.

After a completed turn, the row can show `48 tok/s` after `cached N%`: exact output tokens divided by the sum of each request's time from its start to its last output, including prompt processing and initial waiting but excluding tool time between requests. It counts thinking and tool calls too, so it can read lower or higher than the live speed. The rate is idle-only and clears on send. When space is tight, the weekly usage figure first drops its `· /usage` hint, then `cached N%` goes, then weekly usage, unless it warns, and only then the rate, before effort, the context figure and the model.
A retried, cancelled or errored turn, an incomplete measurement, or replay shows no rate; a positive rate below one reads `<1 tok/s`, and large values use the usual short form, such as `1.2k tok/s`.

## `/context`

`/context` shows a cell in the transcript, never sent to the model. It works while a turn runs too, and is answered from the last finished step. It has five parts, top to bottom:

- **The grid.** Each cell is 1% of the window (10×10), or 0.5% on a 1M window when the screen is wide enough (20×10). Cells are coloured by category in the legend's order, then come the free space (`⣀`) and the reserve past the compaction point (`⡪`). A category with less than one cell's share gets one cell; the others get their whole cells, then one more each, largest remainder first (ties to the bigger, then the earlier), until together they fill the floor of their summed shares. The caption gives the scale (`1 cell = 10k`). Colours and glyphs are in `docs/design/tui-brand.md` §7.9.
- **The header**, beside the grid: the model and the endpoint; the next request's size against `meter_limit` (`159k / 400k tokens (39%)`), coloured like the status-row meter, with the share rounded down like the `Context:` line; and where the figure comes from (`62.4k measured at turn 9, step 4 · 700 since`, or `no request yet: estimated`).
- **The legend**, below the header: `Usage by category`, a row per category with its tokens and share of the window, then `Free before the point` and `Reserve past the point`, the compaction point, whether automatic compaction is on, and the window with its source (`window 1M (shipped)`). The shares are of the window, so with free and reserve they add up to the whole grid. The rows always add up to the next request's size.
- **Sections**, one line each for the instruction files, the tools, the largest tool results and the attachments, with their first items.
- **The costs**, and a hint that `/context all` lists every item.

The layout is the largest form that fits: 20×10 beside the legend with its source column (1M windows, from 97 columns), 20×10 without the column (from 87), 10×10 with it (from 77), 10×10 without it (from 67). Below 67 columns the legend goes under the grid, and below 22 there is no grid. With an unknown window there is no grid, free space or reserve: the legend lists tokens only, followed by the unknown-window line.

| Row | Counts |
|---|---|
| System prompt | The system prompt |
| Tools (n) | Each tool's definition |
| Instructions (n files) | The instructions block in the system prompt; its items are the loaded files |
| Environment | The `<environment>` block |
| Your messages | Your text, outside tool results and images |
| Replies and thinking | Each reply's measured output tokens |
| Tool results | Each result's text; its items are the five largest, with their turns |
| Attachments (n) | Each pasted image, named `image n`, and each file a tool attached, named by its call's target (`docs/spec.pdf`), with its turn; after a compaction, only those after the compacted head. A file has no local estimate: it counts 0 here and its item reads `not estimated`, while a measured or counted total still includes it. Logs and clients before this row called it `images`, which still reads as this row |

Each figure is marked by where it comes from, in the source column when it fits:

- `counted`: the endpoint's own count, by difference (see "Counting with the endpoint" below).
- `measured`: from response usage. Replies are measured when every reply's output tokens are known.
- `estimated`: a local estimate (3 bytes a token for text, `wisp_media` for images), marked `~`. The system prompt, tools and instructions are estimated when the endpoint can't count them.
- `split`: part of a measured or counted total, shared by estimate, marked `~`. After a request, the conversation is the next request's size minus the fixed part (system prompt, tools, instructions, counted or estimated) and minus the measured replies, shared among the other conversation rows by their estimates; their items are scaled with them. If that remainder would be negative, every conversation row is scaled, Replies included, which are then `split` too; if the next request is smaller than the fixed part, every row is scaled. So the rows always add up to the total and none is negative. There is no row for a leftover.

The legend's title says where the figures come from, and a muted line under the legend gives the reason when they are estimated:

| Title | When | Reason line |
|---|---|---|
| `counted by the server` (`counted` without the source column) | the fixed part is counted and the total is measured or counted | none |
| `counting…` | the counts are on their way; the cell is redrawn in place when they arrive | none |
| `partly estimated (~)` | some counts failed | `~ count failed: <reason>` |
| `estimated (~)` | nothing could be counted | `~ this server has no token counter`, `~ counting is off`, `~ count failed: <reason>` or `~ no request yet` |

### Counting with the endpoint

When the endpoint has a token counter (Anthropic's `count_tokens`), `/context` counts the fixed part of the request with it. The counts are free on Anthropic's side and never touch the prompt cache or any message request.

- **What is counted.** Up to four bodies, each with one placeholder user message (`.`) and the session's model, effort and thinking: none of the fixed part (the base), the system prompt, the system prompt and instructions, and those with the client tools. The differences give System prompt, Instructions and Tools (the tool-use system prompt included). The client tools counted are the `tools` array the session sent, with each tool added by value in view (`docs/tools.md`, "Switching tools in a running session") replacing the array's entry of its name or joining it, so each tool counts once and an inline addition counts with the fixed part, in the Tools row and in the whole-request count. An addition a rebuild voided (one before the rebuild's point, of a tool its array holds) isn't counted, so that tool counts with the array's definition. A part that is absent is not counted, and nothing is counted when only the base would be. Server tools are never sent. The bodies go through the same stripping as any count: no `max_tokens`, `stream`, `fallbacks`, `diagnostics`, cache markers, `thinking.block_binding` or effort-marker messages.
- **The conversation** is the measured fill of the last request minus the counted fixed part, plus what was added since. The measured fill is used only when the last request went to the current endpoint and model and was answered by that model. Otherwise (before the first request of a resumed conversation, after a model or endpoint switch, or after a fallback answer from another model) one more count takes the whole next request, stopping at the last user message and adding the output tokens of the replies after it.
- **The cache.** A count is kept for the session under the endpoint, model, effort, thinking and the text it was made from, so the first `/context` makes the calls and later ones usually make none. Changing the system prompt, instructions, tools, model or effort counts the changed parts again. The whole-request count is never kept.
- **Order.** The report comes at once with the cached counts and the rest estimated, titled `counting…`, and is replaced in place when the counts arrive. The counts run in parallel, outside the turn, so a streaming reply never waits for them. The late report describes the moment `/context` was asked.
- **Failures.** An endpoint that answers 404 is remembered as having no counter for the rest of the session, and its reports are estimated at once with no call. A timeout, another HTTP error or an error inside a 200 affects only that report: its failed parts are estimated with the reason, the parts that succeeded are kept, and the next `/context` asks again for the failed ones. Nothing about counting is logged.
- **Turning it off.** `context.count_tokens = false` under `[context]` in `config.toml`, or `--set context.count_tokens=off` for one run, stops every count; the legend then reads `estimated (~)` with `~ counting is off`.

The status-row meter and the `Context:` line never count: they use the measured fill and the local estimate.

Free space is the point minus the next request, and the reserve is the window minus the larger of the two. Past the point the free space is 0 and the fill takes the reserve's cells, never a category's. Past the window (an estimate can be) both are 0, the grid is scaled to the next request, and the legend says `over the window by …` in the error colour.

- `/context all` lists every item under its section, one per line; transcript mode (ctrl-o, twice once anything can be opened) always shows them.
- `/context count` is gone: counting is automatic, and the word gives the hint `/context counts automatically now (context.count_tokens)`.

The costs, priced from `pricing` and shown with the footer's money rule:

- **Each step re-reads:** the fill at the cache-read price.
- **Compacting now:** reading the conversation up to the anchor (below; warm within the anchor's own cache TTL and the system prompt's hour, cold otherwise or with no anchor), the anchor's reply and the content since it at the input price, and a 6,000-token summary at the output price. The next figure, the head's write, is a 15,000-token head at the write price of the session's tail TTL, shown after it and never added in.

A model without prices shows `no prices`.

`--replay` answers `/context` with one empty report, estimated with `replay` as the reason.

After a compaction the cost line ends with the compactions so far and what they cost: `· 1 compaction so far, $0.283`. When compactions failed after spending money and none finished, it still shows the cost: `· no compactions so far, $0.012`.

## Broken thinking

A thinking block is bound to the prefix it was written after (system, tools and the messages before it) and to the thinking block before it in the chain the model read. A deliberate change (tools, system prompt, a closed server-tool tail, a plainer rendering form, a lost image, searches rendered as text for another account, search results sent as text after a refusal) breaks the binding of the thinking before it.

- **Where binding controls are usable** (one test: the model's `adaptive_thinking` capability and a pair state that hasn't fallen back), every break turns them on, if they weren't already, and sends every thinking block exactly as the API returned it. The API drops the broken ones under `drop_block`. The dropped set depends only on Wisp's bytes and the model, and Wisp's bytes only grow, so it never changes: one miss at the change, then hits. A gateway that fills thinking into tool turns that lack it (mnfst/llm-gateway replays a response's thinking for 30 minutes) finds none to fill. A new session asks for binding controls from its first request on such a pair (`docs/endpoints.md`), so a break local to the tail misses only from its edit.
- **Where they aren't usable** (a refused trial, a model without them), Wisp cuts once, as before: the provider's path when the beta can't be sent, leaving every thinking block out from the edit on. A session that kept broken thinking and then runs on such a pair cuts every thinking block once there, and the cut stays on every later pair and across rewinds, so nothing is put back. The cut is skipped when the view no longer holds thinking from before the break, for example after a compaction whose head replaced it. A leading head's kept turns count as broken only when the break reaches past the head's cut: a native block made from exactly the request a kept reply answered keeps that reply's thinking valid (the API accepts the swap when it wrote the summary), so a break kept before the cut leaves them as they are.
- **Why keep.** The model reads what a cut leaves it: no reasoning from before the change, all reasoning since. The provider's docs say to "Use `"drop_block"` as a stopgap while you fix the edit, but not as a long-term setting" and that "A drop on every turn costs more than an occasional drop"; their reason is the output tokens of reasoning the model can no longer read, which a cut loses equally. Dropped blocks aren't billed; they add upload bytes and one `input_transformations` entry each per response until a compaction removes them. The edits here are deliberate changes, each made once.
- **A refusal of earlier thinking.** An endpoint can refuse thinking Wisp sent: a 400 whose message starts, at a word boundary, with ``Invalid `signature` in `thinking` block`` (the prefix check's long sentence, or the bare one for a signature the account can't verify) or ``Invalid `data` in `redacted_thinking` block``. Such a refusal is `ErrorKind::ThinkingBinding`. On a request that carried rendered text the rendering forms come first (`docs/endpoints.md`, "Web search"); if they don't recover it, or the request carried none, and the request still sent a thinking block, Wisp takes the provider's documented recovery once per step: a live paused or open tail is closed first, every thinking block in history is left out from then on (one `thinking_cut` from `{"message":0,"block":0}` through the last message, which clears kept breaks and sets binding controls back to what the turn started with, as a resume reads it), the cache is marked as rebuilt from the first message that sent thinking (`thinking_cut`, or `tail_closed` when a tail was closed), and the step is re-sent. A paused tail ends the turn instead, and the next turn sends the cut. Both compaction engines take the same step once, closing a live tail too; background compaction doesn't, and the next request recovers. A refusal of a request that sends no thinking, or a second one after the cut, ends the turn with the thinking-binding message, which ends with the refusal's own text. Nothing in history changes, and the cut is rebuilt on resume from its record.

## Cache misses

A request misses when it reads less than half of the previous request's first-pass prompt, at least the model's minimum cacheable size. The first pass is the first conversation iteration's prompt tokens when the previous response had iterations (a server tool such as web search samples several times, and the usage sums them), else its `prompt_tokens`: the next request can reuse only up to the first iteration's prompt, so comparing with the sum flagged a full hit after every search step. A request after an endpoint or model switch is checked like any other, against the previous request's first pass and the minimum cacheable size of the model that served it: a switch that kept the cache (another endpoint on the same organisation) is no miss. A reply served by another model than the previous one while neither the endpoint nor the asked model changed (a refusal fallback), and the request after it, aren't checked, nor is a request after a resume whose log has neither `first_pass` nor `used`.

Every miss carries a local `cause`, on every provider, from what Wisp kept of the previous request: the six prefix digests of the warmth key (`docs/agents.md`), a digest of the beta header, one SHA-256 per message as encoded before cache markers, the positions of the thinking blocks it sent, and the provider's drop list (`input_transformations` entries of type `thinking_dropped`). The first that applies names it:

1. `expected` (`reason`): a rebuild mark was set for this request (its `rebuild_marked` reason, a cut or a closed tail included), or it is the first after a resume that changed the prompt or tools (`resume`), or the first after a `/config cache_ttl` change that lengthened the tail TTL (`cache_ttl_change`: a 1h breakpoint reads only 1h entries; a shorter TTL expects nothing, since a 5m breakpoint reads both, and an expectation already pending, such as a resume's, is kept). A compaction request reads the expectation without taking it, so a compaction that fails or isn't installed leaves it for the next step; one that is installed clears it with the list. After a compaction, or a rewind to a point whose request is masked or across a change, no previous request is kept, so the next request isn't checked.
2. `endpoint_changed`, `model_changed`, `effort_changed`, `thinking_changed`, `tools_changed`, `system_changed`: that prefix digest differs, with no mark to explain it. `endpoint_changed` and `model_changed` also come from the previous request's endpoint and asked model, so they need no digests: a resume onto another endpoint than the session's last request (a changed default, no flag) is `endpoint_changed`. A `/model` or `/endpoint` switch sets the mark and so is `expected` (`model_switch`, `endpoint_switch`), and a resume with a `--model` or `--endpoint` flag is `expected` (`resume`).
3. `betas_changed`: the beta header differs. Betas that don't key the cache are left out of the comparison (`Provider::keys_cache`): on Anthropic the inline-tools beta, the compaction beta, the message-threads beta and the refusal-fallback beta (`docs/pricing.md`), so a session's first native compaction after the TTL is `ttl_expired`, not `betas_changed`.
4. `message_changed` (`index`): the first earlier message whose bytes differ, or the first missing one.
5. `injected_thinking` (`first_path`, `count`): the drop list changed within the earlier messages at a position where Wisp sent no thinking, so something between Wisp and the API (a gateway replaying reasoning) put it there; the first such miss in a session gets one notice: "The server re-inserted earlier reasoning Wisp didn't send (a gateway). Each change can cost a cache rebuild."
6. `provider_dropped_thinking` (`first_path`, `count`): the drop list of blocks Wisp sent changed while Wisp's bytes didn't.
7. `ttl_expired` (`gap_s`): the previous request went out at least the cache's life earlier: the tail TTL, or, for a provider that caches by itself, the idle life its route's data names (`Provider::cache_life`; `cache_idle_s` on Gemini's Antigravity route).
8. `remote_loss`: Wisp compared everything (the prefix digests, the beta header, every earlier message and the drop list) and nothing changed, with the gap inside the TTL, so the cache was lost on the provider's or a gateway's side. The TUI shows it as "provider- or gateway-side cache loss, nothing changed locally".
9. `unexplained`: Wisp couldn't compare: no earlier print (after a resume or a rewind), a missing part (a provider without prefix or message bytes, an unknown TTL), or, on a provider with a block lookback (Anthropic's 20-block breakpoint lookback; Gemini has none), a request that added more than 20 blocks (past the provider's lookback, Wisp's own layout can lose the cache). A compaction request is checked with its own send time, like a step.

A provider that gives no prefix or message bytes gets only `expected`, `ttl_expired` and `unexplained`. Remote diagnostics (`diagnostics`) still go out only with `debug_cache`.

A keep-warm refresh (`docs/agents.md`, "Keep-warm") is never checked: it emits no `CacheMiss` or `CacheMissRepeated`, counts in no repeat run and changes nothing the next request is checked against; its own outcome is only in its `cache_refresh` record. A refresh that read does move when its anchor was last used: each entry also keeps `refreshed_at`, the start of the last refresh of it that read, and its **last use** is the later of that and when it went out. Every check of an entry's age takes its last use. `ttl_expired` measures it against the provider's cache life (so a miss after a refresh that read, inside that life, is `remote_loss`). The explicit tail marker's "started longer ago than its TTL", overflow recovery's earlier request, `/context`'s warm price, the rewind points' warm-until and the resume note's warm cache (from the log's last `read` record of the resumed turn) measure it against the tail TTL, also on a route whose own cache life differs.

**Repeats.** The same cause type on two back-to-back requests, other than `expected` and `ttl_expired` (so `remote_loss` and `unexplained` included), emits `CacheMissRepeated { cause, count, usd }` after the second miss and after each further one, logged as `cache_miss_repeated`, with one notice each: "The cache was rebuilt 2 times in a row (cause: …), ~$X." (bare `$X` on a metered account) (`docs/pricing.md`). A hit, an unchecked request, or another cause ends the run. It is shown to the user only; nothing is added to the conversation. The TUI's turn details show a drop list equal to the previous request's as "input transformations: same as the previous request".

## Message threads

On Anthropic's Claude API and on a Claude subscription, for every model the message-threads docs list (`message_threads` in `[providers.anthropic]` of `crates/wisp-core/data/models.toml`), a turn request opens a thread (`thread: {"type": "create"}`, with the `message-threads-2026-08-12` beta), and the next request continues it, sending only the messages after the ones the thread holds, with no `system` or `tools`. Anthropic measured about 35% faster answers at 500k–1M tokens; Wisp's session logs measured requests starting about 0.3–0.9 s sooner between 100k and 400k tokens. Prices, tokens, rate limits and the cache don't change: a continue's usage covers the whole prompt, and a plain request reads what a continue wrote. The threads beta doesn't key the cache (`docs/pricing.md`).

A request continues when the previous reply was committed on the same endpoint less than 5 minutes ago, ended with `end_turn` or `tool_use`, wasn't empty or written by the fallback model, is sent back exactly as received, and the request keeps every fixed field (model, thinking, top-level effort, cache markers, `fallbacks`, system, tools and betas) and starts with every message the thread holds. Anything else, a rewind, compaction, edit, resume, `/model`, `/account` or top-level effort change included, opens a new thread. A reply whose streamed tool input Wisp sends back differently from how the model wrote it (keys out of alphabetical order, say; whitespace between tokens aside) isn't continued, since the thread keeps the model's version; the next request opens a new thread with Wisp's own. On a model with per-message effort or inline tool changes, an effort or tool change rides the continue as a system message. On a continue, the request list and `step_ended`'s `view_len` and `prefix` describe the logical request (the thread's full history, system and tools), not the shorter body sent.

Anthropic holds the conversation, system prompt and tools in memory, encrypted, for up to an hour after the last request. It is never written to durable storage and isn't eligible for ZDR or HIPAA. `message_threads = false` turns threads off from the next session.

A request holding a native compaction block can't use a thread. While the pair uses threads, a compaction that keeps no turns installs the block's non-empty text in Wisp's head form, so the next request opens a thread and later requests continue it. A compaction that keeps turns keeps its block and pauses threads until the next compaction that keeps none. Wisp decides by asking the provider's thread gate about a request without messages, tools or a compaction feature, and checking that threads haven't been dropped on this account. Keep-warm refreshes, token counts, compaction requests and one-shot calls never use one.

A refused thread request costs nothing and is sent again at once, with no error or retry shown: a refused continue as a new thread (a replay), and a refused new thread, or a refused continue of a replayed thread, without threads on that account for the rest of the session. Other accounts can still use threads. The log's `step_ended.thread` and `thread_error` record it (`docs/session-log.md`).

## Server tools and the cache

The API puts an automatic 5m breakpoint on each server tool result (a web search's results), which later iterations of the same request read; nothing is promised for the next request. Measured on 2026-10-29 (the cache-followups probe, Haiku 5.5, direct and through a gateway, one run per case, top-level automatic caching): a 1h breakpoint reads only 1h entries, while a 5m one reads both; the gateway logs agree for Opus 5.5.

So in a 1h session, the request after a search writes the search content again at 1h, once. That is not a miss: the next request is compared with the search request's first pass ("Cache misses"), which it reads. It costs about 2× input per result token. A 5m session reads the search content on the next request. No request layout avoids the rewrite: a 5m marker before the 1h tail is refused, and a 1h marker on the result reads nothing. How those writes are counted is in `docs/pricing.md`, "Web search".

## The anchor and the explicit tail marker

The kernel keeps the epoch's request list in memory: one entry for each request whose reply committed, holding the length of the messages it sent, its top-level prompt tokens, its last iteration's prompt (`used`), its reply's output tokens, when it went out, the tail TTL it was sent with, the endpoint and model it was sent on, and a SHA-256 digest of the prefix it sent. The digest covers the model, the thinking settings, the top-level effort, the tools, the system blocks and the messages up to and including the request's last cache-eligible block, with every cache marker left out; the provider computes it when the request goes out (`Provider::cache_prefix`, a required method with no default, so every provider and every wrapper around one decides; a provider that returns none gets no explicit marker). A failed, cancelled or uncommittable step adds no entry. Each entry is logged on its step's `step_ended` (`view_len`, `started_at`, `ttl` and `prefix`, the digest), and its model and endpoint come from its turn's `turn_started`, so the session log can rebuild the list: `rebuild_history` returns it, cleared at each `context_compacted`, with the mark after the entries logged before the last `rebuild_marked`. A rebuilt entry keeps the digest that was sent, never one recomputed at rebuild: the instructions or tools may have changed across a restart, and the digest check below then leaves the marker off rather than anchor on a prefix that was never cached. Resume doesn't restore the list yet: it starts with one entry, the last committed request, sent when and with the TTL its `step_ended` logged (in older logs, the time of the record before its reply and the turn's TTL), and with the prefix digest that request logged, never one recomputed from the current configuration. A cache-keying beta-header change drops that digest. A summary immediately after a resume can mark that anchor when its digest still matches; a changed system prompt or tools leaves the marker off. Resume sets no last-sent prefix key. That entry is the one the session already logged, so the next `step_ended` doesn't log it again.

Every change that alters the bytes an earlier request cached sets the list's rebuild mark, keeping the entries. Before each turn and before every request, the kernel compares the request's prefix key (endpoint, model, top-level effort, whether per-message effort and binding controls are in use, and a digest of the system prompt, instructions and tools) with the key of the last committed request, so a model or endpoint switch, a top-level effort change, a feature fall-back and a tools or system change set it without wiring of their own. A kept rendering form, and a closed server-tool tail or thinking cut that reaches into an entry's messages, set it where they are applied. A cache TTL change sets nothing, since the TTL is not part of the prompt; each entry keeps the TTL it was sent with. Each time the mark moves the kernel logs `rebuild_marked { turn, reason }` before the next request is built, also when none follows (a change while the mark already sits after the last entry leaves the list as it was, so it logs nothing); the reason names the first difference in the key (endpoint, model, per-message effort, binding controls, top-level effort, tools, the server tools, the system prompt; a server-tools change is named `native_search_refused`, since with no switch before it an endpoint refusing web search (its organisation's switch, or a gateway) is the only way the server tools change today) or the change that set it (`tail_closed`, `thinking_cut`, `rendering_form`, `search_history_unreadable`, `search_history_rendered`, `attachments_as_notes`). A tool change that can't go inline rebuilds the prefix at the turn's tool moment and sets the mark there, named `tools_change`, unless a pair switch at the same opening marked first; a model switch pending when a resumed session closed is marked `tools_change` at its first opening (`docs/tools.md`, "When a change can't go inline"). A tail that a compaction closes logs no mark, since the compaction clears the list. A tail closed at a cross-account recovery inside a compaction is marked like any close, since it is closed before the compaction is installed.

The **anchor** is the last entry after the mark, when it was sent on the current endpoint and model. It is where that request's automatic breakpoint wrote: the last cache-eligible block of its messages, skipping thinking blocks, empty text and an effort-marker message. `/context`'s compaction figure is priced from the anchor; with no anchor the conversation is priced cold.

`build_marked_body` is the request mode a compaction request uses: no top-level automatic marker, the 1h system and tools breakpoint as always, and one explicit marker on the anchor's block at the anchor's own TTL, so the request reads the cached conversation and writes nothing. Naming a chat is this mode's one-shot use: an ask with no tail, no system marker (`drop_base_marker`), no instructions and no tools sends no cache marker at all. The marker is left off when there is no anchor, when the anchor started longer ago than its TTL, when the entry has no digest, or when the digest of the new request's prefix up to that block differs from the anchor's: a changed system prompt, tools, model, thinking, top-level effort or earlier rendering all leave it off. The ordinary request mode is unchanged.

## Compaction

The `compact` command (`{"type":"compact","focus":…,"request":…}`) compacts the conversation between turns: with the provider's native compaction where the pair allows it, and otherwise with Wisp's own engine (below). Automatic compaction and background compaction are above.

- **Which engine.** Native when the model's settings say `native_compaction = true` and the pair hasn't refused the beta this session; otherwise Wisp's engine. A native compaction falls back to Wisp's engine once, inside the same compaction (one `compaction_started`, one end event), when its reply stops for any reason other than `refusal`, `model_context_window_exceeded` or an `end_turn` with no text; when its block is malformed; when the beta is refused and the view holds no block; or when a 529 `compaction_unavailable` is still failing after the retries. A `refusal`, a `model_context_window_exceeded` or an empty `end_turn` ends in `compaction_failed` with `no_summary`, since Wisp's engine would ask the same model to summarise the same conversation. Other errors after the retries end in `compaction_failed` with `error`. When the view holds a block and the request is refused for the beta or the block, the Convert below is the compaction's result, with no request to Wisp's engine.

- **When.** Only between turns (automatic compaction, above, runs inside turns). It is refused, echoing its `request`, with the kind `turn_running` while a turn runs, `nothing_to_compact` when nothing was added since the session began or since the last compaction, and `compacting` while one runs. A `compact` waiting in the command queue (behind a settings save) is answered `compaction_failed` with `kind: cancelled` and no `engine` when `Cancel` arrives or the command channel closes.
- **While it runs.** `compaction_started` comes first. A message sent meanwhile waits and becomes the next turn when the compaction ends; an answer is refused `no_question`; `Cancel` stops it, ending in `compaction_failed` with `kind: cancelled`. Its retries, cache misses and unknown stream events are logged with no `turn`.
- **The request.** The current view, unchanged, with `compaction: {"type":"summarize","instructions":…}` and the `compact-2026-09-04` beta; no `fallbacks`, stop sequences or forced tool choice, and `max_tokens` 32,000 (or the model's own limit when lower). The system prompt and tools are byte for byte those of the last turn. The marker is the explicit tail marker above, so the request reads the cached conversation and writes nothing. The instructions are Wisp's summary instruction, then `Focus: …` when the command has a focus, and always end with the line saying the instructions are in the system prompt; the whole stays within 16,384 characters, the focus being cut first.
- **Wisp's engine.** The request is the current view, unchanged, with the summary instruction appended as the next user content (joined to a final user message, or a new user message after a reply), then, where per-message effort is proven for the pair and the effort in force in the view is above `context.compact_effort` (default `high`), an effort marker at `compact_effort`. It carries no `compaction` field and no beta unless the view holds a native block, the same system prompt, tools, top-level effort and tail marker as the native request, and `max_tokens` 32,000 (or the model's own limit when lower). Its server-tool searches are charged at `pricing`'s per-search price and are part of the compaction's cost. The reply must stop with `end_turn`, hold text, name all six sections of the instruction (the `compaction` plugin's instruction and check, "Compaction strategies", below), which asks for its headings word for word (Goal and standing instructions; Decisions; State of the work; Files, branches and artefacts; Commands, errors and fixes; Open questions), and make the context smaller. The check reads a heading loosely, so a differently styled one still counts and a false rejection rarely bills a failed `/compact`: case and punctuation are ignored, and each section needs only its key word or phrase at the start of a word (goal, decisions, state of the work, files, commands, open questions; `Subgoals` is not `goal`). Text split across several text blocks, as citations split it, is joined as the transcript shows it, with a paragraph break where another block came between. A reply that misses a section, or whose head's estimate (with the system prompt, tools and instructions) isn't below the conversation it replaces, fails with `check_failed`; any other stop, `tool_use` and `pause_turn` included, fails with `no_summary`. Nothing in a failed reply is run, kept or installed. A refusal of a native search or of a feature on this request is handled as on any request, and a refused block in the view converts as below. A request of either engine refused because the endpoint can't read earlier search results converts them once, as a turn's step does (`docs/endpoints.md`, "Unreadable search results"), and is sent again; a second such refusal fails the compaction with its error.
- **The head.** One user message: the provider's compaction block, byte for byte, when the head holds it; then the prompt sections' head texts in resolved order (the `<environment>` block among them, when the session has one), rendered in the head step; then `<compacted_context epoch="N" turns="A–B">`, laid out by the bundled `compaction` plugin ("Compaction strategies", below), which holds:
  - `<summary>`, only in Wisp's form (a summary in text, whether written by Wisp's engine, kept from a native block, or converted, below);
  - `<user_messages>`: your recent messages word for word, newest first, each with its turn, within `context.verbatim_user_tokens` (default 8,000; a model table can set its own). A message that doesn't fit is cut, with the record that holds it whole in the session log. Each answered `ask_user` question counts as one message; a server's card (`Question.source.asked_by` is `Server` or `Unknown`) and its answers do not;
  - `<tool_calls>`: the last 30 tool calls, oldest first, each with its outcome, working directory (when the tool runs in one) and saved output, and the media types of the files it attached (`attached application/pdf`; `attached image/png (withdrawn)` when the API refused them). When any listed call still has attached files, one line follows the list: `The files these calls attached are no longer in the conversation; to see one again, repeat its call.`;
  - `<cut_off_reply>`, after a cut-off reply (above);
  - `Running processes: …`, the processes still running, each with its unread lines, read through `jobs.all()`;
  - `<pointers>`: where the session log and the saved tool output are.
- **After it.** The view is the head followed by every message added since; the next turn's message joins the head message, and the block is sent back as it came, exactly once, with the beta, on every request whose view holds it. While the pair uses message threads, a compaction that keeps no turns keeps the block's non-empty text instead of the block, sends no block or compaction beta after it, and still reports `engine: native`. `compacted` (with `cache_effect` `rebuilt`, reason `compaction`, and `summary`, the summary's text, for clients to show) is followed by `context_changed` with the head's estimate and the new epoch. The full history stays in memory and in the log (`context_compacted`, `docs/session-log.md`).
- **Convert.** When a request is about to go to a pair that can't take the block (its model table sets `native_compaction = false`, its trial refused the beta, an established beta was rejected by shape, or the API refused the block itself: named by `details.error_code`, or, through a gateway that rebuilds errors without `details`, a 400 `invalid_request_error` whose message names `compaction` and that nothing else claimed; it is converted only when the request carries a block, otherwise the turn ends with the error), Wisp converts the head to its own form with no request: the block's text becomes the `<summary>`, the beta is no longer sent, and `compacted` reports `trigger: convert`, `engine: wisp` and `converted: true`, with `partial` when turns after the old head are kept as they were. A pair known not to take the block is converted before the turn starts (**Before a switch**, below); a refusal converts in the turn: while the turn's own message wasn't kept yet, that message then follows the new head; once it was kept, the step is sent again once with a fixed note in its place, `Wisp compacted the conversation in the middle of this turn; continue the task from where you left off.`, followed by the effort marker the new view needs and any steers. The turns and tool results after the old head are then carried only by the head's messages and ledger, so `compacted` has `partial` set, and a web search the turn paused on is closed as `compacted` (`possibly_billed` when an attempt that carried it may have been billed), since no request will carry it again. An attachment withdrawal still waiting for an accepted request when the head is converted is undone first, so a refused attachment is withdrawn again against the new view. A `compact` whose request is refused for the block converts the same way and answers with `trigger: manual`, `engine: wisp` and `converted: true`; a summary Wisp wrote itself has no `converted`. Both carry the head's summary text in `summary`.
- **Before a switch.** When the next turn applies a model or endpoint switch to a pair that can't take the block, that work happens before the turn starts and carries its number. If anything follows the head, Wisp first compacts on the old pair: `compaction_started` with `trigger: switch` and `switch: {"estimate_micros", "head_tokens", "cause": "convert"}`, computed when it starts with the same estimator as `/context`'s compact-now figure (the read and summary only; `head_tokens` is the summary plus the head's additions). It picks its engine as `compact` does (**Which engine**, above): when the native attempt falls back, Wisp's engine writes the summary on the old pair inside the same compaction, so the new head is Wisp's (`compacted` with `engine: wisp` and no `converted`) and nothing needs converting; a native compaction that keeps text for message threads needs no Convert either; otherwise it converts the fresh block. When the old pair refuses the beta or the block, the compaction's result is a Convert of the head it had (`engine: wisp`, `converted: true`, `partial`), with no request to Wisp's engine. With nothing after the head it only converts. Both come before the turn's `turn_started`, in the log and in the event stream, and the turn's settings, effort marker and `Context:` line then come from the new view. The compaction's cost and usage count in that turn. If it fails (an error after retries, a reply that stops without a summary, or a Wisp summary that fails its check), `compaction_failed` names the engine whose leg failed: `wisp` when Wisp's engine failed after the native attempt fell back, with both legs' usage and cost. Wisp then converts the head it had, with `partial`, and the switch applies, unless the converted view wouldn't fit the new pair: the converted head, the system prompt, tools and instructions, and the turn's message and waiting steers, over the new pair's window less 8,000 tokens. Then nothing is converted, and the switch is withdrawn before the turn starts. The pair is read again when the compaction ends, so a switch changed meanwhile counts: a failure never withdraws when that pair can take the block, and a pair that can take it gets no Convert. If it is cancelled, the turn starts on the old pair with nothing pending applied and ends cancelled, and the switch is withdrawn after its `turn_ended`. A withdrawal is a `settings_changed` that answers no command, with `withdrawn` (`switch_compaction_cancelled` or `switch_compaction_failed`), the old pair as `endpoint` and `model`, `changes` restating the old `model` and `endpoint` for this session (and `effort`, when the pending effort doesn't fit the old model and goes back), followed by every pending `cache_ttl` or `debug_cache`, and, on the event only, `restored`: the effort and cache lifetime in effect again. A switch accepted while the compaction ran is withdrawn too. **The quote.** A model or endpoint change that makes this work due carries it on its `changes` entry as `consequence`: `{"type": "compacts_before_switch", "estimate_micros", "head_tokens", "cause": "convert"}`, with `estimate_micros` 0 for a Convert alone. `describe_settings` lists the same quote in `switches` for every model and endpoint whose switch would need one (each model, each endpoint, and each pair of another endpoint and a model its provider serves, as `{"pair": {"endpoint", "model"}}`, which prices a change of both at once), sorted by target. **A Retry on another endpoint** runs the same pre-turn work for the pair it is sent to (that endpoint with the session's model), but from the endpoint that just failed: the compaction is tried there once, with no retries on either engine (a native attempt that falls back gets one Wisp attempt), and if it fails the head is converted at once, with no withdrawal; a converted view that wouldn't fit the target ends the Retry instead (**Compaction before a Retry**, below). A switching Retry never withdraws: if its compaction is cancelled, the Retry ends cancelled and the pending switch stays as it was. A `/model` or `/endpoint` change sent while it runs stays pending for the turns after the Retry, which itself still runs on the endpoint it was sent to with the session's model. It runs on the failing endpoint, as decided for this case; summarising on the new endpoint instead would need the block's text in place of the block with the later turns kept, which Wisp doesn't build, so it is a possible later improvement. A Retry on the same endpoint sends what the failed request had and converts nothing first.
- **A smaller window.** A switch also makes this compaction due when the estimate for the next request (the current view plus the turn's message and waiting steers) is at or over the new pair's point, with that pair's window and reply limit, and something follows the head: `cause` is then `smaller_window`, which wins over `kept_turns` and `convert` when they also apply, and the fresh block is converted after it when the new pair can't take it. The quote names the same cause. A switch quoted as a Convert alone can run as a `smaller_window` compaction when the fill has grown by the time it applies; `compaction_started.switch` always carries the cause and estimate at run time. If a `smaller_window` compaction fails, the switch is withdrawn before the turn (`switch_compaction_failed`), unless the view holds a block the new pair can't take: then the head is converted and the switch applies, under the same fit check as above. The check is made against the pair the turn will use once the compaction ends, so a switch changed while it ran (for example back to the old pair) is withdrawn only if that pair's point is still reached.
- **With automatic compaction off.** A switch never compacts for a smaller window by itself: neither the quote nor its cost names a compaction, and the next request is sent as is (a genuine overflow is then recovered as usual). When the switch is made past the new pair's point (the current view, without a message), a `past_compaction_point` event (`endpoint`, `model`) follows its `settings_changed`, and the transcript shows the notice `Run /compact: past claude-opus-5-5's compaction point.` (at most 60 columns; a model name too long for that reads `the new model's`). It is never logged. A switch below the point says nothing. With automatic compaction on, nothing changes. A `change_settings` batch that switches and sets `context.auto_compact` is judged by the batch's final setting, for both the quote and the notice.
- **Compacting before your next message.** A change to `context.auto_compact`, `context_window` or `compact_at` that leaves automatic compaction due before the next turn carries `{"type": "compacts_before_next_message", "estimate_micros", "head_write_micros"}` as its `consequence`: `/context`'s compact-now figure and the head write, never summed (0 on an unpriced endpoint). `describe_settings` adds `compaction`: `fill_tokens`, the `max_tokens` the next turn sets, and the same two figures, for the next turn's pair; it is absent while the window is unknown.
- **Failures.** `compaction_failed` with `kind` `error` (after retries), `no_summary` (the reply stopped without a summary), `check_failed` (Wisp's summary missed a section or wasn't smaller) or `cancelled`, with the engine that failed and the compaction's usage and cost, a native attempt before a fallback included. A refused beta also marks the pair `fallen_back` (`feature_state_changed` and a `native_compaction` record), so later compactions on it use Wisp's engine.
- **In the full screen.** `/compact [focus]` (`docs/commands.md`) sends the command with the focus, if any. Wisp is busy from `compaction_started` (never from when you press enter, since the command may wait or be refused) to its `compacted` or `compaction_failed`: the working line reads `Compacting… (4s · esc to stop)`, or the retry countdown while its request is retried, and Esc cancels the compaction alone. A message you send meanwhile waits, labelled `next turn`, and starts the next turn when the compaction ends. `/compact` while a turn runs is refused with the hint `/compact runs between turns. Send it after this one.`, and while a compaction runs with `A compaction is already running.`; the text stays in the composer. The kernel's refusals (`Nothing to compact yet.`, or the no-native-compaction refusal an older Wisp sent) show as a note.
  - A finished compaction draws a rule, then `context compacted · 182k → 14k · $0.28`, adding `partial` when turns after the old head are kept only in Wisp's form, `converted` for a Convert, and `converted; focus not applied` when a `/compact` with a focus converted instead. A `/compact` that converted adds `The server refused the summary block, so the existing summary was kept in Wisp's form.` Transcript mode shows the summary under the divider.
  - A failed compaction is one line with its cost: `Compaction failed: Anthropic is overloaded. Nothing changed · $0.012`, or `Compaction stopped. Nothing changed · $0.004` after Esc; transcript mode adds the kernel's message to a failure. A compaction inside a turn shows `Compacting…` while it runs, and its failure is the turn's.
  - `--replay` plays each manual compaction in the recording (its events from `compaction_started` to its end, with the `context_changed` that follows, or a lone refusal) when you send `/compact`, holding `Compacting…` for about two seconds so Esc can stop it. A message sent meanwhile waits and starts the next turn; a second `/compact` is refused `compacting`, `/compact` during a turn `turn_running`, and once the recording has no more, `the replay has no more compactions`. Compaction events inside a turn carry the replayed turn's number. `crates/wisp-tui/tests/fixtures/compact.jsonl` holds a turn, a compaction and a second turn.
  - A switch's quote shows before you choose and in its note: the `/model` and `/account` pickers and the screen's Model and Endpoint rows read `cache rebuild ~$0.04 · compacts before your next message, then switches (~$0.48 · converts the summary)`, or `the new window is smaller` or `kept turns can't go to another model` for the other causes. The rebuild is priced on the system and tools prefix plus `head_tokens`, both written on the target (the prefix at 1h, the head at the next turn's lifetime), never on the whole last prompt. A Convert alone reads `cache rebuild ~$0.04 · converts the summary before switching`. On an endpoint without prices, or for a current model with no pricing row, the kernel's estimate is 0 whatever the work, so the figure is left out (`(converts the summary)`), never shown as `~$0.00`, and the row names the compaction, since a 0 there can't tell a Convert alone from a compaction.
  - An account's `SwitchQuote` can carry only `remembered`, its accepted model and
    effort for an account-only move, even when it needs no compaction.
  - When the switch's compaction starts, a note gives its own estimate: `Compacting before switching to claude-opus-5-5 · ~$0.19`, adding `(not quoted when you switched)` when nothing was quoted, the cause changed, or a quoted Convert alone on a priced endpoint makes a request. A pending switch Wisp started with (a resume) has no quote to compare, so the note never adds it. When the compaction fails and Wisp converts, the note reads `Couldn't compact before switching to claude-opus-5-5; converted the summary instead · turns 11–30 kept only as your messages and the ledger`, naming the turns after the last compaction the screen saw, and leaving them out when it saw none. A withdrawal has its own note: `Switch to claude-opus-5-5 withdrawn: the compaction it needed was cancelled · choose it again with /model`, with the effort that goes back and where the switch is still saved.
  - `--replay` plays the work before a turn (an automatic, switch or Convert compaction, its retries and a failure's withdrawal) as part of that turn, before its `turn_started`, and holds a compaction's `Compacting…` for about two seconds there too. A cancel's withdrawal, which follows the cancelled turn's `turn_ended`, ends that turn's script instead of joining the preamble. The replay's own settings follow every recorded `settings_changed`, the preamble's included (a withdrawal sets the old pair, the restored effort and the effort still pending; any other sets the pending pair), start with the session's cache lifetime, and apply a turn's pending switch only when its `turn_started` plays, never for a turn whose recorded switch compaction was cancelled (a cancelled automatic compaction still lets the switch apply). Esc during a replayed compaction before a turn ends it as the kernel does: `compaction_failed` (`cancelled`), the turn's `turn_started`, a cancelled `turn_ended`, and, for a switch, the withdrawal, whose effort goes back when the old model doesn't take the pending one, as the kernel's re-check does. Esc after that compaction ended but before `turn_started` plays starts the turn first, then cancels it. A Convert reads no commands, so Esc during a replayed one waits for it to end, then stops the turn.
- **`/context`.** After a compaction the Summary row (`Summary (epoch N)`) counts the head, the report carries `epoch`, `compactions` (the compactions that installed a head) and `compaction_cost_usd` (what every compaction request cost, failed and cancelled ones included, so it matches what the session spent on them), and until the next request the fill is the head's estimate (`estimated_after_compaction`).

## Plugins and compaction

A plugin hooks compaction at four points (`docs/plugins.md`): `context-threshold` (below), `before-compact`, `compaction-head` (in the head step, below) and `after-compact`.

**`context-threshold`** is the decision point. It fires each time the core decides whether to compact: before a turn and at each step boundary, once the estimate is counted, whether or not automatic compaction is on, while the window is known, the view has new content and the turn isn't stopped. It never fires for the quote, a Retry's start, a boundary with a live server tail, the boundary after a reply the window cut off (which compacts its own way), while compacting, or for a send whose every input a `user-input` hook blocked: there the core itself couldn't compact, so no hook is called and nothing is logged. Its `fill-info` holds the figures the core decides on: the estimate (the provisional head and the typed message before a turn, the view and the waiting steers at a boundary), `measured` and `epoch` as `context.current-fill` gives them, the window and the point for the next request (the point uncut while automatic compaction is off), the ceiling (the default point for the window and reply limit) and whether automatic compaction is on. A hook with `from` is called only once the estimate reaches it.

A `compact(focus)` reply asks for a compaction; the first one allowed ends the point.

- **When the core is due** (the estimate at or over the point, or at or over the ceiling while a veto holds it), the core's own compaction runs and takes the focus, with no `requested_by`.
- **Otherwise** one automatic compaction runs with that focus, and its `compaction_started`, `context_compacted` or `compaction_failed` carries `requested_by`, the hook's full name. The transcript shows `Compaction requested by aa/ask` as a muted line. It runs through the session's compaction strategy (`context.strategy`) and passes `before-compact` as any automatic compaction does: the strategy's `instruction` gets the focused default and `requested_by` in `compact-info`, and its head comes before the `compaction-head` texts. At or over the ceiling no veto stops it, and below it a veto ends it. A request made while a background precompute runs waits for it, as the core does: a swap that goes in answers the request, with no `requested_by` and the focus dropped, though the hook's `hook_ran` reads `applied`; a swap that is discarded leaves the request's own compaction to run. That swap is the precompute's own: it arms "The hold" as every core swap does and carries no `requested_by`; the request only brings it forward, and a request's own compaction never arms the hold.
- **It is refused** (`hook_ran` `rejected`; the later hooks still run) for the rest of a turn in which a requested compaction failed (`request_failed`) or was vetoed (`request_blocked`), or the core's own automatic compaction failed or left the context over the point (`auto_paused`, the thrash guard above). Each resets at the next turn. The first refusal in a turn draws one line, such as `Wisp refused the compaction aa/ask asked for: a compaction a hook asked for failed earlier in this turn. Hook requests wait for the next turn.`; later ones in that turn draw no line, only their run line in transcript mode. A focus over 2,000 characters is `rejected` with `too_large`.
- **Nothing else refuses.** There is no floor: a hook may ask at any fill, however far below the point. "The hold" and the veto hold hold only the core's own trigger and point, and an earlier compaction or swap in the turn refuses nothing. A plugin's compaction requests aren't rate-limited: each one is a paid request, shown in the transcript and in the turn's cost, and the user removes or switches off a plugin that misuses it (`wisp plugin disable` or `remove`).
- **What a request leaves.** A failed request writes `compaction_failed` with `requested_by` and no `paused`, and the transcript says `Compaction requested by aa/ask failed (overloaded); hook requests wait for the next turn.`; a vetoed one shows its `Blocked by` line. Neither pauses nor holds the core's automatic compaction, which still compacts at its own point in that turn. A requested compaction that succeeds refuses nothing, even when it leaves the context over the point, and never arms "The hold": the request after it is measured as after `/compact`, so it may release the hold. Past `window − 8,000` the turn still ends after it, as after the core's own. A resumed transcript draws the `requested by` line and a failed or vetoed request's line again, and, since resume replays `hook_ran`, the refusal line too, once per turn.
- **Esc** during `context-threshold` ends the turn `cancelled` with nothing sent.

**`before-compact`** is the gate. It fires once per compaction that writes a summary, in `summarise`, after the stopped guard and before any request: at `/compact`, an automatic, overflow or switch compaction, a Retry's re-run and a background precompute (outside a turn, below). A Convert writes nothing and fires nothing, and neither does a compaction on a model without native compaction whose head still holds a block. A native compaction that falls back to Wisp's engine, or retries a smaller earlier request, fires it once. Its `compact-info` gives the trigger, the engine, the turn, the focus, the fill estimate, the point (the ceiling while a veto holds automatic compaction for the turn, below), the epoch and the instruction as it stands. A hook may rewrite the instruction or append lines to it (each hook sees it as the hooks before left it); the result is what both engines send, Wisp's engine as its summary instruction and the native one as its `instructions`, and is counted in the request's estimate only when a hook changed it, so a session with no hook sends what it always did. A rewritten instruction drops Wisp's six-section check, but keeps the others (a reply that stopped on `end_turn`, with text, and smaller than what it replaced). Each change is a `hook_applied` record at `before-compact`, written once the compaction goes ahead, and `context_compacted.instructions_by` names the hooks that changed it, in run order.

**A veto,** a `block` or a failure of an `on_failure = "block"` hook, ends the compaction before any request with `compaction_failed`, `kind: blocked`, and a message naming the hook (`Blocked by aa/gate: not now`), shown as a muted line. What follows depends on the trigger:

- **`/compact`** is answered with that failure.
- **Automatic** compaction is held for the turn: the turn sends as it stands, and automatic compaction in that turn waits for the ceiling (the default point for the window and reply limit, `compact-info.point` while held). The next turn starts without the hold. This per-turn veto hold moves only the core's own point: a `context-threshold` hook's request below it still runs. It is separate from "The hold" above: a veto arms no hold, and a ceiling compaction that runs is an automatic compaction like any other, so the request after it is measured and may arm one.
- **Overflow** (the plan's decision B): the notice, then the overflow goes on as if its compaction had failed. After a rejected request the turn ends with the overflow's own error, the one terminal event; after a reply cut off by the window the turn sends on, and a later overflow ends it; before a turn the turn sends. With automatic compaction on, an automatic compaction may still follow: below the ceiling a second veto gives a second record, at the ceiling it runs.
- **A switch** that is settled goes ahead when the conversation fits the new pair and is withdrawn when it doesn't. A Retry's re-run that is vetoed sends the turn as it stands.
- **Background**: the precompute isn't started, and nothing but the hooks' `hook_ran` records is written (no `compaction_failed`, event or card). The hooks there run outside a turn, under the 2 s budget that cuts a longer `timeout_ms`, so under `on_failure = "block"` a timeout there starts no precompute.

**At or over the ceiling no veto stops an automatic compaction.** That holds for a compaction that runs: while automatic compaction is held ("The hold", above) none runs, at the ceiling too, so no gate is asked, neither before a turn, between steps nor for a background precompute; an overflow is then recovered as usual, through the gate. `/compact` and overflow recovery ask the gate while held, and their `compact-info.point` is the point, which the hold never changes. A `block` is recorded `rejected` with the rule `ceiling`; a failing `on_failure = "block"` hook keeps its `timed_out` or `failed` outcome and blocks nothing; the hooks after it run either way.

**A running precompute.** The discard a compaction makes of a running or ready precompute happens after the gate passes, so a veto leaves the precompute running; the discard's spend is charged to the turn as before (and by resume's `charge_turn`). The background gate runs only when a precompute would start (an anchor, the band); a rewind run during it, or a turn whose figures moved, starts none.

**Esc** during `before-compact` cancels the compaction with nothing sent: the gate skips on a stopped track, and `summarise` reads the guard again after the gate.

## The head step

Every head runs one async step after its summary is in and before the head is built: in `/compact`, a switch's compaction and an in-turn compaction (before `overflow.reserve` is reset), at a background swap and at a Convert outside a compaction. The step renders each prompt section with `at = head` (`docs/plugins.md`, "How the kernel renders sections"), and its result, `HeadTexts`, rides with the head into `install`, `install_leading` and `build_head`, which lay the head out in one order: the native block, the sections, `<compacted_context>` (or a chosen strategy's texts, "Compaction strategies", below), then the texts the `compaction-head` hooks appended (below). The sections' snapshots commit when the head is installed and are logged in `context_compacted.sections`. A head built while a turn's message is unsaved renders to that message's snapshot (`target`); one built before a Retry's first request succeeds has no `target` and renders the current state, so the Retry sends nothing for the section (a departure from the plan's §1.1). The head's estimates (`head_additions_for`, the Convert quote, `head_fill`, the provisional head) call no plugin: they read each section's last head render, refreshed at the async points. `head_additions_for` and the Convert quote also count the `reserve` text of every runnable `compaction-head` hook, since its texts can't be known before the step runs; `head_fill`, which measures a summary already written, doesn't.

The bundled `todos/checklist` section shows the saved, redacted checklist at each new head, before `<compacted_context>`. An empty checklist adds nothing; ordinary turns do not repeat it.

The bundled `agents/children` section, after it, lists at each new head the agent's direct children that haven't ended, other than those idle after a report, each with its state and the time since its `since_ms`, then `Their reports arrive as messages.` (`docs/agents.md`, "States"). With none to list it adds nothing; ordinary turns do not repeat it, and the ages stay as the head was built, since a retry, a resume and a rewind send the head that was installed and logged.

**`compaction-head` in the step.** Once the section loop is done, and only if the track isn't stopped, the step fires `compaction-head` (`docs/plugins.md`) with the head's `head-info`: its epoch, trigger, engine and turns (a kept head's run from the next turn to the last kept one, a Convert's those of the converted head). Its appended texts follow `<compacted_context>` as text blocks, are logged with the head (in `context_compacted`'s head, or the kept head's additions), and are rebuilt byte for byte by resume and rewind, which never call a hook. The hooks share one room, counted in tokens and re-read as the step runs, so it is the room the head has once its sections rendered, corrected by how far their render moved from the estimate the head was sized with:

- **Smaller than before.** For a compaction, the texts must leave the head smaller than what it summarised: `before − after`, with `after` the head without them.
- **Fits its limit.** Under a limit (an overflow recovery, a swap for an overflow or a before-turn swap with an overflow due), the request after the head must still fit: the limit less the head, the pending blocks (`overflow.reserve`, which is why the step runs before it is reset) and the reply's `max_tokens`. A Convert, which summarises nothing, is held only to its limit: the target's `window − 8,000` less the converted estimate (the same bound `converted_fits` checks), from `convert_in_turn`, a switch's plain Convert, a Retry's and a failed settled switch's.

The head's own `reserve` texts are counted once: the estimate they are part of is the head without them. A text that would reach the room is `rejected` with `not_smaller`, and the hooks after it still run; one past 10,000 characters, or a set past 20,000 for the head, is `rejected` with `too_large`. An Esc during a `compaction-head` hook keeps the texts of the hooks that finished. Room is counted against what the head replaced, not against the point, so texts may leave an automatic compaction's result at or over the point: they count like the summary, so the thrash guard pauses automatic compaction for the rest of the turn, and the request after is measured with them and may arm the hold ("The hold", above).

**Esc in the step.** The paid summary is kept and the head built with whatever finished; a section cancelled or not yet rendered counts as unsent in the new window. An Esc in any render sets the turn's `stopped`, and then nothing more is paid for or sent: `summarise` returns `cancelled` first when the open track is stopped, `begin_in_turn` and `switch_compaction` copy `stopped` into the track they open (and a switch carries it back), `before_request` reads it before every attempt, and `auto_before_turn` and `auto_between_steps` end the turn before waiting for a running precompute, which the cancelled turn's end discards. `/compact` completes with its head and opens no turn record.

## Compaction strategies

`context.strategy` names the plugin that writes the summary instruction, checks the summary and lays out the head (`docs/plugins.md`, "Compaction strategies"). Its value `default` means the bundled `compaction` plugin, which holds Wisp's six-section instruction and check and the `<compacted_context>` layout above, so a saved `default` keeps its meaning. The core asks the chosen plugin at three places and keeps every mechanic itself: the triggers, the engines, the cut, the room, the install, the log and rebuilding on resume and rewind, which never call a plugin.

- **The instruction.** In `summarise`, after the stopped guard and before `before-compact`, the strategy's `instruction` is asked with Wisp's instruction for the focus in its `compact-info`. Its text, when it gives one, is what `before-compact` sees and transforms, and is counted in the request's estimate. A background precompute asks it the same way, outside a turn. A Convert asks nothing here.
- **The check.** For Wisp's engine with the instruction no hook rewrote, `accept` replaces the six-section check. A failure or Esc there leaves the summary unchecked, as after a `before-compact` rewrite, and the head uses the core's minimal layout. A refusal from the `compaction` plugin reads as Wisp's own sentence (`The summary has no “Decisions” section, so Wisp kept the conversation as it was.`); another plugin's is wrapped as `docs/plugins.md` says. The not-smaller check moves into the head step, so it measures the head the strategy built.
- **The head.** In the head step, after the sections and only if the track isn't stopped, `head` is asked with the summary (`none` when the head holds the provider's block) and a fresh view. A head from a summary Wisp's engine wrote is then measured: at or over what it replaces, the compaction fails with `not_smaller` and `compaction-head` doesn't fire. `compaction-head` then fires with the room left by the strategy's texts, corrected as for sections by how far they moved from the estimate.

**One fallback per compaction.** A strategy that fails, times out, answers too much or gives an empty head when handed a summary, or a chosen plugin that isn't installed, is off or offers no strategy (checked again before every call, so a ready precompute whose plugin was turned off, removed or unchosen swaps in with the core's minimal fallback), gives one notice (a `hook_ran` record for `<id>/strategy`), and the rest of that compaction uses the core's minimal fallback. The next compaction asks again. The same fallback serves a session whose `compaction` plugin is removed, with the same notice. The core keeps only this much of a layout: a short instruction (`Write a summary of the conversation so far, so that the work can continue from the summary alone. Don't call tools.`, then the focus and the line about the instructions, as above), no check on a summary Wisp's engine wrote beyond the not-smaller one, and after the sections a `<compacted_context epoch="N" turns="A–B">` holding only `<summary>` when handed one, and nothing when the head holds the provider's block. The bundled plugin runs in-process, so none of these fallbacks fires in normal use.

**Estimates.** The estimates that can't wait for a plugin (`head_additions_for`, which sizes the head for the triggers, the quote and `/context`) read the texts of the last `head(summary: none)` call, cached with the plugin's id and the epoch it was made for. The same refresh asks `instruction` once, for the instruction's share of `/context`'s compact-now figure and the earlier-request fallback, and, while the head holds a native block, `head` once more with that block's text as the summary, for the Convert quote. A refresh runs at the async points where sections refresh, at the end of each turn, after each head is installed and after a rewind, so the figures always measure the state they describe; with no cache for the chosen plugin they use the core's minimal layout and instruction. A refresh is silent (an Esc in one before a turn cancels the turn, as a section's does); an empty answer for Wisp's engine counts as failed, and after a failed one, no refresh asks the same plugin again before the next compaction. `head_fill`, used only when no strategy is live, measures the core's layout.

**The log.** `context_compacted.strategy` names the plugin that built the head: `compaction` for the default, and is absent for the core's minimal fallback. `context_compacted.instruction` holds the instruction the strategy supplied, whole. `compaction_failed` carries the chosen plugin and the instruction the same way, so an `accept` refusal's sentence (in `message`) and the instruction it judged are logged together. Both fields are additive and skipped when absent, so a session without a strategy writes the records it always did.
