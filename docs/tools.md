# Tools

Wisp.Core runs tools inside a turn: the model asks for a call, the kernel runs it, appends the result and asks the model again, until a reply makes no more calls. The design is in `docs/plans/tools-bash.md`; this page describes what is built.

Every job carries `WISP_JOB=1`, inherited by the programs it starts. A `wisp`
started there keeps its host in the job, so ending the job ends that chat too;
a chat or `wisp doctor` started there with an explicit account (`--account` or
`WISP_ACCOUNT`) reaches only that account.

## What running tools means today

Security is deferred. With tools on:

- every command the model writes runs at once, as you, with your environment and no sandbox;
- it can delete files, `git commit` and `git push`, install packages, use the network, and read any file you can, including secrets;
- whatever a command prints, and whatever file the model reads, goes to the model provider and into the session log, with the held-key mask below;
- text a command prints (a README, a web page) can steer the model into running more commands;
- Esc (or Ctrl-C) is the stop button: it kills the running command's process group and ends the turn.

The only security hook is the no-op `policy::Gate` (`crates/wisp-core/src/policy.rs`). It sees every call, with its resolved working directory, just before the call starts, and always allows it; it sees the final input, after any `before-tool` hook (below).

Before a tool result joins the conversation, Wisp replaces credentials it holds of 20 characters or more with `[redacted]`, including their escaped text, their spellings with JSON's string escapes or Rust's `\u{…}` nested up to four levels deep (`docs/session-log.md`), and standard-alphabet base64 copies, even with text before or after the credential inside the encoding.
This applies with or without a session log. Account keys, provider sign-in tokens, key variables and exported keys named in an MCP server's `keys` are held from when Wisp reads them; an MCP server's stored keys, sign-in tokens and client secrets are read and held before the chat's first turn. A URL's path and query and a project id are log-only: they are scrubbed in log side fields, not tool results.
Exported variables whose names contain `KEY`, `TOKEN`, `SECRET` or `PASSWORD` (any case) are also held from start when their values have 20 or more characters and do not start with `/`, `~` or `.` (paths). These values are held in memory only.
A long id under such a name also reads `[redacted]`.
A process's output is masked as it is captured, before the output file, live output, terminal screen and process reads receive it.
This also masks a held key before a result window cuts it or a terminal wraps it across rows.
Characters that could start a held value, its escaped spelling included, show only when more output or the end settles them; no timer releases them. So does output that ends in an unfinished escape: a lone `\`, or the start of `\uXXXX`, `\u{…}` or a surrogate pair; a backslash that no later byte can turn into an escape, as in `C:\Users\me> `, shows at once. A possible start is held back for up to about 16 times the longest held spelling's length, so an escaped spelling longer than that, split across output, can show in the live output and output file, and is masked in the result only when the result holds it whole; with an already masked tail, at most 17 times that length is held. Newly held values apply only to retained bytes, not output already released, including a capped run.

A masked result ends with this line for the model, kept unchanged on later turns and resume:
`[redacted] marks a key Wisp holds; the original is unchanged.`

Not covered: values under 20 characters; named-variable values starting with `/`, `~` or `.`, even when they are keys; URL-encoded or hex copies; base64 copies wrapped over lines (plain `base64` wraps at 76 columns); keys drawn in pieces with cursor movements; credentials inside a URL's path or query or pasted into a URL setting; a sign-in an earlier Wisp saved under an MCP server's address; images; a kept process's `.log` file; secrets outside the named-variable rule that Wisp has never held. Reading an output file later through a tool is masked while Wisp holds the value.

When a file contains one of Wisp's held keys, the model reads the mask, not the key. Rewriting that whole file from the result can write `[redacted]` back into it; the mask itself never changes the original file. Use `ask_secret` to move a key without putting it in the conversation.

## Hooks around calls

A plugin's `before-tool` and `after-tool` hooks (`docs/plugins.md`, "The gate points") wrap each call in `run_call`, in this order:

1. the model's input is prepared, and the not-run checks and the call's place in the reply are settled; a call that won't run fires no hook;
2. `before-tool` runs. A block gives the call one failed result, `Blocked by <hook>: <reason>`, before it starts. A rewrite is prepared again as the run's input (a rewrite the tool refuses is `Invalid input: <hook> rewrote the input: …`); the model's `tool_use` and `tool_call_requested` keep the input the model sent, so committed history and the cached prefix never change;
3. the spot after `before-tool`, on the final input, is where a future permission check goes; today's always-allow `Gate` doesn't fill it;
4. the call runs with the final input;
5. the held-key mask runs, then `after-tool` runs, for a call that ran and a turn not stopped, on the masked text without its job lines: a rewrite replaces it, an append adds its notes after it; the model-only held-key notice is added after final assembly;
6. the job lines (a background job's end) go last, after the hook's text, so they are heard once whatever the hook did; then the call's attachments are settled, the final text is masked again, and a masked result gets its one notice as the last line for the model. The notice stays out of the call page's result text.

A call is prepared once for its display, and once more only for a `before-tool` rewrite. Its target, the display's `target` from its `tool_call_requested`, is kept per call id (live, and from the log on resume), so the attachment check, the process rows, the compaction ledger and a withdrawal read it there instead of preparing the call again; a call missing there gets the fallback display's target.

`tool_call_finished` keeps the run's own result and notes; the model gets the hooked text, logged in `hook_applied` (`docs/session-log.md`). Esc during `before-tool` gives the call `not_run: turn_stopped`; Esc during `after-tool` keeps the run's own result.

## Which sessions have tools

A session's tools are names from the plugin catalog (`docs/plugins.md`, "The catalog"), resolved by the plugin registry ("The registry") and fixed for the run. A resumed full-screen root session keeps the logged prefix and applies this run's tools as changes at its first turn ("Resuming a session", below), and a resumed child does the same for its own logged tools; a jsonl session and one with `--tools none` take this run's tools, whatever they ran with before: a difference costs one cache miss and the resume notice names the tools added and removed (`docs/session-log.md`, "Stability"). A child agent keeps its logged tools for life (`docs/agents.md`, "Resume"). `crates/wisp-start/src/tools.rs` builds the catalog before any session, turns `--tools` into the on-set and is the only client code that builds the registry, with `Registry::new(wisp_plugins::bundled(), &config)`; the Kit starts it for each agent. For its first agent `wisp` starts it once itself, before the Kit, to decide on web search, and hands that start to the Kit (`Prestarted`), so the plugins start once.

A plugin switched off or removed (`docs/plugins.md`, "Turning plugins on and off, and removing them") turns its tools off at the next turn, as a `tools` change does (below); its hooks, sections and commands stop from the next turn too. A session that starts with the plugin off or removed leaves its tools out, and so does a child spawned after the switch applied. The registry starts with the saved and flagged switches (`start_switches`), and a removed plugin is never instantiated, so it brings no tool name clash either: of two plugins sharing a tool name, removing one gives the other its tool in the next session.

### Switching tools in a running session

The `tools` setting, and a plugin's `enabled` and `installed` switches, change a running full-screen session's tools at the start of its next turn: the tool moment, beside the plugin switches' (`docs/plugins.md`, "When a switch applies"). Nothing changes at the change itself, and a turn that is running keeps its tools to its end. The `tools` array and the system prompt change only at a rebuild (below); otherwise the cache is kept:

- **On an Anthropic model whose capability row has `inline_tools`** (`docs/endpoints.md`), the changes go as blocks in a system message right after the turn's user message, with the `inline-tools-2026-09-15` beta: a `tool_removal` by name for a tool turned off, a `tool_addition` by name for a tool in the array turned back on, and a `tool_addition` by value (the whole definition) for any other tool, with a text block holding each added tool's system sentence the prompt doesn't already state. On the direct API the beta goes on every request with tools from the session's first; on a gateway the pair is a trial, and the beta goes only on requests whose view holds tool changes, until the trial is proven or falls back. Claude takes a system message with content only where it ends the request or a reply follows it. Where the history holds user messages after one (steers delivered with it, a Retry's waiting message, a turn run on another provider), the request to Claude carries it after the last of them, unchanged; the history and the log keep their order, other providers get it in that order, and a system message that holds only an effort marker stays in place.
- **On the ChatGPT subscription or official OpenAI API, for the exact IDs in `[providers.openai].subscription_additional_tools` or `api_additional_tools` respectively,** additions go as one `additional_tools` developer item at the same position after the user's message, with its definitions sorted by name; removals and by-name re-enabling go as developer text, `Tools turned off: show_diff.` and `Tools turned on: show_diff.`, whose literal wording is replayed prefix bytes. The initial `tools`, instructions and cache key stay unchanged; a change sent immediately after a cold first request may still read no cache, as any request may. A 400 or 422 invalid-request refusal naming `additional_tools`, when an item was sent, falls back for the session: the step is resent without items and the next opening rebuilds; gateways and unlisted models keep their existing behavior.
- **On any other model,** the turn's user message leads with a `core/tools` line, `Tools turned off: show_diff.` or `Tools turned on: show_diff.`, and the definition stays in the array. A call to a tool that is off gets `this tool is turned off` as an error result.

**Plugins removed or added back.** A plugin removed in the window leaves at the plugin moment, before the tool moment, so its tools are gone tools there: an inline removal, or a note where blocks can't go. A plugin added back starts at the plugin moment with its tools held, and the tool moment turns on the wanted ones as any held tool: by name where the array declares them, by value inline, otherwise by one rebuild. Until that moment the plugin is a pending joiner, and its wanted tools count as about to be defined, so the answer to the add-back, keep-warm and a child's resume already say whether a rebuild is due. A plugin added back whose sentence the prompt doesn't state sends it as a text block in the tool message, once.

**When a change can't go inline.** A tool that can go neither as a block nor as a note rebuilds the prefix once, at the tool moment and never mid-turn: a tool never sent, or declared only by a by-value addition the pair leaves off the wire (after a fallback or a model switch), on a pair without the capability; a declared definition older than this build's on such a pair; or any tool turned on while the `tools` array is empty.

- **The array** holds every tool the request declares plus the ones the rebuild adds, sorted by name. Each takes this build's definition where a plugin defines it, else its latest declaration, so a gone tool stays declared and its calls are refused, and an off tool stays in it and is refused: `tools` is never emptied.
- **The system prompt** is built from this run's base, the system lines of the array's tools in array order (a declared tool that is off or held keeps its line), and this run's sentences.
- **The cache.** The rebuild is marked `tools_change`, unless a pair switch at the same opening marked first (a switch to a model without `inline_tools` rides its own rebuild, marked `model_switch`; in a resumed session, a model switch still pending at the close is marked `tools_change` at the first opening, since the resume holds no earlier request to compare). Its request takes binding controls where the pair can use them and otherwise drops the earlier thinking (`docs/plans/tools-bash.md` §8.1). A by-value tool a gateway's fallback took off the wire comes back this way at the next opening, so that case costs two writes.
- **Then the diff.** The moment decides again against the new array and sends what still differs, by note on such a pair.
- **It is shown once:** one `ToolsChanged { via: rebuild, cache: rebuilt (tools) }`, one `tools_changed` holding the new prefix (`docs/session-log.md`), one `tools-changed` hook, even when no tool changed state (a stale definition's rebuild), and one line: `tools added: show_diff · cache rebuilt (tools)`, or `tools rebuilt · cache rebuilt (tools)` with no names. A pair switch's own server-tool change at the same opening is still reported by its own record.
- **The answer** to such a change, from `tools` or from a `plugins.<id>.enabled` or `plugins.<id>.installed` change that makes a rebuild due, is next turn with a tools rebuild (`Rebuilt { reason: tools_change }`; the TUI shows `next turn · cache rebuild` with its estimate), and keep-warm skips its refresh as `changed` while a rebuild is due.
- **After a rebuild** the tool context is this run's (descriptions under a logged context are dropped), the base is this run's, so no base block is due, and base blocks before the rebuild no longer decide the base.
- A continuing Retry has no tool moment and keeps its prefix; a Retry that opens its message again rebuilds there. A compaction's head restates blocks only and leaves the rebuild to the moment.
- **Additions a rebuild replaced.** A by-value `tool_addition` before the last rebuild's point, of a tool the new array holds, is void: it is left off the wire (a system message left with nothing isn't sent), and the offer, `/context`, the trial's proof and a fallback's mark all skip it, so each tool is declared once, with the array's definition. By-name blocks, a native compaction's own additions and additions of deferred tools are never voided, and a log from before the rebuild point existed (point 0) voids nothing. A rewind below the point lowers it.

**`web_search` off and on.** On a direct Claude API pair whose capability row has `inline_tools`, using Claude's `web_search` client function (`web_search_by_call`) with a non-empty tools array, turning `web_search` on or off goes inline like any client tool (`tool_addition` by value or by name, `tool_removal` by name), keeping the tools array and cached prefix (`tools added: web_search` or `tools off: web_search`). Everywhere else (gateways, where `inline_tools` is a trial; Claude's server-tool `web_search_20250305` form; non-inline Claude models; Gemini; OpenAI; or an empty tools array), a flip that changes the tools array rebuilds once at the tool moment like any rebuild above: the array follows the flag, the deferred set and its flags stay as they were, the line reads `tools off: web_search · cache rebuilt (tools)` (or `tools added: web_search · …`), and the one event, record and hook name it. A rebuilding flip off carries the note `Tools turned off: web_search.`; a flip on adds none, since the array says it. A flip where the pair sends no search either way (no native search there, refused, or turned off for the endpoint) only sets the flag: nothing is marked, logged, emitted or noted, the answer is next turn with the cache kept, and a later switch to a pair that can send it brings it with that switch's own change.

**The first tool.** A session whose tools are all held (every tool off at start, or `--tools none`) still holds them, so it can switch: its first tool takes the empty-array rebuild above and runs with its host bound. With no workspace such a session still starts without tools.

Nothing else waits for the next session but a tool no plugin defines (a plugin left out at start, or whose start failed, defines none) and a new or changed tool of a plugin installed while Wisp runs, where inline tool changes aren't established (`docs/plugins.md`, "Installed, updated or deleted while Wisp runs"): such a change answers `next session` when nothing else in it applies, the tool's catalog entry says `waits`, and its row in `/config` reads `pending · next session`. A session that only re-states what the view lost (after a compaction, a rewind or a resume) sends the blocks or note again with no `ToolsChanged` and no `tools-changed` hook; when a native compaction kept the additions but dropped their sentences, that system message holds only the sentence text, which the API takes with no beta ("Sending text system messages does not require a beta header"), and the request layout check allows a text-only system message only right after a user message. A tool turned off also leaves the `<environment>` block the next time the block is sent (after a compaction), so bash's `Shell for the bash tool` line goes with bash; the block already sent stays as it is. jsonl sessions and fresh child agents never switch.

A documented pair is established without a trial: Anthropic's direct API, or the ChatGPT subscription for capabilities named by its exact-ID lists. Every capability later added to a subscription list therefore needs its own live check on that connection first; OpenAI rows do not enable `deferred_tools`.

#### Tools off at start: declared deferred

A full-screen root session declares each installed client tool that is off at its start and that it could turn on, except a tool its manifest holds (and never `report`, which a root never gets) in the `tools` array with `"defer_loading": true`, sorted with the rest, so turning it on later needs no definition in the conversation: a `tool_addition` by name surfaces it, and the API expands it inline, so the cached prefix is kept. A child never defers, a resumed one included: it never logged a deferred set, so the copy it adopts has none. The deferred set is chosen once, from the tools held off when the session starts that `Registry::on_tools_with` would turn on for some `tools` list, and belongs to the session's prefix like the array itself:

- **Per pair.** A pair defers only where its capability row has `deferred_tools` (copied from the tool search page's model list, never inferred from a model name) and `inline_tools`, and its inline tools state is documented (the Anthropic direct API, or the ChatGPT subscription for its listed, live-checked capabilities) or proven, and deferral hasn't fallen back. A Claude gateway or subscription pair never defers: a fresh session starts its inline tools state unknown, and when its trial passes in a session with a deferred set, the hold is logged as a `deferred_tools` record (`fallen_back`, with no `FeatureStateChanged`) that a resume, a start-over and a switch back to the pair all keep, so its array never changes mid-session or across a resume. On any other pair the deferred entries are left off the wire, and those tools count as undeclared there; switching back sends them again. A tool turned on by value on a pair that doesn't defer is sent by name on one that does when the definition is the deferred one, so it is never declared twice, and by value when it differs (an upgrade), so the model sees the new definition; a tool of the set turned on by name, on a pair that defers, goes by value with its definition on a pair with `inline_tools` that doesn't defer (after deferral fell back, or a switch to such a pair), while history keeps the by-name addition.
- **The array as sent.** `session_started.tools` and `ToolsChanged` name only the tools declared normally, while `tools_sha256`, the prefix key's tools digest and every copy that reuses the request (keep-warm, the compaction forks, the summary request) cover the array with its flags. With nothing deferred the bytes and digests are exactly those of a session without the feature.
- **Rules.** At least one client tool stays non-deferred, or nothing is deferred. The tools breakpoint, when it goes on a tool, goes on the last non-deferred one. Provider-native tools and the `web_search` runner are never deferred. A tool turned off mid-session stays declared as it was and is refused. "Declared means sent" gains "surfaced means sent": a compaction or a rewind that drops the addition re-surfaces the tool by name at the next turn.
- **Counting.** `count_tokens` and `/context` never see `defer_loading`: they count the non-deferred tools plus each surfaced one as a plain definition.
- **Compaction.** A native compaction block whose `tool_changes` declare a deferred tool by value with its deferred definition (made on a pair that didn't defer) is sent with that entry as a reference, the rest of the block as it came.
- **Refusal.** A request refused for `defer_loading` is resent once without the deferred entries, and deferral falls back for that pair for the session (`FeatureStateChanged` with `feature: deferred_tools`, and a `deferred_tools` record, `docs/session-log.md`).
- **Rebuild.** A rebuild ("When a change can't go inline", above) keeps the deferred set, minus the tools its array now declares normally, so a deferred tool it turns on leaves the set; it never defers a tool the old array declared normally, and never chooses the set again. Its `tools_changed` copy holds the kept set.
- **Logging.** `session_started` and `session_resumed` hold the deferred set in `deferred_definitions`, beside `tool_definitions`, whether or not the starting pair defers. `tools_on` names a deferred tool only while it is on, like any tool; one that is off is declared only through `deferred_definitions`.

Children, jsonl sessions, `--tools none` and sessions that aren't full-screen defer nothing. What a deferred declaration costs is in `docs/pricing.md`, "Tool changes in a running session".

Each applied change emits `ToolsChanged` (`via: inline`, `turned_off` or `rebuild`, with the cache effect), logs `tools_changed` (`docs/session-log.md`), fires the `tools-changed` hook point, and draws one muted line in the TUI: `tools off: show_diff · cache kept` (`cache kept if passed on` on a trial pair).

### Tools found during a turn

A search can make its tool hits directly callable before the next model step.
It never edits the initial tool array or rebuilds the cached prefix.
`tools_after_results` in a Claude model's row is independent of `inline_tools`:
the latter covers changes at turn start, not proof of this position.
The corresponding OpenAI lists are `subscription_tools_after_outputs` and
`api_tools_after_outputs`. An id needs a documentation source or a successful
live check for this position before it joins its list.

On an eligible full-screen root session, the result says `call it`. Claude gets
one system message after the complete batch of tool results, and after any
steer delivered with them: an addition by name for a deferred declaration, or
by value otherwise. OpenAI gets an
`additional_tools` item after the outputs. A definition sent by value is limited
to 16 KiB; only its description may be shortened, never its parameters. If the
parameters alone cannot fit, that hit stays callable through `use` instead.

All eight documentation-eligible Claude `tools_after_results` fields are false,
and both OpenAI after-output lists are empty. No model loads a found tool after
results until a passing live run fills its row; until then every model runs
found tools through `use`. The ignored tests
`live_tool_changes::live_found_tool_after_claude_results` and
`live_tool_changes::live_found_tool_after_openai_outputs` are connection-specific:
the Claude test may prove its exact model on the direct API; the OpenAI test
checks the project's gateway only, and a pass fills no official API or
subscription row. Those lists require passing runs on their listed endpoint.
A child or a jsonl session keeps `use` even on a proven model.

A trial endpoint's refusal uses the existing inline-tools resend and fallback;
a direct call then says `this tool isn't loaded; run it with use`. `use` still
runs it with its own validation, hooks and gate. No later turn rebuilds merely
because search found it.

Found tools stay loaded until switched off. Compaction restates a definition
only when the retained view no longer offers it. Rewinding before discovery
forgets that discovery, including after resume. Resume keeps accepted additions
exactly, even when the reply failed or was cancelled; a discovery whose next
request was never accepted is offered once at the next accepting step.

### Choosing the starting tools

`preload = ["core"]` is the default: all Wisp tools that are on start loaded.
`preload = ["none"]` starts only `search` and `use`, while they are on. A list
such as `["bash", "view_file"]` starts those tools and their followers; `core`
may appear in a list, while `none` must stand alone. `/config` calls the row
**Start with** and offers `core` and `none`; lists are written in `config.toml`
or a preset. Children always keep `report`; a child without its own preload
uses the session's preload over its parent's permitted tools, including held ones.

A permitted client tool left out by preload stays held. Search returns its parameters,
and `use` runs it with its own row, hooks, time limit and gate, on every model.
A tool that is off is neither found nor run. A resumed chat keeps its loaded tools;
tools held by the current preload stay held. Tools the current preload no longer
holds arrive at the first message, by value where inline changes are supported,
or by one announced cache rebuild otherwise. For example, returning from `none`
to `core` brings the other permitted tools into a resumed root chat.
The `web-search` plugin owns Claude's client implementation; its native-family
runner is outside loaded and held tools. The selection rules stay the same, and
a list may name it, but `none` leaves it out; it cannot be found or run with `use`.

### Finding tools and reading entries

The bundled `search` plugin provides `search` and `use`, on by default.
`use` follows `search` and cannot be selected on its own. A saved `tools` list
that leaves `search` out keeps both off; Wisp never rewrites that exact list.
On a pair that defers tools, both are declared deferred like other off tools.
With that saved list and `preload = ["none"]`, the chat starts with no tools and
cannot find any until search is permitted again.
A chat from before search was bundled gains both tools at its first message:
inline by value where supported, otherwise with one announced cache rebuild.
With search on, one fixed
instruction tells the model to look before working around a missing tool or
saying it cannot do something.

`search` takes `query`, optional `kind` (`tool`, `skill`, `document`) and optional
`limit` (five by default). It searches the current agent's held tools and source
entries. A tool the user turned off is not offered. Results name their kind and
full name, summarize the entry and say what to do next. Tool results include the
parameter schema and say `run it with use`; text entries say `read it with use`.
The transcript row is `Searched "create issue"`, with counts such as
`1 tool · 1 skill`, or `nothing found`.

`use` takes `name` and, for a tool, optional object `input`. The kernel unwraps
a tool call before preparation: its own display, time limit, hooks and gate apply.
History still holds the model's original `use` call. Invalid tool input returns
the parameters for a retry. Opening a skill or document returns its owner's text;
the row says `Read skill` or `Read document`, with its estimated token count.

The cached index is gathered at start and refreshed at a turn opening or after a completed,
uncancelled tool call when a source marks it changed. Draft live document sources are instead read on lookup in the current caller's read-only scope. Refused lookup targets do not appear in new previews or compaction ledgers. This does not change provider
declarations or the cached system prefix. Held server tools follow a listing before
the next step; a child follows only the servers present when it starts or resumes. Shared server-off
filters apply to every agent's lookups. Duplicate names are resolved
by kind (tool, skill, document), then stable source order, with a problem for the
discarded entry; a source's tool entry counts only for a held tool, the owner's replacing the built one. Search ranking is in the plugin, not the kernel. A found tool can load mid-turn where the pair supports it, without changing any
earlier request bytes; `use` runs a held tool without changing the request prefix.

The `chat` plugin's `rename_chat` tool is held too: search finds it when the user asks to rename this chat, and `use` runs it without changing the request prefix. `/rename` needs no search.

### Turning tools off from the chat

The search plugin's third tool, `manage`, is held: it is enabled but never in the
start array or the deferred set, so it costs nothing until `search` finds it. It
turns a tool, skill or server off in this chat, or back on, from the next message, by
changing this chat's `turned_off` list (or, for a tool the `tools` list leaves out,
this chat's `tools`), so the switch goes through the tool moment above. Turning off
`search`, `use` or `manage`, or turning on what the settings have off, asks on the
question card; `web_search` and an `on` that would rebuild are refused
(`docs/search-first.md`). A saved `turned_off` name is left out of the start set,
and a `use` of a listed name answers `… is in Turned off; take it out in /config to use it`.
For a server, `add` and `remove` change the saved server list as `/mcp` does.
They need a shell tool, loaded or held, or the main chat's one-call approval.
An add starts sign-in when needed, showing its link to the user, never the model.

### Resuming a session

A full-screen root session resumes from its logged prefix: the system prompt and tool definitions of the latest whole copy in the log (`session_started`, or the latest `session_resumed` or `tools_changed` that holds `system_prompt`; `docs/session-log.md`). Resume adopts that copy when its `system_prompt` hashes to the logged `system_prompt_sha256` and its definitions, with the server tools of the pair the next request uses, hash to the logged tools digest. A copy the redaction changed, a log without definitions, a pair whose tools can't be computed, or a copy whose digest doesn't match takes the old path: this run's build, with one rebuild when it differs. Log masking changes content strings, never typed record tags, enum strings or keys; values shorter than three non-whitespace Unicode characters are not masked (`docs/session-log.md`, "What is never logged").

After adopting, the session seeds its tools from the ones that were on when it closed: the tools on where the logged copy was written (`session_started`'s array, or the `tools_on` of a rebuilding resume or of a rebuild's `tools_changed`), adjusted by the `tools_changed` records since (`docs/session-log.md`). A copy from an older rebuilding resume, logged without `tools_on`, seeds from the restored view's offer instead. A tool on then is on, even one this run's config turns off, so a Retry before the first opening can still run a call to it. That applied state, together with tools held by the current preload, decides what counts as a difference, excluding tools this run's settings want but its start left off, while the restored view decides what is sent: a change a compaction or a failed opening dropped from the view is restated with no event. Then it compares this run's settings with that state, judged on the pair the next request uses (a model switch still pending included), and every difference goes at the first opening as a switch would, with `ToolsChanged`, `tools_changed` and the `tools-changed` hook:

- a tool turned off in the saved config, or whose plugin was removed or failed to start, goes as a `tool_removal` (or the `core/tools` note), and a call to it gets `this tool is turned off`; a gone tool's catalog entry is neither on nor waiting;
- a tool turned on goes by value, or by reference where the adopted copy declares it deferred on that pair;
- a tool whose definition changed since the log (an upgraded plugin) goes as a same-name `tool_addition` by value, once, with no `ToolsChanged`, since what is offered by name didn't change. The definition logged is compared with this build's and with the one this build's plugins give under the logged build context (`tool_context`), described with fresh plugin instances so the running ones keep this run's context: so bash turned off since doesn't re-add `view_file`, whose text names bash, while its output follows this run's bash.

A resumed child takes the same path with a fixed set: the tools it logged that a plugin still provides, never this run's settings. So a tool whose plugin was removed leaves at its first message, as a `tool_removal` or the note, its calls get `this tool is turned off`, and a compaction's head restates the removal. The copy is checked on the endpoint the child resumes on (its own, or the root's as a fallback); a fallback whose server tools differ, or a copy that fails its check, takes the old path (`docs/agents.md`, "Resume").

**Deferred tools.** Adopting a copy adopts its deferred set too (`deferred_definitions`), never one recomputed from this run's switches, and the digest check hashes the array with the deferred entries the next pair would send. A pair whose deferral fell back is adopted when the array with the logged deferred entries matches, since its requests already leave them out. Where the digest doesn't match but the array without deferred entries does, the logged array sent none, so the pair is held: it doesn't defer for the session, and the hold is logged as a `deferred_tools` record. So a resume never starts deferring where the logged session didn't, whether the pair is a gateway whose trial passed during it or a model the capability table has marked since. A tool off now that the copy declares normally stays declared and is refused. A deferred tool whose definition changed since the log goes once as a same-name addition by value, never by reference, so the model sees this build's definition. On the old path, the set is the logged set narrowed to the tools this run holds off and could turn on, so it is never larger than the logged one, and it is empty when the log has no copy.

Where a difference can't go as a delta (a pair without `inline_tools` that would have to add a tool, or whose array holds a definition that changed since), resume still adopts the copy, and the first opening rebuilds as a live change does (above), with this run's prompt parts, the copy's declared tools kept and a gone tool declared and refused. `session_resumed` then holds no copy; the rebuild's `tools_changed` does. A continuing Retry before that opening keeps the logged prefix. After the first opening, a switch to such a pair rebuilds for a tool whose array definition is older than this build's. The resume notice doesn't name differences that go as deltas; the first message's `ToolsChanged` lines say them.

**The base prompt.** The adopted copy keeps the logged system prompt, including its base instructions. When this build's base differs from the logged one, the first resumed opening on a pair with `inline_tools` sends one text block in its system message: `Wisp's base instructions changed since this conversation began. These replace the earlier base instructions in the system prompt:`, a blank line, then the whole new base. It is logged in `turn_started.tool_message` and restated, like the tool blocks, when a compaction or rewind drops it. The base that is stated is read in order: the latest such block in view, else `system_base_sha256` (`docs/session-log.md`), else, for older logs, whether the logged prompt is this base or starts with it plus a space. A pair without `inline_tools` sends nothing and keeps the logged base until the next rebuild or session. Tool sentences and plugin sentences that changed reach a resumed session only through a rebuild or a new session.

When a session has tools:

- the request carries the sorted, canonical `tools` array, byte-identical on every request;
- the system prompt gains each tool's fixed sentence (bash: `You can run shell commands on the user's computer with the bash tool. Where you can, do each step's work in one bash script, run in a single bash call, rather than one command per call; print only what you need.`; view_file: `You can attach a file on the user's computer to your context with the view_file tool.`; show_diff: `You can show the user a change as a diff with the show_diff tool.`; show_code: `You can show the user code to copy with the show_code tool.`). `ask_user` and web search have none: the model decides when to ask from `ask_user`'s description and its own instructions;
- the session's first user message starts with an `<environment>` block, the bundled `workspace` plugin's prompt section (`docs/plugins.md`): the working directory with `$HOME` shortened to `~`, the platform, the CPUs and memory tools can use, and one line per tool (bash: `Shell for the bash tool: GNU bash 5.2`).

The platform reads `Linux (container)` when `/.dockerenv` or `/run/.containerenv` exists, whatever the kernel string says (`Linux (WSL2)`, `Linux (WSL)` or `Linux` otherwise). The `Resources:` line after it is computed once per agent build, so every request and compaction head of a session carries the same bytes; a resumed session keeps its logged block, and a resume on another machine shows the new facts from the next context window. On Linux (`crates/wisp-core/src/workspace/resources.rs`) it reads:

- the CPUs visible: the count of `Cpus_allowed_list` in `/proc/self/status`, which is what `nproc` shows;
- the memory total: `MemTotal` in `/proc/meminfo`, which is what `free` shows;
- the cgroup v2 limits: the `0::` path of `/proc/self/cgroup`, then `cpu.max` and `memory.max` in that cgroup under `/sys/fs/cgroup` and each parent up to and including the mount's top, the smallest winning, so a container whose mount shows only its own cgroup finds its limits at the top;
- the cgroup v1 limits, for each fact v2 gave nothing for (hybrid hosts): `cpu.cfs_quota_us` over `cpu.cfs_period_us` (`-1` is none) and `memory.limit_in_bytes`, in the `cpu` and `memory` lines' cgroup under `/sys/fs/cgroup/cpu` and `/sys/fs/cgroup/memory`, or at those folders' top.

A CPU quota (capped by the visible count) or a memory limit below the machine's is named as a cgroup limit, with what `nproc` or `free` show, since those are what the model would otherwise trust:

```
Resources: 24 CPUs, 47 GiB memory
Resources: 1 CPU (cgroup limit; nproc shows 24), 47 GiB memory
Resources: 24 CPUs, 2 GiB memory (cgroup limit; free shows 47 GiB)
Resources: 1.5 CPUs and 2 GiB memory (cgroup limits; nproc and free show the machine's 24 CPUs and 47 GiB)
```

CPUs are a whole number, or one decimal for a fractional quota; memory is in GiB, with one decimal under 10 GiB unless whole, and in MiB under 1 GiB. Memory figures are rounded down, the machine's as `free` prints it and a limit too, which errs on the safe side for sizing work; a limit that prints the same as the machine's figure is no limit. A fact whose file is missing or unreadable is left out, and the line too when nothing is readable. On other systems the line is `Resources: N CPUs`, from `std::thread::available_parallelism`. The reader takes its root and the cgroup file's text as inputs, so a daemon can read the tools' cgroup rather than its own.

Wisp loads the project's `AGENTS.md`, or your default `~/.config/wisp/AGENTS.md` when the project has none, into the system prompt, with or without tools (see `docs/instructions.md`). It never loads `CLAUDE.md` or other names; the model can still read one with `cat`. When a project file loaded and the project root isn't the working directory, the `<environment>` block gains a `Project root:` line after the working directory.

## Results and output files

Every call's output goes through the shared `OutputSink` (`crates/wisp-core/src/call.rs`; its wording and limits are in `crates/wisp-tool-text/src/output.rs`):

- the bytes with held keys masked are saved to `<temp dir>/wisp-<session id>/<n>-<tool>.out`, one file per call, numbered in call order. The directory is created with mode 0700 and each file with mode 0600, never adopting anything that already exists unless it is a real directory owned by you with mode 0700. Wisp doesn't delete a file that holds output while its session may still use it ("Old output folders", below);
- the model gets a cleaned copy: CRLF becomes LF (a terminal's `\r\r\n` too, since repeated `\r`s count as one), a line keeps only the text after its last `\r`, escape sequences are removed and invalid UTF-8 becomes U+FFFD. Cleaning never adds or removes a newline, so line numbers match the file;
- up to 16 KiB of cleaned output is put in the result whole. Larger output gets a head of at most 1 KiB, a tail of at most 3 KiB, the file's path, size and line count, and a marker saying which lines (or bytes) were left out;
- a call that finished without writing anything keeps no file: the empty file is removed and the call reports none, so transcript mode and the reader show no `Output saved to` (a silent command, a media view). A job still running when its call returns keeps its file even while it is empty, since the `process` tool names it;
- `ToolCallStarted.file` carries the file's path from the moment the call starts (also on the `tool_call_started` log record), so a client can follow a running call's output; a tool that saves no output, or a file that couldn't be created, gives none. A background process keeps writing the same file. The path may name a file that ends up removed when the call wrote nothing;
- one file is capped at 512 MiB; output past the cap is read but not saved, and the result says how much is missing. If the file can't be created or a write fails, the call still runs and the result says the preview is all there is.

A result reads:

```
Exit code: 1
Output: 98,765 bytes, 1,234 lines, saved in full to /tmp/wisp-<session id>/0007-bash.out
Lines 1–14:
…
[… lines 15–1,190 (94,711 bytes) not shown; read them from the file …]
Lines 1,191–1,234:
…
Working directory: ~/Projects/Wisp
```

### Old output folders

When the first agent of a `wisp` process starts, the Kit removes other sessions' output folders older than `tool_output.max_age_days` (7 days by default; `none` keeps them all, and then no folder is even looked at). It runs on a thread of its own, once per process and never for a child, so the start doesn't wait for it, and every error is ignored without a note: a folder it can't read or remove stays for the next start. It only removes a folder that:

- sits directly in the temp directory and is named `wisp-` and a session ID in its canonical form (a lowercase hyphenated UUID); `wisp-nolog-…`, `wisp-s1` and any other name are never touched;
- passes the same check as adopting an existing folder: a real directory, not a symlink, owned by you, with mode 0700. Nothing is followed through a symlink, at the top or inside;
- isn't the running session's (its ID is known before the sweep starts, so the sweep can't race the session's first output file);
- had no change, to the folder or any file directly in it, for longer than the limit, so a kept background process still writing its file keeps its folder;
- belongs to a session whose log is in this Wisp's sessions dir (`<sessions dir>/<session id>.jsonl`) and isn't open in another Wisp: Wisp takes the log's lock, the one `--resume` checks, and holds it while it removes the folder. A folder without a log there is kept, whatever its age: a `--no-log` session's, or one logged by a Wisp with another data directory, is left for the OS to clean, as before.

There is no sweep at all when this session's own log failed to open. A resumed older session keeps its transcript's previews, which are in the log, but not the saved full outputs: an `Output saved to` path in an old result may name a file that is gone. A resumed tree's children count as other sessions: a child whose log isn't open again goes like any other session's once its folder is old.

## `bash`

**Code:** the `shell` plugin, `plugins/shell/src/bash.rs` and `bash/start.rs`, over the `jobs` host interface; the job machinery under it is the kernel's `jobs` module, with the process helpers in `crates/wisp-core/src/jobs/exec.rs`. Its kernel-level tests are `crates/wisp-core/src/plugin/shell_tests/bash.rs`, run through a `KernelHost` and `KernelCall` as the agent runs them. Spec fixture: `crates/wisp-core/tests/fixtures/tools/bash.json`.

**Input:** `command` (required, non-empty, at most 256 KiB), `description` (optional: the model's five to ten words, for display), `timeout_ms` (optional), `run_in_background`, `tty` and `keep_running` (optional booleans). Any other field is invalid input. The design is in `docs/plans/interactive-exec.md`.

**Four ways to run a command:**

| | Foreground | `run_in_background` |
|---|---|---|
| No `tty` | The call waits for the exit, as below. With a limit above 2 minutes, or none, a command still running at 2 minutes is handed back as a numbered process ("Timeouts, cancel and leftovers"); with the default limit it is stopped at 2 minutes. Ctrl-B in the TUI moves it to the background sooner and the call returns its process number | The call returns within a few seconds with its process number and first output; stdin stays open for `process` |
| `tty` | Runs in a terminal (a PTY). The call also returns once the screen has been still for 10 s, since the program may be waiting for input, with its process number; 1 s when the terminal has echo off (a password prompt). ### `keep_running`: a process that outlives Wisp

Background processes stop when the chat ends: a quit or SIGTERM to its host,
for example (`docs/agents.md`, "Quitting"). Closing a hosted chat's terminal
leaves its programs running. A chat that lives in its window still ends on a
hangup. `keep_running` (with `run_in_background`) keeps one running after that, for a server or other service that must stay up, and the bash description says both. The kernel refuses it, each in one sentence: in a child agent (its processes end with it while Wisp keeps running); without `run_in_background`; with `tty` (a terminal process can't outlive the Wisp that owns its terminal, and the sentence points to a socket or port, such as a VM's serial console on a telnet port); and with `timeout_ms` above 0 (nothing enforces a limit once Wisp has exited). `process` refuses `timeout_ms` above 0 on a kept process for the same reason, and the kernel ignores a limit sent to one.

- **Output goes to a file, not a pipe.** stdin is `/dev/null`, and stdout and stderr are a private append-only `<n>-bash.log` (0600) next to the call's `.out` file in the session's output directory. While Wisp runs, a follower thread reads the log to its end, sleeps 50 ms and reads again, feeding the same queue a pipe would; it stops when that queue closes or once the job has ended and its leftovers are swept, after one last read. So the `.out` file, `process` reads and searches, live events and the 512 MiB cap work as for any job. Once Wisp exits, the program keeps writing to the log: no `SIGPIPE` and no full pipe. The log holds the output as printed, with no held-key mask, isn't capped, like `nohup.out`, and sits in the temp directory, which is RAM on tmpfs systems, so a chatty server can fill memory over days.
- **Not stopped at exit.** A kept job is spawned with tokio's `kill_on_drop` off and a member list that skips its drop-time sweep, and `Processes::shutdown` leaves it out. While Wisp runs, the model and the user can stop it as any job (`process` `signal`, `/ps` `x`); when bash itself exits, its leftovers are swept as for any job, so it is the program given that is kept, not a `server &` inside it. Without `setsid` (macOS) it runs in its own process group, and since its stdin and output aren't the terminal, the terminal's hangup doesn't reach it, so `keep_running` works on every Unix.
- **What the model and the user are told.** The result keeps the first line (`Process 3 is running in the background: python3 app.py`), drops "send it input" from the last, and adds `It keeps running after Wisp exits; its output goes to <log>. Stop it with the process tool.`, the log path shortened as output paths are (home as `~`). The `process` list shows it as `running, keeps running after Wisp exits` with `log <path>`, and `/ps` as `running, keeps running after Wisp exits`. The pid never reaches the model.
- **The goodbye's kept processes.** After the TUI restores the terminal, the goodbye ends with a short block per kept process still running, after a blank line when the goodbye shows, and alone when it doesn't (a resumed chat that ran no turn, or a `/resume` switch). It is built from protocol events only (`ProcessStarted` and, after a resume, `ProcessRestored` carry `keeps_running` and, for a kept process only, its local `pid` and `log`): the heading `Process 3 keeps running: python3 app.py`, cut to the width, then `  stop it   kill -- -4321` when the pid is known and `  output    <log>`, printed whole, when the log is known. The leader's pid is its process group, so `-4321` stops the whole group. A pid can be reused long after the process ends, so check `ps -p 4321` before a late kill; a record Wisp couldn't verify after a resume gets `Process 3 may still be running: python3 app.py` and `  check it  ps -p 4321`, with no ready-to-paste kill. In jsonl mode the events and the session log are the record.
- **After a resume** (`docs/session-log.md`, "Resume"), a kept process whose leader still runs with its logged start ticks on this boot isn't stopped: `/ps` shows `running since before the restart, keeps running after Wisp exits`, the model's notice says `Process 3 keeps running from before the restart (started with keep_running); its output goes to <log>.`, `process` can stop it (TERM, 2 s of grace, KILL) and refuses reads and waits with a pointer to `tail` the log, and the goodbye names it again. Its liveness is checked again on a `process` list, when `/ps` opens and at shutdown; one that has died ends `lost { gone }` without waking the model, and one found dead at a resume, even a later one, is named in that resume's notice as `kept running from before the restart, is no longer running`. Pressing `x` on a kept row in `/ps` drops it from the goodbye, and a kept process stopped this way, or by `process` `signal`, is waited for at exit like any stopped job (TERM, grace, KILL, within the shutdown limit). A restart's carry-on notice wakes an eligible idle agent on its first resume with unread process news, kept processes included; an agent the user stopped, or whose earlier exit's news is still unread, waits for its next turn, as after a resume by hand.
- **Limits.** A login manager with `KillUserProcesses=yes` (systemd-logind) kills even a `setsid` process when the user logs out, as it does `nohup`. WSL2 stops the distro a while after its last terminal closes unless it is configured to stay up, which ends every process in it. A kept process belongs to the chat host, not the daemon. A separate `kept` tool cgroup remains proposed.

**Metadata:** effect class `NonIdempotent`; tags `irreversible`, `external_message` and `reads_untrusted`; not parallel-safe. Recorded for the future policy, not enforced.

**Display:** `ToolAction::Run` with the command's first line as the target, and `display.title` set to the trimmed `description`, or none when it is missing or blank. `ToolMeta.writing` is `a command`.

### How a command runs

- Each call is a fresh `bash --noprofile --norc -c <script>`. `bash` is found on `PATH` once, when the tool is built; `$SHELL` is never used.
- When the script is over 64 KiB, Wisp writes the command to a private file next to the output file so it stays under Linux's 128 KiB single-argument limit, and passes `-c` a short loader that unlinks and reads it before running it through `eval` (so syntax errors read `eval:` and `set -x` lines show `++`, while line numbers stay the same). Wisp waits up to 5 s for the file to disappear (or the job to end) and removes it if still present, so it is gone before the call waits or returns and never touches stdin, the terminal or `$0`.
- The script's first line is an `EXIT` trap that writes `builtin pwd -P` (with its errors and any `set -x` trace discarded, and immune to a redefined `pwd`) to a private `<n>-bash.cwd` file next to the output file, only while that file still exists (checked with `builtin test -f`), so a command that was moved to the background or handed back, whose file Wisp has already removed, doesn't recreate it when it ends; the command, or for a script over 64 KiB the loader that reads it, follows on the next line, so bash's own error messages count the command as line 2.
- Without `tty`, stdin is empty (`/dev/null`) in the foreground and a pipe the `process` tool writes to in the background. Stdout and stderr share one pipe, so their order is the order of arrival. A dedicated reader thread feeds the output through a bounded queue (16 chunks of 64 KiB) to the call's job (below).
- **No terminal unless `tty`.** The command runs under util-linux `setsid`, which makes it the leader of a new session with no controlling terminal: `/dev/tty` fails with "No such device or address", so `ssh`, `sudo` or `gpg` can't read keystrokes or draw over the TUI. `setsid` doesn't fork here, so the pid Wisp spawned is the session and process-group id. Without `setsid` (macOS, minimal containers) the command gets its own process group instead, and can still open the terminal; `wisp doctor` says which applies.
- **Environment:** everything Wisp inherited, except `BROWSER`, `GIT_ASKPASS`, `SSH_ASKPASS`, `VSCODE_GIT_ASKPASS_EXTRA_ARGS`, `VSCODE_GIT_ASKPASS_MAIN`, `VSCODE_GIT_ASKPASS_NODE`, `VSCODE_GIT_IPC_HANDLE` and `VSCODE_IPC_HOOK_CLI`, which are stripped from every job, `capture` and MCP subprocess before caller overrides so inherited VS Code askpass dialogs and browser hooks don't fire (while explicit overrides such as `GIT_ASKPASS=... git ...` in a command still work). Every job, `capture` and MCP subprocess also gets `GCM_INTERACTIVE=never`, `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never` and `WISP_JOB=1`, and bash adds `GH_PAGER=cat`, `GIT_EDITOR=false`, `GIT_PAGER=cat`, `MANPAGER=cat`, `NO_COLOR=1`, `PAGER=cat` and `TERM=dumb` (`TERM=xterm-256color` with `tty`). Wisp never exports its own key; one you exported yourself is visible to commands, as in your own shell.

### Working directory

- The first call runs in the directory `wisp` started in (the session root).
- After each call, the trap's directory becomes the next call's directory, and a change is reported at the end of the result as `Working directory: …`.
- The directory is kept as it was when the command replaces the `EXIT` trap or `exec`s another program, and when the tracking file can't be created (the result then ends with `Working directory not tracked: <reason>`, and no trap is added).
- If the tracked directory no longer exists, the call runs in the session root, else in the home directory, else in `/`, and the result says so.
- Variables, aliases and functions never carry over.

### Timeouts, cancel and leftovers

- `timeout_ms` defaults to 120,000 in the foreground and to no limit with `run_in_background`. Any value from 0 up is accepted, `0` means no limit, and a value too large for the clock is no limit too; a negative value is invalid input. A command at its limit is stopped, and the result says so.
- **A long foreground command is handed back after 2 minutes** (`FOREGROUND_YIELD_MS`, 120,000, fixed, in `plugins/shell/src/lib.rs`; `Timing.yield_ms` lets tests shorten it). A foreground call, pipe or `tty`, whose limit is above 2 minutes or `0` returns then if its command still runs: the command becomes a numbered process with outcome `backgrounded`, reason `still_running` (`is_error` false), and keeps running under its limit, counted from its start, which `process` with `timeout_ms` changes. A limit of 2 minutes or less stops the command as before, so a call with the default limit behaves as it always did. The result reads `Process 3 is still running after 120 s, so the call returned; it keeps running in the background, and is stopped if Wisp exits before it ends.`, then the time left (`It has 780 s left of its 900 s time limit; …`, or `It has no time limit.`), the output so far, `The working directory stays …` (a `cd` in the handed-back command isn't tracked, as after a move) and the process tool pointer. Ctrl-B before then still moves it (`moved_by_user`, no time limit) and Esc before then still stops it; after the hand-back it is a background process, which Esc doesn't stop, so the TUI row reads `process 3 · running · /ps stops it` until it ends. The kernel side is `wait::hold`'s yield arm beside its quiet arm (`Held::StillRunning`, `Waited::StillRunning`). The bash description and the `timeout_ms` text say so; that changed the tools array once, so a session resumed across the change pays one cache rebuild through resume's "prompt or tools changed" path.
- **The processes a call owns** are every process in its session: found by scanning `/proc` for that session id, and each signalled through a pidfd whose session id is checked again after it is opened, so a reused pid is never hit. Until the spawned `setsid` has called setsid(), the session is empty, so the signal goes to that process through a pidfd opened when it was spawned (without pidfds, it isn't sent). The SIGKILL sweep's group kills (below) rely instead on the group ID of a live member being read just before the signal is sent. This catches children that took their own process group, such as GNU `timeout N cmd` or a `set -m` job. If `/proc` can't be scanned, the process group is signalled instead while bash is still running, or the spawned process through its pidfd when that group doesn't exist yet; if a pidfd can't be opened, the pid is signalled directly after its session is re-checked. Without `setsid`, the process group is used instead. The scans run off the async runtime; after a normal exit with nothing left over, one scan is all it costs.
- On a timeout or a cancel, every owned process gets SIGTERM. Wisp then waits until bash has exited and no owned process is left, or 2 s have passed, and sends SIGKILL to whatever remains. Each SIGKILL sweep also kills every process group it finds in the session as a whole; a group signal sent while a member is forking either reaches the new child or cancels the fork, so a fork chain within a process group cannot outrun a slow `/proc` scan. One that moves every child into a new process group or session can still escape. SIGTERM goes to each process once, never through its group as well. Wisp repeats the SIGKILL sweep until the session is empty (for at most 1 s), so a process that forks while being killed leaves no child behind. The call ends `timed_out` or `cancelled` with the output so far.
- When bash exits on its own, whatever it left running (`cmd &`, `nohup cmd`) gets the same SIGTERM, up to 2 s of grace and SIGKILL, so background jobs don't outlive their call and can still clean up (a `git` removing its lock file, say). This holds under `run_in_background` too: `server &` run that way ends at once and leaves nothing running. To keep a program running, give the program itself with `run_in_background`, and add `keep_running` for one that must outlive Wisp.
- Output is then read for at most 500 ms more, or until a cancel. A process that escaped with its own `setsid` keeps running; whatever it writes after the cut-off is dropped, even if it never stops writing. The cut-off holds while output floods in: the clock is checked after each chunk, and once it has passed, at most 16 more chunks are written: those already queued, and any the reader adds while they are being written.
- **Jobs.** A spawned command runs as a job (`jobs/exec.rs`, `start_job`): a task of its own, the pump, owns the process and the call's output sink, waits for the exit, the time limit or a cancel, stops the leftovers as above and finishes the sink when it ends. The sink sits in a slot the pump locks for one chunk at a time. After each chunk the pump yields to the runtime, so a command that floods its output can't keep the runtime from firing its timers: the exit, the time limit and the stop grace are each seen on time. `bash` registers the job in the session's `Processes` table (`jobs/table.rs`) under the call's id, waits for its end and takes the finished sink back. Live `ToolOutput` events come, as before, from the sink's own `write` whenever 8 KiB are pending or 50 ms have passed since the last one, and from the kernel's 50 ms flush of the sink's pending text. A tool that returns while its job is still running (none does yet; `bash` always waits for its job) leaves the job running: the kernel sends the pending text as the call's last `ToolOutput` and turns the sink's events off before `ToolCallFinished`, whose output summary is the sink's snapshot at that moment.
- If the kernel gives up waiting for a call (it didn't stop within the grace after a cancel or its deadline), it takes the call's job out of the table, takes its sink, aborts the pump and finishes the sink itself, so the result keeps the output so far. Aborting the pump, or dropping the table that holds the job (as when Wisp shuts down), drops the process, unless it was started with `keep_running`: every owned process gets one SIGKILL sweep at once; the repeat sweeps then run on a blocking task when a tokio runtime is available, so a drop never stalls the runtime.
- **Limit:** if Wisp is killed outright (SIGKILL, a crash, the OOM killer, or a signal it doesn't handle), or the 10 s deadline cuts a shutdown held up by a settings save, running commands keep running until the chat is resumed, which stops the ones it can prove it started; a chat never resumed leaves them running. Fixing that needs `PR_SET_PDEATHSIG` (an `unsafe` `pre_exec`) or a cgroup, which arrives with the sandbox.

### Results

- `is_error` is false whenever bash exited, whatever its code; the result's first line is `Exit code: <n>` (or `Exit signal: <n>`) and the call's facts carry `exit`. It is true for a timeout, a cancel, invalid input and a failure to start.
- A call that returns while its command still runs (background, a hand-back when quiet or after 2 minutes, a move) gives the process number; so does a finished call whose output was longer than its result showed.
- `wisp doctor` lists the bash path and version, the `setsid` path, whether `setsid` supports `--ctty` (`setsid --ctty`: `yes` or `no`, when `tty` commands are refused), and where output files go.

## `process`

**Code:** the tool itself (parsing its input, choosing what to wait for or read, and writing its result) is the `shell` plugin's `plugins/shell/src/process.rs` and `process/` (`input`, `run`, `view`, `restored`), with the key names and terminal sizes in `crates/wisp-tool-text/src/terminal.rs`. It reaches jobs only through the `jobs` host interface; the host serves it with the kernel's `Jobs` service (`crates/wisp-core/src/jobs/service.rs`), which builds each record with the kernel's `jobs` module (`jobs/write.rs`, `jobs/read.rs`, `jobs/search.rs`, `jobs/wait.rs`, the process table, its states, terminal screens, restored jobs, and the pipes, terminals and process groups in `jobs/exec.rs`). Its kernel-level tests are `crates/wisp-core/src/plugin/shell_tests/process.rs` and `process/`, and its parsing tests are in the plugin crate. The call's output is in `call.rs`, and the sentences are in `crates/wisp-tool-text/src/jobs.rs`. Spec fixture: `crates/wisp-core/tests/fixtures/tools/process.json`. Unix only; it always comes with `bash`.

It works with a process a `bash` result numbered. With no `id` it lists the session's processes (`running in a terminal`, `running in a terminal, echo off` for a password prompt, or how each ended); after a resume the list keeps the numbers from before the restart, and so does `/ps`, which marks them `before the restart`. With `id`, one call runs in a fixed order, each part optional: resize (`size`, `COLUMNSxROWS`, 20×5 to 500×200, terminals only), write `input`, press `keys`, set `timeout_ms` (a new limit from now, `0` for none), send `signal` (`interrupt` or `kill`), wait (`wait_ms` up to 600,000, ending early on `until` or `quiet_ms`), then read (`new`, `tail`, `lines`, `search` with `pattern`, or `screen`). Line numbers count from 1 over the whole output and match the output file.

- **`description`** is optional on every call, a list call and `ask_user_to_attach` included, as on `bash`: its schema text asks for five to ten words on what the call is for, on every call, describing the purpose rather than the text typed. It is trimmed, blank means none, a non-string is refused with `` `description` must be a string ``, and it changes nothing the call does. A list call takes nothing but `read` and `description` (any other field is refused with the `NO_ID` sentence, which says so).

- **The terminal line limit.** A terminal in line mode (`ICANON`, how a shell or `read` takes a line) keeps only the first 4,095 bytes of a line and drops the rest, so `input` with a longer line is refused there, naming the line's length. The check counts only this call's `input`: bytes already waiting in the terminal's line buffer (an earlier `input` with no newline, or your typing while attached) aren't counted, since Linux doesn't expose that buffer, so a line split across calls can still be cut.
- **Echo off.** Every result about a terminal whose input is hidden (echo off, line mode on) ends with `The terminal has echo off, so it is probably asking for a password. Don't type secrets yourself: ask the user for it with ask_secret, which types it into this process.` while the `secret` capability is on. With it off, the sentence is `The terminal has echo off, so it is probably asking for a password. Don't type secrets yourself: ask the user to type it (process with ask_user_to_attach).`
- **`ask_user_to_attach`** asks you to take over a terminal process yourself, with a reason of 1 to 200 characters on one line. Only `id`, `read` and `description` may come with it (``only `read` and `description` may accompany `ask_user_to_attach` `` otherwise), a pipe process is refused, and the call has no kernel time limit; the process's own limit pauses while the request is open. It waits through the question channel (below, "Tools that ask the user") and returns what happened: you typed and detached, you only looked, you declined, the process ended first, or the turn stopped. It never says what you typed.
- **The display.** `prepare` puts the parsed call on `display.view` as `ToolView::Process { id, text, keys, signal, read, pattern }`: `id` is absent for a list call, `text` is `input`, `keys` are the canonical key names (`Enter`, `F5`, `C-c`; `C-C` becomes `C-c`), `read` is the asked read (`new`, `tail`, `lines`, `search`, `screen`) and `pattern` is a search's pattern. `display.title` is the call's `description`, set by the plugin as `bash` sets its own, and left empty when the description repeats typed text: any piece of `input`, split on every control character (`\r`, `\n`, Tab, Esc and the rest) or on `\r` and `\n` alone (so a whole line with a Tab in it counts too) and trimmed, of at least 4 characters (`REPEATED_CHARS`) that the description contains, so `input: "admin\rhunter2\r"` drops `Log in as admin with hunter2`, while `y` or `no` don't count. The guard sees only its own call: a later description that repeats text typed with echo off in an earlier call, or a paraphrase, is shown, and the description stays in the model's history and the session log as `input` does. Without a title a client makes the row's words from the view. `ToolMeta.writing` is `input for a process`.
- **What was typed: `ToolCallFinished.typed`.** A call that writes `input` or `keys`, or sends a `signal`, and reaches the write or the signal, gets a verdict `Typed { echoed, unsent, signalled }`, also logged on `tool_call_finished`. A call refused before anything was sent (a pipe-only key, the line limit, an attached user, an ended process) has none.
  - `echoed`: every chunk of the write that went out (writes go in 1 KiB chunks) found the terminal in line mode with echo on (`ICANON` and `ECHO`) just before it, and at least one did. The terminal mode is read on the writer thread right before each chunk, so a program that turns echo off after the write still counts as echoed, and one that turned it off before as not. Raw-mode programs (readline in `python3` or `bash -i`, `psql`, `npm init`, `ssh`), hidden prompts (`read -s`) and pipes are never echoed, and neither is a call that only signals. A client shows typed text only when `echoed` is true.
  - `unsent`: some bytes of `input` and `keys` weren't written (the program isn't reading, the write failed, or the turn was stopped mid-write). A terminal's interrupt byte doesn't count here.
  - `signalled`: the call's signal was really sent. A terminal sends `interrupt` as the interrupt character after the input, and holds it back when the input before it wasn't all written; a pipe sends SIGINT once the write is over, whether it was short or not. `kill` counts as sent once the stop has been requested.
- **A refused call** gets `Tool::rejected_display`, which never carries `input`: the action as `prepare` would choose it, the `id` as the target, the `description` as the title under the same guard, and a `ToolView::Process` with no `text`, only the key names that are real keys (an unknown key name is dropped), a valid `signal` and `read`, and `pattern`. Refusal messages such as ``unknown key `F99` `` repeat only the name the model gave, never `input`.
- **While you are attached** ("Typing into a terminal yourself", below), `input`, `keys`, `size` and `signal` are refused with `Process 5 has the user typing into it, so input, keys, size and signals are refused until they detach; reads, waits and timeout_ms still work.` The whole call is refused before anything is applied, and the check is made under the same lock as the change, so an attach that lands mid-call never leaves part of a call applied, such as a new size without its input.

**Driving other agents.** `bash` with `tty` and `run_in_background` can start another agent's terminal interface, and `process` can read its screen, type a prompt (`input` and `keys: ["Enter"]`), wait with `quiet_ms` or `until`, and stop it. When the agent has a non-interactive mode (`codex exec --json`, `claude -p --output-format stream-json`, `wisp --output jsonl`), running that with `run_in_background` and reading through `new` and `search` gives structured lines with no screen, at a fraction of the tokens. The tool descriptions name no agent.

### Typing into a terminal yourself

In `/ps` or a process's live screen, `a` takes over a running terminal process; F12 on the main screen takes over the process the agent asked about, or else the newest one waiting for a password, and so does `1` on the agent's card (below). F12 does what the status row offers: in `/ps` or on a process's live screen it takes over the newest waiting program, and does nothing when none waits. Ctrl-] (or Ctrl-5 in a legacy terminal) does the same wherever F12 does, and is the way where a terminal keeps F12 for itself. The key is one match, `take_over_key` in `app/keymap.rs`, for the main screen and the take-over code; its names live in `wisp_render::transcript::copy` (`F12_KEY`, `BRACKET_KEY`), since the render crate draws the top line, and the help screen's key test and `no_source_writes_a_key_name_by_hand` fail when a name and the match drift. While you have taken over, every key goes to the program (Ctrl-C included), paste goes as one paste (bracketed when the program asked for it), and the terminal takes the view's size; only F12 (plain: Shift+F12 and Ctrl+F12 reach the program), Ctrl-] and Ctrl-5 are Wisp's. F12 goes back and restores the model's size: to the chat after taking over from the card or with F12 on the main screen, or to the process's screen after `/ps`; there esc goes on to the chat or to the `/ps` list the same way. The title bar reads `Process 5` with the agent's reason while its request for this process is open, else the command (`Process 5  sudo true`), and `f12 to go back` on the right; the status row reads `typing into 5 · f12 to go back`. The first take-over of a session shows `The agent that started it can read the program's output. Password prompts hide what you type. If f12 does nothing here, ctrl-] goes back too.` under the screen, wrapped, and it gives way before the cursor row in a short view. `/ps` lists every agent's programs, so you can take over any agent's terminal from any chat, and F12 in an agent's chat takes the newest waiting program of any agent, as it does in the main chat; each key goes through the program's agent, which hears what you did as main does. Outside its own agent's chat a program is named with its agent (`Process 4 of /lead/coder`, `typing into 4 of /lead/coder`, `4 of /lead/coder is waiting for a password`).

- **Your keystrokes reach only the program.** `ProcessInput` writes no log record and no event repeats it; the model hears only `You typed into process 5 (the user attached to it).` once after you detach, and the transcript adds `⎆ You typed into process 5 · Install the package`, naming the process by the description of the `bash` call that started it when it had one (`⎆ You typed into process 5` otherwise), never by its command. Attaching only to watch says nothing.
- **The time limit pauses** while you are attached, and ends that happen while you drive, or within 2 s of your last input, start no wake turn, except for an agent that waits on that process to report (`docs/agents.md`), which wakes and reports.
- **Ending:** the process ending, or the client disconnecting, detaches you, and a program that ends while you have taken over goes back like F12: after taking over from the chat or the card the view closes by itself, and after `/ps` you stay on the program's screen, marked `· ended`, where esc closes it. `process 5 exited (0)` shows in the status row then, also while a turn runs, for the program you had taken over, whichever agent's it is (`process 4 of /lead/coder exited (0)`); a program you had not taken over says so only if it is main's, and only while main is idle. After you stopped a program or the session ended, none says so.
- **Asking you:** a step-in request from the model opens a card (`? Take over process 5?`, its reason wrapped, the answers `1 Yes` and `2 No` and the keys row `1–2 choose · ↑↓ move`, with `esc to stop` in the status row under it), in its own rows, like the question card. It opens with nothing marked; `1` or F12 takes over and `2` declines, and with the message box empty ↑↓ move the mark and Enter or Space take it, as in the question card. It takes keys once you have stopped typing for 0.5 s, even with a message half-written in the chat, and while that message holds text only `1` and `2` answer (the keys row reads `1–2 choose`), and not while a full-screen view hides it (`/config`, transcript mode, the reader or the help screen); while it has them, an empty chat row isn't drawn, and a message you were writing stays in view, stepped down. A card that settled while transcript mode, the reader or the help screen hid it, or any card under `/config`, waits after the view closes until you have stopped typing for 0.5 s, the key that closed it included; a card that already had the keys when you opened transcript mode, the reader or the help screen takes them back at once, but a new request that came while the view was open waits. Once it has them, a paste of any kind is dropped: it never reaches the composer, so a password pasted there can't be sent to the model; press `1`, then paste into the process. A key the card doesn't use, or a paste, shows `1 take over, then type` in the status row until the card closes; with text in the message that is every key but `1` and `2`, Tab, ↑↓, Space and Enter included. With no request, a process waiting for a password shows `5 is waiting for a password · f12 to take over` in the status row and `waiting for a password · a take over` on its `/ps` row; it never wakes a turn.

### The `<processes>` notice

News about background processes the model hasn't heard yet (ends, the user typing into one, processes still running or ended across a restart, processes started in rewound turns) opens the next user message as one `<processes>` block, after the `Sent:` and `Context:` lines and before the typed text (on a model with `turn_form`, those two lines move into the data part after the typed text, `docs/gemini.md`). A turn Wisp starts because processes ended (a wake turn) leads the block with `The user didn't send this message; Wisp sent it because background processes ended.`; a turn that also carries mail has no wake line. After a restart, an eligible idle agent with new unread process news wakes on its own carry-on notice; that turn carries the same block, with no process-wake lead line because it carries mail.

- **Who does what.** The kernel's jobs service keeps the bookkeeping: what is news, when it was offered and when the model heard it (once a request carrying it is answered), and a failed turn's notice, which a Retry sends again verbatim. The `shell` plugin only words it: its `before-turn` hook `processes` (`in = ["core/news"]`, `retry = "replay"`, `job_news = true`, `continues = "core/processes"`) reads the typed news from `job-news.opening` and appends the block, with the sentences in `crates/wisp-tool-text/src/jobs.rs` (`item_line`, `WAKE_LINE`). Its notice has no length cap, so one for hundreds of ended jobs arrives whole.
- **Only worded news counts as offered.** If the hook is off (`plugins.shell.hooks.processes`), fails, times out or has its append refused, the news is unoffered at once and waits for the next opening that words it; nothing is lost and nothing is heard.
- **No wake loop.** Process ends start a wake turn only while a `job_news` hook is on, and a turn whose opening left news unworded stops process wakes until a new process ends; a Retry that replays its kept notice, or a continuation that opens no message, never counts as leaving it unworded. A completed turn whose notice was never kept, such as a wake whose reply was cut off with nothing in it, also stops them: the news waits for the next message. Mail wakes don't depend on the hook.

## `ask_secret`

**Code:** the `secret` plugin, `plugins/secret/src/lib.rs`. Spec fixture: `crates/wisp-core/tests/fixtures/tools/ask_secret.json`.

`ask_secret` is on by default in the TUI on Unix. It opens a secret box and types the value straight into a running process, without passing it through the model, plugins, conversation or session log. Its result says only whether it was typed; check the process to see whether it was accepted.

Once the value reaches the program, Wisp keeps it and its trimmed form in the shared in-memory list until Wisp exits, each only if it is at least 20 characters, to mask later tool results as `[redacted]`. Refused, failed or stopped typing adds nothing to that shared list. The held values are never written to disk or the session log.

Before typing, the value and its trimmed form, each with at least three non-whitespace characters, join that process's own masker until it ends, whatever the typing's outcome. Its output file, live output, screen and reads show `[redacted]` for them; shorter values are not masked. A value under 20 characters masks no other process's output or later tool results.

- Give `process` (the process number), `name` (a title up to 40 characters) and `reason` (one sentence up to 200 characters).
- For a password prompt, start the command with `bash` and `tty`, wait for its prompt with echo off, then call `ask_secret`. Wisp types the secret and presses Enter. A terminal must be in line mode with echo off; if it would show what is typed, Wisp refuses before asking and checks again while writing.
- For a command that reads standard input to its end, start it with `run_in_background` without `tty`, then use `end_input: true`: Wisp writes the secret and closes input without a line break. Otherwise it writes the secret and Enter.
- For a command that needs an environment variable or other text, start a short script the same way, read a whole line and pass it on without printing it or putting it on a command line. Leave `end_input` out so the line reader gets Enter.

The model chooses how the box shows a pasted value with `show_start` and `show_end`, each a whole number from 0 to 16, left out for 0. For a password or passphrase, leave both out: only stars show. For a key or token with a public prefix, use its length and 4 at the end; with no public prefix, use 0 and 4. The box may show less for a short secret and always shows only stars for one typed by hand. A pasted value shows its character count when it fits. Tab hides or shows ends in this box only.

Secrets must be nonempty, at most 4096 characters, one line and free of control characters. A terminal has a smaller byte limit; use a pipe for a longer value. A stop or process end while the box is open closes it without typing; an unavailable user channel refuses the call. Never ask for the value in the chat or through another agent. See "The secret box in the TUI" for its keys and input guard.

## `ask_user`

**Code:** the `ask-user` plugin, `plugins/ask-user/src/lib.rs`. Spec fixture: `crates/wisp-core/tests/fixtures/tools/ask_user.json`; result fixtures in `crates/wisp-core/tests/fixtures/ask_user/`. The design is `docs/plans/ask.md`.

**Status:** on by default in the `wisp` TUI on every platform (`--tools` without `ask_user`, or unchecking it in `/config` → Tools, leaves it out); needs the TUI. It adds no system sentence and no `<environment>` line; its description and schema were updated for non-blocking questions and `withdraw`, so a session resumed across this release pays one cache rebuild through resume's "prompt or tools changed" path, as at the tool's first release (resuming with `--tools bash,show_diff,view_file,web_search` keeps the cache and leaves the tool out). Sessions another session starts as a process leave it out (the `live-testing` skill, "Sessions started as processes"), and a child never has it (`docs/agents.md`). What tool definitions cost is in `docs/pricing.md`, "Tools". `crates/wisp-cli/tests/it/live_ask.rs` is its live test, and `crates/wisp-cli/tests/it/tools.rs` drives the real kernel through the real TUI for a pick by number, an own answer with a skip, and Esc. The plan is `docs/plans/ask-user-on.md`.

**What it does:** the model asks the user one to four multiple-choice questions without holding the turn, or withdraws its open questions (`withdraw: true`). The tool goes through world 0.4.0's `questions` host interface (`questions.post` and `questions.withdraw`, "Tools that ask the user" below); it has no provider-specific part. Asking returns at once while the questions stay on the user's screen, and the answers arrive later as plain user-role text on the mail lane (at the next step boundary in a turn, or opening a new turn when idle). Only one posted question set is open at a time; a second ask while one is open or ending is refused with `busy()`, so replacing questions is a withdraw followed by a new ask. A question reopened on resume in a session whose `ask_user` is off can't be withdrawn, though its answer still arrives. Its description tells the model to ask only for a decision that is the user's to make, to ask everything in one call as the last call of its reply, to go on with unrelated work while the questions wait, to put its recommended option first with `(Recommended)`, to make each question stand alone, since the user may see only the questions, never to add an "Other" option, and to withdraw with `withdraw: true` if the questions stop mattering.

**Input:** either `questions` or `withdraw: true`, never both (`withdraw` not `true` is refused). `questions` is an array of one to four objects, each with:

- `header` (required, non-blank): a short tag. Over 12 characters it is shown cut with `…` (the call's row target), never refused; the question itself keeps it whole;
- `question` (required, non-blank, different from the other questions);
- `options` (required): two to four objects with `label` (required, non-blank, different from the other labels of that question) and `description` (required, may be empty);
- `multi_select` (optional boolean, default false).

Any other field, at any level, is invalid input. The `minItems` and `maxItems` in the schema are hints; `prepare` enforces every limit. Fewer than two options gets `A question needs at least two options. If only one choice makes sense, don't ask: take it and say so.` Every other refusal names the rule and where it was broken, such as `options 1 and 3 of question 2 have the same label; labels must differ`.

**Row target:** for an ask, the first header (cut to 12 characters), with ` (+N)` for the other questions: `Database (+2)`. For a withdraw, `the question` with verbs `Withdrawing` / `Withdrew` / `couldn't withdraw` (`Withdrew the question`).

**Metadata:** effect class `ReadOnly`, no tags, not parallel-safe, no time limit (`timeout.max: None`), `saves_output: false`, `needs_workspace: false` and `ends_reply: true`: calls after it in the same reply are not run (reason `after_question`), and a session whose only tool is `ask_user` sends no `<environment>` block.

**Results** are plain text with no time in them; labels, questions, headers and the user's words are copied byte for byte. `wisp_tool_text::question` (`crates/wisp-tool-text/src/question.rs`) builds them from the questions and how the question ended, and holds every ending's text; the plugin uses it over the API types, and the kernel's `tool::question` wraps it over the protocol types; resume will use the same function to rebuild a result from the log.

```
The user answered:

1. [Database] Which database should the service use?
   PostgreSQL (Recommended)

2. [Features] Which features should ship first?
   - Auth
   - Search

3. [Deploy] Where will it run?
   In their own words: Fly.io, but keep a Dockerfile in the repo

4. [Name] What should the crate be called?
   Skipped. Decide yourself and say what you assumed.

Read the answers in the user's own words carefully: they may ask for something else, or ask you not to go on. Follow what they say.
```

- A single-select choice is its label on one line. A multi-select question lists each choice as a `- ` line in option order, even when only one was chosen.
- Every answer line is indented three spaces, and so is each further line of a multi-line label or of the user's own words (an empty line stays empty). The user's own words follow `In their own words: `. On a multi-select question they can come with choices, as the last line.
- A question answered with nothing chosen and nothing typed reads `Skipped. Decide yourself and say what you assumed.`
- When any answer is in the user's own words, the block ends with the caution shown above.
- An answered question is `completed` with `is_error: false`.

| How it ended | Result text | Outcome, `is_error` |
|---|---|---|
| Posted (`questions.post` → `open`) | `Asked. The user sees your questions now and their answers will come in a later message, whenever they reply. Until then, go on with any work the questions don't decide, and end your turn when nothing is left. If the questions stop mattering, withdraw them: call ask_user with withdraw set to true.` | `completed`, false |
| Already open (`questions.post` → `busy`) | `Not asked: your earlier questions are still open. Withdraw them first (ask_user with withdraw set to true), then ask again with everything you still need.` | `failed`, true |
| Withdrawn (`questions.withdraw` → `true`) | `Withdrawn: the user no longer sees your questions.` | `completed`, false |
| Nothing open (`questions.withdraw` → `false`) | `Nothing to withdraw: none of your questions is open. If the user answered them, their answers come in a message.` | `failed`, true |
| User closed a posted question (Esc / Ctrl-C) | Non-waking plain user-role note on the next request: `The user closed your open questions without answering them. Don't wait for the answers: decide yourself and say what you assumed, or ask again if you still need them.` | — |
| The user stopped the turn (blocking card) | `Not answered: the user stopped the turn while this question was open.` | `cancelled`, true |
| The user sent a message instead (older sessions only) | `Not answered: the user wrote a message instead.` | `completed`, false |
| Nobody can answer (no `UserChannel`) | `Not asked: no one can answer questions in this session. Decide yourself and say what you assumed.` | `failed`, true |
| Wisp stopped while a blocking card was open (resume's repair) | `Not answered: Wisp stopped while this question was open.` | true |

## `view_file`

**Code:** the `view-file` plugin, `plugins/view-file/src/lib.rs`, with the reading in `look.rs` and the wording in `words.rs`; the file sentences it shares with the kernel are in `wisp-tool-text`'s `files`. Spec fixture: `crates/wisp-core/tests/fixtures/tools/view_file.json` (2,093 bytes on disk: the 2,092 bytes of canonical JSON the `tools` array carries, plus a final newline). The designs are `docs/plans/attach-tool.md` (§4–6) and `docs/plans/view-file-slicing.md`.

**Status:** on by default in the `wisp` TUI on Unix (`--tools` without `view_file` leaves it out). Its system sentence is `You can attach a file on the user's computer to your context with the view_file tool.`; it adds no `<environment>` line. What tool definitions cost is in `docs/pricing.md`, "Tools". `crates/wisp-cli/tests/it/live_view_file.rs` is its live test.

- **Input:** `path` is required, non-blank, at most 4,096 bytes, with no NUL. Give at most one of `pages` (a 1-based page or closed range such as `"5"` or `"14-16"`), `seconds` (a closed whole-second range such as `"0-30"` with end greater than start), or `sheet` (a positive JSON integer such as `2`). `null` is the same as omitting an optional field. Bad values and unknown fields fail before the file is opened. The row shows the path as written (`Read`, no output).
- **Paths:** `~` and `~/` expand to the user's home; a relative path joins the working directory. Symlinks are followed; the file is opened read-only and non-blocking, and must be a regular file. The result names the resolved path, shortened with `~/`; errors name the path as written, plus `(resolved to …)` when the two differ.
- **Sniff:** the first 8 KiB decide. OLE compound files are always refused, even when the endpoint lists `application/msword`, the type `infer` assigns them. The refusal names `an OLE compound file (such as an old Office document or an installer)`. Next, valid UTF-8 with no NUL (after an optional BOM, allowing a sequence cut at 8 KiB) is read as text unless it starts with `%PDF-`. Otherwise, `view_file` normalizes five legacy `infer` names: `audio/x-wav` → `audio/wav`, `audio/x-flac` → `audio/flac`, `audio/x-aiff` → `audio/aiff`, `video/x-msvideo` → `video/avi` and `video/x-ms-wmv` → `video/wmv`. A detected type that matches `media.media-types`, including subtype prefixes ending in `*`, is attached with its original bytes and normalized type. Anything else is refused by type name, or as `application/octet-stream` when no type was detected.
- **Text:** at most 2,000 lines and 50 KiB, cut at a line end; a line over 2,000 characters ends `… (line cut at 2,000 characters)`, and invalid UTF-8 becomes U+FFFD and is counted. The rest of the file is counted up to 64 MiB or 20 s, past which the total reads `more than N lines` (N counts complete lines only). Sizes read in bytes, KB, MB, then GB from 999.95 MB, in thousands. When every line was sent but some were cut at 2,000 characters, the header never says `all below`: it reads `every line below, N cut at 2,000 characters` (`the line below, …` for a one-line file), and a part names its cut lines the same way (`lines 1–2,000 below, 3 cut at 2,000 characters`). The result is a header (`build.log: text, 9,412 lines (1.2 MB); lines 1–2,000 below (about 16,800 tokens).`), the text, and, when cut, `[9,412 lines in all; read the next part with bash: sed -n '2001,3300p' 'build.log']`. The next part's range is sized from the bytes read for the lines just sent, cut lines counted in full (three quarters of bash's 16 KiB `INLINE_LIMIT` divided by their bytes per line, between 1 and 2,000 lines), so its output fits in one inline bash result when the lines ahead are like the lines just sent. It may not: later lines can be longer, and a line over about 12 KB can't fit in any line-based `sed`, so bash then shows its usual head and tail. The estimate is bytes ÷ 2.97. The text also goes to the output sink, so the row's body, the reader and transcript mode show it, and the facts are `Part { sent, total, more_than }` and `Tokens`, with no media type. `more_than` (omitted from JSON when false) marks a count that stopped early, so the total is a lower bound; `sent` may then exceed it by one when the last sent line had no end yet.
- **Media:** after sniffing, a slice on text, the wrong type or an unsupported model is refused before reading the file body, checking the attachment size or asking the server for a count. A file over 7,500,000 bytes is then refused from its size before it is read in full, and again after. An image over the model's image edge (`ImageCaps.many_image_edge` in the capability table, 2,000 px for every described model; no check for a model without a row) is refused with a `magick … -resize` example; a header that can't be read is attached anyway. Then the endpoint counts a request holding one user message with only the media block (no system, no tools), through `media.count-tokens` with the same slice, if any. The count gets 10 s of its own (`TOKEN_COUNT_LIMIT`, so it always ends before the view's 30 s limit, and its expiry counts as a failed count); over 50,000 tokens the view is refused, and when the endpoint can't count, the count fails or takes too long (or `context.count_tokens` is off), the file is attached with its size only. The bytes are attached unchanged as a tool-result attachment ([Files that tools attach](media.md#files-that-tools-attach)), with the facts `Media`, `Bytes` and `Tokens`. A sliced result says `attached whole (read only …)` and asks the model to read only the named part. A media view writes no output, so it leaves no output file (below).
- **Errors** are results with `is_error: true` and no attachment: not found (with up to 3 similar names in that folder), a directory, a FIFO, a socket or a device, permission denied, a type the endpoint can't carry, too large, too wide, too many tokens, a slice on text, the wrong file type or an unsupported model. A stop returns `Stopped before the file was attached.`
- **Without bash** (for example `tools = ["view_file"]`), view_file shows only the first part of a long text file and can't convert or cut media, so nothing it says names bash. Its definition is a second fixed text (fixture `view_file_without_bash.json`), chosen once per session from whether `bash` is in the session's tools, never from the active model, so the cached prefix stays byte-stable. A slice the model can't read suggests omitting the slice or switching to a model that supports it, and warns that either retry sends and stores the whole file. A cut text file ends `[9,412 lines in all; only this part can be viewed in this session]`; a directory reads `… is a directory, not a file.`; a type the endpoint can't carry, a file too large, too wide or of too many tokens ends `so it can't be read in this session.` (`viewed` for the image edge and the token count). The same holds for a tool attachment the agent refuses, and for a withdrawn file's note (`docs/media.md`, "A refused attachment"): `It can't be read in this session.` for a single unsliced file, `Check the requested range and try again, or omit the slice to read the whole file.` for a single sliced file, or `It may be fine: view it again on its own.` when others went with it.

## `show_diff`

**Code:** the `show-diff` plugin, `plugins/show-diff/src/lib.rs`, on top of `wisp-diff` (`docs/diff.md`). Spec fixture: `crates/wisp-core/tests/fixtures/tools/show_diff.json` (1,655 bytes on disk, with a final newline). The design is `docs/plans/diff-rendering.md` §4.

**Status:** on by default in the `wisp` TUI (`--tools` without `show_diff` leaves it out). Turning it on changed the tools array once, at that release, so a session resumed across it pays one cache rebuild through resume's "prompt or tools changed" path, as `view_file` did. Its system sentence is `You can show the user a change as a diff with the show_diff tool.`; it adds no `<environment>` line. It is read-only, parallel-safe and needs no workspace, with a 5 s limit. What tool definitions cost is in `docs/pricing.md`, "Tools". `crates/wisp-cli/tests/it/live_show_diff.rs` is its live test.

- **Input:** `files`, 1 to 20 entries, each with `path` and `language` (both optional) and either `diff` or both `before` and `after`, plus an optional `title`. The schema has no `oneOf`: the form is checked in `prepare`, as `ask_user` does. Any other field, at either level, is invalid input.
- **`language`** is kept to its first non-blank line, trimmed, so the view's language is always one line.
- **The work happens in `prepare`:** `before`/`after` go through `diff_texts` (3 context lines), and a `diff` through the tolerant `parse_diff`. A `diff` holding several files is split, with paths from its headers.
- **Errors** (`InvalidInput`, which the model reads and can fix), each naming the file: an entry with both forms, neither, or only one of `before`/`after` (`file 2 needs either diff, or both before and after (use "" for a new or deleted file)`); a side over 10,000 lines or 512 KiB (for a `diff`, its old side is context and `-` lines and its new side context and `+` lines, summed over every file the `diff` holds, so the limit is per entry); more than 1 MiB of text in all; a `path` over 4,096 bytes or holding a NUL or a line break; and no file with any change (`nothing to show: before and after are the same in every file`, `nothing to show: no file's diff has a + or - line`, or `nothing to show: no file has a change` when the forms are mixed). A `title` is cut to its first line and 200 characters, never refused.
- **The result** is short and deterministic, and doesn't echo the diff: `Shown to the user: <path>, +3 -1.`, with `1 file` when the one file has no path and `N files` for several. Notes follow on their own lines in this order, each only when it applies: counts recounted, lines with no prefix shown as unchanged, a `diff` split into several files, and files with no changes left out. The outcome is `Completed { is_error: false }` with `Fact::Diffstat` for the whole call.
- **The display:** `ToolAction::Show` (`Showed`, `Showing`, `couldn't show`), `OutputKind::None`, and the target is the title, else the single file's path, else `N files`, cut to 80 characters. `display.view` is `ToolView::Diff { title, files }`, each file a `DiffView` with its `hunks` as `FileDiff::text()`, so the log keeps the diff byte for byte and replay never recomputes it (log schema 27, `docs/session-log.md`). `display.title` is the title when one was given (none otherwise), and `ToolMeta.writing` is `a diff`. `ToolMeta.purpose` is `Show`, so `display.purpose` is `show` on every show_diff call. A view type from a newer writer reads as `ToolView::Unknown`.
- **A refused call** gets `Tool::rejected_display` instead of the fallback: `ToolAction::Show`, with the target from the input's `title`, else the first entry's `path`, else `diff`, the input's `title` as `display.title`, and no view. Tools without it, and calls to a tool that isn't registered, fall back to `fallback_display`, whose target lists only the input's keys, such as `{id, input, keys}` (`{}` for an input that isn't an object), cut to 80 characters, and never a value. That target also names the call in the compaction ledger and in attachment refusals.

## Tool rows in the TUI

Each call is exactly one row in the transcript, drawn by `wisp-render` (`transcript/tool.rs`, laid out by `transcript/tool/row.rs`) from protocol events alone; nothing in `wisp-render` or `wisp-tui` names a particular tool. The design is `docs/plans/tool-rows.md`.

```
 ✓ Run the wisp-core tests  cargo test -p wisp-core                     exit 0 · 12s
 ✓ Read crates/wisp-core/src/cache.rs                                 412 lines · 0s
 ⨯ Lint the workspace  cargo clippy --workspace                          exit 101 · 2s
 ⠘ Build the release binary  cargo build --release                                7s
 ◦ Check formatting  cargo fmt --all --check                                  queued
 ⇗ Start the dev server  npm run dev                             process 27 · running
 ✓ Ask the planner to revise the plan  typed and pressed Enter        process 3 · 1s
 ✓ Read process 27's output  Start the dev server                                0s
 ⠘ Writing a command                                                             14s
```

- **The row:** the mark in column 1, the title from column 3 in `text`, two spaces and the command in `text.muted`, and the facts ending at the content edge: the state, then the time. Nothing is drawn under a row, except a content tool's view (below) and a closed question's question and answer rows; output lines, a failure's message and a withdrawal's reason live in the reader and in transcript mode.
- **The title** is the kernel's `ToolDisplay.title` when the tool set one (bash's `description`, show_diff's `title`), with the command (the target) muted beside it. Without one the renderer makes a title from the action and the target, with the verb in bold: `Ran cargo fmt --all --check`, `Read {path}`, `Showed {path}`, `Used {name} {target}` for any other tool. Made titles use the present tense until the call has finished (`Running cargo test`). A plugin can name its own verbs in `ToolDisplay.verbs` (`doing`, `done`, `failed`; `wisp-plugin-api`'s `Verbs`): the renderer then uses `doing` while the call runs and `done` after it, before the target alone (`Brewing tea`, `Brewed tea`), and `failed` in place of `couldn't use` on a refused call; each is cut to one line and cleaned like any plugin text. An action the renderer doesn't know (`unknown`, written by a newer Wisp) draws as `Used {name} {target}` with the call's tool name, a fact it doesn't know is skipped, and an output kind it doesn't know reads as text; a call that never ran shows its target with no verb (`◦ cargo doc  not run · the turn was stopped`), a search's in quotes (`◦ "fn main"`), or `Used {name}` when the target is empty. A process call that was refused before it ran reads as a plain use, `⨯ Used {name} 27  couldn't start`, never as typed or listed (below). A multi-line command shows its first line and `(+N lines)`.
- **Marks:** the comet while running (150 ms frames; `-\|/` in ASCII; a still `◌` with reduced motion or full repaint), `✓` done, `⨯` failed (in `error`), `◦` queued, and `◦` in `text.muted` for stopped, timed out or not run.
- **States never replace the title.** They are facts: `queued`, `not run · the turn was stopped`, `not sent`, `exit 101` or `signal 9` (in `error`), `stopped`, `timed out`, `interrupted · Wisp stopped while it ran` (a call a resumed log shows still running when Wisp stopped), `couldn't start` (invalid input, or a failure the kernel reports before the call started), `failed`, `couldn't read`, `couldn't attach`. The time is the `copy::clock` form (`12s`, `2m 00s`), and a running call's clock ticks.
- **Short rows:** counts drop first (`exit 0`, line and byte counts, a file's media facts, the reason after a state), then the command is cut and then dropped, then the title is cut at its end. The state and, when it fits, the time stay; at the very narrowest the time drops and the row is clipped at the edge.
- **While the model writes a call,** its `tool_use` block shows `Writing {phrase}` with the comet in `text.muted` and a clock from `BlockStarted`, where the phrase comes from the tool's `ToolMeta.writing` (`a command`, `a diff`, `input for a process`), or `Writing a {name} call` without one. `ToolCallRequested` turns that same row into the call's row, `queued` and then running; a row no call claims by its step's `StepEnded` closes as `◦ Writing …  not sent`.
- **Background calls** read `⇗ {title}  process 27 · running` (`waiting in terminal` for one moved there because it went quiet), and when the process ends the row takes `/ps`'s mark and words (`✓ … process 27 · exit 0`). A process restored on resume adds `before the restart`, as `/ps` does.
- **Process calls** say what happened in plain words. `N` below is the process (`process 27`), `D` the call's own description (`display.title`) and `S` the description of the `bash` call that started the process; the raw command is never on a row, an entry or the status row, only in the reader and the picker's filter.
  - **With `D`:** the title is `D`, the muted part is what the call literally did (`✓ Stop the dev server  interrupted  process 27 · 0s`), and the facts start with `N`. The act reads `typed "yes" and pressed Enter` (`typed and pressed Enter` when the text isn't shown), `pressed Up + Enter`, `, then interrupted` or `, then stopped` when the verdict says the signal was sent, `interrupted`, `stopped`, `waited`, `read the output`, `read the screen`, `searched the output for "…"`, `asked you to take over`, in the present tense while the call runs (`typing and pressing Enter`); a list call has none.
  - **Without `D`:** a made sentence naming `N` before any typed text, verb in bold, with `S` muted beside it when known: `Typed into process 27 and pressed Enter: "yes"`, `Typed into process 27`, `Pressed Up + Enter in process 27`, `Interrupted process 27`, `Stopped process 27`, `Waited for process 27`, `Read process 27's output` or `screen`, `Searched process 27's output for "…"`, `Asked you to take over process 27`, `Listed background processes`, in the present tense while running or queued. A call that only resizes or changes the time limit reads as its read. An old log's call without a view reads from its action (`Typed into process 27`).
  - **`N` appears exactly once:** in the title of a made sentence (the cell drops the finish's own `Fact::Process`), or as the first state fact beside `D`. States and their facts are unchanged (`queued`, `stopped`, `timed out`, `partly sent`, `interrupt not sent`).
  - **A refused call,** or one that never started, reads `D` with nothing muted and `N · couldn't …`, or `Used {name} 27` with `S` muted and only the error; `Used {name} 99` with nothing muted for an unknown process.
  - **`S`** is the starting call's title, linked when the process starts (`ProcessStarted`), when the starting call finishes with the process (`ToolCallFinished.process`) or when a resume restores it (`ProcessRestored`, which renames the rows already drawn); a cut keeps it.
  - **Step-in rows** name `N` with `S` muted and no `N` fact: `⎆ Waiting for you to take over process 27` (with the reason), `You typed into process 27` (also when the process ends while you type into it), `You looked at process 27 without typing`, `Declined to take over process 27`, `Process 27 ended first`; `Not answered` keeps `N` as a state. Typing yourself into a process reads `⎆ You typed into process 27 · S`, or `⎆ You typed into process 27`.
  - **The reader and transcript mode** start a process call's body with a muted line naming it, `process 27 · Start the dev server · npm run dev` (each part when known, the command whole and wrapped), then the input lines; a process call's `description` is shown only as the row's title, never again on the page.
- **Typed text** is shown only when the call's verdict says the terminal echoed it (`Typed { echoed: true }`), so a password typed into a raw-mode prompt or a pipe never reaches the screen: in quotes, a newline as `⏎` (`\n` in ASCII), the first line only plus `(+N lines)`, cut to 40 columns. Keys always show (`+ Enter`). The facts add `partly sent` when some bytes weren't written and `interrupt not sent` when a signal was asked for and not sent. The rule covers the row, the reader, the ctrl-o picker's entries and their filter, transcript mode, copying and the `[` hand-off, since all of them draw from the cell. It covers a hook's change too: a `before-tool` hook that rewrites a `process` call's `input` is drawn from the cell's verdict when it is drawn, so before `ToolCallFinished` and for an unechoed call the row and the hook's run line name the changed fields only, and an echoed call shows the value quoted and cut as above. Other calls show a rewritten input whole in transcript mode, as before. A call to a tool that isn't registered, or an old log's refused call, whose target is the input's JSON keeps only the input's keys (`{action, input}`).
- **A click on a row opens the call alone in the reader** (`docs/commands.md`, "Folded rows, the ctrl-o picker and the reader"), 400 ms after the press, or at the release if that is later, so a double-click can still select a word (a second press one column over still counts as a double-click; a click that slips by one column between the press and the release still opens the call).
- **Every call is an entry in the ctrl-o picker,** in every state, drawn as its row at the dock's width; a background job is its call's entry, with its process's state, and has none of its own (`docs/commands.md`, "Folded rows, the ctrl-o picker and the reader").
- A row whose facts describe a file (`Fact::Media` or `Fact::Part`) shows them in the pasted-image chip style with no clock: `✓ Read screenshots/home.png  image/png · 1.6 MB · ≈3k tokens`, or `text · 2,000 of 9,412 lines · ≈17k tokens` for a text view (`text · 412 lines` when every line was sent, `text · first 2,000 lines; the file has more` when the count stopped early). A `Fact::Part` always means a text view, so it is drawn with `text` and never with a media type. A single sliced attachment also shows `read only …` as a state fact after its media type.
- When the API refuses a step and its attachments are withdrawn (`docs/media.md`, "A refused attachment"), each call that attached one becomes `⨯ Read {target}  couldn't attach`; the refusal's reason is in the reader.
- The status row says `Writing {phrase} · 14s` while a call is written, then the running call's title, `Run the wisp-core tests · 7s` or a made one such as `Running cargo test · 7s` (`Working` when there is nothing to name), and its request count updates after every request (`StepEnded`). The footer adds `N requests · N tools` when a turn used tools or made more than one request.
- After the turn summary settles, an idle chat with its own background processes says `Ready · agent continues when process 3 ends`, or `Ready · agent continues when 1 of 3 processes ends`. `Ready` means you can type; the sentence counts only this chat's processes, while the existing running-count hint and `/ps` cover the whole tree. When the shell plugin's `processes` hook is known to be off, the sentence stays plain `Ready`; without catalog information it assumes the hook is on. This reports continuation on a process ending, not a wait for a server to finish.
- While a process needs your input, you are attached to one, or another chat needs you, the idle sentence stays plain `Ready`. Other action and back hints keep their place; the sentence is cut no earlier than `Ready · agent continues when`, or gives way to `Ready` if even that cannot fit. The running-count and `/ps` hints follow the sentence, then account, model and cache facts use the existing fit order, dropping cache first and account/model last. Existing notices such as a process exit still take precedence.
- A stopped or failed turn that kept steps says so: `Stopped. 2 steps were kept: the commands that ran and their output.`

Transcript mode (ctrl-o, then ctrl-o again or `Full transcript` in the picker; `docs/commands.md`) shows each call in full, and the reader shows one call the same way (its exact-log page, `docs/commands.md`): `$ ` and the whole command (for a process call, the typed text under the rule above, its keys and a search pattern), one facts line with `in {cwd}`, the outcome in words and the duration (`in ~/Projects/Wisp · exit 101 · 2s`; a refusal's or a failure's first line takes the outcome's place), the description, a view the call carries, the rest of the result (the whole result for a `Couldn't …` row; a file's first line names its resolved path), the withdrawal and its reason, `Saved copy: {path}` for each attachment the session log saved, `Output saved to {path}` (from the call's start, since `ToolCallStarted.file` names it), then the output file itself, cleaned the same way, and after it any file problem. Files are read off the render thread when transcript mode opens (the reader reads only its own call's file), with `Loading the output file…` shown until they arrive, and are dropped when it closes. A file is opened without following a symbolic link or blocking on a FIFO, and only a regular file is read. Each file shows at most its last 2 MiB of decoded text (starting at a line when one begins within 4 KiB), and all files together at most 4 MiB, newest first, which keeps opening and resizing transcript mode under 100 ms in a release build; past the 2 MiB the output starts with `… earlier output is in {path}`; past the 4 MiB, or when a file is gone, the row's last lines are shown with a note, and the path to the whole file is always shown. A running call's file (`ToolCallStarted.file`) and a background call's are read while they run too, and read once more when the call or its process ends, keeping the old text on screen until that read lands; only the reader reads them again while it follows. Rows are cached per cell by its version and the width, so a refresh rewraps only the cells that changed. Transcript mode refreshes when a call changes state, not on every output line, so a running call's clock is the one from that refresh.

A call still running when the turn ends is shown as `◦ Ran {target}  stopped`; a call that never started keeps its title with `not run · the turn was stopped`.

### The diff cell

A `show_diff` call is drawn from `display.view` alone (`wisp-render`, `transcript/tool/diff.rs`), from `ToolCallRequested` on:

- **The row:** a row like any other, over the same diff: the call's title (or the view's title in a log from before titles), or `Showed {path}` (`Showed 2 files`) without one, with nothing muted, since the file headers or the made title name the files; the diffstat from `Fact::Diffstat` is its facts, `+N` in `ok` and `−N` in `error`, with no clock. The diff is drawn under the row because show_diff declares `ToolPurpose::Show`; a `Run` call carrying a diff view, or a `Show` call whose view kind the client doesn't know, is one line with its content in the reader.
- **A header per file** when there is a title or more than one file: the path in bold `text` (`old → new` for a rename). For several files, each header has its diffstat right-aligned, coloured the same way. A one-file diff keeps its count on the title line only.
- **Lines:** the line number in `text.muted`, right-aligned in at least 4 columns, then the sign and the code. Context and `+` lines show the new number and `-` lines the old one; a hunk with no numbers (a bare `@@`) has no number column. `+` and `-` rows take `diff.add` and `diff.del` from the number to the content edge, and wrapped code hangs under the code column.
- **Between hunks:** `… N unchanged lines`, counted on the old side, when the numbers give N; `…` when they don't; nothing when the hunks are adjacent. In the scrollback only, a run of more than 6 context lines inside a hunk shows 3, `… N unchanged lines`, then 3.
- **Folding** (`FOLD_ALL_LINES`, `FOLD_SHOWN_ROWS`): the count is the diff's lines (context, `+` and `-`; not headers or notes), as logical lines rather than wrapped rows. A diff of up to 30 lines shows whole; a longer one shows its first 20 rows and `… N more lines ▸`, laying out only those rows; a click on that row opens the whole diff in the reader (`docs/commands.md`, "Folded rows, the ctrl-o picker and the reader"). N counts the lines not shown, leaving out context already reported by a shown `… N unchanged lines`; a line the fold cuts part-way counts as not shown. Transcript mode shows every file in full.
- **Copying** a selection of the cell gives the sign and the code of each line, with the code's own indentation and no number or separator column, and a wrapped line joins back into one. The notes (`… N unchanged lines`, `…`, the fold) are not copied, so a copied hunk under its `@@` line parses as the same hunk. Tabs are copied as the spaces they were drawn with. A blank context line copies as an empty line, and trailing whitespace on a line is not kept.
- **Colours:** the rows render structure first (signs, tints, numbers) and gain syntax colours and changed-word emphasis when the highlight worker reaches them. Each file is sent to the worker once as its own fence, with the language `diff-hunks <language> <path>`: the worker uses the first word that names a grammar, so a `language` it doesn't know falls back to the path's extension. The transcript keeps such cells in its code sources (`Transcript::views`) until every file's spans reach its last line, however far the transcript has moved on, so a call finished before the grammars load is still highlighted when they arrive, and so is one rebuilt from a resumed log or played by `--replay`. If the grammars fail to load, `Transcript::code_failed` empties the set and later cells stay structural. A turn's Esc never cancels a diff cell's highlighting.
- A refused call has no view: `⨯ Showed {title or path}  couldn't start`, one line, with the error in the reader. A view type from a newer Wisp draws the row alone.

### The code cell

A `Show` call whose view is a code view (`ToolView::Code { language, code }`) is drawn by the diff cell's code (`transcript/tool/diff.rs`), as one file of lines with no numbers or signs, sharing its highlighting, folding and reader page:

- **The row:** the call's title, or `Showed code`, with its line count as its facts and no clock.
- **The box** runs from the gutter, under the row's title, to the content edge, drawn in `line` with the frame glyphs every box uses (rounded in unicode, `+`, `-` and `|` otherwise). Each line sits one space inside the side, starting at column 5, and a line wider than the box wraps inside it and goes on at column 5. The code takes syntax colours from the language (sent to the highlight worker as a plain code block's language), and is plain `text` without one; rows carry no band.
- **The top border** holds the language in `text.faint` and `copy` in `text.muted`: `╭─ rust ───── copy ─╮`. A long language is cut at its end, leaving at least one rule after it. `copy` is drawn only where a click copies, the main view with the mouse on (the transcript view's `mouse`) in the `Scrollback` detail; with the mouse off, in Verbose, the reader, transcript mode, the hand-off to the scrollback and an agent's chat, the border holds the language alone, or nothing. A box too narrow for `╭─ copy ─╮` leaves `copy` out.
- **The word after a click** starts as `copying` in `text.muted` while a clipboard program runs; the previous toast's timer never clears this pending word. After the result, it follows the copy for the toast's 3 seconds: `copied` for a copy that reached a clipboard and `sent` where the toast says `Sent` (OSC 52), both in `ok`, and `not copied` in `error` for every other outcome (too large, a failed writer, no clipboard); the toast keeps its count, route and reason. Local WSL uses only the Windows clipboard, including in VS Code and when X11 or Wayland is available. One box holds a word at a time, the one clicked last: any newer copy (another click on a border, ctrl-c, a right-click, a drag release, `c` in the reader) or the toast's end puts `copy` back. A box too narrow for the longer word keeps `copy` and stays a click target. `c` in the reader doesn't mark the border (`CopyLabel`).
- **A click** anywhere on the top border (`Opens::Copy`) clears any selection and, on release, copies the code exactly, as given, through the clipboard path a selection takes, with the same toast. A press just after the window regains focus doesn't copy, and the second and third presses of a double or triple click do nothing, so the first toast stays. A click that slips by one column between the press and the release still counts as a click and copies as a still click does; a drag of two or more columns selects as usual.
- **Folding:** past 30 lines the box shows its top border, 19 lines and a bottom border that holds `… N more lines ▸`; a click on that border opens the reader, as a fold row does. In the reader the box is drawn whole and `c` copies the code (`docs/commands.md`).
- **A drag selection** copies the code it covers and never the borders, sides or padding: a blank line is kept, a wrapped line comes back whole, spaces at a wrap included, and a line's own trailing spaces are dropped; tabs come back as the spaces drawn. The click and `c` give the exact code.

## `write_todos`

**Code:** the `todos` plugin, `plugins/todos/src/lib.rs`, over the kernel's `todos` host interface (`docs/plugins.md`); its rules and wording are in `crates/wisp-tool-text/src/todos.rs`. Spec fixture: `crates/wisp-core/tests/fixtures/tools/write_todos.json` (1,390 canonical bytes). The design is `docs/plans/subagents.md` (§4, MR 2).

**Status:** on by default in the `wisp` TUI on every platform (`--tools` without `write_todos`, or unchecking it in `/config` → Tools, leaves it out); off in jsonl unless named with `--tools write_todos`. Turning it on, with the agent tools, changed the tools array once, at that release, so a session resumed across it pays one cache rebuild through resume's "prompt or tools changed" path, as `ask_user` and `show_diff` did; a saved `tools` list stays exact and doesn't gain it. With it off nothing about a request changes; with it on, the tools array gains its definition once, at the session's start. It adds no system sentence and no `<environment>` line, and has `needs_workspace: false`. Its manifest says it provides `todos`, and a rewind or a resume restores the checklist only while the tool providing `todos` is on (`Toolbox::provider_of("todos")`); resumed without it, the tools differ, so the cache is rebuilt.

- **Input:** `{ "todos": [{ "text", "status", "section"? }] }`, the whole checklist in order; each call replaces the previous list. `status` is `pending`, `in_progress`, `completed` or `cancelled`. The description says to use it for multi-step work only (three or more steps, or several things asked at once), so a simple chat spends no step on a checklist.
- **The rules,** checked by the plugin when the call is prepared (an invalid call never runs and is an invalid-input result) and again by the kernel host before it commits: 1 to 50 items (`` `todos` has 0 items; give 1 to 50 ``); each `text` a string (`` item 2's `text` must be a string ``), not blank after trimming (`` item 2's `text` is blank ``) and at most 500 characters after trimming (`` item 1's `text` is 501 characters; the limit is 500 ``); a known status (`` item 1's `status` must be pending, in_progress, completed or cancelled ``); at most one item `in_progress` (`items 2 and 4 are both in_progress; at most one item may be in_progress at a time`); no other field (`` unknown field `id` in item 1 ``). Text is trimmed.
- **Sections:** an optional `section` string names a heading; absent, `null` or blank means no section. Names are trimmed, at most 60 characters, with no control characters after trimming. The plugin and host keep trimmed texts and names, items without a section first, then each section's items together in the order the names first appear; items within each group keep their order, and names match exactly, capitals included. The row draws each name alone, bold and muted, with its items two columns in; long names wrap. No sections draws exactly as before. Adding the schema property changes the definition once across the release: resume uses a same-name addition by value or one cache rebuild on a pair without inline tools, while older calls stay valid and are never rewritten.
- **The result** is one line: `Todos updated: 2 of 5 completed. In progress: "Write the plan".`, without the second sentence when nothing is in progress.
- **The display:** `ToolAction::Other("write_todos")`, `OutputKind::None`, the target `2 of 5 completed`; the row reads `✓ Used write_todos 2 of 5 completed`.
- **The checklist** belongs to the agent. A completed call's list becomes the agent's checklist and is announced with `AgentEvent::TodosUpdated { call_id, items }` right after the call's `ToolCallFinished`, logged as `todos_updated` (`docs/session-log.md`). A call that fails, is refused, stopped or timed out changes nothing. The checklist is a projection of the log: the last unmasked `todos_updated` (`wisp_protocol::todos::checklist`), so a resume restores the latest list, and a rewind past an update restores the list from before it (empty when no update is kept), announced as `TodosUpdated` with no `call_id`. Compaction keeps the checklist, since it isn't history.

**In the TUI** (`wisp-render`, from events only):

- **The row** draws the list under its title, one item per line at the output indent: `✓` (ok) for completed, `◌` (accent, the text bold) for in progress, `◦` (muted) for pending and `−` (muted, struck through) for cancelled; ASCII glyphs `+`, `o`, `.` and `-`. A long item wraps under its own text. The list is the one that call wrote, so earlier rows keep showing earlier lists.

## Live tool test

`crates/wisp-cli/tests/it/live_tools.rs` is ignored by default because it calls the real API, with a $0.05 cap. It uses Sonnet 5.5 at low effort with `max_tokens` 1024, and the session's conversation tail uses the 5m TTL, as a short run should; the system and tools breakpoint stays at 1h. Before each turn and after each `StepEnded` it prices the worst next request. If the amount spent plus that price would pass the cap, it stops and prints why. The worst next request is:

- the previous request's whole prompt (`input + cache_read + cache_write` from the last `StepEnded`), read from cache;
- plus the most one step can add, written at the 5m rate: one 16 KiB inline result limit at 3 bytes per token (about 5,460 tokens) for each `ToolCallRequested` in the step that just ended, since a reply can ask for several calls at once, and, once per step, the previous reply written back (at most `max_tokens`, 1,024, thinking included) plus 200 tokens for the `tool_result` wrappers or the new user message;
- plus 1,024 output tokens;
- before the first request, also the prefix (the system prompt and the `bash` tool, taken as 1,500 tokens), written at the 1h rate.

Two assumptions are stated but not priced:

- the tail is read from cache; a miss would write the previous prompt again at the write rate;
- tool output averages about 3 bytes per token.

At Sonnet 5.5's rates the first request's worst case is about $0.0193. After a step with one call on an 8,000-token prompt, the worst next request is about $0.0278, so the run goes on while the spend is under about $0.0222. After a step with three calls it is about $0.055, more than the cap, so the guard stops the run whatever has been spent. The measured run cost $0.0069. No-network tests check the first request, the one-call threshold, and that three calls are refused at a spend where one call is allowed.

## Tools that ask the user

The seam lets a tool ask the user questions, ask them to type into a process, or ask them for a secret (`crates/wisp-core/src/call/user.rs`, served by `agent/question.rs`). Its users are `ask_user` (above), on by default in the TUI, `process`'s `ask_user_to_attach`, `ask_secret` (`plugins/secret`), on by default in the TUI on Unix, and `show_page`'s wait for the board's report (`screen-report.wait`); the test-only `confirm` tool (in `plugins/testkit`) proves the seam on its own.

- **Six kinds of request.** `AskRequest` is `Questions { questions, reply }`, `Attach { id, reason, reply }`, `Secret { goes, asked_by, name, reason, show, reply }`, `Report { reply }`, `Post { questions, reply }` or `Withdraw { reply }`. At most one blocking question, attach or secret request is open at a time; a second secret request is answered `Busy`, other blocking requests `Unavailable`. A report and a posted question each keep their own slot, so a blocking card can open in front of a posted question without refusing it (`docs/plugins.md`, "`screen-report`", "`questions`"). A posted question survives call end, timeout, turn end and Wisp exiting, and closes once on `Answer`, `Withdraw`, `Cancel` (in a turn, pre-turn hook or idle) or a rewind that drops it; after `Answer` or `Cancel` its slot stays ending until its letter commits to history, or reopens on resume when its letter was lost (withdrawn or masked by an interrupted rewind). An attach request writes no record, emits `AttachRequested { call_id, id, reason }`, and ends in exactly one `AttachRequestClosed { call_id, how }` (`typed`, `attached_only`, `declined`, `process_ended` or `stopped`), with the reply `Attached { typed }`, `Declined` or `ProcessEnded { typed }`. `DeclineAttach { call_id }` declines it (`no_attach_request` when none is open), and `AttachProcess` for the requested process takes it, closing at your detach or the process's end. A stop closes it as it closes a question; a steer leaves it open.
- **A secret request** has its own reply, `SecretReply { Entered(Secret), ProcessEnded, Busy, Unavailable }`, so the value can never become the plugin's `AskReply`. It writes no record and emits `SecretRequested { call_id, id, destination, asked_by, name, reason, show }` (`show` is `Ends { start, end }`, the form the model asked for, two `u8`s passed on as given since the masking function holds the limits) and exactly one `SecretRequestClosed { call_id, how }` (`entered`, `process_ended` or `stopped`) before the call's `ToolCallFinished`. `AnswerSecret { call_id, value }` answers it: with no open request for that call it is `rejected` as `unknown_id`, and a value that fails `check_secret` (one line of anything but control characters, at most `KEY_MAX` characters) as `bad_answer` with words that name no problem, and the request stays open. For a process request, the value goes through a one-shot channel to the jobs service, which types it into the process and holds it as described in the `ask_secret` section. For a server request, it goes to the server-key operation and then that server's environment and secret store, or once to the asking server's form response without storage; no event, record, result or `Debug` output holds it. A terminal process is written to only while it is in line mode with echo off, checked before the box opens and before every chunk, and a pipe process only while its input is open. A stop closes the request `stopped`; a process request closes `process_ended` when its process ends. A steer leaves either request open. A child agent never gets the command or the tool.
- **Who must answer.** An enabled tool with both `ToolMeta.asks_user` and `ToolMeta.ends_reply` set, such as `ask_user` or `ask_secret`, needs a channel: `Agent::channel_problem()` names the problem and `wisp` refuses to start such a session without one. `process` can run without a channel; an attach request returns `Unavailable`.

- **The channel.** A call's `KernelCall.user` is a `UserChannel`, which `call-context.ask` and `job.ask-attach` use. `ask(questions)` sends the questions to the kernel and waits for an `AskReply`: `Answered` with one answer per question, `MessageInstead` (never sent now; kept in the plugin contract), or `Unavailable`. `attach(id, reason)` sends an attach request the same way. A tool also waits on `ctx.cancel`, so a stop is never waited on.
- **Who can answer.** Only a client that can answer sets `Agent::with_user_input(true)`. Without it, `ask` and `attach` return `Unavailable` and nothing is shown; a root agent's calls still get the channel for reports.
- **One question at a time.** The kernel writes `question_asked`, syncs the log, then emits `QuestionAsked`. A second request from the same call while one is open is answered `Unavailable`.
- **Answers.** `ClientCommand::Answer { call_id, answers }` is checked against the open questions: one answer per question, in order; each chosen index in range, sorted and listed once; at most one choice on a single-select question, and not both a choice and the user's own words there; own words not blank. A bad answer gets `Rejected` with kind `bad_answer`, and one for a question that isn't open gets kind `no_question`; neither has an `id`, and the question stays open. A good one emits `QuestionClosed { how: answered }`.
- **Other endings.** For a blocking question, a stop (Esc, Ctrl-C or a closed command channel) closes the question `stopped`; a steer (`Send { mode: steer }`), whether already waiting when it opens or accepted while it is open, leaves it open and reaches the model after the step's results as usual, or, while a web search of the same reply is still under way, once that search has ended or been closed (see "Web search"); a call that reaches its kernel time limit, or a tool that returns while its question is open, closes it `stopped`; and every blocking `QuestionAsked` ends in exactly one `QuestionClosed`, before its call's `ToolCallFinished`. Only older sessions hold a question closed `message_instead`. A queued message leaves either kind open. A posted question closes `stopped` on Esc or Ctrl-C (never on a closed command channel, timeout or call end), `withdrawn` on `withdraw: true` or a rewind that drops it, or `answered` on `Answer`, after its call's `ToolCallFinished`.
- **Results a tool writes itself.** `ToolRun.result`, when set, is the call's result text in place of the one built from its output; Wisp's notes still follow it, and the final text is logged as `tool_call_finished.result`. Wisp doesn't cap it, so a tool that sets it bounds what it writes.
- **Files with the result.** `ToolRun.attachments` lists files the call returns beside its text. An unsliced file has raw bytes and a media type; `media.media-types` lists the types the session's provider carries. World 0.4.0 adds an optional `slice`. The kernel checks the type, any slice against that type and the active model, the 7.5 MB per-file cap and the conversation media budget before saving and sending the files after the text in the `tool_result` (see [Files that tools attach](media.md#files-that-tools-attach)). The files of a call the kernel asked to stop are dropped, whatever the tool reported.
- **Metadata.** `ToolMeta.saves_output: false` opens no output file and numbers none, and the call's `output` view is empty. `needs_workspace: false` skips the working directory: the call gets the session root as `call-context.cwd` without checking that it exists, so a deleted directory neither fails the call nor adds a note, and `ToolCallStarted.cwd` is empty; a session whose tools all have it false sends no `<environment>` block (`workspace-facts.environment` answers `none`, so the `workspace` plugin renders nothing), unless the agent has a parent or has `spawn_agent`: such an agent always gets the block, with its agent lines (`docs/agents.md`, "What a child gets"), so the agent tools keep `needs_workspace: false` and still run after the agent's directory is deleted. `ends_reply: true` means that once the call has finished, however it ended, every later call of the same reply is not run, with `Not run: it came after a question call in the same reply, so it wasn't run. Call it again if it still applies.` (reason `after_question`; a stopped turn still gives `turn_stopped`). `timeout.max: None` gives the call no deadline. Bash saves output, needs the workspace, doesn't end the reply and keeps its 600 s maximum.

### The question card in the TUI

The TUI draws a card for each `QuestionAsked` and closes it on `QuestionClosed`; it never looks at the tool's name. The card is drawn by `wisp-render` (`chrome::question`) in its own rows above the composer (whose row isn't drawn while the card has the keys and the chat is empty), and the transcript ends above it; its state and keys live in `wisp-tui` (`app/question.rs`, `app/presenter/card.rs`).

- **Keys.** It takes the keys once the chat is empty and you have stopped typing for 0.5 s (`waiting for you to finish typing` until then): while the chat holds a message you're writing, keys, pastes and Enter go to the chat, and clicks on the card do nothing. While the card or any other prompt (a picker, `/ps`, `/agents`, the usage page, the account and sign-in cards, rewind, the sidebar overlay) has the keys, an empty chat row isn't drawn; the retry choice and a focused waiting message keep it. Arrows, digits, Space and Enter pick or toggle; Tab and Shift-Tab change question (Shift-Tab doesn't cycle effort while the card has the keys); any other printable key types your own answer. Esc, or Ctrl-C without a selection, stops the turn (when one runs), closes the card (and any card put aside behind it) and puts typed answers back in the composer under one note, except a server's typed field (`docs/mcp.md`); the card shows no stop hint, since the status row shows `esc to stop` during a turn and `esc close` while idle with the card holding the keys and no overlay open. Another question opening puts a waiting card aside with its typed text and brings it back when the front card closes; a card stays open past its call and past `TurnEnded` until its own `QuestionClosed`. Ctrl-O, Ctrl-L, Ctrl-Z, mouse selection, the mouse wheel and the scroll keys (PageUp, PageDown, Ctrl-Home, Ctrl-End) keep their meaning, so the wheel and the scroll keys scroll the chat above the card, and while the card has the keys its keys row names `pgup/pgdn scroll` when the row has room. A sent answer brings the chat to its end; `/model`, `/effort` and `/endpoint` wait until the card closes, but a picker already open when the question arrives stays open and keeps the keys until you close it. A card that arrived or settled while transcript mode, the reader or the help screen hid it waits after the view closes until you have stopped typing for 0.5 s, the key that closed it included; a card that already had the keys when you opened the view takes them back at once. Several questions end on a review page, where unanswered ones are sent as skipped.
- **Small terminals.** Under 8 view rows the card shrinks: the header and the whole question, wrapped, then the focused option with its position and the keys; when rows run out the question gives way first and its last row ends in `…`. On a tight screen the full card keeps the whole question: the focused option's description gets the rows left, and the line you are typing your own answer on stays in view.
- **Status and bell.** The status row reads `Waiting for your answer` with a clock when this window saw the question asked, and in the last sixth of the cache TTL counted from the end of the last step, `cache expires in N min` or `cache expired`; a question reopened in a later window or after a restart shows the phrase alone, with no clock. When a turn ends with a question still open, the status row stays on `Waiting for your answer` with `esc close` while the card holds the keys; a later turn thinks as usual and returns to waiting when it ends. When the agent withdraws its question during a turn, the main status row shows the hint `The agent withdrew its question` until your next key. Once you answer during a turn, it goes straight to the thinking line, as after any other tool. One BEL rings when the card opens while the terminal reports the window unfocused.
- **Transcript.** While a question waits past its call, its row reads `◉ Asked {headers}  waiting for your answer` (`!` in ascii), with nothing under it. Once closed, it reads `✓ Asked {headers}`, or `◦ Asked {headers}  not answered · {reason}` (`the turn was stopped`, `you closed it` after the call finished, `withdrawn`, `Wisp stopped`, or, in older sessions, `you wrote a message instead`). Under it, once closed, each question shows muted on its own row, and under an answered one the answer after `›` (`>` in ascii), in the words of the card's review page (labels joined with ` · `, `your own: …`, `skipped`); long text wraps with a hanging indent. On a short row the reason drops first and `not answered` stays. When an answer is delivered as a question letter, one muted note per answered question (`∙ You answered {header}: {answer}`, skipped questions omitted) is drawn where the agent takes it up. A later call of the same reply keeps its title with `not run · came after a question`. Transcript mode shows every question with its options, descriptions and choices, ending with `waiting for your answer`, `withdrawn` or `you closed it` where applicable.
- **Model text is sanitised.** Headers, questions, labels and descriptions go through `wisp-render`'s sanitisation, so escape sequences show as `^[` and never reach the terminal.

The TUI offers `ask_user` by default. To see the card with no model and no cost, replay the fixture: `wisp --replay crates/wisp-tui/tests/fixtures/ask.jsonl`, type a message, let the turn finish with the card open, and answer to open the next turn. The replay answers `Answer` commands like the kernel would, refusing bad ones with `bad_answer`.

### The secret box in the TUI

A `SecretRequested` opens the same form card as a question, above the composer, for any listed process that has not ended, terminal or pipe, or for a server with no process number. It shows the request's name and reason and the destination's process number and command, or the server's name and optional command.
The server's destination wraps whole; a process's keeps its cut. A key set anew shows the server's name only.
A process request has `id: Some(number)` and no `destination`, preserving its existing event bytes. A server has no `id` and `destination: { server, command? }`; it never marks a process and closes only when the request or turn ends.
Server keys go only to that server's environment and Wisp's secret store, never a plugin, model, event or log. Type or paste; Enter sends to the process's input or the server-key operation, according to the destination, and empties the field. Tab hides or shows pasted ends only when the two forms differ at the current width; ctrl-u clears; Esc or ctrl-c stops the turn. F12 and ctrl-] do nothing here. A bad paste leaves the field unchanged and names its problem beneath it.

While the box is drawn but still waiting for a pause in typing, every key and paste is dropped and restarts the half-second wait. When a process request's process ends, either request closes, or something other than the box's own Esc or ctrl-c stops the turn, the field is cleared and the status says `Box closed; nothing was sent.` After any stop or close by itself, further keys and pastes are dropped until another half-second pause. Nothing is given back to the composer. A sent field stays closed with `sending…` until the request closes; a refused answer opens an empty field again.

## Web search

Claude's and Gemini's fixed functions call `model.ask` through the bundled `web-search`
plugin. Each search takes the tool call's row with the existing result count;
its sources accompany the final answer. A resumed Claude chat with past native
searches sends them as text and rebuilds its cache once. In-reply pairs and
toolboxes without a runner keep the native rendering rules below.

- **The common result type** (`wisp-protocol`): `SearchHit` (`title`, `url`, `snippet`, `page_age`; a native hit never has a snippet, since the API sends page content only encrypted) and `SearchOutcome`: `results` with the hits in the provider's order, or `failed` with a `SearchFailure` kind (`rate_limited`, `invalid_query`, `unavailable`, `failed`, and any later kind read as `Other`) and the provider's own `code`.
- **The native normaliser** (`provider::anthropic::search`) reads Anthropic's blocks, which stay `Opaque` and are sent back byte for byte, `encrypted_content` and `encrypted_index` included:
  - `search_call` gives a `web_search` `server_tool_use` block's id and query;
  - `search_result` turns a `web_search_tool_result` into a `SearchOutcome`. `too_many_requests` is `rate_limited`, `invalid_tool_input` and `query_too_long` are `invalid_query`, `unavailable` is `unavailable`, and every other code is `failed`. The code is kept only when it is at most 64 characters of `a`–`z`, `0`–`9` and `_`. A shape it doesn't know (content that is neither a list of `web_search_result` hits nor a `web_search_tool_result_error`, an item of another type, a hit without a `url`) is `failed` with no code, never a guess. A result block without a `tool_use_id` pairs with no call, so `search_result` gives nothing for it, and the block is still sent back unchanged. An empty list is a search with no results;
  - `cited_sources` lists a text block's `web_search_result_location` citations, one per distinct `url` with its `title`, in order of first citation.
- **Events**, emitted by the kernel when a search block finishes streaming (`SearchStarted`, `SearchEnded` done, `Citations`) or when it closes a search (`SearchEnded` unfinished), each tagged with `step` and `attempt` (the step's `Retrying` events before it, so a client can drop a discarded attempt's rows): `SearchStarted { call_id, query, action }` (`action` is left out for a search, else `open_page`, `find_in_page` or `other`; `docs/session-log.md`, `search_started`), `SearchEnded { call_id, outcome }` where `outcome` is `done` with a `SearchOutcome` or `unfinished` with a `reason` (`stopped`, `paused`, `failed`, `refused`, `compacted`) and `possibly_billed`, and `Citations { index, sources }` for the cited text block at `index`.
- **`Retrying.resend`**: `breakpoint_limit` marks a re-send after a mid-stream breakpoint refusal, which is not a retry. Absent on every retry.
- **The organisation refusal.** `Feature::NativeWebSearch` in `FeatureStateChanged` (state `fallen_back`) says an endpoint's organisation has web search switched off; it covers every model on that endpoint. The `SettingsChanged` that follows carries `Rebuilt { reason: native_search_refused }`. During a turn it is a correction, like a rejected effort marker: the turn's footer names the rebuild and the next turn's doesn't, a pending switch keeps its own reason for the next turn, the TUI draws `web search isn't enabled for this account on <endpoint>; continuing without web search` at once, naming the endpoint from the `FeatureStateChanged` before it, and a pending settings answer stays paired with its own `SettingsChanged`. Between turns it is an ordinary rebuild, noted at once.
- **Paused replies.** A reply that stops with `pause_turn` is committed as it is, and the next step's request ends with it, so the API continues it; nothing is added after it. The provider sets the continuation limit: at most 5 in a row by default, after which a sixth pause closes its tail (`Unfinished { paused }`) and the turn carries on as if the reply had ended. Gemini searches use ordinary tool calls rather than pauses.
- **The steer hold.** While the tail is live (the last reply is paused, or holds a search with no result and the step's results end the history), a waiting steer is held, since a message after an unanswered `server_tool_use` is refused by the API. It is delivered once the search ends or the kernel closes it.
- **Closing a search.** A search left without a result is closed, never run later: at a stop or at the pause cap (before `turn_ended`); when a turn ends with the tail still live (before the step boundary, so before any waiting steer, as `stopped`, or `paused` for a paused tail); and after an error end, at the next turn's start or at the session's end, as `failed`. A closure writes `tail_closed`, then a `thinking_cut` when the closed range holds thinking. Wisp refuses to send a history with an unanswered, unclosed `server_tool_use` anywhere but the live tail. A search that started before a model fallback inside a reply and has no result before it is dropped from the reply that is sent back, so the kernel ends it at the `Fallback` event with `SearchEnded` `unfinished` (`failed`, `possibly_billed`), and a result for it after the fallback emits nothing more. A search in an attempt that is never committed ends the same way when the attempt is discarded: `stopped` when the turn is stopped mid-stream, `failed` when the attempt fails (retried or not), is refused or can't be committed. A result for a call made in an earlier reply (a carried call) is held until its reply is committed; if that attempt is discarded, the held result is dropped and the later attempt or the closure ends the call. Every `SearchStarted` gets exactly one `SearchEnded`.
- **Rendering a closed call.** A closed `web_search` call is sent as the text `[web search for "q": the turn ended before its result arrived]`, and any other closed server tool as `[<name> call: the turn ended before its result arrived]`; thinking from that point to the end of the closed range is left out. When an endpoint's history is rendered as text (rule R), a search call is `[web search: "q"]`, a result is its numbered `title — url` lines, `failed: code`, or `no results` for an empty list, and cited text is plain text.
- **A refused rendering.** When the API refuses a request that carries a rendered block, before any event, with a 400 `invalid_request_error` (as an HTTP 400, a JSON error body or a first-event error chunk) or a thinking-binding error, and no feature rejection took it, the adapter marks the error `refused: Rendering` and the step is re-sent in the next plainer form, within the same step and not as a retry: `without_thinking` leaves out the thinking of each message holding a rendered block, and sends a rendered message that holds a client tool call and uncut thinking, with the messages it pairs with, in the `flattened` text form, so a gateway finds no tool turn to refill; `flattened` turns whole exchanges into plain text, pairing a message with the messages whose calls it answers or that answer its calls, and with the paused reply before it or the continuation after it, then joining adjacent assistant messages into one text message (`[called <name>: <input JSON>]` per call, `[result of <name>: <content>]` per result in the next user message, an image as `[image]`). A context overflow never escalates. Each re-send leaves out the thinking from the first byte it changes to the end of history. A form and its cut are kept only once the API accepts the re-send (its first event), and then logged as `rendering_form` and `thinking_cut` before the step's messages; they hold for the rest of the session and never go back. If every later form is refused, the first error ends the turn and nothing changes. Resume does not restore the form yet.
- **In the TUI** (`wisp-render`'s transcript and status row), drawn only from these events:
  - each search is one row in the place of its `server_tool_use` block: `◌ Searching "query"` while it runs, then `✓ Searched "query" · 5 results`, `✓ Opened https://…` (an opened page, its URL bare) or `✓ Searched page for "pattern"` (a search in a page; only a search shows its count), `⨯ Search failed · rate_limited` (the kind, left out when it is just `failed`; transcript mode adds the query or URL and the provider's code), or a `◦ No result · …` row for each `unfinished` reason: `the turn ended first` (stopped), `the turn failed first` (failed), `paused by the provider` (paused), `web search is switched off for this account` (refused), `the context window ran out` (compacted), and `stopped while it may have been running` whenever `possibly_billed` is set. A row left open by an error end stays open, even across turns, until its `SearchEnded` arrives. The row takes the place of the newest `server_tool_use` block not yet claimed. Transcript mode lists each hit's title, URL and age. Rows show no cost; searches are in the turn's cost. A `web_search_tool_result` block draws no row of its own; another server tool's block keeps its "block this version doesn't show" row;
  - a text block that directly follows another in the same step and attempt continues the same paragraph, since Anthropic splits one sentence into uncited and cited pieces. A cited piece's `[n]` marks wait until the unit holding the piece's end is complete, and the text after the piece is held back from the stream until then. The unit is a top-level item of a list, complete once the next item has started, or otherwise the top-level block, complete once a following block has started or the cell has closed. A check runs on the first non-whitespace text after a line end, which is the earliest moment a parse can show a new block or item. Total parse work is capped at 8 times the bytes received plus 64 KiB; past that, a check runs only when the parsed copy has doubled since the last one. Each check parses only from the start of the unit holding the first waiting mark (earlier text is dropped from the copy, down to the last item's start inside a list), and each unit is judged once with all its marks inserted, so the work stays proportional to the text. Once the unit is complete, the renderer's own parse (its IR after linkifying and sanitising, guarded against parser panics) decides. If the marks join plain paragraph or list-item text, so not code, a link or a bare URL, and leave the unit otherwise unchanged (judged with stand-in numbers that don't occur in the text, so an earlier `[1]` or literal text such as `arr[1]` can't be mistaken for a mark), they go inline at the ends of their pieces, escaped so they can't form a Markdown link. Otherwise they become a paragraph right after the block (`\n\n[n]\n`), before any following text. A mark cited before any text of its block becomes a paragraph of its own before that block. An item that refuses its marks (code, a quote, a heading or a table inside it) waits for the whole list. Once one mark of a block goes below, its later marks follow, so reading order matches number order. Marks for the cell's last block at close, or cited after the cell closed, are drawn after the cell: on its last row if that row ends in plain text, else on a row of their own, spaced so they can wrap. A text block continues the previous one across events the transcript ignores (held inputs, settings and tool changes, cache diagnostics); only step and turn boundaries, a retry, or a non-text block end it. Each reply with citations gets a numbered `Sources` list (title and URL, in order of first citation) under it, drawn when its step ends. A Markdown link to a URL cited in its prose cell shows its text without the ` (url)` that follows other links, since `Sources` carries that URL; matching is by URL, so a second link to the same URL in that cell loses its URL too, while a link in another cell or to another URL keeps it. The rows render again when a citation adds a URL, apart from rows already written to the terminal's scrollback, which keep their look. Where the marks go below a block, the link still shows only its text. Reply text holds no terminal hyperlinks, so the link isn't clickable inline; its URL under `Sources` is the one to open. Titles and URLs are sanitised, kept on one line and never drawn as links. The list is transcript text, so selecting and copying the reply includes it. In the ordinary view, an address wider than a source row is shortened with an ellipsis; Ctrl+O shows it whole, so selecting and copying it there preserves the full address;
  - on every `Retrying`, the step's rows and sources from the discarded attempt are dropped (a carried call's `done` result is never sent from a discarded attempt, since the kernel holds it until its reply is committed, and a row the kernel closed as `unfinished` stays closed);
  - a re-send (`resend: breakpoint_limit`) reads `Too many cache breakpoints; sent again without one.` in the transcript, `re-send of step N: …` on transcript mode's details line, and, in the status row, a 3-second hint with the same words and never a retry count.
- **Cost**: see `docs/pricing.md`, "Web search".

## Adding a plugin

A new tool is a plugin. Follow `docs/plugins.md` and `docs/plans/plugins.md` §2: a crate under `plugins/<id>/` with its `wisp-plugin.toml` and an `impl Plugin` (its `instantiate`, `describe`, `prepare`, `run` and the rest), only the dependencies the no-privilege rule allows, a feature and one line in `crates/wisp-plugins` `bundled()` (its tools then reach `--tools`, the `tools` setting and `/config` through the catalog, each tool by its own name unless it `follows` another, as `process` follows `bash` and `list_agents`, `send_message` and `stop_agent` follow `spawn_agent`), its golden spec fixture in `crates/wisp-core/tests/fixtures/tools/` and a section here. A tool the TUI offers by default also goes into the tool list in the `live-testing` skill's line on sessions started as processes (`.agents/skills/live-testing/SKILL.md`, "Sessions started as processes"), unless it is one such sessions must leave out, as `ask_user` and `spawn_agent` are.

- **`ToolDisplay.title`:** set it when the tool's own input names the call in plain words (bash's `description`, show_diff's `title`); leave it `None` otherwise, and clients make a title from the action and the target. Never put a value there that the model meant only for the program.
- **`tool-meta.writing`** (the kernel's `ToolMeta.writing`): the phrase for the call while the model is still writing it, such as `a command` or `a file path`; the agent copies it onto `BlockStarted` as `BlockKind::ToolUse { name, writing }`. `None` for tools without one. Current phrases: bash `a command`, show_diff `a diff`, show_code `code`, view_file `a file path`, process `input for a process`, ask_user `a question`.
- **`tool-meta.purpose`** (the kernel's `ToolMeta.purpose`): `show` for a tool that exists to show the user content, carried in its display's `view`; `run` for a tool that does something. It has no default, so every tool states it: show_diff and show_code are `show`, every other built-in `run`, bash and process included. The registry maps it onto `ToolMeta.purpose`, and the agent copies that onto each call's `ToolDisplay.purpose`, refused calls included; a plugin's display has no purpose of its own, so no call sets its own; a call to a tool that isn't registered, and a server tool, get `Run`. A tool that runs something and also produces a diff stays `Run`. Clients read only `ToolDisplay.purpose`, never a tool name; it is never sent to the model.
- **`rejected_display`:** give one when the input can be named without showing values the model typed for a program; otherwise the fallback lists only the input's keys.

### MCP server tools

The bundled `mcp` plugin holds saved server definitions for `search`; `use` calls
one over the session tree's shared connection. Their names start with `mcp__` and
they are marked as reading untrusted text and using the network. Add and remove
command or HTTP servers with `/mcp`; `/mcp sign-in <name>` signs in to an HTTP server.
`manage` adds or removes a server with the same checks as `/mcp`; it requires a
shell tool or the main chat's approval. Newly added tools are held until found,
and can run in that reply. A server switched off is refused throughout the tree.
The chat window shows sign-in links and tries to open them in the user's browser,
never giving them to the model. Repeating `manage` add with the name tries again.
See `docs/mcp.md` for lifetime and failure rules.


MCP form questions carry `Question.source: Option<QuestionSource>`; `QuestionSource` holds `asked_by` and `typed` (omitted when false).
`AskedBy` is tagged by `kind`: `Server { name }` uses the configured server name; unrecognized kinds read as `Unknown` and draw no attribution line.
`SecretRequested.asked_by` is optional too, and absent on a model's secret request or a stored server key's box.
Only the kernel supplies these fields; `ask_user` and the plugin API cannot claim a server as their source.
A typed server question opens on `Type your answer`; its typed answer is shown without `Your own:`. Server form values never enter a model request.
An MCP tool's overall limit is 13 minutes: 60 seconds startup, 120 seconds server time and the question card's ten minutes.
