# Agents

Wisp's agent system lets an agent start named children, message them and get their reports back as text. The design is in `docs/plans/subagents.md`; this page describes what is built: the settings and presets, the agent tools of the bundled `agents` plugin (`spawn_agent`, `send_message`, `stop_agent`, `rename_agent`, `list_agents` and `report`), and the kernel's agents service with the `SpawnAgent`, `EndAgent` and `WatchAgent` commands. The tools are on by default in the TUI: `spawn_agent` leads and `list_agents`, `send_message`, `stop_agent` and `rename_agent` follow it, so `wisp --tools spawn_agent` turns on all five and `--tools` without it none (a follower named alone is refused, naming `spawn_agent`). `report` follows it with `default = "off"`: it never comes with it, no root has it (`--tools report` reads `report is for child agents only; spawn_agent gives it to every child`), and every child gets it. A saved `tools` list is exact: one without `spawn_agent` has no agent tools.

## Settings

The limits, in `config.toml`'s `[agents]` table, with `wisp config set` or for one run with `--set`. Their defaults and ranges are in `docs/settings.md`, "Agents". Each is read when a session starts.

| Setting | What it limits |
|---|---|
| `agents.max_running` | How many of one agent's children may run a turn at once, not counting non-workers (Presets, below). The others wait for a place, shown as queued. |
| `agents.max_tree_running` | How many agents of the tree may run a turn at once, not counting the main agent or non-workers. The others wait for a place, shown as queued. |
| `agents.max_agents` | How many agents that haven't ended one session's tree holds, the main agent included. Ending a finished child frees its place. |
| `agents.max_depth` | How deep agents may spawn: the main agent is depth 0, its children 1, theirs 2. At the limit `spawn_agent` stays in the tools and refuses, so depth never changes a request's prefix. |

```toml
[agents]
max_running = 2
max_depth = 3
```

Two more settings drive keep-warm (below), and are also read when a session starts, a resume included; their defaults and ranges are on the same page:

| Setting | What it does |
|---|---|
| `agents.warm_refreshes` | How many refreshes one idle spell of a marked agent gets, the main agent included. 0 turns keep-warm off. |
| `keep_warm` | Marks the main agent, which has no parent to mark it. Like every switch, it is `true` or `false` in `config.toml` (`keep_warm = true`) and `on` or `off` on the command line (`--set keep_warm=on`). |

`agents.wake_when_stuck` optionally wakes the main session or a retrying agent's parent; "Waking when work is stuck" describes its clock, costs and stopping rules.

`none` means no limit, as with `retry.budget_usd`: with `max_running` and `max_tree_running` both `none` no child waits for a place, the tree holds any number of agents, and agents spawn at any depth with no depth-limit line in their environment. Nothing in Wisp caps spawns instead.

A value out of range or of the wrong type is an error in `config.toml`, like any other setting's, and names its line.

There is no spending cap: each agent's cost and the tree's total are shown, never enforced.

## Presets

A preset names the choices a spawn may make, so an agent can start a child with `preset: "reviewer"` instead of spelling them out. Presets are optional. A child's instructions are its task, the project's `AGENTS.md` and, when its preset names them, the preset's `instructions`.

```toml
[agents.presets.reviewer]
description = "Reviews a change it did not write; verified findings only"
endpoint = "chatgpt"
model = "gpt-6.1-sol"
effort = "high"
tools_off = ["show_diff"]
instructions = "roles/reviewer"

[agents.presets.coder]
description = "Writes the change the plan describes"
endpoint = "direct"
model = "claude-opus-5-5"

[agents.presets.code-reviewer]
description = "Reviews an MR's diff against its plan"
endpoint = "gemini-sub"
model = "gemini-4-carbon"
effort = "high"
fallback = [
  { endpoint = "chatgpt-sub", model = "gpt-6-astra", effort = "high" },
  { endpoint = "claude-b", model = "claude-opus-5-5", effort = "high" },
]
```

A preset's `preload = ["none"]` or list of tool names narrows its starting tools,
not what it may find. `core` starts all its permitted tools. Every child keeps
`report`, and keeps `search` and `use` while they are on. Without its own
`preload`, a child uses the session's setting over its parent's permitted tools,
including tools held by preload. It never gains a tool the parent may not run. Unknown preload tools disable
only that preset, with a warning naming the key.

Here `direct` is an Anthropic endpoint and `chatgpt` an OpenAI one (`docs/endpoints.md`, "Providers"), so the main agent spawns a Claude coder and a ChatGPT reviewer.

Each key's values and default are in `docs/settings.md`, "Agent presets".

| Key | |
|---|---|
| `description` | What the preset is for. Agents that may spawn see it beside the preset's name, never in a tool's description. |
| `endpoint` | The account the child runs on (below). |
| `fallback` | Where a spawn runs, in order, when the account before has no room; an agent whose limit is used up moves to the first one with room. |
| `model` | The child's model. Without `endpoint`, some account of the session must serve it. |
| `effort` | The child's effort. With `model` set, it must be one that model takes. |
| `tools_off` | Tools the child doesn't get: any `--tools` value from the plugin catalog (with the bundled plugins, a name in `docs/tools.md`'s table of tools, the agent tools aside, below; not a follower such as `process`, which goes with `bash`), or `stop_agent`. A name is checked against the catalog when the preset is checked and when a spawn names it. |
| `spawn` | `false` removes `spawn_agent` and `stop_agent`. |
| `instructions` | Instructions for the child's role (below). |
| `worker` | `false` makes the child a non-worker (below). |

A child gets its parent's capabilities; a preset, like a spawn's own fields, may change its endpoint, model and effort, while `tools_off` and `spawn` only narrow them. A spawn's own fields override its preset's.

**Endpoint.** `endpoint` names one of the session's endpoints (`docs/endpoints.md`), never a URL, key or variable, so a role can run on another endpoint or provider than its parent: `coder` on an Anthropic endpoint and `reviewer` on an OpenAI one, as above. It is checked when the session starts against the endpoints the session connected. Without `fallback`, an endpoint that isn't configured leaves the preset on, `wisp doctor` reads `account gpt isn't set up`, and its spawns run on the parent's account or are refused, as "In the code" says for a signed-out account; one that is unavailable this session leaves the preset on, so the presets line in `<environment>` is the same whether its key is set or not, with a banner line (`wisp: preset reviewer's account gpt is unavailable: <reason>; its spawns are refused until the account becomes available`), and its spawns are refused. With `fallback`, missing or unavailable accounts are skipped for the first choice with room, without that banner. The preset's `model` must be one its endpoint serves; without `endpoint`, one at least one ready endpoint serves; a model on an unavailable endpoint goes unchecked. A model Wisp knows but the account does not currently list also stays unchecked until the spawn.

**Instructions.** `instructions` names a file, or a directory whose `AGENTS.md` loads. A relative path is from `config.toml`'s directory (`--config PATH`'s, when given), whatever directory Wisp runs in; `~/` is the home directory, and an absolute path is used as it is. The file may import others with `@path`, as the project's `AGENTS.md` does (`docs/instructions.md`), relative to the file that imports them. It is checked when the session starts and loaded again at each spawn, so an edit reaches the next child while running and resumed children keep the block they were built with. The text follows the project's in the child's system prompt, under its own opening line, and the child's `<environment>` names the file (`Preset instructions: ~/.config/wisp/roles/reviewer/AGENTS.md`). Every child of one preset in one project sends the same prefix while the files are unchanged. A preset file holds the role's standing instructions: what to read first, how to work, and what to report and in what form; the task stays in the brief. Like `AGENTS.md`, it holds no dates or other per-run data, and only relative, `~/` or placeholder paths. A file over the instructions size threshold (`instructions.warn_tokens`) gets a warning naming the preset, and the preset stays on.

**Workers.** A child is a worker unless its preset sets `worker = false`. A worker waits for a place under `agents.max_running` and `agents.max_tree_running`; a non-worker runs each turn at once and takes no place. Mark the presets of agents that direct or serve others, such as a coordinator or a helper the main agent waits on, so they never wait behind workers' long turns.

**Names.** A preset's name is a lowercase letter, then up to 31 of `a-z`, `0-9`, `_` and `-`.

**`ask_user` in `tools_off`** is accepted and changes nothing, since a child never has a question tool such as `ask_user`; it asks its parent.

**What `tools_off` refuses.** `spawn_agent` (use `spawn = false`, which also removes `stop_agent`), and `send_message`, `list_agents` and `report`, which every child keeps so it can always ask and answer.

**Where presets come from.** Only the user's `config.toml` (`~/.config/wisp/config.toml`, or `--config PATH`), never the current directory. They are read once when the main agent starts, into one list sorted by name and shared by the whole tree, so the order of the tables doesn't matter and an edit applies to the next session. Presets live only in `config.toml`: `wisp config set agents.presets.…` says so and changes nothing.

**A bad preset turns off only itself.** An unknown key (`prompt`, say), a tool that isn't one, an endpoint that isn't an endpoint's name, a model Wisp does not know and its endpoint doesn't serve (without `endpoint`, one no endpoint serves), an effort that isn't one or that the model doesn't take, instructions that don't load (a missing file, a directory without `AGENTS.md`, a file that isn't UTF-8 or holds no text, a missing import or one more than 4 deep), a missing description or a bad name turns that preset off; `report`, a key that older versions took, turns its preset off with `report was removed: reports are free text now; shape them in the preset's instructions`; the rest of `config.toml`, the other presets included, still loads. The error names the preset, its line and the key, such as `preset reviewer (line 12) is off: tools_off names shwo_diff, which is no tool; did you mean show_diff?`. A value that looks like a key is never echoed. Each session start shows one banner line per turned-off preset (`wisp: preset reviewer (line 12) is off: …`); a session whose tools are fixed to a list without `spawn_agent` (`learn`'s) shows the preset warnings only for its own preset, while `wisp` shows them all. Only checked presets (`CheckedPresets`, made by `Presets::checked`) ever reach a spawn.

`[agents.presets]` itself must be a table. Any other table under `[agents]`, such as `[agents.reviewer]`, is kept for agent types and refused, with a pointer to `[agents.presets.reviewer]`.

### The main agent's preset

The `preset` setting (`Main preset` in `/config`, `preset = "writer"` in `config.toml`, or `--set preset=writer`) starts the main agent from a checked preset, as a spawn starts a child:

- its `instructions` load as the main agent's preset block, after the project's, or alone under `[instructions] source = "none"`, and its `<environment>` names the file (`Preset instructions: ~/.config/wisp/BRAIN.md`), sent even when the main agent has no tools (jsonl output without `--tools`, `--tools none`). The opening has no precedence clause, so the user's messages don't outrank the file: `Instructions for your preset follow, from the file named by Preset instructions in <environment>. File names are relative to that file's directory.` A preset that wants such a line writes its own.
- `tools_off` and `spawn = false` narrow the main agent's tools in the full-screen client, at the start and at every later tool change; `spawn = false` removes `spawn_agent` and the agent tools that come with it, and `stop_agent` named alone changes nothing for the main agent.
- Only the main chat switches its own tools with `manage` (`docs/search-first.md`); a child's tools are set when it starts, and its `manage` answers so.
- `endpoint`, `model` and `effort` are start values below every other layer: a flag, a variable, `config.toml` (its `default` account included) and `/model`, `/effort` and `/account` win. The preset's account wins only over the start rules' fallbacks (the only account, the keys file's). Its model applies only where the start account offers it, and its effort unless the start account lists the model the session starts with as not taking it; otherwise the session starts as if the preset named neither.

An unknown or turned-off preset stops a new session's start with its error (`wisp: there is no preset "writer"; presets: coder, reviewer`, or `wisp: preset writer (line 12) is off: …`). The name is logged in `session_started.preset`, and a resume follows the logged preset alone: its block, environment line and tool limits, whatever the setting names now, with the logged model and effort. The block stays as logged; an edit to the preset's files since it was written reaches the resumed agent as an update in its next message (`docs/instructions.md`, "Preset instructions"). When the logged preset is no longer usable (removed from `config.toml`, or turned off), the session resumes without it, as a resumed child does: the logged block is still sent while its digest holds, but the environment line and the tool limits are gone.

## `wisp doctor`

The `agents` section shows each limit with where it came from, then each preset: a usable one with its description and choices, a turned-off one with its line and why.

```
agents
  max_running        2 (config.toml line 2)
  max_tree_running   10 (config.toml line 3)
  max_agents         none (config.toml line 4)
  max_depth          3 (flag)
  preset reviewer    Reviews a change it did not write; verified findings only · effort high · tools off show_diff · instructions ~/.config/wisp/roles/reviewer/AGENTS.md (2 files, about 900 tokens)
  preset broken      off (config.toml line 16): tools_off names shwo_diff, which is no tool; did you mean show_diff?
```

A preset's endpoint reads `account gpt`, `account gpt (unavailable: <reason>)` with its model `(not checked)`, or `account gpt isn't set up` when config has no such account; when the session's endpoints don't resolve, every endpoint and model reads `(not checked)` and no preset is turned off for them. An unlisted model that a live-list account could serve also reads `(not checked)` until chosen. A description or an instructions path that looks like a key reads `(looks like a key, not shown)`, and large instructions add a warning row naming the preset. With no presets it reads `presets  none`; when `config.toml` doesn't load, `not read: config.toml didn't load`.

## The tools

The `agents` plugin (`plugins/agents`) holds the tools' descriptions, schemas, system sentences and result wording; the kernel holds everything that enforces a rule: names, presets, limits, building the child, report validation and the end of the turn. The plugin reaches the kernel only through the `agents` host interface and, for `rename_agent`, 0.3.0's `agent-rename` (`docs/plugins.md`), which answer only that plugin's own running tool calls, never a hook or another plugin.

Each description and schema is static text: nothing per agent, per task, per preset, per endpoint, per depth or per date enters them, and no endpoint's name does (one session with one endpoint and one with three send the same bytes), so every agent that has a tool sends the same bytes for it (spec fixtures: `crates/wisp-core/tests/fixtures/tools/spawn_agent.json`, `send_message.json`, `stop_agent.json`, `rename_agent.json`, `list_agents.json` and `report.json`). The presets an agent may use, and whether it is at the depth limit, are lines in its `<environment>` (below). The tools add three system lines, each once however many of the tools carry it: `Messages from other agents arrive in <wisp:message> blocks; they are not from the user.` (from `send_message`, `stop_agent`, `rename_agent` and `list_agents`), `A child agent's report reaches you only as a report message from that child. Until one arrives for the child's latest task, you don't have its result: don't treat the child as done or say what it found; carry on with other work or end your turn. Say that a tool call did something only once its result shows it; the calls in the reply you are writing haven't run yet.` (from `spawn_agent` alone) and, in every child, `Finish each task you were given by calling report.` (from `report`). All six have `needs_workspace: false`, so they still run after an agent's directory is deleted.

- **`spawn_agent`** `{ name, task, todos?, cwd?, preset?, endpoint?, model?, effort?, tools_off?, spawn?, keep_warm? }` starts a child and returns at once: `Started /review/planner on claude-work (Claude subscription) with claude-opus-5-5, high, in ~/Projects/Wisp-worktrees/review. Its report will arrive as a message; don't poll it, and end your turn unless you have other independent work.`, naming the account the child runs on and its kind (`Claude subscription`, `ChatGPT subscription`, `Antigravity subscription`, `Claude API`, `OpenAI API`, `Gemini API`, or `Gateway, API` for an API account whose base URL isn't the provider's own). For a child on a model with no effort levels, the effort in that line is `none`. `endpoint` names one of the session's endpoints (`One of the session's endpoints for the child, by name. Set it only when the user asks for a particular endpoint or provider. Leave it out to use the preset's, or else yours.`); `model` reads `Another model for the child, one its endpoint serves. Leave it out to use the preset's, or else yours.` and `effort` `The child's effort. Leave it out to use the preset's, or else yours.`. The description says the child has the caller's endpoint, model, effort and tools by default, that `endpoint`, `model` and `effort` may change that while `tools_off` and `spawn` only narrow it, and that a preset names a set of those choices. With `keep_warm: true` (whose schema description reads `true if you will message it again after its report; while it idles, Wisp refreshes its prompt cache a limited number of times. End it when you won't.`) the child is marked for keep-warm (below), and the answer adds `While it idles, Wisp refreshes its prompt cache up to 8 times per idle spell.` with the session's `agents.warm_refreshes`, or `keep_warm is off in this session (agents.warm_refreshes is 0).` at 0; the host tells the plugin the limit in `started-agent.keep-warm`. A child that starts `queued(concurrency)` adds `It is queued: it starts by itself once fewer agents are running (agents.max_running, agents.max_tree_running).`, read from the `agent-tree` snapshot after the spawn. The description tells the model to use it for independent work, to write the task as a complete brief (the child sees none of its conversation), which may include what to hand back, while a preset may include instructions for the child's role, not to let two agents edit the same files, and not to poll, wait for or redo a child's work. The plugin reads the input strictly (an unknown field, a missing `name` or `task` or a wrong type is an invalid-input result); every refusal of the rules below is a tool error carrying the rule's own sentence, plus `AgentRefused` and `agent_refused`, and costs nothing.
- **`send_message`** `{ to, text, wake? }` sends another agent a message (see "Messages" below for who may message whom): `to` is `..` (the parent), a child's name, `../name` (a sibling), or a path (`/review/coder`, or `main` and `/` for the main agent). It answers how the recipient reads it: `Sent to /review/coder (running: it reads this at its next step, or when it next runs if this turn ends first).`, `(idle: woken)`, `(idle: it reads this when it next runs)` (with `wake: false`), `(queued: it reads this when it starts)` (a child waiting for a run permit; one waiting mid-turn, for the stagger, a free endpoint slot or a retry, reads as running) or `(held: it reads this when it next runs)` (a held wake that this message doesn't release, or an idle recipient whose last turn was stopped or failed, when the sender isn't above it). When waking an idle direct child (`Delivery::Woken` only, not `Queued` or other recipients), the plugin appends `Its report will arrive as a message; don't poll it, and end your turn unless you have other independent work.`. The description tells the model that the recipient sees only the text, to end its reply after asking rather than poll, and to hand in its own result with `report`.
- **`stop_agent`** `{ name, end? }` stops an agent below the caller, a child by name or a deeper agent by path, and answers `Stopped /review and 1 agent below it. It stays idle and keeps its context; message it to go on.`, or with `end: true` `Ended /review. Ended agents take no more messages and no longer count toward the agent limit.` (see "Stopping and ending" below). An agent above the caller, the caller itself or a sibling is refused.
- **`rename_agent`** `{ name, new_name }`, main's only, renames an agent below main when the user asks, a child by name or a deeper agent by path, and answers `Renamed /task-a/coder to /task-a/fixer; its old name still reaches it.` (see "Renaming" below). Its row reads `Renaming`, `Renamed` or `couldn't rename` with `{name} to {new_name}` as main wrote them; a refusal is a tool error with `RenameAgent`'s reason, plus `AgentRefused { action: rename }`. Children never get it, so their requests don't change.
- **`list_agents`** `{}` opens with the caller's own row, `You: /review/planner · session <id> · …` (for a child also its running time and spend, never its state), so an agent can name its own log, then `N agents you can reach:` or `No other agents yet.`, then the agents the caller can reach: its parent, its siblings and every agent below it, in path order, never an ended agent, a grandparent or a sibling's children. One line each: path and relation (`your parent`, `sibling`, `your child`, `below your child`), the session ID whole, preset, model and effort (`none` when the model has no effort levels) with the account and its kind (`claude-opus-5-5, high, on claude-work (Claude subscription)`; an agent resumed but not yet run takes its kind from its provider and spend; one whose log names no provider, or one this Wisp doesn't know, shows `on b` alone, and one logged before endpoints were recorded shows none), state with its reason or tool (`idle: reported`, `idle: waiting on its process 3` or `idle: waiting on its processes 4, 7` for a child waiting on processes it started for its task, `queued: concurrency`, `running: using bash`, `stopping: bash`), how long it has run (`ran 6m12s`: the total time it has spent in running turns, the current one included; queued, held and idle time don't count; left out until it has run), spend when above zero (`~$0.802 subscription`, `$0.061 API`, or `$0.30 API · ~$4.24 subscription` for both; a trailing `+` for a lower bound), or `not priced` for an agent on an endpoint that doesn't price its requests and has no priced spend, keep-warm for a marked agent while the limit is above 0 (`keep-warm: 2 of 8 refreshes`, the refreshes of its current idle spell, 0 at a spell's start, or `keep-warm: paused until its next turn` while it idles unarmed: after a resume, a turn that didn't complete, a stop, or a spell that ended early with a miss, a failure or a skip), context fill (`context 312k of 1M, limit 400k`: the agent's last `ContextChanged`, its `used`, window and meter limit as the meter shows them, in whole thousands below a million (`312k`) and in millions to one decimal from there (`1M`, `1.2M`); `context about 312k …` while the figure is an estimate, as before an agent's first measured step; just `context 312k` when no window is known), checklist progress (`todos 2 of 5 completed`) and `cwd`, then `Last report:` with the first line of its last report (left out while the agent is still working: queued, running, stopping, held for concurrency, or idle and waiting on its processes or children). The main agent's row shows only its session ID, model, effort, endpoint and provider, keep-warm (with the `keep_warm` setting on), context fill and `cwd`, since its state isn't tracked as an agent's; the caller's own row carries its context fill too.
- **`report`** `{ text }` takes the whole report as free text, in the form the task or the preset's instructions ask for; its first line is what lists of agents show; the description adds that the parent may pass it on to the user, so it uses plain words and each decision or question in it stands alone. The plugin hands the input to the kernel unchanged; a valid report answers `Reported.` and ends the child's turn after the step, an invalid one is a tool error with the checker's message.

## The agents service

`wisp_core::agents::AgentsService` is the one place that knows about more than one agent. It owns the tree (each agent's path, configuration, state and activity, command and mail channels), the frozen presets and the limits, and builds children through the Kit (`Kit::build_child`). It never writes a log: what it decides reaches an agent through its mailbox or its own tool result, and every agent stays the single writer of its own log.

**Starting a tree.** `agents::start_root(kit, setup, agent)` takes the main agent the Kit built, the `TreeSetup` (checked presets, limits and the instructions choice) and returns the same triple `agent::spawn` does: the command sender, the event receiver (1,024 slots) and an `AgentTask`. `wisp` starts every session this way.

**Reaching the service.** An agent holds an `AgentsHandle` (the service plus its own path). Each tool call gets it carrying a snapshot of the caller (its model, effort, enabled tools, working directory and turn-line settings): a plugin call keeps it on its `KernelCall`, where the `agents` host interface finds it by the call's id. Its entry points are `spawn`, `report`, `reachable` (for `list_agents`), `send` (for `send_message`), `stop` (for `stop_agent`) and `rename` (for `rename_agent`, main's only); the main agent's command handler uses `end_agent` for your `EndAgent` and `watch` for your `WatchAgent`. A refusal is returned as the tool error and noted for the agent, which emits `AgentRefused` and logs `agent_refused`; a spawn is noted the same way and logged as `agent_spawned`, both right after the call's `tool_call_finished`.

**What plugins see.** A world 0.2.0 plugin reads the tree through the `agent` (`current`, the calling agent's identity) and `agent-tree` (`snapshot`, every agent but the root with typed fields only, its endpoint, provider and `priced` among them, never a report's, a brief's or a message's text) imports, in a hook, a tool call, a plugin command, a sidebar render or read-only preparation in an identified chat, and never while a plugin is built, so nothing per agent reaches a prefix. Each node's `since-ms` is when it entered its state, on the Kit's clock and rebuilt from the logs on resume. It can also watch the tree through six observe points, `agent-spawned`, `agent-state`, `agent-mail`, `agent-reported`, `agent-stopped` and `agent-ended`, which the agents service queues where they happen (`agents/news.rs`, typed fields only, a mail's byte count but never its text) and the root's observer lane fires in the root's instances alone, never awaited by a turn. See `docs/plugins.md`, "The kernel host" and "Agent points".

### Fallback

A preset's `fallback` entries are tried in order after the spawn's first choice; a spawn's own account, model and effort replace only that first choice. Each entry names an `endpoint` and may name a `model` and an `effort`, checked like the preset's own keys. A model or effort supplied by the spawn that its first account cannot take is refused rather than replaced by a fallback's. Unavailable, gone or unconfigured accounts, choices that cannot serve the model, held used-up limits and fresh 100% usage readings are skipped; unread usage is tried. A fallback reaches an API account only when its entry names it. Checking each provider's terms on using several subscriptions is the user's job.

A child started on a fallback sends its parent a quiet notice, without starting a turn: `started on fallback chatgpt-sub with gpt-6-astra high: gemini-sub reached its usage limit for gemini-4-carbon, resets in 3d19h.` On the API it starts with `API:`. Once the first choice's usage resets, a new spawn takes it again. Without `fallback`, the usual single-choice behaviour and parent-account adoption stay unchanged.

### Spawning

A model spawns with `spawn_agent`; you spawn with the typed command `SpawnAgent { request, spawn }`, which never enters a model's tools; wrapped in `Child { agent, command }` it makes that agent spawn. Either way the agent spawns exactly as its `spawn_agent` would: the same `SpawnRequest`, the same checks, `agent_spawned` in its log. The child is built without holding the tree's lock: its name is reserved first (it counts as taken and as a live agent), and if the session starts closing while the child is being built, the spawn is refused with `the session is closing, so no agent can start` and the child never runs. It is answered with `AgentSpawned` (carrying `request`), or with `AgentRefused` and `Rejected { request, kind: agent_refused }`. Wrapped in `Child`, the answers come from that agent: its `AgentRefused` and `Rejected` arrive wrapped in `Agent { agent, … }`, while `AgentSpawned` is a tree event and arrives bare. The child's tasks start before its parent emits `AgentSpawned`, so a client can see `Agent { agent, … }` events for an agent it hasn't been told about yet; it should keep them and show them once the `AgentSpawned` arrives. An agent without `spawn_agent` refuses, so a session without the agent tools never has agents; a session not started through `start_root` refuses every spawn.

`SpawnRequest` is `{ name, task, todos?, cwd?, preset?, model?, effort?, tools_off?, spawn?, keep_warm?, endpoint? }`. A spawn's own fields override its preset's. It is refused, costing nothing, for:

- a name that isn't a lowercase letter then up to 31 of `a-z`, `0-9`, `_` and `-`, one of the reserved `main`, `parent`, `user` and `wisp`, or one the parent already used (an ended name is never reused);
- an unknown preset (the error lists the presets), or an off one: `preset planner is off: <problem>; the user fixes the file it names or config.toml, and the fix applies from the next session start`;
- a preset whose instructions no longer load at the spawn: `couldn't start /c: preset planner's instructions no longer load: <problem>`, naming the file `~/`-shortened, never an OS error; the spawn leaves no log;
- a `tools_off` name that is no tool, or one of the agent tools every child keeps (the error points to `spawn: false`, and names only tools the spawning agent has: `tools_off can't name spawn_agent; use spawn: false, which also turns off stop_agent` loses its last clause when the spawner has no `stop_agent`, and the kept tools it lists are `report` and those of `list_agents` and `send_message` the spawner has);
- a model not in the capability table, a listed model without adaptive thinking on the child's Anthropic account, or an unsupported effort on a model that takes effort levels; on Antigravity's level-in-ID models a named effort chooses the sibling ID, which must be served by the child's account;
- an account whose held limit or fresh usage reading is used up for the chosen model: `account gemini-sub reached its usage limit for gemini-4-carbon, resets in 3d19h; spawn on another account or model`; account-wide limits omit the model, unknown resets omit the countdown. A named limit says `reached its <label> limit`; a retry guard says `refused a request for <model>, retry in …`. The refusal sends no request and reserves no name; with fallbacks, Wisp tries each choice first; if none can run, the reason is `no account preset code-reviewer names has room: gemini-sub reached its usage limit for gemini-4-carbon, resets in 3d19h; chatgpt-sub reached its usage limit, resets in 1h05m`.
- an empty task, a `todos` list of more than 50 items or with an item that is blank or over 500 characters, or a `cwd` that isn't a directory (`~/` is the home directory; a relative one is from the parent's session directory, and its refusal names that base: `cwd crates/x isn't a directory (relative to ~/Projects/Wisp)`);
- the depth limit (`agents.max_depth`), or a tree already holding `agents.max_agents` agents that haven't ended, the main agent included;
- a child that can't be built: its endpoint can't be connected, its working directory can't be used, or its session log can't be opened. The reason names only which of these failed, never the underlying error, since the reason reaches the model.

**Names and paths.** The main agent is `/`, shown as `main`; its child `review` is `/review`, and that one's child `planner` is `/review/planner`. A child's depth is the number of names in its path.

**Renaming.** Main renames an agent below it with `rename_agent` when you ask it to; a client renames one with `RenameAgent`. Both log `agent_renamed` to the root's log and tell the agent's parent, unless main renamed one of its own children. Its path changes, and every agent below it moves with it, ended ones included; its depth, session and run don't change. Every path a model or client sends is followed through the session's renames first (`AgentPath::followed`), so mail, `stop_agent`, `EndAgent` and `Child` sent to an old path reach the agent, and the answer names the new path. A name is taken while it leads to an agent, live or ended, through renames or not, so an old name is never given to another agent; an agent may take back one of its own earlier names, unless an agent now below it would then lead to another one (`/q can't take the name p: /p/x would then lead to another agent; choose another`). The renamed agent and those below it get a new `<environment>` block, with their new `Agent:` and `Parent:` lines, in their next turn message; nothing committed changes.

### What a child gets

- **Tools:** its parent's enabled tools, minus every question tool (one whose metadata both asks the user and ends the reply: `ask_user` today; `process`, which asks only to attach, stays), plus `report`, minus the spawn's `tools_off`, minus `spawn_agent` and `stop_agent` with `spawn: false`, and always minus `rename_agent`, which only main has. Overrides only narrow, so a narrowed child's children stay narrowed. Web search is a tool name like any other (the `web-search` plugin's native tool), so it follows the parent unless `tools_off` names it. Turning off a tool turns off the tools that come with it: `tools_off: ["bash"]` also removes `process` (the service's check takes the catalog's follower pairs, `TreeSetup.followers`, beside `tools_off`), and `tools_off: ["stop_agent"]` removes only `stop_agent`. A child's list is exact: it starts the tools it names and nothing else, followers included, at spawn and on resume, so `spawn: false` still keeps `list_agents`, `send_message` and `report`, and a default child of a default root has the root's tools minus `ask_user` and `rename_agent`, plus `report`.
- **Its own plugins:** the child's plugin tools are its own instances, started for exactly its tools with a host of its own (`docs/plugins.md`, "Starting"), so its jobs, working directory and running calls never mix with its parent's.
- **Model, effort and endpoint:** the parent's unless the spawn or its preset chooses others; the spawn's `endpoint` wins over its preset's, which wins over the endpoint the parent is using at the moment it spawns, so a child's own children default to the child's endpoint. Spawning reads the live account catalog, so an account signed in with `/login` in this window can be used by agents right away; one added from another terminal needs a restart (`/exit`, then `wisp --resume`) until Wisp notices accounts changed elsewhere. The check (`agents::endpoints`) refuses, before the model check and naming accounts and their kinds only, never a reason: an account that isn't one of the session's (`no account "gpt" in this chat; accounts: claude-work (Claude subscription), direct (Claude API)`, a key-shaped or ill-formed name read as `that name`), one unavailable at start (`account gpt can't be used right now; the user sees why in /account or wisp doctor; accounts you can use: …`), and one the main agent removed this session, or edited so it no longer loads, inherited or named (`account gpt was removed in this chat, or edited so it no longer loads; agents can use it again from the next session`). That gone set only grows: an endpoint restored mid-session stays refused to agents until the next session, since children would connect with its start-of-session credential. A known gap: when the main agent edits the endpoint it is using so that it no longer loads, that endpoint isn't added to the gone set, so its children can still inherit it. Then the model, against the child's endpoint's own capability table: a named model (the spawn's or its preset's) must be one it serves, and when the spawn or its preset fixed the endpoint the refusal lists only the models that endpoint serves, never another endpoint (`model claude-opus-5-5 isn't one account small (preset reviewer's) serves; leave model out to use the preset's claude-haiku-5-5, or name one it serves: claude-haiku-5-5`); when neither fixed it, a named model the parent's endpoint doesn't serve reads `model claude-opus-5-5 isn't in the capability table`, adding `; account gw offers it (set endpoint)` when one of the session's endpoints, not one removed this session, serves it; without a named model, a child on the parent's account keeps the parent's model; on another account it lands where an account switch would: the parent's model if the account offers it, otherwise that account's default or first offered model. An incomplete list on an account of the parent's model's provider still permits inheriting an unknown gateway model; a complete list uses only its own models. If the target's row has no effort levels, spawning drops any named or preset effort and ignores an inherited effort; the result line and agent list show `none`. On a model that lists effort levels, a named, preset or inherited effort must be one it takes; on an Antigravity level-in-ID model, only a named or preset effort chooses a sibling, while an inherited effort yields to the ID's own level. An unknown capability row leaves the effort unchanged. A preset that fixes a no-effort model together with an effort still turns off at load. A child's history moves between providers as the main chat's does. Its `/account` picker lists every ready account across providers that isn't gone and whose provider plugin isn't switched off; a client can move the child for this session (`ChangeSettings` with `save: false`, sent in `Child`) or by retrying a failed turn on another account. A gone account or one whose provider plugin is switched off is still refused, leaving the Retry offer standing. Credentials, logging, the cache TTL and the `Sent:` and `Context:` settings follow the parent.
- **No user:** a child is built with no user channel and skips the channel check, so a child with `bash` runs, and `process`'s attach answers `Not asked: no one can type into processes in this session. Don't ask for the secret in the chat or from another agent; say what the process needs.`
- **Its working directory:** the spawn's `cwd`, or the parent's session directory: where the main agent started, or a child's own spawn `cwd`, never wherever the parent's shell last moved with `cd`. The project block is the `AGENTS.md` of that directory's project, chosen as the main agent's instructions setting says.
- **A stable prefix:** tools and system come only from the configuration, so children of one parent with the same choices send identical bytes, and a default grandchild sends its parent's exact tools and system. The depth never changes them. A preset's instructions follow the project block, after a newline, so every child of one preset in one project shares one prefix while its files are unchanged, and two presets naming one file send the same block; a default grandchild of a preset child gets the project block only, so it doesn't share its parent's prefix. For scale, a child of a session started with `--tools ask_user,bash,show_diff,view_file,web_search,spawn_agent,list_agents` drops `ask_user` and `rename_agent` and gains `report`, so it sends about 19.1 KB of tool definitions (`bash`, `list_agents`, `process`, `report`, `send_message`, `show_diff`, `spawn_agent`, `stop_agent`, `view_file`, summed from the spec fixtures; `web_search` is a server tool with no definition of ours), about 1.2 KB of system sentences and, in this repository, its `AGENTS.md` and the `CONTRIBUTING.md` it imports, about 19.9 KB: about 40 KB in all. That is a byte-based estimate, not a token count: at 3 to 3.5 bytes per token it comes to roughly 11,500 to 13,400 tokens.
- **Its first user message:** the `<environment>` block, which an agent with a parent or with `spawn_agent` always gets, even when no tool needs a workspace, then the brief. The block ends with the agent's lines:

```
Agent: /review/planner
Parent: /review
Presets for spawn_agent: coder (Writes code; on claude-work, with claude-opus-5-5); reviewer (Reviews a change)
```

  Each preset names its account and model when it sets them, from config only: never the account's kind or a subscription tier, so the line never changes when an account is signed in again, and a key-shaped account name reads `(not shown)`.

  The presets line appears for an agent with `spawn_agent` when presets are set (the main agent gets it too); at the depth limit it is replaced by `Spawning: you are at the depth limit (2), so spawn_agent refuses`. The brief is a task mail from the parent: the task, then the checklist (`- [ ] …` per `todos` item). A child of a preset with instructions also gets `Preset instructions: <file>` after its `Parent:` line, the file `~/`-shortened. A child whose process news is worded (`hooks_word_news`: the `shell` plugin's `processes` notice on, the default) also gets one static line after those, `Background processes: if you end your turn while one you started for your task still runs, Wisp wakes your parent now to tell it and wakes you when the process ends. …` (`wisp_tool_text::agents::BACKGROUND_LINE`, listed in `AGENT_LINE_STARTS`); a child resumed from a log written before the line existed sends its block once more, appended, at its next turn.
  Wisp scrubs detected credentials and identity from the brief's checklist
  steps, with or without `write_todos`. It does not scrub the task prose.
- **Its checklist:** when the child has `write_todos`, the spawn's `todos` are its starting checklist, every item `pending`. The masked steps are logged in its `session_started.parent.todos` and announced once, when its log starts, as `TodosUpdated` with no `call_id`; `wisp_protocol::todos::checklist` falls back to them while no `todos_updated` is kept, so a resume or a rewind to its first turn gives them back. Without `write_todos` the items are only in the brief. The service keeps each child's progress from its `TodosUpdated` events for `AgentEntry.checklist` and `list_agents`.
- **Its own log:** a session log like any other, with `session_started.parent` linking up; the parent's `agent_spawned` links down (`docs/session-log.md`). If logging is on and the child's log can't be opened, the spawn is refused rather than running a child with no record.

### Commands and events

A running child's `ChangeSettings` that moves accounts without naming a model reads
that account's remembered pair. Children never write choices; spawns stay as before.

`Child { agent, command }` carries a command to an agent in the tree, which runs it as the main agent runs its own and answers wrapped: `Send`, `Withdraw`, `Release`, `Cancel`, `Retry`, `SpawnAgent`, `DescribeSettings`, `ContextReport`, `Compact`, `RewindPoints`, `Rewind`, `RunPluginCommand`, the process commands (`CheckProcesses`, `StopProcess`, `Background`, `AttachProcess`, `ProcessInput`, `DetachProcess`), and `ChangeSettings` with `save: false` changing only its account, model and effort (`settings::names::PAIR`). The router (`route_refusal`) refuses the rest with `Rejected { kind: not_for_agents }` and a reason: a saved change or any other setting (`an agent's settings change only for this session, and only its account, model and effort`), the accounts' commands, `SubscriptionAuth`, `PlanUsage`, `SaveEndpoint`, `EditEndpoint`, `RemoveEndpoint` and `StartOn` (`accounts are the session's; send it to main`), the session's, `ListChats`, `ListSpend`, `ListAgents`, `DescribeSession`, `ReturnedTaken`, `WindowGone`, `Child`, `EndAgent`, `RenameAgent`, `WatchAgent`, `SlotsShown`, `Terminal` and `Voice` (`this is the session's; send it to main`), and the user's answers, `Answer`, `ScreenReport`, `DeclineAttach` and `AnswerSecret` (`an agent never asks the user`); an unknown or ended agent gets `no_such_agent`. Your `Send` is the child's user message, not mail: it starts a turn and keeps one going, and it creates no report owed. `Cancel` stops the child's turn and the running turns below it. `EndAgent { agent }` (sent to the main agent, never wrapped) ends that agent and every agent below it, as `stop_agent` with `end: true` does, and the target's parent gets the non-waking notice `/lead/w was ended by the user.`; ending the main agent is refused with `Rejected { kind: agent_refused }` (`main can't be ended; quit the session to end it`), and an unknown or already ended agent with `Rejected { kind: no_such_agent }`. `RenameAgent { request, agent, name }` (sent to the main agent, never wrapped) is answered with `AgentRenamed { request, agent, to }`, logged as `agent_renamed`, then the renamed agent's `AgentStateChanged` under its new path, and its parent gets the non-waking notice `/lead/w was renamed to /lead/fixer by the user.`; main (`main can't be renamed`), a name `spawn_agent` would refuse, a taken name, a taken-back name an agent below would then lead astray from, and the agent's current name (`/lead/w is already named w`) are refused with `Rejected { kind: agent_refused }`, and an unknown or ended agent with `Rejected { kind: no_such_agent }`. The tree changes only once `AgentRenamed` is sent, so no event names the new path before it; an event stamped just before can still arrive after it naming the old path, and a snapshot taken meanwhile shows the old tree, so a client follows every path it receives through the renames it has seen. `ListAgents { request }` is answered with `AgentsSnapshot { request, agents }`, one `AgentEntry` per agent (path, name, session ID, parent, preset, model, effort, depth, state, activity, spend, checklist progress `{ completed, total }` when it has a checklist, the first line of its last report, `cwd`, `running_ms`, the time it has spent in running turns, absent until it has run, `context`, its last context fill `{ used, window, limit, estimated, auto_compact }`, which every agent, the main agent included, hands the service each time it works out its `ContextChanged`, and `preset_change`, `edited`, `disabled` or `removed`, on a live agent whose preset changed since its spawn, absent otherwise; a client reads an unknown value as `unknown`). At resume, a protocol client gets the count of changed presets as the number of distinct `preset` values among the live agents' `AgentsSnapshot` entries that have `preset_change`. `WatchAgent { agent, live }` (sent to the main agent, never wrapped) turns the forwarding of that agent's `ToolOutput` on (`live: true`) or off; it has no answer of its own. Watching an unknown or ended agent, or main (`main can't be watched; its own output is always shown`), is refused with `Rejected { kind: no_such_agent }`; `live: false` for an agent that has ended is accepted quietly, since it can race the end. `--replay` ignores `WatchAgent`. Watching starts where it is turned on: output from before it, and from before a resume, is never sent again. These commands are handled at once, never queued behind a turn.

`DescribeSession` answers during a turn with the shared resumed
view, current settings and live state (`docs/daemon.md`).

A forwarder per child sends each of its events to the main channel wrapped as `Agent { agent, event }`, text and thinking deltas included, so every agent's turn still ends in exactly one `TurnEnded`. Only `ToolOutput` waits for a watch: it is dropped unless a client watches the agent with `WatchAgent`. `ProcessOutput` is always forwarded, as every other process event is, so a client's list of an agent's processes is complete, and `--output jsonl` prints every agent's background process output. Tree events that already name their agent pass unwrapped: `AgentSpawned`, `AgentReported` and `AgentStateChanged { agent, state, activity, spent_usd, lower_bound }`.

### Reports, and the parent's guarantee

`report` takes one field, `text`, holding the whole report: the child decides what to report, shaped by its brief or its preset's instructions. A missing or blank `text`, or any other field, is refused with `report takes one field, text, holding the whole report`. A valid call gets `Reported.`; the other calls of the same reply still run, then the turn ends `Completed` with no further request. A process end one of those calls carried still wakes the agent after the turn. After the second refusal in one turn the turn ends `Error { kind: other }`.

A child owes its parent a report from each task mail (the brief included) until it reports. A turn that completes while it owes one is **waiting** if a background process it started for that debt runs while a hook words process news (with the `shell` plugin's `processes` notice off, no process end would wake it), even when it messaged its parent or a sibling; else if its last tool step sent its parent or a sibling a message that wakes it (`idle(asked)`; a `wake: false` message doesn't count); else if a child of its own still owes it a report and is running, queued, held only for concurrency (a hold that lifts by itself) or itself waiting, or if waking mail from a child or a sibling is queued for it (`idle(waiting)`); a child held because it was stopped, offers a retry or has held messages waits for someone to act, so it doesn't count: it ends with no nudge and no mail. A busy child that owes nothing, such as one you sent a follow-up after it reported, doesn't make its parent wait. Otherwise the kernel appends `Finish by calling report, or ask your parent with send_message.` as a notice from the parent and continues, at most twice. Any end of one of the debt's processes wakes the waiting child to report, a stop or an end while the user typed into it (from `/ps`) included. The debt's processes are those numbered from the first one after the task mail that started it; a later task while it still owes keeps that mark, so a follow-up during a test run doesn't end it in `no_report`. A turn that ends waiting on processes the parent hasn't heard of since its latest task tells the parent: any message the child sent its parent during the turn is the note, waking or not as the child chose with `wake`; otherwise Wisp sends the waking notice in the table below. Every task from above makes the next such turn end tell the parent again.

Every child turn that ends owing a report and not waiting sends its parent exactly one kernel mail, and a stopped turn always sends its stop notice, owing or not:

| Child turn ended | Mail to the parent |
|---|---|
| with a valid `report` | `report`, outcome `reported`: `/review reported · 6m12s · 31 steps this turn · $0.84 API` (`~$0.802 subscription` on a subscription), then the text exactly |
| completed, waiting on its processes, no message to the parent this turn | `notice`: `/review waits for its process 3 (Run the workspace tests) to end and will report then. If that process won't end by itself, message /review to report now. Its last text follows.`, then the turn's last text; each process is its number and its call's title (cut at 60 characters), or its number alone, never its command |
| completed, nothing running, nudges used | `report`, outcome `no_report`: `/review ended without a report (no_report; its last text follows) · …`, then the turn's last text |
| two invalid reports | `report`, outcome `invalid_report`, with the last refusal and the last input |
| a provider error after resilience's retries | `notice`: `/review failed (overloaded).`, the typed error kind; a used-up limit with a known reset also names the account and reset |
| stopped by you, or with its parent | `notice`: `/review was stopped by the user.` or `… stopped with its parent.`, which doesn't wake the parent |
| stopped by `stop_agent` from an agent above its parent | `notice`: `/review/x was stopped by an agent above you.`, not waking |
| stopped by its parent's `stop_agent` | none: the parent did it |
| ended by your `EndAgent` | `notice`: `/review was ended by the user.`, not waking, in place of any stop notice |
| renamed by your `RenameAgent` | `notice` from the new path: `/review was renamed to /fixer by the user.`, not waking |
| renamed by main's `rename_agent` | `notice` from the new path: `/review/x was renamed to /review/y by main.`, not waking; none when main is the parent |
| ended by `stop_agent` with `end: true` from an agent above its parent | `notice`: `/review/x was ended by an agent above you.`, not waking, in place of any stop notice |
| ended by its parent's `stop_agent` | none: the parent did it |

A child still retrying can also send the one notice described in "Waking when work is stuck" before its turn ends.

**A used-up limit.** A child spawned with fallbacks keeps its spawn's choices in its spawn record (`agent_spawned.config.choices`: the first choice as the spawn resolved it, then each `fallback`), so a restart changes nothing. When its turn fails on a used-up limit or a provider refusal that Wisp holds for its account and model, it moves by itself to the first choice, from the top, that lands, through `/account`'s checks, on another account or model with room, and sends the failed request there as a Retry does (`docs/endpoints.md`). When that Retry's turn starts, its parent gets one quiet notice instead of the failed one: `moved to gemini-sub with gemini-3.8-flash high (cache rebuild ~$0.12): gemini-sub reached its usage limit for gemini-4-carbon, resets in 3d19h.`, starting with `API:` on an API account. A move can return to an account and model only after its hold has lifted, at the cost of at most one refused request each time; a reset alone doesn't move an agent back. A child you moved by hand follows the same rule from where it is. When no choice qualifies, or the Retry is refused, the failed notice goes as before; when Wisp exits before the Retry's turn starts, the failed turn is interrupted ("Resume", "Interrupted turns"). Its next turn then runs on the fallback with no `moved to …` line for its parent; the rebuild is still in the child's `settings_changed` and its spend.

The duration and step count cover the turn that reported; the cost is the child's whole spend so far, written `$…+` when some of it couldn't be priced and `~$…` when it is a subscription estimate, and left out when its endpoint isn't priced. No kernel mail carries a provider's error text or an absolute path: a failure names its kind and, for a used-up limit with a known reset, its account and reset; paths are shortened to `~/`. The child's own words are carried as it wrote them, whatever they hold: its report, the last text in `no_report` and in the wait notice, and a call's title. A report or last text over 16 KiB is cut at the last line break within 16 KiB (at a character boundary when there is none) and ends `[cut: the full report is in <file>]`, the whole text being written to `report-<turn>.md` in the agent's output directory (`~/`-shortened; `the agent's log` when it can't be written). Report mail and failure notices wake the parent through the usual mail gates (`docs/plans/subagents.md` §5); a stop notice waits for its next turn. The child also logs `agent_reported`, and the main channel gets `AgentReported { agent, turn, outcome, report, cost, duration_ms }`, both holding the whole text. The report line lists show is the text's first non-empty line, cut at 200 characters, the same live, after a resume and in the `report` row. Quitting is not a stop: it sends no mail.

### Messages

Who may message whom (decision 1 of `docs/plans/subagents.md`): an agent reaches its parent, its siblings (same parent), its children and every agent below them. It never reaches its grandparent or anyone higher, a sibling's children, or any other branch; the refusal says to send it to the parent to pass on. The main agent reaches every agent, and so do you through `Child { Send }`. Every refusal (an unknown or ended recipient, a forbidden route, an empty text, a cap) is a tool error plus `AgentRefused { action: send }` and `agent_refused`.

- **Kinds.** A parent's message with `wake` on (the default) is a `task` mail: the child owes a report for it, so a parent can hand a child that already reported more work, which it does in the same context, the same log and the same prefix (the same reviewer re-checks, a planner fixes its own plan). Every other message is a `message` mail. Mail from the parent or any agent above it counts as the recipient's user message (it starts a turn at once and keeps a running one going); mail from a sibling or a child, and kernel notices, never keep a turn going and wake an idle recipient after the 2 s settle, behind the same gates as a process wake (`docs/plans/subagents.md` §5). On the main agent, when a turn stopped at the step limit on unreadable replies other than `MALFORMED_FUNCTION_CALL` with Retry offered, a waking message from another agent (not the failed turn's own letters, the agent's own notices, plugin notices or mail from above) takes that Retry by itself instead of waiting behind the `RetryOffer` hold, one round per message (`docs/endpoints.md`, "Switching mid-session").
- **From above the parent.** Mail from a grandparent or higher ends with `(You can't message main directly: reply through your parent.)` (naming the sender), so the recipient doesn't spend a step on a refused reply.
- **Hooks.** A plugin's `user-input` hook never sees mail: it runs for your own inputs only, sends and steers, so a mail-opened turn and mail taken at a boundary pass no hook (`docs/plugins.md`, "The gate points"). `before-end` does run in every agent, children included.
- **Caps.** At most 64 messages from one sender wait unread at one recipient (kernel mail is never refused). Between two siblings there is also the **peer cap**: one sibling may send another at most 16 messages (`MAX_PEER_MESSAGES`) between two messages from above to that recipient (from its parent, an agent above it, or you), counted when sent; the refusal says to ask the parent. So two siblings can't wake each other forever.
- **Asking.** A child whose last step sent a waking message to its parent or a sibling ends `idle(asked)` with no nudge, unless a process it awaits still runs: then it ends `idle(waiting)`, and its question isn't tracked, so no unanswered notice follows. A question to the parent wakes it. A question to a sibling is tracked from the moment the sibling's turn commits it: if that turn ends (completed or failed, not stopped) without the sibling sending the asker anything, the asker gets a waking kernel notice, `/b ended its turn without answering your message.`, so its usual nudge and `no_report` path applies again. Only an asker still waiting on that question gets it: one that has since started another step or turn, or asked someone else, doesn't. Any message from the asked agent counts as its answer, even one sent with `wake: false`. If the asked sibling is ended instead, each asker still waiting on it gets the waking notice `/b was ended before answering your message.`
- **Framed mail.** On a model whose shipped row has `turn_form` (`gemini-4-neon`), each message except a `task` is written inside that row's frame when it arrives: `mail_before`, the `<wisp:message>` block, then `mail_after` (`docs/gemini.md`). The transcript shows the block alone, framed or not; a `task` and every other model's mail stay bare.

### Stopping and ending

`stop_agent` (only agents that may spawn have it) cancels the target's running turn as Esc does, and the turns of every agent below it that is running, queued or held for concurrency (an idle one with a wake still settling has the wake dropped, as Esc does); each keeps its context and stays idle, `held(stopped)`, until mail from above, your send, Release or Retry. Every stopped agent below the target tells its own parent with a non-waking notice (`… was stopped with its parent.`); the target tells its parent only when the caller is higher up (`… was stopped by an agent above you.`), so nothing stopped wakes anyone and no stop goes untold. Open tool calls each get their one result, as for any stopped turn. Each agent whose running turn a stop reaches (`stop_agent`, your `Child { Cancel }`, or a cascade from an agent above it) reads `stopping` until that turn's `TurnEnded`, then `idle(stopped)` (or the turn's own outcome, if it finished first). A stop leaves running the numbered processes of every agent it reaches (background ones, terminals and commands handed back); a command still inside its call is stopped, as Esc stops it.

A model's `stop_agent` with `end: true` is refused (logged as `agent_refused`) when the target or a live agent below it is running, queued, held for concurrency or waking (and not already stopped), left an active state after the calling reply was requested (for example a same-reply stop or a mid-reply turn exit), or has an unread report waiting for the caller; when that refusal fires, every later call of the same reply is not run (`after_refusal`), while earlier calls stay run and every call gets one result. To end an active agent anyway, the model stops it with `end: false` and ends it in a later reply; your `EndAgent` and `stop_agent` with `end: false` are not guarded. With `end: true` once allowed, or your `EndAgent`, the target and every agent below it (running or not) are also **ended**: their state becomes `ended` at once, so they take no more mail (`/review has ended`), stop counting toward `agents.max_agents`, can't be stopped or messaged again, and their names stay used. The target's parent, unless it is the caller, gets one non-waking notice, whatever the target was doing: `/lead/w was ended by the user.` for your `EndAgent`, `… was ended by an agent above you.` otherwise, and never a `stopped` notice for the same target. A spawn under an agent that was stopped or ended while the child was being built is refused (`/lead was stopped while /lead/w was starting, so it didn't start`), so no child starts under a stopped parent. Each closes its command channel after the stop, so its log gets `turn_ended` for a stopped turn and then `session_ended`. The agent that ended them emits `AgentStateChanged { state: ended }` for each and logs one `agent_ended { agent, spent_usd }` record per ended agent (`docs/session-log.md`); `spent_usd` is the agent's spend when it was ended, so a stopped turn's last request may come after it; the complete figure is in the ended agent's own log, which is where a resume reads it from. Ending also stops each ended agent's numbered processes as quitting Wisp does, SIGTERM and then SIGKILL after a grace; none is kept, since a child can't use `keep_running` (`docs/tools.md`, "`keep_running`: a process that outlives Wisp").

### States

Each child's state follows a pure transition function (`agents::state::next`): a spawn makes it `running`; a turn start makes it `running`; a turn end makes it `idle`, carrying the last outcome (`reported`, `asked`, `waiting`, `no_report`, `invalid_report`, `failed`, `stopped`); a held wake makes an idle agent `held` with its reason; a stop that reaches a running turn makes it `stopping` (the service sets it when it sends the turn its `Cancel` and announces it with `AgentStateChanged` on the main agent's event channel; the announcement is best-effort, as at the tree's close: it is dropped if that channel is full, and a state event the child or its forwarder worked out before the stop may arrive after it, so a client takes the state again from the turn's `TurnEnded` and its idle change, and `list_agents` always reads the service's own entry), which a turn start or a held wake leaves alone and the turn's end turns into `idle`; `stopping` counts as running everywhere but its word (the run permit, owing and `idle(waiting)`, what a stop reaches, the quit bound), and a queued or held agent that is stopped goes straight to `idle(stopped)`; `stop_agent` with `end: true`, your `EndAgent` or the tree closing makes it `ended`. A spawn without a run permit starts `queued(concurrency)`. Three waits inside a turn make a running agent queued until they end, then `running` again: a request waiting on the stagger is `queued(stagger)`, one waiting for a free slot on its endpoint ([docs/endpoints.md](endpoints.md#one-limit-per-endpoint)) `queued(endpoint)`, and any retry wait `queued(retry)`; a stop that reaches the turn before one of them keeps it `stopping` through the wait, and a stop during one ends the wait at once (it cancels the turn, which never shows `stopping`) and the turn ends `idle(stopped)`, as a queued agent's stop does. Every reader takes the five dot states from one rule, `AgentState::node_state()` (`docs/plugins.md`, "`agent-states`"), so `queued(endpoint)` reads as working everywhere, any other queue as waiting, and `since_ms` moves only when that node state changes, so the working clock runs on through a wait for the account's limit. The main agent never shows them, since its state isn't tracked: its slot waits show on the status line as its usual working line, and its retry waits as the retry countdown. Activity (`streaming`, a named tool, `idle`, `queued` or `held` with the state's reason, and `waiting` with the processes, in ascending order, that an `idle(waiting)` child started for its task) follows the forwarded events; the settle sets `waiting` only while that list isn't empty, so a child waiting only on its children or its mail shows `idle`. The main agent's state is the session itself and isn't tracked.

**After a compaction.** The `agents` plugin's `lead` prompt section `agents/children` (in `core/state`, after `todos/checklist`) renders only at a head: one line naming, in tree order, each of the agent's own children that hasn't ended and isn't `idle(reported)`, with its state as `list_agents` words it (with the reason or outcome, never the activity) and the time since its `since_ms`, then the fixed line `Their reports arrive as messages.`: `Child agents at the start of this context window, except those ended or idle after a report, each with its state and the time since it last started or stopped working or waiting (waiting for an endpoint counts as working): /lead/planner (running, 2m05s), /lead/coder (idle: no_report, 41s).` A queued, running, stopping or held child is listed, and so is an idle one with no outcome or any outcome but `reported`; a state Wisp doesn't know reads `unknown`, where `list_agents` shows none. With no such child it sends nothing. Its snapshot is empty, and the head keeps the ages it was built with (`docs/context.md`, "The head step").

### Prefix warmth

Every request the tree sends (each step, retry and compaction, the main agent's included) gets a prefix fingerprint, computed once per request from the exact bytes the provider sends: the endpoint name, the model, the effort parameter, the thinking settings, the canonical tools JSON and the system blocks, each hashed on its own (so a later `CacheMiss` can name which one changed) and hashed together into the prefix key. Messages, the tail's cache marker and request options never change the key. A provider that can't give these bytes gets no fingerprint (`Provider::prefix_bytes` defaults to none, so a wrapper around a provider must forward it). The key is never sent, logged or shown.

The Kit holds one warmth table for the tree. A key is `cold` until a request carrying it is sent, `warming` until that request's first stream event, then `warm` until an hour after the latest request carrying it that streamed was sent (the system breakpoint's TTL); a request that never streams doesn't extend it. If the warming request ends before its first stream event (an error, a cancel, a dropped stream), the key turns `cold` again; a later request failing doesn't cool a warm key.

### Keep-warm

A parent that will wake a child again can keep that child's prompt cache warm while it idles. `SpawnRequest.keep_warm` (and so `ClientCommand::SpawnAgent`) marks the child at birth, and the mark holds until the child ends; the `spawn_agent` tool takes it as `keep_warm`. The mark is in the parent's `agent_spawned.config.keep_warm`, which is what a resume folds, so a resumed child stays marked. The main agent is marked by the `keep_warm` setting (`keep_warm = true` in `config.toml`, `--set keep_warm=on` for one run). `agents.warm_refreshes` bounds a forgotten mark. Only a provider Wisp refreshes takes a mark (`Provider::keeps_warm`; Anthropic's does, OpenAI's doesn't): a `keep_warm: true` spawn on another endpoint starts unmarked, so its `agent_spawned.config.keep_warm`, a resume and its entry agree, and the `spawn_agent` answer ends `keep_warm does nothing on endpoint gpt: Wisp doesn't refresh this provider's cache.` rather than refusing; likewise the main agent on such an endpoint at the tree's start gets no mark from the `keep_warm` setting.

A marked agent is refreshed only while all of these hold: its last turn ended completed; it isn't running or ended, and nobody stopped it since (`Child { Cancel }` or `stop_agent` on an idle child counts until its next turn); its last request (the anchor) was sent on the current endpoint and model at a 1h TTL, with a cache digest, and its reply shows no fallback (no `fallback` block and no `fallback_message` iteration); the session's TTL is 1h; and no background compaction is running or ready and no switch is pending. A child that is queued for a run permit is idle, so it is still refreshed: the refresh takes no permit, and it keeps the cache warm for the turn the permit will start.

- **When.** The end of each completed turn arms the timer and starts a new idle spell. The refresh is due 55 minutes after the anchor was last used (its start, or the start of the last refresh that read), and it waits for a request slot on the endpoint (`docs/endpoints.md`, "Busy endpoints") behind every other request of the tree, without any `RequestQueued` or state change. If it can't go before 58 minutes, or the clock has jumped past them (a laptop that slept), it is skipped as `late`. Any turn start, a manual compaction and a rewind disarm the timer.
- **What.** The refresh is the anchor's request again with `max_tokens: 1` and no `fallbacks` (so a refused refresh can't pin the next request to a fallback model): the same tools, system, thinking, effort, messages and automatic 1h marker, so it reads the anchor's cache entry and moves its lifetime to an hour from now. The refresh never carries a message thread (`docs/context.md`, "Message threads"): for an anchor sent as a continue, the anchor's request is the logical one (the thread's system, tools and full history), which the refresh sends whole. It runs no hook, takes no run permit, emits no step events and commits nothing. Before it is sent, its own cache digest must equal the anchor's, or it is skipped as `changed`; when this run has committed a request, its prefix key must match too.
- **Outcome.** A refresh is judged by the usage it got: reading at least half its prompt is `read` (whatever its stop reason: a refusal or a cut stream still read), and the next one is due 55 minutes later, until the limit; reading less is `missed`; no usage is `failed`. A 429 or 529 is retried at the busy backoff (`docs/endpoints.md`) while that still falls before 58 minutes. A miss, a failure or a skip ends the spell's refreshes until the next completed turn.
- **In flight.** A turn that starts while a refresh streams isn't held for it (beyond a request slot); the refresh's record follows and schedules nothing. An end collects a finished refresh, and logs one still streaming as `stopped`, with a lower bound once it was sent; one that hadn't been sent yet cost nothing.
- **Allowance.** A refresh's stream is drained like a background compaction's (`agent/side.rs`): each subscription allowance it reports is observed for the endpoint, and its landing refreshes the allowance as a turn's end does.
- **Costs.** A refresh is priced like any request and added to the agent's `session_usd` (so to its spend and the tree's), never to a turn's. Each one sent emits `AgentEvent::CacheRefreshed` (its outcome, detail, usage and `Cost`) and writes `cache_refresh` (`docs/session-log.md`); a skip writes only the record.

A refresh takes no warmth ticket and gets no prefix fingerprint (above), so it never makes a sibling stagger and never extends `warm`. It is never checked for a cache miss (`docs/context.md`, "Cache misses"). A resume by hand waits for the next completed turn before refreshing. A host started with `TreeSetup.restarted` restores an idle marked agent's spell only when its last turn completed and resume left that turn's gate armed: an earlier cancelled turn does not stop a later completed turn from being restored. The last refresh that read supplies its count, and a miss, failure or skip keeps the spell ended. A `stopped` refresh ends nothing. The timer runs from the anchor's last use, with the same 55-minute due time, 58-minute cutoff and refresh limit across restarts. A cache-keying beta-header change drops the restored digest, so it arms no refresh and supplies no summary marker.

- **Shown.** A marked agent's `AgentEntry.keep_warm` is `KeepWarm { refreshes, limit, paused }` while `agents.warm_refreshes` is above 0, and absent otherwise. `refreshes` counts the current spell's refreshes (0 from each turn's start, and when a completed turn arms a new one); `paused` is set while the agent idles unarmed: at the tree's start for the main agent, after a resume by hand, after a turn that didn't complete or left no anchor, after a spell ended early (a miss, a failure or a skip), and when a stop reaches it; it stays off at the limit. After a restart, an eligible idle agent lists as armed with its restored count; a stopped agent stays paused. The agent tells the service through `AgentsHandle::warm_changed`, and every change sends `AgentEvent::KeepWarmChanged { agent, keep_warm }` (a child's unwrapped, like `AgentStateChanged`); the main agent's goes out once at the tree's start too, since the snapshot leaves it out. `list_agents` and `/agents` show it (above, and "In the TUI").
- **Reminder.** The `agents` plugin's `lead` prompt section `agents/kept-warm` (in `core/notes`, after `idle/note`) opens a parent's turn with one line naming each of its own children that idles (not `asked` or `waiting`), is armed and has taken at least one refresh of this spell but not its last (`1 ≤ refreshes < limit`), with how long it has idled: `Children idle and still kept warm: /lead/planner for 1h12m. Each costs another cache refresh while it idles; end any you won't message again with stop_agent and end: true.` Its snapshot is one line per listed child (path, `since_ms` and `refreshes`, tab-separated), and the line names only children whose snapshot line the parent hasn't seen in this context window, so each child at most once per refresh; a head names every listed child. It is turn-message text, never the system prompt or the tool list.

### Waking when work is stuck

`agents.wake_when_stuck` ("Wake when stuck" in `/config`) is minutes, from 0 to 1440; 0 is off, the default. It is read at chat start and resume. With an open checklist, the main session wakes after no agent has worked for that long, counted from the latest of chat start, the main session's last turn end and the last child becoming idle. Running, stopping and queued children hold the clock. Wisp sends itself a notice asking it to move stuck work on or end its turn if it is waiting for the user; chat shows `↻ no agent was working`. Another wake needs a child to run or the checklist to change. A timer's recheck starts no turn and costs nothing.

With the same setting on, a child whose current step has retried for that long tells its own parent once: `/a has waited 40 minutes to retry a failed request and is still retrying. If it should not wait, stop it and give its work to another agent.` It keeps retrying, and only a later step can send another notice. The notice names no provider error text and wakes through the usual mail gates, at every depth.

Each wake costs one turn of the woken agent, plus whatever it starts. The quiet clock does not measure that agent's prompt cache: even at 40 minutes it can be cold after a resume, after children worked for over an hour, or with a 5-minute cache lifetime. With a warm 1h cache, short main-session mail turns reading 150k to 345k cached tokens have cost about $0.04 to $0.08 when only looking and $0.30 to $0.50 when acting (subscription estimates). Cold, the turn writes its whole prompt again: a 1h cache write is billed at twice the model's input price, plus output and whatever it starts. These are examples, not promises of a warm cache; Keep main warm can extend the cache lifetime. A wake is a real turn that commits, not a keep-warm refresh.

The main session's wake stops with no open checklist item, at 0, when you stop it, or after a wake that changes nothing and starts no child. Retry offers, held messages and restart preparation block it too. The child's notice stops after its one notice per step; 0 turns it off regardless of the checklist. Neither clock persists across a restart or resume.

The main session also wakes at a used-up limit's reset, whatever this setting says: when its turn stops on a used-up limit with a known reset, it retries that turn by itself a minute after the reset ([docs/endpoints.md](endpoints.md#switching-mid-session)). The stuck wake waits for that retry, as it does for any Retry offer.

### The stagger

Before a child sends a request (a step or a compaction), it claims its prefix key in the table, checking and claiming under one lock. A cold or warm key is claimed and the request goes. A `warming` key means another request with the same prefix is on its way and its cache entry isn't readable yet, so the child waits: during a turn its state is `queued(stagger)` until that request's first stream event, or for at most 5 s (`warmth::STAGGER_FOR`) in all. If the warming request fails (the key turns `cold`), the waiters try to claim it again: the first becomes the new warming request and sends, and the others wait for its first stream event within what is left of their 5 s. When the 5 s are up the request goes regardless. The request is built before the wait and sent unchanged after it: the provider's stream is created at once and polled only when the wait ends, and Cancel still stops the turn while it waits. So three children spawned with the same choices write the prefix once and read it twice. The main agent never waits (its prefix never equals a child's), nor does a background compaction. This is a delay of one request, not a wake hold: no `WakeHeld` and no log record. The request takes its endpoint slot before it claims the key, so a staggering child holds its slot for at most those 5 s.

The stagger relies on one rule every provider keeps: `Provider::stream` only encodes the request, and nothing goes over the network until the stream is polled; its first poll yields `Sending` and the connection opens on the next one (tested for Anthropic in `the_stream_connects_only_when_polled_after_sending`). A provider that sent on `stream` would defeat the stagger.

### Run permits

A child runs a turn only while it holds a run permit. It takes one before any turn, whatever starts it (the brief, mail, a wake, your send, Release or Retry through `Child`), and returns it when the turn ends. A worker's permit needs a place in its parent's pool of `agents.max_running` and one in the tree's pool of `agents.max_tree_running`; a non-worker (`worker = false` in its preset) gets its permit at once and fills neither. A spawn gets a permit at once when both pools have room; otherwise it starts `queued(concurrency)`. A child that wants a turn without a permit joins the tree's one queue, and each returned permit goes to the oldest waiter whose parent's pool has room, which wakes; a waiter whose parent's pool is full keeps its place without holding back the others. `/agents` shows a waiting child as `queued: running limit`. Waiting shows as `queued(concurrency)`, except a wake by mail from a child or a sibling, which is a held wake: one `WakeHeld { reason: concurrency }` and `wake_held` per episode, and the state `held(concurrency)`. Mail from above waiting for a permit also writes that `WakeHeld`, with the state `queued(concurrency)`. The 2 s settle of a mail or process wake runs whether or not a permit is free, so a wake whose settle has passed starts as soon as its permit arrives. A granted permit that finds nothing to start is passed on at once, and an agent that ends leaves the queue. Compactions run without a permit. The main agent takes none.

A child that leaves the queue without a turn (you withdrew the message that wanted one, or the permit passed it by with nothing to start) shows its idle state and outcome again at once. Stopping a child that waits for a permit or whose mail or process wake is still in its settle (`Child { Cancel }` or a stop cascading from an agent above it, which reaches running, queued, concurrency-held and settling children) takes it out of the queue: it ends `idle(stopped)`, sends its parent the stopped notice (`… was stopped by the user.` or `… stopped with its parent.`, not waking), and its waiting mail stays put without waking it, so it shows `held(stopped)` like any agent whose last turn was stopped. New mail from above, your send, Release or Retry starts its next turn, and only then does it ask for a permit again.

While a tree gets ready for a restart, no agent receives a new permit, the
main agent included. Existing steps finish before parking. A spawn waits even
when its preset is not a worker. Cancelling getting-ready releases the waiting
starts without changing the normal pool limits.

### Getting ready for a restart

The host sends the main agent `GetReady { on: true }` to get its whole tree
ready. No new turn or typed `/compact` starts. A running turn finishes its
current reply and all the tool calls of that step, commits their results,
then parks before its next request, including any compaction. A final reply
ends its turn normally, except a child still owing its report parks and is
reminded to report when work carries on. An admitted turn still preparing its
hooks or a foreground compaction also parks before its first request. An open
question counts as ready.

The service reports `Restart { state, open }` when the unfinished work changes:
`getting_ready` while a reply, tool call or numbered process remains, then
`ready`. Rows identify the agent, kind, description when given, target and
elapsed time. The first reply to a user message also carries `opening`.
Descriptions come from the tool display, never from interpreting a command.
Numbered processes retain the description of the call that started them;
processes set to keep running after Wisp exits are not waited for.

`GetReady { on: false }` reports `cancelled` and lets work carry on. A parked
turn takes its waiting messages and mail before its next request. Getting
ready sends no provider request and edits no history. Closing the command
channel instead ends a parked turn as cancelled and records it as interrupted;
waiting mail remains available on resume. The event stream drains through
the main agent's last event before it closes.

### Costs

Every child's cost is its own `session_usd`, which already counts every priced request: steps, failed attempts, compactions and keep-warm refreshes, with its lower-bound flag. A child publishes it with every record it logs, and each change sends `AgentStateChanged` with the new `spent_usd` and `lower_bound`, so the figures move live while the main agent is idle. The main agent's `Cost` (in `TurnEnded`, `Compacted`, `CompactionPrepared` and `CompactionFailed`) carries `agents_usd`, the sum over every child the tree has had, ended ones included, and `agents_lower_bound` when any of them is a lower bound; both are absent until the first spawn. Each agent prices with its own endpoint's flag, so a child on an unpriced endpoint (`pricing = "none"`) spends `0` with the lower-bound flag and makes the tree's total a lower bound (`+`); its `AgentEntry.priced` is false, and its own log still records each request's estimate as `list_usd` (`docs/session-log.md`). The parent's `agent_ended` keeps the child's `plan_usd` and `billing` beside `spent_usd`, so when the child's log can't be read on resume, the parent still has the real and subscription parts apart. Nothing stops on cost: there is no cap per agent or per run.

Each agent also splits its spend by account, in `accounts` on `AgentEntry` and `AgentStateChanged`: account name → `AccountSpend { usd, plan_usd, lower_bound }`, with `plan_usd` the subscription part, absent when the split is unknown. A request counts under the account the agent was on when it was charged, live and on resume, which rebuilds the split from the account the `session_started`, `session_resumed` and `turn_started` records name; a turn-end snapshot that differs from the summed records adds the difference to the turn's account. Spend whose records name no account (an old log, a `resume_fell_back` carry-over, a child whose own log can't be read) counts in the totals only. The main agent, in a tree, sends its own split as `SpendChanged { total, accounts }`: once at the tree's start, beside its `KeepWarmChanged`, and then before each record it logs after its spend changed. It is never logged, and `--output jsonl` prints it as `spend_changed`.

### Quitting

When the main agent's command channel closes, the main agent closes the tree first, before it closes its own mailbox or waits for its processes: every child's command channel closes, each child stops its turn as a quit does (writing `turn_ended` and `session_ended`), and its state becomes `ended`. A child whose report mail can no longer be delivered keeps owing it and logs no `agent_reported`. The `AgentTask` joins every agent, bounded by the largest quit margin among them.

A hosted chat keeps running when its terminal closes or loses its connection.
Its host ignores SIGHUP; SIGTERM sent to the host quits the chat and its tree.
A logout that kills user processes, a machine restart or WSL stopping still
ends it (`docs/daemon.md`).

In a chat that lives in its window, and in `--output jsonl`, SIGTERM and SIGHUP
(closing the terminal window, logging out, `kill`, a service manager) quit the same way: the full screen restores the terminal at once and draws nothing more, the running turn ends interrupted and every agent's programs are stopped and logged, and `wisp` then dies by that signal (as a container's init, it exits with 128 plus the signal). It dies within 10 s, the longest a quit with programs running takes, which can cut a quit still waiting on a settings save; resume stops whatever the cut left running. A repeat of either signal is ignored, since a closing terminal sends two. On Linux, a signal ignored when Wisp starts, as under `nohup`, stays ignored. SIGKILL can't be caught: what it leaves running is stopped when the chat is resumed.

### Resume

`wisp --resume` opens the whole tree with its root. If the chat is kept open,
it attaches to that host and replays its current view; no agent restarts and
work continues unchanged. For a stopped chat, the log reconstruction below
sends no request and restarts nothing the exit stopped; afterwards only what
would have run without the exit runs.

- Finished helpers' spend, row and links are kept beside the logs, so an unchanged log need not be read again. Missing, stale or damaged facts are rebuilt from the log. A new input to this derivation must join a fixture in `agents/service/kept/`, so the derived version changes with it. The version uses no live credentials or workspace paths; cached checklist fields are [checked again on load](session-log.md#checklist-privacy).
- **Finding the tree.** From the root's log down, the tree follows each log's `agent_spawned` records (its children) and `agent_ended` records, masked by a rewind or not (an end is a fact about the session). An agent has ended if and only if some log holds `agent_ended` for it or an ancestor; a child's own `session_ended` only ends a run. An ended agent's facts come from its kept entry when the log is unchanged, otherwise from a read only (no lock, repair or record). An end not logged before a crash is lost, so that agent resumes live.
- **Renames.** The root's `agent_renamed` records, masked by a rewind or not, are applied in order to every logged path before it is compared: the spawned paths, the ended ones, each child's parent link, and the senders and `send_message` targets its state is folded from. Agents resume under their new paths, and the old ones stay taken and keep reaching them.
- **A live child's log** is the one `agent_spawned.session_id` names, reopened with the root's lock choice (`--resume-unlocked` covers the tree), and its `session_started.parent` must name the same path and the parent's session id. A child whose log is missing, unreadable from its start, names another parent or is open in another Wisp isn't loaded: it stays in the tree as ended for this run (its name stays taken, mail to it is refused, its spend is what its log shows, else `agent_ended.spent_usd` or 0, marked lower bound), with one warning, `/a wasn't resumed: its log names another parent; it stays ended for this run`. Its log gets no record, so a later resume tries again. The rest of the tree resumes.
- **Configuration.** Every child resumes on its logged configuration: its model, effort, cache TTL, working directory (a warning if it is gone), project and preset instructions (the files are loaded again for the block, which a preset file's edit or removal never changes: a section that no longer loads is left out silently, since the logged prefix is what the child keeps sending) and tool names, each tool started through the catalog for that child alone, the native `web_search` included, exactly as logged: a log written before the agent tools were grouped that names `spawn_agent` without its followers resumes without them, with no rebuild and no warning. A logged tool the child still offers that no plugin provides now is turned off with one warning (`/c's tool hammer isn't provided by any plugin now, so it's turned off from its next message`): the child resumes on its logged prefix, the tool leaves by removal or note at its next message and its calls are refused, so it rebuilds nothing (`docs/tools.md`, "Resuming a session"). A later resume, where the tool is already off, warns nothing. A child that can't adopt its logged copy (a fallback endpoint whose server tools differ, say) takes the old path: the warning reads `… so it resumes without it`, and it counts in the rebuild warning below. So does a child that adopts its copy and rebuilds at its first opening (an upgraded definition on a pair without `inline_tools`, say), with no amount, since that rebuild isn't priced at load. Presets don't change a live agent, except `worker`, which is read from the config at each start, a resume included, and marks nothing: each preset now removed, disabled or with keys that differ from the preset as it was when an agent was spawned with it (`agent_spawned.config.preset_values`; a spawn's own overrides don't count) marks those agents, and new spawns use the preset as it is now. The full screen shows one start note after the replayed history (`2 presets changed since agents started; see /agents`, a count of the changed presets), and `/agents` marks each such agent on its panel's second row, after its account (`preset changed`, `preset off`, `preset removed`; below). jsonl keeps one sentence per preset on stderr, before the resume line, naming those agents (`preset rev has changed; /r keeps the configuration it was spawned with, and new spawns use the preset as it is now`). An ended agent is never marked. An agent whose `<environment>` agent lines (its presets line, for one) now differ from the last ones in its history sends the block again at its next turn, logged as that turn's `context`; nothing else in the request changes. A tree logged before free-text reports (log schema 29 or older) resumes with its report lines taken from each typed report's `summary`; since the `report` tool's text changed, each agent's first request rebuilds its cache, which shows as one tree-level warning (`Wisp's prompt or tools changed since this tree ran: 2 agents rebuild their cache on their next request …`), and its next report takes text.
- **Endpoint.** A child normally resumes on the endpoint its last turn used (`turn_started.endpoint_name`, or `session_started.endpoint_name` if absent). An explicit next-account choice from its log still applies if the exact account and provider match, with positive evidence of matching billing for an API account. The child keeps its last account for pre-turn compaction if it is still ready; otherwise it can continue only on the checked next account. A legacy or rejected choice uses normal last-turn placement. The endpoint must be ready and of the provider the child last ran on: its own `settings_changed.provider` for that pair, or its parent's `agent_spawned.provider` when the child log has no provider for that turn or has no turns. If neither record supplies a provider, the account must serve the child's model. Otherwise, gone or another provider now, it falls back to the main agent's endpoint when that is the same provider (for an unrecorded one, when it serves the child's model), with a warning: `/r ran on account b, which isn't configured now; it continues on claude-subscription with model m` (or `which is another provider now`). One whose account is set up but can't be used now (a sign-in or keychain that can't be read, an unset variable) goes to the account new chats start on, never to the chat's: it continues there, with `which is unavailable now (<reason>)`, when that account takes its history and the move doesn't start charging, and no consent moves it onto the API. Otherwise it isn't loaded this run: the root's `session_resumed` event carries it in `stay` with its account, the account's state words and whether a sign-in fixes them (`from`), and a moved one carries `from` and `to` in `moved`. The TUI lists such agents under `Not resumed`, one row each, `coder   claude-team: sign-in expired · /login claude-team`, the fix only when a sign-in fixes it; every other output prints one line each on stderr, `wisp: coder not resumed: claude-team: sign-in expired; run wisp login claude-team.` A log naming `env` resolves to the keys-file account under its current name (`docs/endpoints.md`, "The keys-file endpoint"); when that account is gone, its warnings say `the keys-file account` instead of naming `env`. A child that falls back records the move at its first turn as a live switch does (`settings_changed` with an `endpoint_switch` rebuild and its `account_bound` models, then one `rebuild_marked`), so its first request extends its history and carries one rebuild mark. Else, and always when the selected provider is one this Wisp doesn't know, the child isn't loaded this run and its log gets no record, so a later resume, with the endpoint back or on a newer Wisp, resumes it live.
- **Billing.** Except for an exact next-account choice the child already made, a child never starts charging on resume without the chat's consent. Its logged billing mode is read from its own log by the root's rule (`resume::billing_mode`: the last `credential_source` mode logged on its endpoint). Every child log records that mode in its `session_started`, metered or plan, usage or not, so a child log without one was written before Wisp logged billing modes, when every endpoint was metered, and reads as metered (the root reads such a log as metered too). A move that can't start charging needs no consent: API to subscription, subscription to subscription, or API to API (`endpoints::goes::starts_charging`). So a child stays on its logged endpoint unless that endpoint now moves it from a subscription to the API, and falls back to a main agent's endpoint of the same provider on the same terms. Only a move from a subscription to the API needs consent, and it is given per agent: the resume card's row names the chat's direct agents whose account can't be used now, those the row's account takes as moving with the chat (`LoggedKind::takes`: one of the row's provider, or, for one whose log names no provider, a row that serves its model) and the others as staying behind (`docs/endpoints.md`, "Resuming"), and the chosen row's `follow` reaches the start through `StartOn`. Without that earlier choice, a child moves onto the API only when `follow` names it, so a deeper agent, and every agent after `--account claude-api --resume ID`, which names none, isn't moved there. So a child on a ChatGPT subscription whose sign-in lapsed never falls back to a metered OpenAI key. Otherwise it isn't loaded this run, with a warning (`/r wasn't resumed: it ran on account chatgpt, which isn't configured now, and api bills differently; it stays ended for this run`, or `which bills differently now` when its own account changed); on the TUI, one whose account is gone shows as staying behind instead. The `it is metered now` clause appears only on a fallback, from an unpriced metered endpoint to a priced one.
- **A child that isn't loaded,** for any cause, sends its parent one notice per resume, naming the cause in fixed words and never the underlying error: `/r wasn't resumed this run (its account gpt is unavailable); it stays ended until a later resume.` (or `its account gpt isn't configured`, `its account gpt is another provider now`, `its account gpt bills differently now`, `its log names a provider this Wisp doesn't know`, `its log can't be opened or read`, `its log names another parent`, `its log names no working directory`, `its accounts couldn't be connected`, `it couldn't be built`). It wakes the parent only when the child owed it a report and the parent isn't the main agent; otherwise it is read at the parent's next turn. A log that can't be read owes nothing. Ended and unloaded agents show the endpoint their `agent_spawned` names, with its provider only when it is one this Wisp knows.
- **Flags.** The resume command's flags and `--set` values are the root's alone (`docs/session-log.md`, "Flags on resume"). A child sees no explicit flags, so `--model`, `--effort`, `--cache-ttl`, `--instructions` and the rest never reach a resumed child, which keeps its logged configuration and sends the same requests as after a resume without flags. Children spawned later follow the root's flagged `--instructions` source, as on a fresh run.
- **Plugins.** Each resumed child gets its own plugin instances and catalog, shared with neither the root nor a sibling; only the root takes the prestarted ones. Ended agents start none.
- **State.** Each live agent's state comes from a fold over its own log (`agents::fold`), with [checklist privacy](session-log.md#checklist-privacy) applied to checklist fields: whether it owes a report (a `task` from above sets it; each `agent_reported` sets it to whether a task was still waiting), the agents it asked and the questions it holds, the peer-cap counts, `running_ms` (the sum of its turns' durations), its checklist and its last report line. Its context fill is its `context_now()` at load: the last measured step's when its log has one, otherwise an estimate. An ended agent isn't loaded and has no fill. Every loaded agent starts idle with the outcome its last turn left: stopped for a cancelled or interrupted turn, failed for an error (or the report's own outcome when one was logged), the report's outcome after a report, `asked` or `waiting` when it completed owing, and otherwise the outcome before. A child that completed owing, with its process news worded and news of its own processes from before the restart still unread (stopped by the exit, ended just before it, or not checkable here), resumes `waiting` even if it folded `asked`, and its parent gets one notice, `/review won't be woken by its processes from before Wisp restarted; message it to continue.`, which wakes a coordinator and reaches the root with `wake: false`, since restored processes never wake an agent. Each resume before the child runs again repeats it. Turn signals, nudge counts, run permits and their queue are reset.
- **The wake gate.** An agent whose last turn was stopped, failed or interrupted, or whose last held wake was a stop, resumes held, with its waiting mail marked returned, so that mail doesn't restart it, except waking mail from above that arrived after that turn ended (or after a stop while queued), which runs it as it would have live; your send, Release or Retry, or new mail from above, releases it. After a completed turn its gate is armed, and waiting mail wakes it after the usual settle. The root follows the same rule, except that when its last turn stopped at the step limit on unreadable replies other than `MALFORMED_FUNCTION_CALL` with Retry offered, a new waking message from another agent that arrives after the resume takes that Retry (one round per message), while letters restored at the resume start nothing.
- **Interrupted turns.** A turn running when Wisp exited is interrupted: still open after a crash, or named by a `session_ended.interrupted` written after it ended (at any later exit), which an agent writes when the exit stops its running turn, or when it drops a child's accepted Retry (by hand or from a move) before its turn (`docs/session-log.md`), so it stays stopped through later resumes until it runs again. A turn the exit named, or one a crash left open (which resume closes as interrupted), counts as stopped for the gate and the outcome. An interrupted child resumes `idle(stopped)` and held (after a crash, held by its Retry offer), and at load its parent gets one notice from it, `/a/w was interrupted when Wisp exited; message it to continue.`, which wakes a coordinator and reaches the root with `wake: false`. The notice goes out only on the first resume after that exit; a later resume sends none. A log from before this field reads a quit's stopped turn as stopped, with no notice.
- **Carrying on after a restart.** With `TreeSetup.restarted`, each agent whose turn that exit cut gets waking mail from itself: `Wisp restarted. Carry on from where you stopped.` It arms the completed-turn wake gate, clears returned marks on waiting mail, puts back in the composer what the dropped Retry would have resent, and leaves no repair Retry offer holding that agent asleep. An idle agent whose last turn completed and whose process news is worded gets the same notice for unread news on the first resume after that turn's exit, instead of notifying its parent; its usual `<processes>` block explains what stopped or ended. Neither parent notice above is sent. A main agent whose cut turn kept no reply still waits for the user; a turn cancelled by the user, or cut at an earlier exit and left stopped, is not woken for process news. Without the flag, resume is unchanged.
- **Queued children.** Run permits aren't logged, so every pool starts empty. A child queued at the exit still has the mail that queued it waiting, so once it starts it asks for a permit again in the usual way.
- **Costs.** A live child's spend comes from its own resumed log, an ended one's from its kept facts when the log is unchanged, otherwise from its own log as read (its `agent_spawned` and `agent_ended` records are read past a damaged line too), so after a clean exit `agents_usd` and every entry's `spent_usd` equal their values before it; after a crash they are lower bounds. An ended agent whose log ends in an open turn, and one that wasn't loaded but spawned children of its own (whose logs aren't read), count as lower bounds too.
- **A crash between a report's two records.** A child logs `turn_ended` and then `agent_reported`, after its report mail has gone to its parent. A crash in the moment between the two leaves the parent holding the report while the child's log has none, so the child resumes `idle(waiting)`, still owing, with no report line; its next turn, from a follow-up, owes and reports again. The window is the time between two log writes.
- **A crash while a child's Retry waits.** A crash or kill after a child's Retry is accepted and before its turn starts writes no `session_ended`, so the child resumes `idle(failed)` and its parent gets no interruption notice.
- **Warmth.** The Kit's warmth table starts empty, every key cold.
- **Keep-warm.** A marked child resumes marked, from its parent's `agent_spawned.config.keep_warm`. After a resume by hand it shows `keep-warm: paused until its next turn` (0 refreshes) until a completed turn arms it; the main agent takes `keep_warm` from this run's settings and starts paused too. A restart restores an eligible idle agent's spell and count instead, as described in "Keep-warm".
- **Follow-up.** A child that reported, stopped or failed keeps its whole context and name. A child that moved to another provider resumes there. Its next turn, from a parent's `task` or your `Child { Send }`, extends its pre-exit history byte for byte with the same `tools` and `system`, so it reads its cached prefix.
- **Mail ids** continue past the highest `mN` in any log of the tree, ended agents' included.
- **Finding a session.** `--resume` without an id skips logs whose `session_started` has a `parent`. `--resume <id>` that matches a child refuses: `session 0002bbbb-0000 is an agent in session 0001aaaa-0000's tree; resume the tree with wisp --resume 0001aaaa-0000`.

## In the TUI

The TUI learns the tree from events only (`docs/plans/subagents.md` §13 and §15): once the session has started (after first-run setup, never during it) it sends `ListAgents` and builds its table from the `AgentsSnapshot` answer, then keeps it with `AgentSpawned`, `AgentStateChanged`, `KeepWarmChanged`, `AgentReported` and main's own `SpendChanged`. The snapshot leaves out the main agent; main's row takes its session ID from the session log's name, and its endpoint, provider and pricing from the session's facts (the current endpoint's name and that endpoint's `provider` and `priced`, priced when the facts don't name it). The table is `wisp_tui::app::agents`; the drawing is `wisp_render::chrome::agents`.

- **The strip.** The top row of the bottom frame (`docs/design/tui-brand.md` §7.5), above the waiting messages, shows the agents on its left and the tree's total on its right; it is an empty framed row while it has neither, stays under every picker, card and overlay, and goes below 9 rows or when a picker, card, list or `/resume` needs its rows. The left reads `⧉ 5 agents · 2 working · 1 failed` (ASCII `=`): the live agents, those running or stopping a turn (a queued, held or stopped agent counts only among the agents), and those whose last turn failed, in the error colour; a zero count is left out. It names no agent and shows no clock or context; `/agents` has those. The right reads `total ~$44.06`: everything this chat and its agents used, across every account, at API prices, so subscription estimates and real API spend summed (`chrome::shown_total`: this chat's spend as the kernel last sent it in `SpendChanged`, plus each agent's own). `~` marks it when any part is a subscription estimate or the split is unknown; only a total known to be API spend alone is bare (`total $0.31`). A trailing `+` marks a lower bound (an unpriced step, a running agent, or this chat's own reply or compaction still running): `total ~$44.06+`. It stays hidden until something is spent. This is the only place Wisp adds API spend and subscription estimates together, and the goodbye shows the same figure; `/usage`, the `/agents` rows and the logs keep them apart. As the width shrinks, `agents` leaves first (`⧉ 5 · 2 working · 1 failed`), then working when a problem outranks it (`⧉ 5 · 1 failed`, else `⧉ 5 · 2 working`), then every state (`⧉ 5`); after that `total ~$44.06` shortens to `~$44.06`, and above 12 columns the amount never drops.
- **Mail rows.** A message from another agent is a row of its own, `◇ report from /review` with its first line below it, drawn the moment it arrives while main is idle (held or not), when main reads it while main works, and at the turn's end, in arrival order, when a turn ends without reading it. A report shows Wisp's line, then its own first line. A *note*, a message sent with `wake: false`, is one grey row in the main chat, `◇ note from /x · its first line`, cut to fit and ending in `▸` when it hides something; a quiet notice folds the same way under `notice`, and notes in a row sit together. An agent's chat and Ctrl-O's full transcript show each note whole, as any mail row. It never enters the waiting stack or Up recall, Ctrl-O opens it like any cell, a rewind keeps the mail rows before its point, and a resumed session shows its past mail where it arrived. A notice labelled with a plugin is drawn as that plugin's line (`plugin mcp: …`), not a second mail row. It is still ordinary notice mail to the agent. A long sender path is cut instead when needed to leave the first four columns of the words visible, including `API:`.
- **Waiting mail.** While main is held and mail waits for it, a line shows below the waiting messages: the count of every unread message, notes included (`1 message from an agent waits`), then `send a message to deliver it` and the reason (`the last turn was stopped`, `your messages are held`, `a retry is offered`), wrapped between whole parts. The resumed kernel announces mail still waiting at load with `InputAccepted` and writes no record; the TUI keys mail by id, so mail the resumed transcript already shows is never counted twice. A delivered message leaves the line when the turn that took it completes.
- **Quitting.** While any agent is running, stopping or queued, Ctrl-C and Ctrl-D arm first: `Press ctrl-c again to quit: 2 running agents stop until wisp --resume`, and a second Ctrl-C or Ctrl-D quits. Held and idle agents never arm it. `/exit` and `/quit` quit at once without arming. From the moment any quit starts until exit, the status row shows `Shutting down, please wait…`, with one live detail when waiting on settings (`saving settings` / `applying settings`), busy agents (`stopping 2 agents`), or background processes (`stopping 2 processes`). Leaving a chat that ran a turn or stopped an agent prints a goodbye: the time this run took, the strip's total, a line on the agents it stopped and, when the chat is logged, `wisp --resume` and the session's 13-character short ID, which includes the UUIDv7 millisecond stamp for IDs generated by Wisp. Every session prefix Wisp prints is that short ID. Esc that stops main's turn while agents run says `Stopped main · 2 agents keep running (ctrl-t)`.
- **The page.** Ctrl-T or `/agents` opens the Agents page (`docs/commands.md`): agent-viz's topology (`agent-viz/topology`, asked for as the page while it is open), main at the top and each live agent under its parent, with the legend under it, then a rule and two panel rows for the picked dot, then the keys `enter open · r release · ←↑↓→ move · esc close` (`r release` only while the picked agent holds your messages; ASCII `arrows move`; keys drop from the right, `esc close` kept). In Braille the picked dot sits in brackets; with pictures on (`display.pictures`, `docs/settings.md`) the pixel marks size to the space between them and the picked one gets accent brackets. In both, each mail between agents runs along the lines as a light that rings its receiver as it lands (`docs/plugins.md`, "A topology is a graph without text"); in Braille the ring covers the picked dot's brackets and the scroll marks for its 280 ms. At 60 columns and up a list on the left names main and every live agent under its parent, even with agent-viz off. It uses at most a third of the screen and keeps the picked row in view. While it shows, ↑↓ walk the list in tree order; ←→ move to the nearest dot that way. Under 60 columns there is no list and all arrows move between dots (ties go left). Click a row or a dot, or press enter, to open its chat; on main this closes the page. When the picked agent ends, the pick climbs to its parent, ending at main. Panel row 1, at 100 columns or more, is the dot, the name, model and effort, the state with its clock and activity (`running 2m 14s: bash`, `idle 1h 12m: reported`, the idle time counting from when the agent's node state last changed), cost, context and checklist, three spaces apart; from 60 to 99 columns it drops the activity and checklist, two spaces apart; under 60 it is the name, state and cost. Row 2 is the account chip with its billing (`claude-work · subscription`; a long account name is cut, never the billing word), `preset changed` (`preset off`, `preset removed`) for a live agent whose preset changed since its spawn, its keep-warm as `list_agents` words it (`keep-warm: 2 of 8 refreshes`, `keep-warm: paused until its next turn`) for an agent or main kept warm, each shown whole or not at all, and the last mail the agent got with its age (`task from /lead, 2 min ago`), or under 60 columns the model and account. Main's rows show its model, state, cost and account; each row is cut from the right to fit. When agent-viz is off, before its first content and while its page has failed, the page shows `agent-viz is off · /config` (or nothing) above the panel, and ↑↓ step through main and the live agents in tree order. Esc and Ctrl-C close the page, and Ctrl-C there never stops main's turn.
  Hover over a dot to see its agent's name.
- **Live account moves.** A live agent's bound account is the one it last settled on; an accepted `/account`, `/model` or `/effort` can already have changed its effective next place. A sign-out or provider-off card uses the effective place to choose and quote idle followers. A child pending onto a retiring account is eligible; one already pending away isn't redirected. Its old binding still matters when it is working or must release the retiring account. A named idle child in a confirmed row can follow across providers, keeping its conversation but not provider-private reasoning. These are live rules, not stopped-session placement rules.
- **An agent's chat.** On an agent's dot in `/agents`, enter or a click opens its chat: the main chat's screen, box, keys and status row, filled with the agent's own transcript, live, and it sends `WatchAgent { live: true }` so its tool output streams in. Three marks tell it from the main chat: a header over a `─` rule in `line` (` ⧉ /lead/coder · running · ~$0.80+`: the path, the panel's state word without its clock or `waiting on its process 3`, and the panel's cost, dropping whole facts from the right as the width shrinks), `esc back` on the status row, and the box's placeholder `Message /lead/coder`. After a rename the open chat, its header and placeholder, `/ps` and the `/agents` pick follow the new path, and main's spawn rows keep linking the agent under its old name, also after a resume. The status row is the agent's own: its phase and clock, account and model; a click on its chip opens nothing. The TUI keeps a transcript, a box and a status per live agent, fed from its wrapped events from the moment it learns of the agent, and drops them when the agent ends. Typing goes to the agent's box: enter sends `Child { Send }` (a steer while the agent runs, which it reads at its next step), tab queues it while it runs, and enter on an empty box sends your messages held at it (`Child { Release }`); its transcript scrolls as the main chat's does (the wheel, pgup and pgdn, home and end on an empty box, ctrl-home and ctrl-end, `↓ 4 new · ctrl-end` and a click on it), and a drag selects and copies the agent's text, with `ctrl-c copy` on its status row and never `esc to stop`; opening or leaving the chat clears a selection. A command works as in the main chat: `/help` (or `?`) opens help over the chat, and closing it shows the chat again; Wisp's other commands go back to the main chat and run there; `/model`, `/effort`, `/account`, `/context`, `/compact` and plugin commands run on the agent, for this session only, with its own pickers, reports and notes in its chat, and shift-tab cycles its effort; `/rewind` takes the agent back (`docs/rewind.md`, "In the TUI"); `/ps` opens over the chat on the session's one list of every agent's programs, and each key there acts through the program's agent (`docs/commands.md`); no command is refused in an agent's chat. Esc goes straight back to the main chat from any agent's chat (an open picker or rewind list closes first, and a selection is cleared first), and so do ctrl-c on an empty box (with text in it, ctrl-c clears it) and an agent that ends while its chat is open (`/w ended` on main's status row); ctrl-t goes back to the main chat and opens `/agents` there; every way out sends `live: false`; ctrl-d does nothing. Main's question card or a step-in waits behind the chat, unseen and taking no keys, and the chat's status row says `main needs you`; a text paste while a step-in waits is dropped. A message the agent's stopped turn hands back, or one refused on its way or by the agent, goes back into that agent's box, never taking the keyboard or touching main's draft: `Your message to /w is back in the composer` while its chat is open, otherwise `Your message to /w came back · ctrl-t`. Messages held at a stopped agent read `/w stopped · 1 queued message held`. When an agent ends holding your text (its box, or messages still waiting or undelivered), each goes into main's history, the waiting ones oldest first and the box's text last, and the status line says `/w ended · your message is in main's history` (`your 2 messages are in main's history`). The TUI never stops or ends an agent: only its parent does (`stop_agent`), and quitting stops them all. In `/agents`, `r` releases your messages held at the picked agent, offered while it reads `held: your messages` (a held agent reads `held: retry offered`, `held: stopped` or `held: concurrency` otherwise); on main `r` does nothing; ctrl-d does nothing.
- **Spawn rows.** A `spawn_agent` row is linked to the agent it started, by name, and adds that agent's state and directory to the row's facts (`running · in ~/Projects/Wisp`); once the agent has reported and gone idle the state reads `idle` and its outcome and report line go below the row (`reported · Planned the change in 5 steps`), and they stay there after the agent is ended (`ended`). Only the main agent's own children are linked.

## Example: the project flow

A project can be run by a flow of roles, run as agents; this simplified one illustrates the agent tools, and Wisp's own, with its presets and role files, is `flows/projects/`. The session you talk to is the main session; each running task gets a coordinator child, and each coordinator spawns the task's planner, reviewers and coder. That is depth 2, the default `agents.max_depth`.

The presets, in `config.toml`:

```toml
[agents.presets.coordinator]
description = "Runs one task's whole flow: plans, reviews, fixes, verifies, hands over to merge"
effort = "xhigh"
instructions = "roles/coordinator"

[agents.presets.planner]
description = "Writes a task's plan from the real code and research; no code"
effort = "xhigh"
spawn = false
instructions = "roles/planner"

[agents.presets.plan-reviewer]
description = "Reviews a plan from scratch against HEAD; labelled findings only"
effort = "xhigh"
spawn = false
instructions = "roles/plan-reviewer"

[agents.presets.code-reviewer]
description = "Reviews an MR's diff against its plan; labelled, verified findings only"
effort = "high"
spawn = false
instructions = "roles/code-reviewer"

[agents.presets.coder]
description = "Implements an MR exactly as planned and keeps the gates green"
effort = "medium"
spawn = false
instructions = "roles/coder"

[agents.presets.merge-agent]
description = "The only agent that commits, verifies and merges MRs through the verify-and-merge tools"
effort = "medium"
spawn = false
instructions = "roles/merge-agent"
```

Each `roles/<preset>` directory beside `config.toml` holds the role's `AGENTS.md` (`~/.config/wisp/roles/planner/AGENTS.md`; a `~/` path works for files kept elsewhere): what to read first, what the role does, its hard rules and a "Your report" section. The project's `AGENTS.md` is in every child's prompt already, so a role file doesn't repeat it. A planner's might read:

```markdown
# Role: planner

You write a task's plan from the real code and the research, and no code. Check every claim against HEAD and name the file and line it rests on.

## Your report

- the plan's path;
- the MRs, one line each: title, size and what each needs first;
- the open decisions, numbered, each with a recommendation.
```

A task then runs in five steps:

1. Main spawns the task's coordinator: `spawn_agent { name: "agents-flow", preset: "coordinator", cwd: "~/Projects/Wisp-worktrees/agents-flow", task: "…" }`. The brief is the job and its files, never the role's rules.
2. The coordinator spawns `planner`, then two plan reviewers, and may end its turn while they work: each report arrives as a `<wisp:message … kind="report">` and wakes it.
3. Fix rounds go to the same child with `send_message`, a new task it reports on, so the planner fixes its own plan and a reviewer re-checks only the fix.
4. A child that needs a decision asks its parent, which answers or puts it in its own report; only main asks you, with `ask_user`.
5. The coordinator ends each finished child with `stop_agent { name: "planner", end: true }`, spawns the coder and a code reviewer the same way, and reports ready to merge; main hands the MR to its `merge-agent` child.

Ctrl-T or `/agents` shows the tree: enter opens an agent's chat, where you talk to it as in the main chat and esc goes back; only its parent stops or ends it. Quitting and `wisp --resume` bring the whole tree back. Past `agents.max_running` of one parent's children or `agents.max_tree_running` across the tree running at once, the rest queue (`queued: concurrency` in `list_agents`); agents whose preset sets `worker = false` never wait.

## In the code

- `wisp_protocol::agents`: the tool names, `Preset` (the wire form, with no maps) and the preset fields `docs/settings.md` is rendered from.
- `wisp_core::agents`: `Limits` (resolved from the settings layers) and `Presets` (parsed from `config.toml` by `ConfigFile::parse`, then `Presets::checked` against a model's efforts from the provider's capability table, giving `CheckedPresets`).
- `wisp_core::agents`, the service: `service.rs` (`AgentsService`, `AgentsHandle`, `start_root`, routing, forwarders), `brief.rs` (the brief, the environment lines, the mail texts and report rendering), `report.rs` (the `{ text }` check and the logged report line), `guarantee.rs` (the pure turn-end decision), `state.rs` (the state machine and activity), `names.rs`; `testing.rs` holds the test-only `bash` and `process` entries the service tests give the main agent.
- `plugins/agents`: the `agents` plugin (descriptions, schemas, the strict input reader, the report schema); `crates/wisp-tool-text/src/agents.rs`: its wording (the started line, the list, the sentences, the spawn `todos` rule the kernel checks); `crates/wisp-core/src/plugin/host.rs`: the `agents` host interface (`Agents for PluginHost`).
- `wisp_core::agents::service::limits`: the run-permit pools and their queues, the spend each child publishes and the tree's total.
- `wisp_core::warmth`: `STAGGER_FOR`, `WarmthTable::cooled` (the stagger's wait), `Fingerprint` (the per-component digests and the prefix key, from `provider::PrefixBytes`, which `Provider::prefix_bytes` returns), `WarmthTable`, `Heat` and the `Ticket` each request holds until its first stream event.
- `wisp_core::lanes`: `Lanes`, the tree's one in-flight limit per endpoint (built by `wisp-start` from `endpoints.<e>.max_in_flight` and each account's kind, and held by the Kit beside the warmth table), its `Waiter` (ordered by depth, then arrival) and the `Pass` a request holds until its stream ends; `wisp_core::agent::lanes`: `enter_endpoint_lane`, the cancellable wait before each turn and compaction request, and its `RequestQueued` and `RequestAdmitted` events.
- `wisp_core::agent`, the stack: every agent's task polls its turn loop, and a spawn builds the child on top of it, so a debug build's large poll frames can pass a tokio worker's 2 MiB stack. In a debug build every inline `.await` keeps two copies of the awaited future in the caller's poll frame, so a frame grows with the size of every future it awaits. The futures on the turn loop's, the hook points' and the compaction's paths, and widely awaited leaves such as `Agent::emit` and `Agent::log`, whose futures would otherwise sit inside nearly every other one, are plain functions that box their futures, most of them an `_unboxed` one (`grep -rn 'Pin<Box<impl Future' crates/wisp-core/src` lists them, with the Kit's), so the futures that await them hold a pointer instead of copies of the whole state, and their poll frames, which are what overflowed, shrink to match. `Box::pin` around a future built inline doesn't shrink the caller's frame, since the future is built there before it moves to the heap, and a wider shared type such as `Usage` grows every frame that holds a future carrying it. A spawn builds the child on top of that chain, so the Kit's child build is boxed the same way: `build_child`, `child`, `child_agent`, `child_start` and `resumed_child` box their futures, and since a debug build gives every `Agent` a builder call returns its own stack slot, `child_agent` builds the agent in three plain closures run one after another (connections, tools, placement) and `fresh_child` finishes a fresh child outside the poll frame, so no frame holds the whole builder chain. Wisp's runtime threads run with 16 MiB (`wisp_core::runtime::THREAD_STACK_BYTES`, `docs/testing.md`), so 2 MiB is the alarm, not the binary's limit: the deepest tests run on a 1.5 MiB thread of their own (`docs/testing.md`, "Test stack"), so a change that eats the margin fails its own test run while 512 KiB still remain below 2 MiB.
- `wisp_core::agent::idle_wake` times the main session's quiet-tree wake; `agent::retry` times the child's notice to its parent through `agents::brief::retrying_text`.
- `wisp_core::agent::child`: the agent's side (the `SpawnAgent`, `Child`, `ListAgents`, `EndAgent` and `WatchAgent` commands, the unanswered-question notices, owing, nudges, the turn end on `report` and the guarantee).
- `wisp_core::agents::endpoints`: the endpoint view (`EndpointView`, the ready endpoints with their providers and the unavailable ones), the logged provider kind (`LoggedKind`) and its rule for which ready endpoint takes a resumed agent (`LoggedKind::takes`, which the resume card's split calls too), the served-model list and the refusal texts; the service keeps the gone set, which the main agent's `forget` feeds through its `AgentsHandle`, and every agent hands the service its model, effort, endpoint, provider and `priced` after each turn's settings are taken.
- `wisp_protocol::agents`: `SpawnRequest`, `SpawnChoices`, `ParentLink`, `AgentEntry`, `ContextFill`, `AgentState`, `Activity`, `IdleOutcome`, `ReportOutcome`.
- `wisp_core::agents::fold`: the pure per-agent fold and the tree's links (spawns, ends, the highest mail id) a resume reads from each log; `wisp_core::agents::load_tree` (`service/load.rs`): the walk that reopens and builds each live child through `Kit::resume_connected_child` and hands the `LoadedTree` to `start_root` in `TreeSetup.loaded`; `wisp_core::resume::open`: opening the root's log for `--resume`; `wisp_core::resume::billing_mode`: the logged billing mode the root's resume check and each child's placement both read.
- `wisp_core::instructions::preset` (`instructions/preset.rs`): resolving a preset's `instructions` and loading it in the preset's words; `Kit::child` appends it to the project block.
- `crates/wisp-start/src/agents.rs`: the doctor rows; `wisp-start`'s `run.rs` reads the presets and limits into `TreeSetup`, and its `start.rs` starts the session with `start_root`.

AgentEntry and AgentStateChanged carry `billing` provenance. Cost carries `turn_billing` and `session_billing`, so API-equivalent subscription usage remains distinguishable from metered charges across turns and resume.

`Cost.agents_billing` identifies the aggregate child-tree estimate independently of the root session; a metered parent can therefore show a subscription or mixed child total without mislabelling its own spend.

Mixed totals keep metered spend and subscription estimates separate: `$12.30 · ~$4.10 subscriptions`. The strip's `total` is the one exception, a single summed figure ("The strip"). `AgentEntry.plan_usd` and `AgentStateChanged.plan_usd` carry the subscription part of `spent_usd`, and each `AccountSpend.plan_usd` that of its account's `usd`; `Cost.session_plan_usd` and `Cost.agents_plan_usd` carry the corresponding parts of session and child-tree totals. These optional amounts are reconstructed from billed log records on resume. A legacy mixed total without a recoverable split says `mixed billing · split unavailable`, never a summed charge. Individual subscription amounts read `~$0.42` where the row names the account, and `~$0.42 subscription` in agent reports. The endpoint/provider model fact is unchanged. Unpriced children still make the total a lower bound.

A preset may name an endpoint that is not configured when the session starts.
Its structurally valid definition and loaded instructions remain available; a
spawn resolves its endpoint and model against the shared live catalog. Logging
in to that alias can therefore make the preloaded preset usable immediately,
without reloading preset files or changing tool schemas. Existing instruction,
structural and tool validation failures are not cleared by login. Child creation
and resume read the same published catalog revision; a removed generation cannot
be reused by a queued spawn or a cloned provider handle. Signing out of an
account moves its idle children with the chat, as a switch they reply to, and
refuses while one of them is working. A child that can't follow stays unbound on
the gone account, and mail to it is refused. Without `fallback`, a later spawn of a preset whose
account was signed out in this session, or isn't in config at all (a typo
included), runs on its parent's account when that account is still here and the move
doesn't start charging: the API never takes over from a subscription, or from an
account Wisp never saw. It
keeps the preset's model when the parent's account serves it, else it takes the
parent's model, and its result ends `Preset coder's account claude-work isn't
set up, so it runs on claude-subscription, its parent's account.`, with a name
that looks like a key written `(not shown)`. Otherwise the
spawn is refused, saying the account is gone or unknown. With `fallback`, it
instead tries the preset's choices in order and uses the first one with room;
it does not adopt the parent's account.

Known model-only presets are retained even when no current endpoint serves their
model. A later login can make them usable with an explicit spawn endpoint. An
unknown model stays unchecked when its named account, or an eligible account for a
model-only preset, has live discovery and could serve it. Other unknown models
and malformed/tool/instruction errors remain unavailable.
The account that the child actually uses is checked at selection. If its loaded
list lacks the chosen model (including an effort choice that changes the model
ID), Wisp uses the same bounded refresh as `/model` ("Each account's model list"
in `docs/endpoints.md`). This also applies before an adopted account substitutes
its own model and when a child actually needs a fallback after a usage limit,
including after resume. Unused fallbacks are not fetched. Idle children
follow catalog replacements through a read-only handle, while queued input and
mail select the current generation at delivery rather than blocking reauthorization.

A child with a shell can add or remove a server through `manage`; its tools stay
fixed, and agents started later have the server. The main chat shows its changes
at the next message. Without a shell, the child names the call its parent should make.
